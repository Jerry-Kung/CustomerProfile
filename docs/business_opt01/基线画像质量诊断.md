> 单一定义哈希 `f86dd16f…`、单一提交 `de028de`，批次自洽）。

## 0. 一句话结论

**结构与格式高度稳定，问题全部集中在「语义正确性」「证据落点」「推理实质」三层。**
最终产出中，字段矛盾、字段缺失、非法取值、证据链自我引用、事实归属错误**均已成规模出现**，
足以直接误导销售人员。三项历史反馈（字段互相矛盾、信息错误、推理链乱写）**全部复现**。

## 1. 诊断方法

- 对 39 份 `result.json` 的 `result1.analysis_result` 做结构化抽取（10 个顶层节、2227 个
  `reasoning_detail` 块）。
- 每份的 Notes 更新项（`basic_notes_updates`）与画像正文（`profile_summary` /
  `inferred_tags` / `usage_scenarios` / `communication_strategies` / `customer_overview` /
  `emotion_state`）交叉比对。
- 把上游「证据子流程」产出的 `evidence_items`（39 份共 1283 条）与最终产出的
  `evidence` 锚点做可追溯性比对。
- 关键引文回原始转写（`attempts.json`）逐字核对，区分「真事实」与「加工产物」。

## 2. 严重问题（会直接误导销售）

### 2.1 枚举字段用了中文标签，而非契约要求的枚举键 【系统性 · 高】

Notes 模板里每个 `enum` 字段都定义了英文 `items` 键（如 `purchase_purpose` 的
`family/commute/business/offroad/transport`），并要求「取值必须在枚举值列表 items 中选择」。
基线的 `basic_notes_updates` 里，**8 个字段、共 38 处出现中文取值**：

| 字段 | 中文取值案数 | 示例 |
|---|---|---|
| `core_concerns` | 13 | `"油耗\|\|安全"`（应为 `fuel_efficiency\|\|safety`）|
| `purchase_purpose` | 9 | `"家用\|\|通勤\|\|代步"`（应为 `family\|\|commute\|\|transport`）|
| `driving_preference` | 4 | `"平顺\|\|舒适"` |
| `emotion` | 3 | `"喜欢直接\|\|讨厌被催"` |
| `communication_rhythm` | 3 | `"谨慎"` |
| `personality_and_preferences` | 3 | `"理性型"` |
| `primary_driver` | 2 | `"自己"`（同批次另有 24 案正确填 `"self"`）|
| `electronic_ecosystem` | 1 | `"小米"` |

同一字段在**同一批数据里取值范围不统一**（一半英文键、一半中文标签），下游 Notes 服务若按
枚举键匹配，这些行会匹配失败或被静默丢弃。**这是最确定、最容易修的一类缺陷。**

### 2.2 同一语义字段被拆成多个不同 key 【系统性 · 高】

Notes 更新项的 `attribute_key` 本应与模板字段严格一一对应，实际出现大量**同义变体**，把
同一信息拆到不同键上：

| 语义 | 实际出现的 key | 案数分布 |
|---|---|---|
| 对比品牌 | `comparison_brand` / `comparison_brands` / `compare_brand` / `compare_brands` / `对比品牌` | 8/4/1/1/1 |
| 对比车型 | `comparison_model` / `comparison_models` / `compare_model` / `对比车型` | 8/4/1/1 |
| 竞品优势 | `competitor_advantage(s)` / `competitor_strength` | 3/4/3 |
| 竞品劣势 | `competitor_disadvantage(s)` / `competitor_weakness` | 2/4/4 |
| 品牌顾虑 | `brand_concern` / `brand_concerns` | 5/7 |
| 试驾车型 | `test_driven_models` / `test_driven_model` | 7/1 |
| 增程认知 | `knowledge_of_erev` / `knowledge_of_range_extender` | 1/1 |

**后果**：同一字段的信息被分散，任何按 key 聚合的下游逻辑都会漏数据；`对比品牌` 这种中文 key
更是与模板完全对不上（模板里根本没有这个字段）。上表共 **23 个实际出现的同义 key** 受影响。

### 2.3 购买类型与旧车信息互相矛盾 【历史反馈复现 · 高】

历史反馈点名的「识别出旧车却仍填首购」**在基线上以多种形态复现**，且不止一种：

- **`15818891947`**：最终 `purchase_type` **缺失未填**，但正文明确写「现有 2019 年别克旧车，
  有明确置换需求」；`old_car_model` / `trade_in_requirement` 也**全部为空**。
  **同一条已知事实，画像正文写了、Notes 却没写** —— 这是纵向不一致。
- **`16541242243`**：`old_car_model` 填成 **`"1190"`**（应为车型，实为录音里「我以前部1190」
  被误读成的数字），`purchase_type` 判 `replacement`，但其推理 steps 引用的是**个人特征画像
  的 `overall_tag`**，而非原始事实。
- **`13530559591`**：`purchase_type` 填成 **`"additional||replacement"`** —— 但该字段
  `multiple_value: false`（单选），多值本身即违规；来源是「推测可能有车」。
- **`15308826588`**：`purchase_type=first`、`old_car_model="无"`，属自洽，但字段与正文措辞割裂。
- **`15818891947`** 是唯一「判 `replacement` 但 `old_car_model` / `owned_car_age` /
  `owned_brand_model` 全空」的案子——即「说是换购，却拿不出任何可入字段的旧车证据」，
  而它恰恰是本批中旧车信息最明确的常识案例（2019 年别克）。

`purchase_type` 在整个批次只填了 27/39，**12 案直接缺失**，而其中多数正文其实提到了用车历史。

### 2.4 画像正文与 Notes 之间事实归属/一致性错误

- **旧车信息进不了字段**：多案正文有旧车描述，Notes 对应字段却空（见 2.3）。
- **职业字段大量依赖「第三方画像预测」**：`occupation` 的证据来源中，**10 案**直接引用
  「第三方画像预测职业…」，6 案引用自身画像。第三方画像是**统计预测**（如「货车司机概率
  0.835」），把它当事实写入 Notes 的 `occupation`，正是「妻子是电力局职工被写成客户本人」
  那一类错误的温床 —— 预测模型的属性不等于客户本人属性，且**没有任何环节校验归属**。
- **企业字段把已注销主体当有效企业**：`13926073386` 的 `company` 填「广州喜客来装饰工程有限
  公司」，其证据原文含「**登记状态注销**」，但字段照填不误。
- **`customer_name` 大量是残片/昵称**：如 `"仁"`、`"丘"`、`"坤"`、`"Q"`、`"张家培π"`、`"客户0972"`。
  规则说「昵称大概率为真实姓名才填」，但这些单字/符号显然不满足，仍被写入。
- **`wechat_id` 直接填手机号**：25 个有值的 `wechat_id` 中，**23 个等于手机号本身**（另
  `15818891947` 填成 `"未知"`、`13760736409` 填成 `"cl1556"`）。微信号与手机号同号只是「可能」，
  未加区分即写入。

### 2.5 `deal_level` 与 `business_opp_level` 互相打架 【高】

两处独立的「客户等级」判断不一致，**4 案冲突**：

| 手机号 | `profile_summary.deal_level` | `customer_overview.business_opp_level` |
|---|---|---|
| 13570263031 | A | B |
| 13702911703 | A | B |
| 13751688167 | A | B |
| 18520211913 | B | C |

两者由不同 LLM 节点生成，各自独立评分，**没有任何一致性约束**，销售人员会看到两个矛盾的等级。

### 2.6 跨节数值/格式不一致

- **年龄格式全批不统一**：`profile_summary.age` 用 `"25 ~ 30"`，Notes 的 `age` 用 `"25~30岁"`，
  **15 案两者字符串不同**。Notes 提示词明写「此处内容应与 profile_summary - age 字段的内容
  保持一致」，实际未遵守。
- **性别值不统一**：`profile_summary.gender` 出现 `"男"/"女"/"女性"/"未知"`，其中 `13620040615`
  填 `"女性"` 而非 `"女"`，与全批其余不一致。
- **`overall_tag` 超字数**：规则要求 8 字以内，4 案超限（最长 10 字，如「务实性价比餐饮经营者」）。

## 3. 证据链与推理链问题（历史反馈「乱写一通」的量化）

### 3.1 证据锚点被写成二次加工内容 【历史反馈复现 · 高】

提示词对 `inferred_tags` / `usage_scenarios` / 销售线索类节点**三令五申**：
证据锚点须「直接来源于客户的原始证据线索」，**禁止**用「画像」「人设」「分析」类主观推断内容。
实测（非 Notes 类共 4531 条锚点）分两种情形：

- **引用自产中间产物**（「客户的个人特征画像」「人设特征画像」「客户画像中…评分为…」）：
  **仅 20 条（0.4%）** —— 集中在订单 `16761543251` / `18922445657` / `16580531294`
  这类「信息极度匮乏」的案子，模型无原始证据可引，转而引用中间画像的评分。存量虽小，
  但一旦命中就是「凭空造证据」，性质最恶劣。
- **把「第三方画像数据」当作证据锚点**：**737 条（16.3%）**，分布 `scn` 140、`tag` 129、
  `ov` 122、`product_preferences` 109、`cs` 94、`purchase_motivations` 78、`resistances` 65。
  这一项性质不同：第三方画像是**合法输入源**（提示词本身把它列为输入），所以不算「违规」；
  但它是**统计预测**而非客户的直接言行，把它当「证据」会给人一种「这人确实这样」的错觉
  （如「第三方画像标签：数码摄影达人」被当作 `product_preferences` 的证据）。

**同时，上游证据子流程自己就污染了源头**：1283 条 `evidence_items` 中 **316 条
`evidence_description` 含主观推断词**（「可能/推测/表明/预测」等，占 24.6%），其中 **16 条还被
评成 A 级**（最高可靠性）。而这 316 条里 **235 条来源是「第三方画像数据」** —— 即主观性主要
顺着第三方画像这一路渗进来的。A 级定义是「直接事实证据」，含主观推断的条目评 A 属评级失准。

### 3.2 证据锚点无法回溯到任何原始证据 【中·高】

对「以『录音：』开头」的引文型锚点（465 条）回原始留痕逐字核对：**311 条能在原始转写中
匹配到连续 12 字以上，其余约 1/3 匹配不足**。集中在少数几案：

- `15818891947`（25 条不匹配）、`13430349943`（44 条）、`18675756738`（34 条）、
  `13751688167`（33 条）、`13729218381`（11 条）。
- 失配样本多为**加工改写**而非原话，例如「录音：智驾占比率96%」「试驾录音：客户独自试驾，
  未提及家人」「录音：关注几万元差价和补贴」——这些是**归纳结论**，被冠以「录音：」的引文
  格式输出，**形式上像原始证据、实为二次总结**。

### 3.3 推理 summary 与 steps/evidence 脱节 【中 · 高】

- **333/2227（15.0%）** 的 `reasoning_detail` 里，`summary` 与 `steps`+`evidence` 四元组
  零重叠 —— 即总结与推理过程**没有任何可提取的语义关联**。多数是模板句：summary 写
  「基于 XX 推导」，steps 却是另一套内容。
- **96 个块的 `steps` ≤ 1 条**（如 `wechat_id` 的 steps 只有「提取微信号字段内容为…」），
  谈不上推理。
- 反例（**质量好的**）：`13430349943`、`13926073386` 的标签与策略推理链完整、原话引用充足、
  summary 与 steps 对应 —— 说明模型有能力做对，**问题在提示词约束与节点分工，而非模型能力**。

### 3.4 证据分级规则的遵守情况（这部分基本合格）

按提示词明令的规则抽查：
- 「头像类证据评级不高于 C」→ **0 条违规**。
- 「归属地类证据不高于 C」→ **0 条 A 级违规**。
- 试驾录音证据级别分布 A182/B139/C36/D22/E34，未见明显倒挂。

分级规则本身执行尚可，问题出在**「证据描述内容」的污染**（3.1）与**「引文格式的内容」的
伪造感**（3.2）。

## 5. 结构层面值得肯定的部分

- 39/39 成功，单一定义哈希，批次可比、自洽。
- 2227 个 `reasoning_detail` **全部**含 `summary`/`steps`/`confidence`/`evidence` 四段，
  无缺字段、无空 evidence。
- **0 条**证据锚点使用 `ev_001` 类证据 ID 或 JSON 字段名 —— 格式禁令被严格遵守。
- 标签名 `title` **0 条超 8 字**，`confidence` **0 条越界**。
- 证据分级的三条硬规则（头像≤C、归属地≤C、试驾性别降级）**零违规**。

**这说明：格式类约束提示词写得住；语义类约束（事实归属、字段一致、证据落点）写不住。**

## 6. 面向优化的建议（按性价比排序）

1. **给 Notes 节点加「枚举键白名单 + 键名白名单」的硬校验**（code 节点在 LLM 之后做归一与
   拒绝）：中文标签→英文键映射、非法 key 重命名/丢弃、`multiple_value:false` 字段拒绝多值。
   这一类是**确定性可修**的，收效最快。
2. **合并同义 key**：以 Notes 模板的 `configs` 为准，对同义变体做映射表；模板里不存在的 key
   （如「对比品牌」）直接丢弃或映射。
3. **建立跨节一致性校验**：`deal_level` vs `business_opp_level`、`profile_summary.age` vs
   Notes `age`、`purchase_type` vs `old_car_model/trade_in`，冲突时触发重算或标记。
4. **切断画像→证据的反向引用**：在代码层校验 `evidence` 锚点不得包含「画像/人设/标签」等词，
   命中则要求重生成，或直接回退到最近一条原始 `evidence_item`。
5. **修证据子流程的主观词污染**：`evidence_description` 禁用「可能/推测/表明」等词，含则降级；
   A 级必须是无修饰的原始事实。
6. **约束事实归属**：涉亲属/陪同人的信息必须显式标注归属主体；「第三方画像预测」类证据
   不得单独作为职业/企业等身份字段的依据。
7. **引文格式收紧**：`evidence` 里以「录音：」开头的条目，要求逐字摘自原始转写，禁止改写式
   归纳（可在代码层对引文做原文包含校验）。

## 7. 复现方式

本文数字来自对 `experiments/batches/baseline-39-dsv41-noThink/runs/*/result.json`
（以及上游证据用的 `nodes.json`、引文核对的 `attempts.json`）的一次性抽取与统计脚本。
**该诊断脚本未入库**（本目录只存文档）；需要重跑时再落地，检查项清单以本文 §2–§3 为准。

抽取出的中间产物与核对用摘要保存在仓库外的工作目录，**未入库**——它们含真实客户姓名、
企业名、手机号与录音片段，属「真实客户数据」。
