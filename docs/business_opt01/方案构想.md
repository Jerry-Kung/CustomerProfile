> 本文回答一个问题：**把现行的证据分层 / 特征打分 / 预置标签整套设计丢开，从「任务边界」重新设计，
> 有哪些值得入选 AB 实验的方案。**

> 本文是新写的工作稿，不修改也不替代 `基线画像质量诊断.md`——后者是「病」，本文是「药」。
> 文中每个方案都附**本次在 39 份基线上的实测验证**；凡属推算、未实测的数字，均显式标注「预估」。
>
> **后续**：`端到端方案.md` 把本文的五个单点机制收进一条完整链路，给出「主方案 + 两个备选」。

## 0. 结论先行

**基线里 50 处以上的字段矛盾、16 例「收入靠第三方预测」、31 次「老婆」被写成「未知」，
都不是提示词没写清楚，而是架构造出来的。**

现行流程把「取证」「推理」「填表」压在同一批 LLM 节点里，且每个字段各自生成、彼此不知道对方在写什么。
于是：

- 矛盾不可能被拦住（没有一个地方同时看得见所有字段）；
- 第三方统计预测和客户原话在同一个证据数组里排队，模型分不出谁是事实；
- 信息稀疏时没有「我不知道」这个出口，提示词还明写「允许合理的联想发挥」，于是只能编。

**因此本文的五个方案，全部是结构性的，不是补丁。** 它们分别从五个不同的层面切断病根：

| 方案 | 切的是哪一层 | 一句话 |
|---|---|---|
| 一 · 事实账本 | 数据流 | LLM 只写「事实 + 出处」，字段由代码投影出来，矛盾在结构上不可能发生 |
| 二 · 单次长上下文 | 调用形态 | 31 次调用并成 1 次，跨节点矛盾的前提消失，成本降约一个数量级 |
| 三 · 原文跨度锚点 | 证据表示 | 锚点从「自然语言描述」改成「指向原文的坐标」，定位不到即拒绝 |
| 四 · 抽取—对抗校验 | 流程环节 | 第二通道专门证伪：主体对不对、有没有矛盾、是不是过时 |
| 五 · 可答性路由 | 分诊 | 先判「这题能不能答」；答不了就明说信息不足，而不是联想 |

**推荐路线（§5 有细化）**：以**方案三**为证据基座，**方案一**为数据流骨架，**方案五**处理稀疏输入，
**方案二**作为成本与一致性的实现手段；**方案四**作为可选的质量闸门按预算叠加。
其中「三 + 一」是解耦事实与表达，「五」是承认能力边界——**这三件事是基线暴露出的病根的直接对立面。**

## 1. 边界（用户给定，方案不得越界）

**输入**：接口「获取全量用户数据」返回的全量客户数据。不同来源的**全面程度、可靠程度不等**
（实测见 §2 表 A：微信搜索 39/39、关联企业 32/39、第三方打点 32/39、外呼录音 20/39、试驾录音 19/39）。

**输出**（两部分，均不得改变对外契约）：

- **Notes 更新项**：42 个固定字段（`attribute_key` 见实测表 B），回写企业级 IT 系统的客户信息表；
- **客户画像卡**：`profile_summary` / `inferred_tags` / `usage_scenarios` / `communication_strategies` /
  `customer_overview` / `purchase_motivations` / `product_preferences` / `resistances` / `emotion_state`。

**要求**（用户给定优先级）：准确性、自洽性、可读性三项优先，推理成本次之。

> 注：上一轮诊断提出的 7 条建议（加白名单校验、合并同义 key、加跨节一致性检查……）属**在现行结构上加约束**。
> 用户已明确不采纳。本文不再重复它们；本文的方案均**不要求保留**证据分层、特征命题打分（P-LS-xxx）、
> 预置标签库这些现有构件。

## 2. 从「病」到「设计约束」：基线实测给出的 7 条硬约束

先摆事实。以下均来自本次对 39 份基线的重新实测（脚本口径见 §6）。

### 2.1 输入其实相当丰腴，稀疏是少数

**表 A · 输入渠道覆盖（39 案）**

| 渠道 | 覆盖案数 |
|---|---|
| 微信手机号搜索截图 | 39 / 39 |
| 关联企业信息 | 32 / 39 |
| 第三方大数据打点（Datamet） | 32 / 39 |
| 外呼录音 | 20 / 39 |
| 试驾录音 | 19 / 39 |

**39/39 全部拿到语音转写文本**，平均转写长度 **85,055 字符**；输入包平均 **32,618 字符**，最大 49,570。
只有 **7 案**是「2 个渠道」的极稀疏（T0）。

→ **约束 1：不要为「普遍信息不足」设计。** 失败发生在**信息充足却仍然编造**的案子上。

### 2.2 真正的病：第三方统计预测被当成客户事实

第三方打点（Datamet）本质是**统计预测**（如「预测职业司机(小车)：是，置信度 0.985」），
它不是客户说过的话。但基线的证据数组里，它和录音原话**混在同一个列表、同样的自然语言格式**：

```
19874695020  occupation = "蓝领工人||求职过渡期人员||小商户经营者"
             evidence[0] = "第三方画像预测蓝领工人: 是 (0.870644)"
13530559591  occupation = "小车司机||网约车/出租车司机||城市通勤服务类职业"
             evidence[0] = "第三方画像数据：预测职业司机(小车)是"
```

**表 B · 身份类字段的来源结构**（仅一手 = 锚点只含录音/聊天/人工/系统；仅第三方 = 只含第三方预测）

| 字段 | 已填 | 仅一手 | **仅第三方** | 零证据 |
|---|---|---|---|---|
| `age` | 39 | 1 | **10** | 0 |
| `annual_income` | 36 | 9 | **16** | 0 |
| `occupation` | 30 | 10 | **8** | 0 |
| `family_structure` | 24 | 6 | **9** | 0 |
| `driver_license_status` | 23 | 16 | **4** | 0 |

**年收入 36 个有值里有 16 个仅靠预测撑起；年龄 39 个有值里 10 个如此。**
反馈②「客户妻子是电力局职工、却被写成客户本人」——就发生在这个机制上：
预测模型的属性 ≠ 客户本人属性，而**没有任何环节校验归属**。

→ **约束 2：事实与预测必须是两种东西，不能共用一个证据通道。** 预测只能是「假设」，不能单独支撑身份字段。

### 2.3 归属丢失：亲属信息被吞掉

试驾录音里客户会提到家人（「老婆」「妻子」「太太」），基线实测：**若输入含亲属信息，
输出几乎不保留归属**。典型：

```
16761543238  转写中「老婆」出现 31 次
             输出 profile_summary = {gender:"未知", name:"客户3238", age:"25 ~ 45"}
             → 一段满是家庭信息的试驾录音，最后得到「性别未知」的客户
```

反向的例子（信息进了字段却丢了主体）：

```
13926073386  occupation = "机关/事业单位工作人员"，证据 = 试驾录音「我们单位也要买一个」
             company    = "广州喜客来装饰工程有限公司"，证据原文含「登记状态注销」
```

→ **约束 3：每条事实必须带主体（谁）。** 「单位」「老婆」「我们」这类词不能直接升格为客户属性。

### 2.4 跨字段矛盾是批量存在的

把「本可以写成代码的规则」在基线上跑一遍，**命中 50 处**（表 C 摘录）。
注意这些规则本身**与模型无关**——它们是对「自洽性」这一要求的直接翻译：

**表 C · 一致性规则命中**

| 规则 | 命中 | 例子 |
|---|---|---|
| `R8` Notes 年龄 ≠ 画像卡年龄 | 15 | `25~30岁` vs `25 ~ 30` |
| `R12` 枚举字段填中文而非枚举键 | 19 | `purchase_purpose = "家用\|\|通勤\|\|代步"` |
| `R11` 用途含「家用」但家庭结构为空 | 6 | `15218802252` |
| `R2` `purchase_type=replacement` 却无任何旧车字段 | 4 | `15818891947` |
| `R9` `deal_level` ≠ `business_opp_level` | 4 | `13570263031` A vs B |
| `R6` 单选字段出现多值 | 1 | `purchase_type = "additional\|\|replacement"` |
| `R13` 事业单位属性但企业已注销 | 1 | `13926073386` |

→ **约束 4：能写成代码的约束，就不该交给提示词。** 以上 50 处没有一处需要「理解语义」才能发现。

### 2.5 成本：31 次调用、65 万字输入、11 分钟

**表 D · 单案平均开销（实测 39 案）**

| 指标 | 单案均值 | 全批合计 |
|---|---|---|
| LLM 调用次数 | 31.0 | 1,208 |
| prompt tokens | 312,969 | 12,205,817 |
| completion tokens | 64,463 | 2,514,067 |
| 墙钟（LLM 累计） | 654 s | 25,488 s |

→ **约束 5：现行调用结构本身就贵，且贵在不必要**（同一份输入被 31 个节点反复重读、反复改写）。

### 2.6 稀疏案上的「无中生有」

基线诊断里 **20 条证据锚点引用了自产中间画像**（「客户的个人特征画像中……评分为……」），
集中在信息最少的案子（`16761543251`/`18922445657`/`16580531294`）。提示词还明写
「客户信息过于匮乏时，允许进行合理的联想发挥」。

并且存在**自述与输入矛盾**：

```
13530559591  输出断言「客户无试驾录音、无外呼录音、无聊天记录」
             但该案输入包里含外呼录音转写 3,149 字符
```

→ **约束 6：需要「我不知道」这个出口。** 不给出口，模型就只能用编造来填满所有字段。
→ **约束 7：需要一道校验，检查结论与输入的原始事实是否冲突**（不是格式校验，是事实校验）。

### 2.7 七条约束汇总

| # | 约束 | 直接对立于 |
|---|---|---|
| 1 | 为「信息充足却矛盾」设计，不为「普遍稀疏」设计 | 2.1 |
| 2 | 事实与预测分属不同通道，预测不得单独支撑身份字段 | 2.2 |
| 3 | 每条事实带主体 | 2.3 |
| 4 | 确定性约束交给代码，不交给提示词 | 2.4 |
| 5 | 消灭重复读取与重复生成 | 2.5 |
| 6 | 保留「无法判断」的合法出口 | 2.6 |
| 7 | 设一道事实校验闸门 | 2.6 |

## 3. 五个方案

### 方案一 · 事实账本（Fact Ledger）+ 确定性投影

**一句话**：LLM 只负责产出「事实 + 出处」，Notes 与画像卡由代码从账本**投影**出来；两个产物不再各写一遍。

#### 机制

一次（或少数几次）抽取，产出**类型化的账本**，每条是一个带主体、带出处、带类型的断言：

```jsonc
// 账本条目（示意）
{
  "claim_id": "c_017",
  "subject": "customer",          // customer | spouse | colleague | unknown
  "attribute": "occupation",
  "value": "充电桩行业从业者",
  "source_ref": "rec_testdrive",  // 指向原始记录
  "source_type": "primary",       // primary | thirdparty | social | inference
  "verbatim": "我知道，我以前做充电桩。",
  "confidence": 0.9
}
```

然后**代码**做三件事：

1. **投影**：按固定规则把账本映射成 42 个 Notes 字段与画像卡的各个 section；LLM 不直接写字段。
2. **枚举归一**：`value → enum key` 用查表完成（`"家用"` → `family`），非法值直接拒绝并回落。
3. **规则求值**：表 C 那类规则对**投影后的对象**求值，冲突则要么自动推导（有旧车 ⇒ `purchase_type ≠ first`），
   要么标记为待人工确认，**绝不两者都写出去**。

#### 治什么病（实测）

- **表 C 的 50 处矛盾**：投影是单点、纯函数的，`R8`（年龄两处不一致）与 `R9`（两个等级）
  在结构上**消失**——因为年龄和等级各只有一处、由代码算出来。
- **`R12` 的 19 处中文枚举**：查表归一，不依赖模型遵守提示词。
- **约束 2**：`source_type=thirdparty` 的条目按规则**不能单独支撑身份字段**（表 B 的 16+10+9+8 例会被拦下，
  改为输出「信息不足」或降级进入画像卡的软性 section）。

#### 成本

抽取通常 1–2 次调用（输入包 32.6k 字符，长上下文模型单次可容纳）；
投影与规则求值是**代码，零 token**。预估从 31 次降到 2–3 次。

#### 代价与风险

- 需要先设计账本 schema 与投影规则表——**这是本方案的主要工作量，也是它的价值所在**。
- 抽取召回不足会丢信息；缓解：抽取阶段宁多勿漏，投影阶段再筛。
- 「预测不能支撑身份字段」会**让一部分字段空出来**（预估约 30–45 个字段实例，见表 B）。
  这是**有意为之**——空着比填错强，符合「准确性优先」。

#### 初步验证

已用基线完成「投影 + 规则」的等价推演：把 39 案的字段按上述规则重算，
表 C 的 50 处冲突**全部可判定**，其中 R2/R8/R9/R11/R12/R13 可**确定性修正**，
无需任何模型参与。验证脚本口径见 §6。

### 方案二 · 单次长上下文 + 结构化约束解码

**一句话**：把 31 次调用并成 1 次——把完整输入包一次性喂入，一次生成**一个** canonical JSON；
用 **JSON Schema 约束解码**（而非提示词叮嘱）保证格式。

#### 机制

- 输入：整合后的输入包（实测平均 32,618 字符、最大 49,570 字符）——**远小于现代长上下文窗口**。
- 一次调用产出**同时包含事实与结论**的单一对象：账本（方案一）+ 画像卡各 section + Notes 字段。
- 解码阶段用 schema 约束：枚举只能取 `items` 的键，`multiple_value:false` 的字段只能单值，
  必填/可空由 schema 声明。

#### 治什么病（实测）

- **`R8`/`R9` 这类「两个节点各打一次分」的矛盾**：只剩一个节点，**不存在两个分数**。
- **`R5` 成本**：预估单案 prompt 从 313k 降到约 35k tokens、墙钟从 654s 降到约 15–30s（预估，需实测）。
  全批 1,208 次调用 → 约 39–78 次。
- **约束 7 的一部分**：单节点能看到全部输入，减少「自述与输入矛盾」（`13530559591` 断言无录音而输入有）。

#### 代价与风险

- **长上下文中间信息丢失**（lost-in-the-middle）：32k 字符里靠后的细节可能被忽略；
  缓解：输入包结构化分节 + 关键段前置。
- **单点失败**：一次调用失败即无产出；需要重试与降级策略。现行 31 次调用天然容错。
- 需要模型/推理栈**支持约束解码**（structured output / grammar）。若当前 `deepseek-v4.1-flash` 不支持，
  退化为「schema 校验 + 失败重试」，效果打折。
- 「一次写完所有字段」可能让模型在长输出里**后段质量下降**；缓解：分 2 次（事实一次、表达一次）。

#### 初步验证

已测输入包体积（§2.1），确认**单次可容纳**；成本投影基于现行 token 计数推算，
**标为预估**，应在 AB 实验首轮实测。

### 方案三 · 原文跨度锚点（Span-Anchored Provenance）

**一句话**：证据锚点不再是「一句自然语言」，而是**指向原始记录的一段坐标**；
代码必须能在原文里定位到它，定位不到就拒绝。

#### 机制

锚点从自由文本改为结构化指针：

```jsonc
{
  "record_id": "rec_testdrive_18902281339",
  "char_start": 1042,
  "char_end": 1063,
  "quote": "我以前做充电桩"     // 由代码从原文截取，不信任模型转写
}
```

渲染给人看时，由**代码**把 `quote` 贴出来（附记录名与位置）；模型**不负责誊抄原文**。

#### 治什么病（实测）

- **反馈③「证据信源是二次加工」连根拔除**：一段「录音：智驾占比率96%」如果不在原文里，坐标就定位不到，
  **直接判无效**。基线诊断中「录音：」引文约 **1/3 无法回溯原文**——本方案让这 1/3 在生成阶段即失败。
- **`R12` 引文伪造感**：锚点要么是原文切片，要么就不是锚点；不存在「像引文的归纳结论」。
- **可读性**：输出里的引文永远**逐字准确**（由代码截取保证），符合「引用原始数据准确翔实」。

#### 代价与风险

- 要求**保留可寻址的原始记录**（转写文本、OCR 文本、接口原文），并稳定编号；
  现行 `nodes.json`/`attempts.json` 已经留痕，具备条件。
- **推断类结论无处安放**：画像卡里大量是有价值的归纳（「偏实用主义」），它们**本就不该伪装成引文**。
  本方案要求给它们**单独一条通道**，明确标注为「推断」而非「证据」——这正是方案一要解决的**类型分离**。
- 若某输入源未保留可寻址文本（如已 OCR 成图的社媒截图），需回退到「记录级引用 + 人工可核」。

#### 初步验证

已确认基线具备可寻址性：39 案均有 `attempts.json`（原始请求/响应）与转写文本，
`13926073386`/`18902281339` 等案的原话（「我以前做充电桩」「登记状态注销」）均可在原文定位。
跨度校验的实现成本低（纯字符串包含判定）。

### 方案四 · 抽取—对抗校验双通道

**一句话**：抽取通道负责「大胆提」，校验通道负责「逐个证伪」——两者用**不同的问题、不同的输入**做，避免同源同错。

#### 机制

- **通道 A（抽取）**：从输入包提断言（账本条目）。
- **通道 B（校验）**：只拿到「断言 + 它声称的原文出处」，**不给**通道 A 的推理过程，逐条问三件事：
  1. **主体对吗**？——「单位也要买一个」说的是谁的单位？
  2. **有矛盾吗**？——同一客户其它字段/原文是否与之冲突？
  3. **时效对吗**？——「登记状态注销」的企业还能当作在职企业吗？
  判为不成立 → 丢弃或降级。

#### 治什么病（实测）

- **反馈②（归属错误）**：主体检查直接命中 `13926073386` 的「单位」类推断——通道 B 会问「这是客户本人的单位吗」。
- **`R13` 注销企业照填**：时效检查命中。
- **`R2` 换购却无旧车证据**：矛盾检查命中（`purchase_type=replacement` 与「无任何旧车字段」互斥）。
- **`13530559591` 自述与输入矛盾**：独立通道 B 只看输入，更容易发现「输出说无录音、输入却有」。

#### 成本

校验调用较小（每条断言一次，或按字段批量）。预估**增加 0.5–1 倍调用量**，
但换来的是本方案唯一能提供「**语义级**事实核查」的能力——方案一/三的规则只能查**结构化**矛盾。

#### 代价与风险

- 通道 B 与通道 A 若共享同一次推理，会**同源同错**；必须真正独立（独立提示词、独立上下文）。
- 「证伪」会带来**假阴性**（把对的判错而丢弃）；需允许「存疑」第三态，交人工。
- 成本上升与「推理成本次优先」的要求存在张力——建议**按预算选择性启用**（如仅对身份类字段启用）。

#### 初步验证

已用基线构造校验问题并人工核对：表 C 的 `R2`/`R13` 与反馈②的归属案例，
在「只看断言 + 原文」的条件下**均可被独立判定为不成立**。这是**离线人工复核**，
正式效果需在 AB 实验中与方案一/三同跑对比。

### 方案五 · 可答性路由（先判「这题能不能答」）

**一句话**：先跑一个轻量分诊，判断「这份输入够不够回答这位客户」；够则走「事实优先」，
不够则走「保守模板」——**显式输出「信息不足」，而不是联想**。

#### 机制

- **分诊器**：一个很小的调用，读输入包的**清单**（有哪些渠道、各多少内容），输出三档：
  - `sufficient` —— 有录音/聊天等一手材料 → 走事实优先流程（方案一/三）；
  - `thin` —— 只有社媒/第三方 → 走保守流程：只输出能坐实的字段，其余留空，
    画像卡以「当前信息不足」为主基调；
  - `empty` —— 几乎无数据 → 输出「待补充」骨架，不产生任何具体断言。
- 分诊**不评判客户**，只评判**数据是否支持评判**。

#### 治什么病（实测）

- **2.6 的无中生有**：20 条自引锚点集中在最稀疏的案子；保守流程从源头上不产生具体断言。
- **7 个 T0 稀疏案**（2 渠道）：预估走保守流程，省掉全部下游重推理，同时避免编造。
- **与提示词里「允许合理联想发挥」的冲突**：本方案用**架构**替代那句话——需要发挥的地方，
  改成明确标注的「推断（非事实）」，而不是混进证据。

#### 成本

分诊是 1 次小调用；稀疏案因跳过下游而**净省**成本。富信息案多 1 次小调用，可忽略。

#### 代价与风险

- **分诊误判**：把`sufficient`判成`thin`会白白少输出信息；阈值需在 AB 实验中校准。
- **保守模板的「业务观感」**：销售可能觉得「什么都没说」。需要设计好「信息不足」的表达方式
  （给出**建议的补充动作**，如「建议电话确认用车人」），让它可行动而非空洞。
- 与「画像要丰富」的期待有张力——但**本轮的验收标准是「不准」，不是「不丰富」**（见诊断报告 §4 非目标）。

#### 初步验证

已按渠道数把 39 案分档（7 案 T0、32 案 T≥1.5），确认**稀疏是少数**、
且**稀疏案恰好是自引锚点集中的案子**，说明路由能精准命中问题区。分诊阈值待实验校准。

## 4. 方案对比

| 维度 | 一 · 账本 | 二 · 单次 | 三 · 跨度锚点 | 四 · 对抗校验 | 五 · 路由 |
|---|---|---|---|---|---|
| 主要治 | 字段矛盾、枚举、预测污染 | 成本、跨节点矛盾 | 证据可信、可读 | 语义级事实错误 | 稀疏输入、编造 |
| 治的是 | 数据流 | 调用形态 | 证据表示 | 校验环节 | 分诊 |
| 对准确性 | 强 | 中 | 强（证据） | 强（事实） | 中 |
| 对自洽性 | **最强** | 强 | 中 | 中 | 中 |
| 对可读性 | 中 | 中 | **强** | 弱 | 中 |
| 对成本 | 省（投影零 token） | **大省** | 略增 | 增 0.5–1× | 净省 |
| 是否需改模型能力 | 否 | **需约束解码** | 否 | 否 | 否 |
| 主要风险 | schema/投影工作量大 | 单点失败、中间丢失 | 需可寻址原文 | 假阴性、成本 | 误判、观感 |
| 与其它方案耦合 | 基座 | 是实现手段 | 是证据基座 | 可叠加 | 独立 |

**关键判断**：方案一是**结构**（数据怎么流），方案三是**表示**（证据长什么样），二者互补且必须同时上——
没有跨度锚点，账本里的 `verbatim` 仍是模型转写；没有账本，跨度锚点无处安放。
方案二是**实现载体**（把二者合并到一次调用）。方案五**独立且便宜**，应无条件先上。
方案四**最贵但最准**，作为可选闸门。

## 5. 推荐路线与验证计划

### 5.1 推荐组合

**主线：五（路由）→ 三（跨度锚点）→ 一（账本投影）→ 二（单次实现）**，
四（对抗校验）按预算选择性叠加。

理由：这四步**每一步都能单独上线并单独度量**，且互不阻塞：

1. **五先上**：改动最小（加一个分诊 + 一套保守模板），立刻消除稀疏案上的编造。
2. **三再上**：把锚点改成坐标，锚点可信度立刻可见（可度量的「可回溯率」）。
3. **一随后**：账本 + 投影，兑现「矛盾不可能发生」。
4. **二收口**：确认前三步稳定后，用单次调用替代多节点，兑现成本。
5. **四按需**：若 AB 实验显示语义级事实错误仍高，再加校验通道。

### 5.2 建议的 AB 实验指标（与验收标准对齐）

| 目标 | 指标 | 口径 |
|---|---|---|
| 准确性 | 事实错误率 | 人工抽检：字段值与「原文可坐实的事实」不符的比例 |
| 自洽性 | 规则命中数 | 表 C 那套代码规则在产出上的命中数（目标：趋零） |
| 可读性 | 锚点可回溯率 | 锚点能在原文定位的比例（目标：100%） |
| 成本 | 单案 tokens / 墙钟 | 与现行 313k / 654s 对比 |

**探针集**：本轮基线已定位出若干「已知答案」的案子，可直接作为回归探针——
`16761543238`（亲属信息，应为家庭结构而非「未知」）、`13926073386`（「单位」非客户本人单位、企业已注销）、
`13530559591`（输入有录音，不得输出「无录音」）、`15818891947`（明置换，必须落到旧车字段）。
