# 客户人设画像 · 端到端业务方案

> 本文回答一个问题：**把「客户人设画像」从取数到回写当成一条完整的生产线来重造，应该长什么样。**
>
> 与 `方案构想.md` 的关系：那一份给出的是五个**单点**改造（账本 / 单次 / 跨度锚点 / 对抗校验 / 分诊），
> 本文承认用户的判断——单点叠加在当前流程上很可能被流程本身稀释。本文把那些机制**收进一条完整链路**，
> 以**主方案 + 两个备选**的形式给出，并对每个环节标注本次实测依据。
>
> 本文不改代码，只做方案。凡属推算的数字标「预估」。

---

## 0. 结论先行

**当前流程的根本问题不是某个环节做得不好，而是它把「取数、取证、推理、填表、成文」压在同一批
无状态 LLM 节点里，每个环节都只能看见上一个环节的**二次加工产物**，而每个环节都在做有损压缩。**

本次实测把这个链条量化了出来：

| 环节 | 损失 |
|---|---|
| 15 个取证渠道 → 有效证据 | **9 个渠道 39/39 只产出 E 级「缺失信息」**，合计 351 条纯噪声；A 级证据 97% 只来自录音 |
| 原始转写 → 录音分析报告 | 718 句 / 8,184 字符的转写，被压成 **682 字符**报告（`16761543238`，保留 8%） |
| 录音分析报告 → 录音类证据项 | 全批转写 221,736 字符 → 证据 51,679 字符，**保留 23.3%** |
| 证据项 → 证据锚点 → 最终字段 | 引文可回溯率 **58.1%**；`raw_support` 可回溯率 **56.5%**，且仅 37.8% 带引号 |
| 字段 → 卡片 | 卡片正文 **39/39** 提及身份类字段，与 Notes 各自生成、无人对齐 |

**主方案：事实账本四段式。** 一句话——
**取数只负责把原始记录收进来（代码），取证只负责把原文摘成带主体、带坐标的断言（1 次 LLM），
填表与校验全部由代码从断言投影出来（0 token），成文只负责把已定稿的事实写成话（1 次 LLM）。**

它把「事实」和「表达」彻底分开：事实只有一个来源、一份副本；表达不得新增事实。
用户点名的三类问题——字段互相矛盾、信息错误（妻子说成客户）、推理链乱写——分别在第三段、第一段、第三段被结构性消除。

**备选一**：单次调用 + 代码后置校正（1 次调用，最省，但归属与矛盾只能靠提示词与后置兜底）。
**备选二**：取证—核验双通道（3 次调用，最准，唯一能做语义级事实核查）。

## 1. 边界与验收（用户给定，方案不得越界）

**输入**：接口「获取全量用户数据」返回的全量客户数据。不同来源的全面程度、可靠程度不等。

**输出**（对外契约不变）：

- **Notes 更新项**：42 个固定字段，形状 `basic_notes_updates: [{attribute_key, attribute_value, reasoning_detail{summary,steps,confidence,evidence}}]`，回写企业级 IT 系统的客户信息表；
- **客户画像卡**：9 个 section，形状固定（`profile_summary` / `inferred_tags` / `usage_scenarios` /
  `communication_strategies` / `customer_overview` / `purchase_motivations` / `product_preferences` /
  `resistances` / `emotion_state`）。

**要求与优先级**：准确性、自洽性、可读性优先；推理成本次之。其中「数据过少时输出至少与常理一致」、
「推理链逻辑清晰、引用原始数据准确翔实」是硬要求。

## 2. 本次实测：这条链路的六个事实

数据源：`experiments/batches/baseline-39-dsv41-noThink/`（39 案，单一定义哈希，含 `nodes.json` /
`attempts.json` / `result.json`）。口径见 §8。

### 2.1 输入面：清单 ≠ 内容，一半以上渠道是结构性空的

入口 `GET /api/v1/remote/data/history/{phone}` 返回的是**清单**：39 案共 **142 条记录**，5 个 `channel`：

| channel | 案数 | data_type | media_urls |
|---|---|---|---|
| WeChatPhoneSearchScreenshot | 39/39 | image | 有 |
| DatametInterestPoints（第三方打点） | 32/39 | text | 无 |
| RelatedEnterpriseInfo | 32/39 | text | 无 |
| AIOutboundCallRecordingFile | 20/39 | audio | 有 |
| TestDriveRecordingFile | 19/39 | audio | 有 |

**每案恰好 1 个录音渠道**（20 通外呼 + 19 通试驾 = 39）。渠道数只有两档：**2 个（7 案）/ 4 个（32 案）**。

但清单**不含内容**：`analysis_summary` 全批 **0/142 非空**。真正的内容由 `evidence_subagent`
扇出到 **14 路子流程**各自去取（截图各按 `media_urls` 下载、录音走 AUC、企业/号码走分析子流程、
人工确认与 Feedback 走 mhero）。

**关键实测：15 个证据渠道里，9 个是结构性空的。**

| 渠道 | A | B | C | D | E | 合计 |
|---|---|---|---|---|---|---|
| 试驾录音信息 | 182 | 139 | 36 | 22 | 34 | 413 |
| 第三方画像数据 | 0 | 5 | 202 | 61 | 7 | 275 |
| 外呼录音信息 | 112 | 24 | 9 | 2 | 24 | 171 |
| 微信手机号搜索界面信息 | 2 | 0 | 59 | 8 | 33 | 102 |
| 手机号归属地信息 | 0 | 0 | 11 | 45 | 12 | 68 |
| 关联企业信息 | 7 | 0 | 4 | 1 | 31 | 43 |
| **朋友圈截图内容信息** | 0 | 0 | 0 | 0 | **39** | 39 |
| **微信主页截图信息** | 0 | 0 | 0 | 0 | **39** | 39 |
| **支付宝主页截图信息** | 0 | 0 | 0 | 0 | **39** | 39 |
| **小红书主页截图信息** | 0 | 0 | 0 | 0 | **39** | 39 |
| **抖音主页截图信息** | 0 | 0 | 0 | 0 | **39** | 39 |
| **客户与我方销售人员的聊天记录信息** | 0 | 0 | 0 | 0 | **39** | 39 |
| **销售人员对当前客户历史画像数据的反馈记录** | 0 | 0 | 0 | 0 | **39** | 39 |
| **销售人员人工确认的客户Notes信息** | 0 | 0 | 0 | 0 | **39** | 39 |
| **客户留存在我方销售数据系统中的信息记录** | 0 | 0 | 0 | 0 | **39** | 39 |

两条结论：

1. **A 级证据 97% 来自录音**（试驾 182 + 外呼 112 = 294 / 全批 A 级 303）。社交类渠道**一条 A 级都没出**。
2. **9 个渠道 × 39 案 = 351 条 E 级噪声**，纯粹占用提示词与注意力，且它们**看起来像输入**，
   让模型误以为「信息很全」。
3. **猛士 IT 系统的 15 个字段全部 0/39 非空**——数据块在、值全空。

→ **设计约束 1：渠道必须分级为「有内容 / 结构性空」，空渠道不得进入取证上下文，
只能在记录层留一条 `status=exception` 的痕。** 这一条同时治愈「输入有录音、输出却说无录音」——
因为「有没有」由记录层说了算，不由模型回忆。

### 2.2 真正的可用素材只有四路

去掉 9 路空渠道后，能支撑判断的只有：

- **一手交互**：录音转写（外呼 / 试驾）—— 39/39 都有；
- **声明性登记**：微信手机号搜索截图（昵称 / 微信号 / 声明性别）；
- **弱登记**：关联企业（8/39 有值）、手机号归属地；
- **统计预测**：第三方打点（Datamet）。

第三方打点**不是客户说过的话**，是统计预测（「预测职业司机(小车)：是，置信度 0.985」）。
基线把它和录音原话混在同一个证据数组、同一种自然语言格式里，于是它撑起了大量身份字段：

**表 · 身份类字段「仅靠第三方预测」的实例数（39 案）**

| 字段 | 仅第三方 | 说明 |
|---|---|---|
| `annual_income` | 11 | 收入几乎全靠预测 |
| `age` | 10 | 年龄同样 |
| `family_structure` | 10 | |
| `occupation` | 7 | 「妻子在电力局」那类错误的温床 |
| `driver_license_status` | 4 | |
| 合计 | **42** | |

→ **设计约束 2：事实（客户说过/做过的）与预测（模型推断的）必须分属两类，
预测不得单独支撑身份字段。** 预测只允许进入卡片的软性 section，并以「预测」字样显式标注。

### 2.3 转写被两跳压掉四分之三，且长转写损失最重

**原始转写全程没有进入最终成文节点。** 它的路径是：

```
AUC 转写 → (LLM) 识别结果校对 → (LLM) 内容有效性判断 → (LLM) 录音文件分析 报告
        → 客户数据聚合（作为「外呼录音信息 / 试驾录音信息」纯文本）
        → (LLM) 证据线索整理 → evidence_items → (LLM) 成文节点
```

两跳都是 LLM 有损压缩，实测：

| 案 | 转写字符 | 报告字符 | 报告/转写 |
|---|---|---|---|
| `16761543238` | 8,184 | 682 | **0.08** |
| `18902281339` | 21,008 | 4,268 | 0.20 |
| `13826204651` | 20,280 | 5,262 | 0.26 |
| `15818891947` | 20,823 | 5,895 | 0.28 |
| … | … | … | … |
| `13530559591` | 256 | 460 | 1.80 |
| `13415100087` | 220 | 3,354 | 15.25 |

**转写越长，被压得越狠**（长转写比值 0.08–0.4，短转写反而被注水 3–15 倍）。
全批 转写 221,736 字符 → 录音类证据项 51,679 字符，**保留 23.3%**。

`16761543238` 就是这条链的完整病历：**718 句转写里「老婆」出现 31 次，输出
`gender=未知`、`name=客户3238`、`family_structure` 为空**。信息不是没有，是在压缩里没了。

→ **设计约束 3：原始转写必须以逐字原文进入取证，不得经过任何中间 LLM 摘要。**
（转写体量完全支持：39 案合计 28.1 万字符，单案均值 7,195、中位 975、最大 32,106——单次调用可容纳。）

### 2.4 说话人标记不可用，但性别有一个确定性锚点

AUC 的 `auc_result` 每句带 `{emotion, gender, speaker, speech_rate, volume, text}`。
本次实测 **`speaker` 索引与 `gender` 不自洽**：同一个 `speaker=1` 下同时出现男声与女声句
（`13527911093`：speaker 1 有 27 句 female + 22 句 male；`13570263031`：15 female + 29 male）。
**39 案中没有一例是「两个说话人、性别各自干净」的。** 因此 **说话人编号不能用来判断「谁是客户」**。

但**性别有一个可用的确定性锚点**：微信搜索截图里的声明性别。

| 项 | 实测 |
|---|---|
| 微信明确声明性别（男/女） | **25 / 39** |
| 未声明 | 14 / 39（12 案 `gender="未知"`，2 案该字段为空 / 缺失） |
| 声明 vs 输出一致 | **25 / 25（100%）** |
| 未声明却仍给出性别 | **8 案** |

这 8 案的推理链**全部**写着「个人特征画像中 gender 为男/女」——即**引用中间产物自证**
（`13535737221` / `13702911703` / `13719210972` / `16541242243` / `18003012053` /
`18675756738` / `18902281339` / `18906860015`）。这正是用户最不能接受的那类错误：
**没有依据，却给了一个确定值。**

顺带发现性别取值本身也不统一：`13620040615` 输出 `"女性"`，其余用 `"女"`。

→ **设计约束 4：身份的判定优先级固定为「人工/系统登记 > 一手交互 > 社交自呈现 > 预测」，
且当链路只能追到中间产物时，必须输出「未知」而不是猜。** 25/39 有锚点，其余 14 案应合法留白。

### 2.5 三类缺陷全部可由代码判定

把「自洽性」直接翻译成**与模型无关的规则**，在基线上命中 **97 处**：

| 规则 | 命中 | 性质 |
|---|---|---|
| 身份字段仅靠第三方预测 | 42 | 事实污染 |
| 枚举字段填中文而非枚举键 | 38 | 契约违规 |
| 年龄两处写法不一致 | 8 | 跨产物矛盾 |
| 客户等级两处打架 | 4 | 跨产物矛盾 |
| 单选字段出现多值 | 2 | 契约违规 |
| 判换购却无任何旧车字段 | 1 | 自相矛盾 |
| 已注销企业照填在职 | 1 | 时效错误 |
| 有旧车证据却未判换购 | 1（`15308826588`） | 漏填 |

**没有任何一处需要「理解语义」才能发现。**

另外两处必须点名的横跨性缺陷：

- **卡片与 Notes 从未对齐**：卡片正文 **39/39** 提及身份类字段（年龄 33、职业 32、家庭 35、收入 28），
  而 Notes 由另一批节点独立生成。只在 Notes 侧做校正，会立刻制造新的卡片-Notes 矛盾。
- **自述与输入直接冲突**：`13530559591` 输出断言「客户无试驾录音、无外呼录音、无聊天记录」，
  而该案输入含 256 字符的外呼转写（21 句）。

→ **设计约束 5：所有能写成代码的约束，不交给提示词；跨产物的字段必须来自同一份事实。**

### 2.6 成本：44 倍冗余

| 指标 | 单案均值 | 全批 |
|---|---|---|
| LLM 调用 | 31.0 | 1,208 |
| prompt tokens | 312,969 | 12,205,817 |
| completion tokens | 64,463 | 2,514,067 |
| 墙钟（LLM 累计） | 654 s | 25,488 s |

**同一份素材被反复重读**：全案唯一素材合计 685,185 字符，而实际累计喂入 **30,161,752 字符**——**44 倍**。
其中三个节点最重：`识别结果校对` 59 次 / 242 万 token、`内容有效性判断` 58 次 / 82 万 token
（二者都在录音子流程内，每段录音各跑一次）、`Notes审核` 39 次 / 135 万 token。

→ **设计约束 6：取证一次、成文一次，中间全部走代码。**

### 2.7 六条约束汇总

| # | 约束 | 对立于 |
|---|---|---|
| 1 | 渠道分级；空渠道不进上下文，只留痕 | 2.1 |
| 2 | 事实与预测分属两类，预测不得单独支撑身份字段 | 2.2 |
| 3 | 原始转写逐字进入取证，不经中间摘要 | 2.3 |
| 4 | 身份判定有固定优先级，无依据即「未知」 | 2.4 |
| 5 | 确定性约束交给代码；跨产物字段同源 | 2.5 |
| 6 | 取证一次、成文一次 | 2.6 |

## 3. 主方案：事实账本四段式

### 3.1 总览

```
┌─ L0 记录层（纯代码，0 token）────────────────────────────────┐
│  入口清单 + 14 路子流程取数                                    │
│  → records[]  每条含 record_id / channel / source_class /     │
│                status / created_at / content（逐字原文）        │
│  规则：空渠道记 status=exception，不入下文；转写逐字留存         │
└───────────────────────────┬──────────────────────────────────┘
                            ↓
┌─ L1 事实提取层（1 次 LLM + 代码定坐标）──────────────────────┐
│  输入：records 全文（结构化分节，含逐字转写）                    │
│  输出：claims[]  每条含 subject / attribute / value /         │
│         record_id / span / quote（代码切片）/ claim_type       │
│  规则：quote 由代码按 span 从原文截取；定位不到 → 丢弃该 claim   │
└───────────────────────────┬──────────────────────────────────┘
                            ↓
┌─ L2 核对与投影层（纯代码，0 token）──────────────────────────┐
│  a 归属过滤  b 来源分级  c 冲突消解  d 枚举归一                 │
│  e 单/多值约束  f 跨字段规则  g 缺失即留白                      │
│  → facts（规范事实）+ notes_updates[]（42 字段）+ to_confirm[] │
└───────────────────────────┬──────────────────────────────────┘
                            ↓
┌─ L3 表达层（1 次 LLM）───────────────────────────────────────┐
│  输入：facts（唯一事实来源）+ 产品/邀约预置                      │
│  输出：卡片 9 section + reasoning_detail                       │
│  规则：evidence 只能填 claim_id，由代码展开为「原话 + 记录名」    │
└───────────────────────────┬──────────────────────────────────┘
                            ↓
┌─ L4 校验与分诊层（纯代码 + 1 次小调用）──────────────────────┐
│  分诊：sufficient / thin / empty → 决定走事实流程还是保守模板    │
│  校验：枚举/单值/跨字段/锚点可回溯/卡片-Notes 一致/自述-输入无冲突 │
└──────────────────────────────────────────────────────────────┘
```

要点：**L2 是整条链路的闸门。** 它同时看得见所有字段、所有断言、所有来源，
所以「矛盾」在这一层被消解，而不是靠提示词祈祷模型不写矛盾。

### 3.2 L0 记录层（纯代码）

**做什么**：把入口清单与 14 路子流程的取数结果，统一成一份带来源、带状态、带时间的记录集。

```jsonc
// records[]
{
  "record_id": "rec_testdrive_13415100087_0",  // 稳定可寻址
  "channel": "TestDriveRecordingFile",
  "source_class": "primary_interaction",        // primary_interaction | declared | weak | prediction | exception
  "status": "ok",                               // ok | empty | exception
  "created_at": "2026-09-22T…",                 // 入口清单自带，142/142 都有
  "content": "…逐字原文…",                       // 转写 / OCR 文本 / 接口原文
  "content_kind": "transcript"                  // transcript | ocr | json | report
}
```

**四条硬规则**：

1. **渠道分级由代码按 `channel` 定**，不由模型猜。9 个空渠道 → `status=exception`，
   不进 L1 上下文，但**在记录层留痕**——这是「不得输出无录音/无聊天记录」的结构保证。
2. **转写逐字留存**，`content_kind=transcript`。**禁止**在 L0/L1 之间插入任何 LLM 摘要。
3. **ASR 的 `speaker` / 逐句 `gender` 只作为原文属性附着**，不作为归属依据（2.4 已证不可用）。
   归属交由 L1 按语义判定主体。
4. **时间戳随记录携带**，L2 做时效判定（如「登记状态注销」的企业不得当作在职）。

**成本**：0 token（与现行取数阶段等量，只是加了簿记）。

### 3.3 L1 事实提取层（1 次调用 + 代码定坐标）

**输出是「断言账本」而非「画像」**——这是与现行最大的一处不同。

```jsonc
// claims[]
{
  "claim_id": "c_017",
  "subject": "customer",       // customer | spouse | family | colleague | salesperson | other | unknown
  "attribute": "occupation",
  "value": "充电桩行业从业者",
  "record_id": "rec_testdrive_13415100087_0",
  "span": [1042, 1063],
  "quote": "我知道，我以前做充电桩。",   // 由代码按 span 截取，模型不誊抄
  "claim_type": "fact",        // fact | observation | prediction
  "confidence": 0.9
}
```

**三条规则，全部在代码侧执行**：

1. **主体必填**。`subject` 为空或 `unknown` 的断言不得支撑身份字段。
   `13926073386` 那句「我们单位也要买一个」→ `subject=salesperson_or_workplace`，**不能**升格为客户职业。
2. **坐标由代码切**。模型只给 `span`；代码从 `record.content` 里切出 `quote`。
   **切不到就丢弃该条断言**。这一条把基线里 58.1% 可回溯的引文，强制提到 100%——
   因为留下的一定是原文切片，不存在「像引文实为归纳」的东西。
3. **预测单列**。`claim_type=prediction` 承接第三方打点；`fact` / `observation` 承接一手与登记。

**输入**：`records` 全文，按渠道分节、关键段前置（规避长上下文中间丢失）。
实测合并体量：输入包均 32,619 字符 + 转写均 7,195 = 约 **3.98 万字符 ≈ 2.5 万 token**，
最大 78,787 字符 ≈ 4.9 万 token——**单次可容纳**。

**为什么这一步值得单独一次调用**：它是唯一需要通读全部原文的环节，也是唯一能同时
「看见老婆出现 31 次」和「看见昵称是店铺名」的环节。

### 3.4 L2 核对与投影层（纯代码，0 token）

**这是全案的枢纽。** 输入 `claims[]`，输出 `facts` + `notes_updates[]` + `to_confirm[]`。

**a 归属过滤**：`subject != customer` 的断言不得写入身份字段；可写入家庭结构、可进入卡片叙述。
**b 来源分级**：`claim_type=prediction` 的断言不得单独支撑 `基础身份` 类字段（16 个），
只能作为卡片软性内容并标注「预测」。
**c 冲突消解**：同一 `attribute` 出现多值时，按 `人工/系统登记 > 一手交互 > 社交自呈现 > 预测` 排序，
同档按 `created_at` 取新；仍冲突 → 进 `to_confirm`，**绝不两个都写出去**。
**d 枚举归一**：`value → enum key` 走查表；含 `items` 为对象的结构化枚举（`has_children` /
`driver_license_status.yes` / `seating_requirement.large_space` / `trade_in_requirement.yes`）
按契约填 `input_value`。非法值拒绝并回落。
**e 单/多值约束**：按契约 `multiple_value` 强制（`purchase_type` 等 16 个单选字段拒绝多值）。
**f 跨字段规则**：年龄/等级/姓名等**跨产物字段在此唯一化**；旧车 ⇒ `purchase_type=replacement`；
`trade_in_requirement=yes` ⇒ 换购；企业已注销 ⇒ 不填在职属性。
**g 缺失即留白**：无断言支撑的字段**留空**，不生成任何替代文本。

**实测效果（基线回放）**：

| 动作 | 命中 |
|---|---|
| 清除「仅第三方」身份断言 | 42 |
| 枚举归一 | 38 |
| 年龄两处统一 | 8 |
| 等级两处统一 | 4 |
| 单选多值截断 | 2 |
| 换购无证清理 / 旧车漏填修复 | 1 / 1 |
| 已注销企业清理 | 1 |
| **合计** | **97** |

**代价（有意为之）**：约 42 个字段实例会因「只有预测撑腰」而**空出来**。
这是准确性优先的必然结果——**空着比填错强**，且空出的字段全部转成 `to_confirm` 交给销售。

### 3.5 L3 表达层（1 次调用）

**输入只有 `facts`**（规范事实）与产品/邀约预置。模型**看不到**原始 records。

**输出**：卡片 9 个 section，含每个 `reasoning_detail` 的 `summary` / `steps` / `evidence` / `confidence`。

**三条规则**：

1. **不得新增事实**。卡片里的每个具体值（年龄、职业、收入、家庭）只能来自 `facts`，
   且 `facts` 里没有的就不能写。
2. **evidence 锚点只填 `claim_id`**，由代码展开为「原话（记录名）」渲染给销售。
   既满足「引用原始数据准确翔实」，也避免模型自由誊抄（基线里 15.0% 的 summary 与 steps 零重叠、
   96 个块 steps≤1 条，都源于模型被要求同时创造与引用）。
3. **一致的边界表达**。`facts` 缺失的维度，以「当前信息不足」+ **建议的补充动作**表述
   （如「建议电话确认用车人」），而不是联想填空。

**为什么 Notes 与卡片不再打架**：两者在 L2 都由 `facts` 投影出来，
年龄/等级只有一个来源，**结构上不可能出现两个值**。

### 3.6 L4 校验与分诊层

**分诊（1 次小调用）**：读记录清单（有哪些渠道、各多少内容），输出三档：

- `sufficient`：有一手交互 → 走 L1–L3 事实流程；
- `thin`：只有声明/社交/预测 → 保守模板，只输出能坐实的字段，其余留白；
- `empty`：几乎无数据 → 输出「待补充」骨架，不产生任何具体断言。

**校验（纯代码）**：枚举合法性、单值约束、跨字段一致、**锚点 100% 可回溯**、
卡片-Notes 逐字段一致、**输出与 records 无冲突**（自动拦截「输出无录音而输入有录音」）。
任一项失败 → 只重生成该字段，或置入 `to_confirm`。

**`to_confirm` 是产品的一部分，不是失败品**：它把「我们不知道」变成销售的下一步动作，
既守住准确性，又不让产品显得空洞。

### 3.7 契约保持

对外契约**一个字节都不变**：

- `basic_notes_updates` 仍为 `[{attribute_key, attribute_value, reasoning_detail}]`；
- 42 个字段的 `attribute_key` / 枚举 `items` 严格按 `GET /api/v1/remote/config/note-attributes`；
- 卡片 9 个 section 及其内部字段名不变；
- 回写仍走原有 `@writeback` 开关（当前 `WRITEBACK_ENABLED=false`）。

**唯一的变化在内部**：字段不再由模型直接写，而由 L2 投影；锚点由 `claim_id` 展开。

### 3.8 成本（预估，需 AB 实测）

| 环节 | prompt | completion | 调用 |
|---|---|---|---|
| L1 取证 | ≈ 24,900 | ≈ 5,000 | 1 |
| L3 成文 | ≈ 10,000 | ≈ 9,600 | 1 |
| L4 分诊 | ≈ 300 | ≈ 100 | 1（稀疏案更省） |
| 合计 | — | — | **2–3 次** |

单案约 **5 万 token**，对比现行 377,469（313k + 64k）——**降约 87%**；墙钟预计从 654 s 降到十秒级。
L2 投影与规则求值是代码，**零 token**。

## 4. 备选一：单次调用 + 代码后置校正

**一句话**：把 L1 与 L3 合并成**一次调用**，直接产出 `facts` + 卡片 + Notes；
模型在同一上下文里自己保证一致，代码只做事后校正。

**机制**：输入 `records` 全文；一次生成一个 canonical JSON（账本 + 卡片 + Notes）；
随后跑一遍 L2 的规则集做校正与拒绝。

**治什么**：成本与时延最优（1 次调用、约 3.5 万 token）；
跨节点矛盾消失（只有一个节点）。

**治不了什么**：
- **归属仍靠模型自觉**——没有独立的主体判定环节，「我们单位」被写成客户职业的风险仍在；
- **锚点仍是模型誊抄**——`quote` 由模型写，可回溯率只能靠提示词与事后校验，达不到 100%；
- **单点失败**——一次调用出错即无产出。

**适用**：时延/成本成为硬约束，且能接受「归属与锚点用后置校验兜底」的场景。

## 5. 备选二：取证—核验双通道

**一句话**：在**主方案**之上加一条**独立核验通道**——它只拿到「断言 + 它声称的原文出处」，
**不给**取证通道的推理过程，逐条问三件事：

1. **主体对吗**——「单位也要买一个」说的是谁的单位？
2. **有矛盾吗**——同一客户其它断言或原文是否与之冲突？
3. **时效对吗**——「登记状态注销」的企业还能当在职吗？

判为不成立 → 丢弃或降级为 `to_confirm`。

**为什么必须独立**：与取证通道同源同错是这类校验最常见的失效方式。必须独立提示词、独立上下文。

**治什么**（实测可命中的具体缺陷）：
- 归属类：`13926073386` 的「单位」误置；
- 时效类：已注销企业；
- 矛盾类：`purchase_type=replacement` 与「无任何旧车字段」互斥；
- 自述类：`13530559591` 的「无录音」——独立通道只看输入，更容易发现冲突。

**代价**：每次调用成本增加 0.5–1 倍；且「证伪」会带来假阴性，需允许「存疑」第三态。
建议**按预算选择性启用**（如仅对身份类字段与商机等级启用）。

## 6. 三案对比

| 维度 | 主方案 · 四段式 | 备选一 · 单次 | 备选二 · 双通道 |
|---|---|---|---|
| LLM 调用 | 2–3 | 1 | 3–5 |
| 单案 token | ≈ 5 万（预估） | ≈ 3.5 万（预估） | ≈ 7–10 万（预估） |
| 字段矛盾 | **结构上消除** | 提示词保证 + 事后校正 | 结构上消除 |
| 归属正确 | **强**（主体必填 + 代码过滤） | 中（靠提示词） | **最强**（独立复核主体） |
| 锚点可回溯 | **100%**（代码切片） | 中（模型誊抄 + 校验） | **100%** |
| 语义级事实核查 | 无 | 无 | **有**（唯一） |
| 单点失败风险 | 低 | **高** | 低 |
| 主要风险 | L2 规则表工作量大 | 归属/锚点兜不住 | 成本、假阴性 |

**判断**：主方案在「准确性/自洽性/可读性优先、成本次之」的给定优先级下是正解；
备选一是成本敏感时的降级；备选二是唯一能做语义级核查的路径，作为**闸门**按预算叠加在主方案之上。

## 7. 推荐与验证计划

**推荐**：**主方案落地，先用 L4 分诊 + 备用二的「身份类字段」子集作闸门。**

理由：主方案把三类反馈分别归位（归属→L1 主体、矛盾→L2 规则、证据→L1 坐标 + L3 claim_id），
且**每一段都能单独上线、单独度量**：

1. **L0 + L4 先上**（取数分级 + 分诊）：改动最小，立刻消除稀疏案编造，并让空渠道不再污染上下文；
2. **L1 + L2 再上**（账本 + 投影）：兑现「矛盾不可能发生」「预测不撑身份」「锚点可回溯」；
3. **L3 随后**（成文只读 facts）：兑现卡片-Notes 同源；
4. **备选二的子集按预算叠加**：先只核身份字段与商机等级。

**AB 实验指标（与验收标准逐条对齐）**

| 目标 | 指标 | 口径 |
|---|---|---|
| 准确性 | 事实错误率 | 人工抽检：字段值与「原文可坐实的事实」不符的比例 |
| 准确性 | 无依据确定值率 | 输出确定值但锚点仅指向中间产物的比例（目标：0） |
| 自洽性 | 代码规则命中数 | §2.5 那套规则在产出上的命中数（目标：趋零） |
| 自洽性 | 卡片-Notes 一致率 | 逐字段比对（目标：100%） |
| 可读性 | 锚点可回溯率 | 锚点能在原文定位的比例（目标：100%） |
| 可读性 | summary-steps 语义重叠 | 二者有可提取关联的比例 |
| 成本 | 单案 tokens / 墙钟 | 与现行 377k / 654 s 对比 |

**探针集**：§3.9 的 5 组共 12 案，逐案核对「已知正确答案」。
