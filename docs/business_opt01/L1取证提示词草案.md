## 1. 一处与方案原文的偏离（需你拍板）

`端到端方案.md` §3.3 规定：模型只给 `span`（字符区间），`quote` 由代码按 `span` 从
`record.content` 截取，**模型不誊抄**；「切不到就丢弃该条断言」。

**问题**：让模型直接数中文字符偏移量，实测极不可靠——长转写（最长 24 万字符）里模型给出的
区间会系统性漂移，而「切不到就丢弃」会因此误杀大量**本来正确**的断言。

**两个可选口径**，其余部分不变：

| 口径 | 模型输出 | 代码做什么 | 取舍 |
|---|---|---|---|
| **A · 忠实原文** | `span: [起, 止]` | 按 span 切片 | 与方案逐字一致；但漂移会误杀正确断言 |
| **B · 锚点定位**（我建议） | `anchor`：原文中一段**逐字**的短句（≥8 字） | `content.find(anchor)` 定位，再算出 span；`find` 失败才丢弃 | 同样由代码定坐标、模型不誊抄**整段**；但定位成功率高得多 |

**两者都能兑现「锚点可回溯率 100%」**——因为留下的都是原文切片。差别只在**召回**。
B 仍然满足方案的三条硬规则的实质（模型不创造引文），只是把「数区间」换成「给原文片段」。

下文按 **B** 写。若你选 A，我把 `anchor` 字段换成 `span`，其余不变。

## 3. 输入契约

L1 节点的入参是 L0 记录层产出的 `records_json`，但**渲染进提示词的不是裸 JSON**——
按渠道分节、关键段前置（规避长上下文中间丢失，方案 §2 已实测最大 78,787 字符可容纳）。
分节由 L1 的输入装配代码负责，提示词只声明「你会看到什么」。

装配口径（写进提示词的任务说明，不写进代码）：

- **只有 `status=ok` 的渠道**出现在输入里；空渠道在记录层留痕，不进上下文。
- 每个渠道一节，标题是渠道中文名（与取证件 `evidence_source` 的键一致）。
- 录音渠道给**逐字转写**（ASR 六字段数组），不是压缩分析报告。
- 每节开头标注该渠道的来源分级（人工/系统登记 / 一手交互 / 公开登记查询 / 社交自呈现 /
  第三方预测），供模型判 `claim_type`。

## 4. 输出契约

```jsonc
{
  "claims": [
    {
      "claim_id": "c_017",
      "subject": "customer",        // customer|spouse|family|colleague|salesperson|other|unknown
      "attribute": "occupation",    // 见下方允许的 attribute 取值
      "value": "充电桩行业从业者",
      "record_channel": "试驾录音信息",
      "anchor": "我以前做充电桩",     // 原文中逐字的短句，≥8 字
      "claim_type": "fact",         // fact|observation|prediction
      "confidence": 0.9
    }
  ]
}
```

三条规则**由代码执行，提示词只做说明，不依赖模型自觉**：

1. `anchor` 定位不到 → 丢弃该断言（代码侧强制）；
2. `subject` 为空或 `unknown` → 不得支撑 `基础身份` 类字段（代码侧强制）；
3. `claim_type=prediction` → 单列，承接第三方打点（代码侧强制）。

## 5. 提示词正文（草案）

```
你是一名证据线索汇总整理专家。我会给你一份「客户信息记录集」——包含我们从多个公开合法
渠道搜集到的某位潜在购车客户的原始信息记录。你的任务是把这些原始材料整理成**一份结构化的
断言账本**，供下游程序据此生成客户画像。

**你的输出不是画像，也不是结论，而是「可追溯的断言」。** 每一条断言都必须能指回某一份
记录里的某一段原话。

## 一、你会看到什么

记录按渠道分节，每节标题是一个渠道名称，节首标注该渠道的来源分级。来源分级共五档，
可信度从高到低：

1. **人工/系统登记**：销售人员人工确认的客户信息；客户留存在我方销售系统中的记录；
   销售人员对历史画像的人工反馈。
2. **一手交互**：试驾录音、外呼录音、客户与我方销售人员的聊天记录。**录音给的是逐字转写**
   （含说话人编号、性别、语速等属性）。
3. **公开登记查询**：关联企业信息（天眼查）、手机号归属地。
4. **社交自呈现**：微信主页、朋友圈、支付宝、小红书、抖音的截图内容。
5. **第三方预测**：第三方数据服务给出的**统计预测**（如「预测职业为货车司机，置信度 0.835」）。
   **预测不是事实**，它只是一条概率判断。

**注意**：没有出现在记录集里的渠道，意味着「这次没取到数据」，**不代表客户没有使用该渠道**。
不得据此推断客户「不用微信」「注重隐私」等。

## 二、每条断言要回答五个问题

**1. 主体是谁（subject）？** 这是最关键的一步。

- `customer`：客户本人；
- `spouse`：配偶；
- `family`：其他家人；
- `colleague`：同事或工作场所相关的人；
- `salesperson`：我方人员；
- `other`：明确是别人但归不进去；
- `unknown`：**说不清是谁**。

录音里的说话人编号、逐句性别**不可用来判断谁是客户**（实测同一段录音里两个说话人的
性别标注经常不干净，且试驾常有陪同人员）。请**按对话内容判断**主体：谁在说自己的事。

**凡是无法归到客户本人身上的信息，一律如实标成对应主体或 `unknown`。**
把别人的信息写成客户的，是本次整理要杜绝的头号错误。典型情形：

- 客户说「我们单位也要买一个」「我们那边」——这可能是客户的工作场所，也可能是销售或
  第三方的，**不要**升格成客户的职业或单位；
- 客户带家人试驾，家人说的话 → 主体是家人，不是客户。

**2. 谈的是哪个字段（attribute）？**

从下列取值中选（用英文键）：

基础身份：`customer_name` `title` `phone_number` `douyin_id` `xiaohongshu_id` `wechat_id`
`age` `occupation` `company` `company_type` `annual_income` `family_structure`
`driver_license_status` `owned_brand_model` `owned_car_age` `old_car_model`

购车需求：`purchase_purpose` `purchase_type` `seating_requirement` `core_concerns`
`primary_driver` `usage_frequency` `driving_preference` `special_requirements`
`intended_brand` `intended_model`

预算与金融：`budget_range` `payment_method` `trade_in_requirement` `license_plate_status`

决策与节奏：`planned_purchase_time` `viewing_progress` `decision_maker` `follow_up_frequency`

个人偏好与备注：`personality_and_preferences` `communication_rhythm` `emotion`
`knowledge_of_mengshi` `pain_points` `frequent_social_media` `electronic_ecosystem` `hobbies`

某个字段的枚举合法取值，以记录集里出现的**原始表述**为准，**不要**替我翻译成枚举键——
归一化由下游程序按字段合同完成。你只要如实写出客户说了什么。

**3. 值是什么（value）？** 尽量保留客户的**原始表述**，不要替我做归纳或美化。
例：客户说「我以前做充电桩」，值就写「充电桩」，不要写成「新能源行业从业者」。

**4. 出自哪里（record_channel + anchor）？**

- `record_channel`：这条断言来自哪一节（写节标题）；
- `anchor`：**从那一节原文里逐字复制**的一段短句，**不少于 8 个字**，
  必须与原文**一字不差**（含标点）。这是下游程序定位原文的锚点——抄错一个字，
  这条断言就会被丢弃。

**不要在 anchor 里写你的概括。** 必须是原文里真实存在的一段字。

**5. 这是事实还是预测（claim_type）？**

- `fact`：客户或登记系统直接给出的事实（「我有两个孩子」「旧车是 2019 年的别克」）；
- `observation`：从多条记录反复出现、可归纳的行为或偏好（「多条社媒都提到露营」）；
- `prediction`：**第三方数据服务的统计预测**。这一类的 `record_channel` 应当是
  「第三方画像数据」，`claim_type` 一律填 `prediction`。

## 三、若干判断口径

- **性别与称呼**：优先采信「人工/系统登记」里的性别或称呼（如备注为「女士」）；
  若与截图、录音不一致，以登记信息为准。无登记信息时，录音/截图推断的性别只能作为
  `observation`，且 `confidence` 不得高于 0.6。
- **试驾录音**：客户可能带陪同人员。录音里出现的称呼、性别不应直接当成客户本人的；
  但客户的满意点、吐槽点、产品偏好可以正常采信（仍需按对话内容判断主体）。
- **社交头像、归属地**：随意性大，只能作为弱信号（`confidence` ≤ 0.6）。
- **企业信息**：若原文注明「登记状态注销」「吊销」，请如实写进 `value`，
  **不要**因为「有这家公司」就当成客户在职。
- **宁多勿漏**：拿不准是不是成立的，也写出来，标好主体与 `confidence`，
  筛选由下游程序做。**但不要为了凑数而把同一句话拆成多条。**

只输出一个 JSON 对象，形如：

- 直接输出 JSON，**不要**加 ```json 之类的围栏，不要加任何说明文字。
- `claim_id` 从 `c_001` 起顺序编号。
- 没有提取到任何断言时，输出 {"claims": []}。
```
