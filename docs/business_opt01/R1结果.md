## 4. 三个根因（已在 `b6a7023` 修复）

### 4.1 锚点长度门在误杀正确断言【主因】

原实现：`anchor` 短于 8 字**一律丢弃**。实测被丢的 226 条短锚里：

- **189 条（84%）逐字存在于原文**——不是模型抄错；
- **其中 163 条（72%）在原文里只出现一次**——本来就唯一可定位，不存在歧义。

对照 R0：中位锚长 16、短锚占比 10%；R1：中位锚长 8、短锚占比 38%。
**同一批记录、同一段 anchor 口径（提示词第 63 行未改），锚系统性变短了**——见 4.3。

**修法**：长度从来只是「能否唯一定位」的代理指标。改为按**唯一性**判定——
短锚只要在同一记录里唯一出现即保留（新增 `_occurrences`，与 `_locate` 同口径含忽略空白回落），
另设 `MIN_SHORT_ANCHOR = 4` 下限：「好」「幺三九」这类切片没有证据价值，仍丢。

### 4.2 空产出会清空 production 已填字段【严重】

`16761543238` 的 L1 返回 `{"claims": []}`——**合法 JSON、重试机制不触发**，
覆写后 production 本来填好的 8 个字段**全部消失**。

「L2 认定这些字段无据」与「L1 这次什么都没抽到」是完全不同的两件事，
前者可以覆写，后者必须保持原样。

**修法**：`overwrite_notes_updates` 增护栏——产出为空时不覆写、保持原样并留痕。

**另**：该案 2 案复跑（`A-pipeline-recheck1-20261010`）得到 **22 个字段**，
说明空响应是**偶发抖动**而非必然。同批复跑的 `13530559591` 得 5 字段（首轮 4），
两案都稳定在低位——**说明低产不是抖动，只有 16761543238 的空响应是**。

### 4.3 枚举键附录放在末尾，诱导 anchor 变短【成因】

修订一（枚举键附录）**本身是有效的**：`d_enum` 拒绝从 11.7 条/案降到 2.4 条/案，
说明模型确实开始输出合法键了。但它被放在了**记录之后、紧贴输出指令**的位置，
而附录是一串短 token（``Mr=先生 / Ms=女士``），**模型把 anchor 也写成了同样短的裸串**：

| 轮次 | 第三方预测记录的典型锚点 | 带 JSON 键包裹的锚点占比 |
|---|---|---|
| R0 | `'"name": "预测年龄段"'`（15 字） | **29%** |
| R1 | `'预测年龄段'`（5 字） | **4%** |

**修法**：附录移到记录**之前**，让记录原文成为模型最后读到的内容。

2. **空覆写护栏**（§4.2）：`16761543238` 从 R1 的 **0 字段**回到 **14 字段**（含 `purchase_type`

**头像画面不再被写成 `hobbies`——修订二的用户名禁令生效了。** 但两案的新值都改从
**第三方预测档**取，属**有据但非客户本人陈述**：`hobbies` 不在 L2 的身份豁免集里，

与 R0 §5.3 的禁令字面冲突，需单独确认。

### 5.3 成本：上升不是因为修复，是阶段二的结构

720,273 vs R1 的 714,620，**几乎不动**；对比基线 437,809 是 **+64.5%**。
这不是缺陷：阶段二只**增加** L1 一次调用（13 案含两段超长转写，`13926073386` 单次 prompt
就 30 万 token），**并未削减 production 的 11 路生成节点**。成本收敛是阶段三（T6）的事，
R2 之前不必为此改设计——但「L1 输入体量」这个增量因子要在 R2 前定性。

### 5.4 剩余缺口的分层（本节结论的落点）

`360 - 192 = 168` 是**计数差**；**集合差集是 224 条**（基线有、R1b 完全没有的字段），
另有 **56 条是 R1b 净增**的字段（基线无、R1b 有）。两者不等是正常的算术，**引用时须用 224**。

把 224 条按**基线那侧的证据档位**分层：

| 分层 | 条目 | 含义 |
|---|---|---|
| 真缺口（基线有 登记/一手/公开登记 档依据） | 106 | 本该能坐实却没坐实 |
| 伪缺口·仅预测档 | 26 | 基线靠第三方预测撑，本就不该当事实 |
| 伪缺口·基线无 evidence | 92 | 基线连依据都没有 |

**别名假设已核实**（2026-10-10）：基线证据前缀里的 `试驾录音`（39 案共 609 次）
`外呼录音`（123 次）**就是**取数渠道 `试驾录音信息` / `外呼录音信息` 的简称。两条独立证据：

1. **同一份 ASR**——基线节点「录音文件内容抽取（纯识别，无加工）」的 `file_content` 是
   `speaker 1: 元都可以抢。(neutral, female, 5.43, 80.44)`；管线 L0 的对应片段是
   `{"speaker":"1","speech_rate":5.43,"volume":80.44,"text":"元都可以抢。"}`。
   同一句话、同样的 `speech_rate` 与 `volume`，只是序列化形态不同；
2. **内容可对上**——`18902281339`（试驾 L0 完好、基线有 45 条 `试驾录音：` 引文）里，
   引文的核心短语 `充电桩` `换电站` `汕尾` `宁德时代` `银色` `外放电` `极氪` 全部出现在
   L0 试驾正文中。

因此**真缺口取 106**，不用 14。此前一度算出「命中率 1%」是**比对方法的假阴性**：
把 `前缀：引文` 整串拿去对一份**序列化形态不同**的 JSON 数组，自然对不上。

**两条必须随附的限定**：

- 前缀 `录音`（98 次）**不区分试驾/外呼**，无法归入任一渠道，分层时不计入「取数渠道」侧；
- **归档对 >1 MB 的节点输出只存 `{_truncated, bytes, sha256}` 摘要**
  （`scripts/baseline_artifacts.py:72`；R1b 有 23 个字段如此，含 3 案的 `records_json`）。
  因此**大载荷案的 L0 内容无法从归档复原**，「基线引文 vs 管线 L0」这类逐案比对
  在长转写案上做不到，只能在归档未截断的案上做。

**更正一处口径错误**：本节草稿曾写「1005 个 Notes 条目里 722 条（72%）证据锚点落在
非取数渠道」——**该数字是错的**。39 案全量重算：证据锚点**全部**落在非取数渠道的
Notes 条目是 **333 条（33.1%）**；`试驾录音`/`外呼录音` 既已核实为取数渠道，不应计入
「非取数」。非取数前缀的真实构成是空前缀 244 次、`个人特征画像` 197 次、
`预提取信息` 28 次、`预提取的客户初始信息` 19 次等——**`个人特征画像` 才是自产画像那一类**，
规模 197 次，仍对应主方案要淘汰的「证据链引用自产画像」，但**远没有 72% 那么严重**。

## 8. 结论与下一步

1. **四段式架构的端到端正确性未被证伪**：链路跑通、判据 3 首次通过、覆写生效、
   枚举归一显著改善。字段少是判据过严与输入位置不当所致。
2. **三项修复已提交（`b6a7023`）并复跑（R1b）**，R1b 结果见 §5。
3. **R1 首轮的数字本身不可用作质量结论**——它测的是「带三个缺陷的实现」。
   若要对外引用，只能引用 R1b。
4. 待办（R1b 出数后定）：修订二为何未生效、长转写是否分段、账号装饰是否需要代码侧兜底。
