## 修订一 · 枚举字段改为「直接输出合法键」（对应 R0 §5.1，严重）

### 问题

现行正文第 50 行：

> 某个字段的枚举合法取值，以记录集里出现的**原始表述**为准，**不要**替我翻译成
> 枚举键——归一化由下游程序按字段合同完成。你只要如实写出客户说了什么。

这句话我写下的**承诺，下游兑现不了**：L2 的 `normalize_enum` 只能**精确匹配**合法键或
契约里的展示名（`油耗` → `fuel_efficiency`）。客户的口语表述一律归不了，实测被整条丢弃：

| 字段 | 实测取值 | 为何归不了 |
|---|---|---|
| `emotion` | 「对自驾表现紧张、担心」 | 不是 `prone_to_anxiety`，也不是展示名「容易焦虑」 |
| `core_concerns` | 「担心电池衰减」 | 不是 `safety`，也不是展示名「安全」 |
| `payment_method` | 「6万两年免息，首付6万7」 | 不是 `loan`，也不是展示名「贷款」 |

`13926073386` 有 **17 条**、`16761543238` 有 **14 条**如此被拒。基线**能**填出合法键，
因为 production 有 `GET /config/note-attributes` 节点，把**字段清单与合法枚举值**渲染进了
它的提示词输入。实验臂缺的正是这一段。**这是我的设计缺口，不是模型不听话。**

### 改法（两件事必须同时做）

**(a) 正文第 50 行** → 替换为：

```
**枚举字段必须输出合法枚举键，不要输出中文展示名。** 本节末尾附有每个枚举字段的
**合法键清单**（含中文展示名），取值时对照该清单：

- 客户的表述能对上清单里的某一项 → **值就写那一项的英文键**。
  例：客户说「想省油」，`core_concerns` 写 `fuel_efficiency`，不要写「油耗」或「想省油」；
- 一项也对不上、或你无法判断 → **不要硬凑**，照实写客户的原始表述，下游会按合同复核。

**自由文本字段**（清单里没有的，如 `hobbies` `pain_points` `occupation`）照实写客户的
原始表述，不要替我做归纳或美化。
```

**(b) 在 `build_l1_input` 的输出末尾追加一段附录**（由 `notes_contract` 快照生成，
**不手抄**，契约一变附录跟着变）。形如：

```
## 可选字段的合法取值（枚举字段必须用英文键）

- `title`（单选）：Mr=先生 / Ms=女士
- `purchase_type`（单选）：first=首购 / company=公户购车 / unknown=未知 / additional=增购 / replacement=换购
- `core_concerns`（多选，多个值用 || 连接）：power=动力 / smart=智能 / space=空间 / safety=安全 / appearance=颜值 / fuel_efficiency=油耗
- `family_structure`（单选，结构化）：married=已婚 / unmarried=未婚 / has_children=有孩子（**需随带填孩子人数**）
- `driver_license_status`（单选，结构化）：no=无 / yes=有（**需随带填驾龄年限**） / novice=新手
- ……（共 21 个枚举字段，逐条列出）
```

附录约 1 KB，对 token 影响可忽略。清单里的「需随带填…」对应契约的结构化枚举
`input_value` 要求（否则 L2 会补空串，再由 L4 追认）。

### 影响

- **正面**：枚举字段的召回与合法性大幅提高（R0 里被整条丢弃的那些断言有机会落库）。
- **代价**：L1 提示词输入变长（+1 KB）；模型需多花一点注意力对照清单。
- **不改**：自由文本字段的口径不变（仍要求原始表述）。

## 修订二 · 账号元字段禁令与姓名清洗（对应 R0 §5.3，中）

### 问题

L1 把**账号的装饰**当成了**客户本人的事实**，并给出了三类错误值：

| 字段 | 实验臂给的值 | 依据（错在哪里） |
|---|---|---|
| `hobbies` | 「一张风景照片，画面主体为秋季山间溪流…」 | 来源是 `avatar_description`（头像画面的机器描述） |
| `personality_and_preferences` | 「男性」 | 来源是 `gender`（账号性别标签） |
| `customer_name` | 原始微信昵称（含国家码前缀与表情符号） | 来源是 `nickname` |

客户**从未说过**自己的兴趣爱好是「一张风景照」——那是账号头像的**画面描述**。基线把
`customer_name` 清洗成规范姓名（production 提示词有「若判断微信昵称为真实姓名，可填写
相应部分，否则不填」的规则），实验臂直接抄了原始昵称，是**召回上的回归**。

### 改法：在「三、若干判断口径」中**新增两条**

**新增第一条（置于该节最前）：**

```
- **账号装饰不是客户事实。** 微信昵称、头像图片的画面内容、账号性别标签、地区/归属地，
  都属于**账号的呈现**，不是客户本人的陈述。它们**不得**直接作为下列字段的值或依据：
  - 头像的画面内容（「一张风景照」「宠物照」）**不得**写成 `hobbies`；
  - 账号性别标签**不得**写成 `title` 或 `personality_and_preferences`；
  - 昵称**不得**直接写成 `customer_name`（见下条）。
  这类账号信息最多只能作为 `observation` 类弱证据，且 `confidence` 不得高于 0.6。
```

**新增第二条：**

```
- **`customer_name` 只写能判断为真实姓名的部分。** 记录中的微信昵称、带表情符号或
  国家码前缀的账号名、店铺名、或明显不是姓名的字符串，**不要**直接当作 `customer_name`；
  只有当记录里明确出现「我叫…」「贵姓…」或登记信息给出姓名时，才写 `customer_name`。
  若只有姓、或只有昵称且判断不出真实姓名，**宁可不写**。同时区分**购车人**与**陪同人**：
  陪同人员的姓名不得写成 `customer_name`。
```

现行第 72 行「社交头像、归属地：随意性大，只能作为弱信号（`confidence` ≤ 0.6）」与新
第一条重复，**保留原文不动**（它讲的是弱信号分级，新条讲的是「不得当事实」的禁令，互补）。

### 影响

- **正面**：堵住「把账号装饰当客户事实」这一类错误；`customer_name` 回到基线的清洗水平。
- **不改**：不禁止把账号信息作为**弱证据**（如「头像为帆船运动 → 可能喜户外」仍可作
  `observation`，只是不得升格成事实）。
