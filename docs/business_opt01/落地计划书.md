## 2. 关键架构决策（须拍板）

### D1 · 实验臂是一个自包含的顶层工作流

`run_baseline.py` 的入参只有 `phone_number` / `batch_id`，且要求被调工作流产出一个 `result1`。
因此实验臂必须是一个**顶层入口形状**的新工作流 `customer_profile_pipeline`：

```
start(phone_number, batch_id)
  ├─ [取数层] http 获取全量用户数据 + 14 路 tool 子流程（原样复用，不新建）
  │    └─ code L0 记录层 → records[]
  │         ├─ llm L1 取证层 → claims[]（阶段二起）
  │         │    └─ code L2 投影层（阶段二起）
  │         └─ code L4 分诊层 → sufficient / thin / empty
  └─ tool customer_profile_production（既有成文与回写，输入契约不改）
       └─ [阶段二] code Notes 兼容覆写
  → end(result1)
```

### D2 · **不改** `evidence_subagent.py`

`落地方案.md` §1.1 说「取证部分下线」。本次把它实现为「**新工作流不再包含那个节点**」，
而不是去编辑既有工作流。理由：`customer_profile_entry`（基线臂）用的正是
`evidence_subagent`，改它会让同一条分支上的基线臂一起变，AB 立刻不成立。

**代价**：新工作流的取数层要与 `evidence_subagent` 的 14 路 tool 声明重复一份
（可参照其 `_tool()` 构造函数，但**不能**从它 import）。

### D3 · 基线臂用**已冻结的历史批次**，不重跑

`experiments/batches/baseline-39-dsv41-noThink/`（39 案、单一定义哈希、`attempts.json` 全文）
就是对照物，场地自己的 README 也这么定义这个目录（「改动前的对照物，只读」）。

关键理由：`customer_profile_production` 是**两臂共用**的模块。阶段三（L3）要改它，一改基线臂
也跟着变。若坚持「两臂同脚本同日重跑」，阶段三就必须把 production 复制成 v2 工作流。
用冻结批次可以省掉这份重复。

**唯一需要重跑基线臂的场合**：阶段三落地后要出一份同日同配置的正式对比。此时在**分支点 commit**
的 worktree 里跑基线臂，保证它拿到的是改动前的 production：

```
git worktree add ../cp-baseline <dev-business-opt01 的 HEAD>
```

### D4 · 阶段一/二先用「兼容覆写」把 L2 的成果接进 `result1`

阶段一、二都不动 production 内部。为了让 L2 纠正过的 Notes 真的出现在产物里，
在新工作流末尾加一个 code 节点，用 L2 产出的 `notes_updates` **覆写**
`analysis_result.basic_notes_updates`。

- 好处：阶段二就能端到端度量，不必等 L3；
- 代价：这是**临时手段**，阶段三落地后删除；
- 风险：卡片与 Notes 此时仍不同源（阶段性不一致可接受，阶段三解决）。

### D5 · 阶段三改动 production 前，**提示词正文须单独确认**

仓库约定（`templates.py` 模块说明、`templates/README.md`）：提示词文本属业务优化，任何改动
须单独提出并获确认。因此本次要确认两批文本：

1. **新增**：L1 取证提示词、L4 分诊提示词（新模板文件，不改既有）；
2. **修改**：`customer_profile_production` 的 11 路提示词（阶段三）。

批准时我会把 L1/L4 的提示词草案贴出；production 的修改留到阶段三开工前单独提。

### D6 · `profile_features_analysis` 保留，但新链路不调用它

它产出的三段画像正是主方案要淘汰的「二次加工产物」。本增量**不删模块**（删了要动
`WORKFLOW_MODULES` 与基线臂），只让新工作流不引用它。回滚成本因此为零。

## 4. 子任务分解

每个子任务都**独立可验证**，且尽量「不花 token 就能验」。

### T0 · 分支与脚本开关（规模：小）

- 从 `dev-business-opt01` 新建实验分支；
- `scripts/run_baseline.py`：把硬编码的 `ENTRY_WORKFLOW` 改成 `--workflow-id`（缺省仍是
  `customer_profile_entry`），并让 `manifest.json` 的 `workflow_id` 记录**实际使用的值**
  （现在写死常量，加开关后不改这里会记错，污染可比性判据）；
- 顺手更新 `experiments/abexperiments/README.md` §3 的「尚未加进脚本」提醒。

**验收**：既有测试全绿；传未知 `--workflow-id` 时报错清晰；两臂命令都能正确构造运行请求。

### T1 · L0 记录层（纯代码，0 token）（规模：中）

- 新模块 `src/customer_profile/workflows/customer_profile_pipeline.py`，登记进
  `WORKFLOW_MODULES`；
- 取数层：复刻 14 路 tool 声明 + history http（见 D2）；
- L0 把入口清单与各渠道产物统一成 `records[]`（形状见 `端到端方案.md` §3.2）；
- **渠道分级由代码按 `channel` 定**，9 个结构性空渠道记 `status=exception`，不进 L1 上下文；
- 录音转写**逐字留存**（`content_kind=transcript`），中间不插任何 LLM；
- `speaker` / 逐句 `gender` 只作原文属性附着，不作归属依据。

**验收（离线，0 token）**：离线探针 `scripts/probe_pipeline_l0.py`，从基线批次的
`attempts.json` / `nodes.json` 重建本案输入，驱动 L0。**2026-10-09 已全量通过（39 案）**：

1. 9 个结构性空渠道 × 39 案 = **351 条** `status=exception`（实测吻合）。全案 exception
   合计 **411 条**——多出的 60 条是**逐案偶发缺失**（试驾缺 20、外呼缺 19、极光/关联企业/
   归属地各缺 7 案），属正常波动，非缺陷；
2. `13530559591` 外呼转写：载荷 3149 字符、**逐句正文合计 256 字符**，`content_kind=transcript`；
3. **有内容的**清单背书记录 **174 条，缺 `created_at` 0 条**。措辞收紧：`exception` 记录
   本就无时间可继承，不在此断言范围内；人工确认 Notes / 历史画像反馈走 mhero，无 `created_at`，
   记录层**留空而不伪造**。

**语义用例**：`tests/test_pipeline_l0.py`（21 项，纯合成夹具、不出网）钉住同一套判定——
清单缺渠道即 exception、原文不被压缩报告顶替、空壳与哨兵归零、`: []` 不算内容、
分诊三档。另有 1 项钉住「两臂取数声明逐条一致」，防日后单边漂移。

### T2 · L4 分诊层（纯代码 + 1 次小调用）（规模：小）

读记录清单，输出 `sufficient` / `thin` / `empty` 三档；`thin` / `empty` 走保守模板。

**验收**：39 案分诊分布合理（**实测：`sufficient` 39 / `thin` 0 / `empty` 0**）。
原预估「`thin` ≈ 7」**不成立**：每案都**恰好**有一条录音通道——20 案只有外呼、19 案只有试驾，
二者**互补且不重叠**，因此 39 案全为 `sufficient`。这说明该批次**没有**覆盖 `thin`/`empty`
两档，保守模板（只输出能坐实的字段）在本批次上**取不到样本**；若要验证这两档，须另行构造
缺录音的用例。

### T3 · L1 取证层（1 次 LLM + 代码定坐标）（规模：中大）

- 新增提示词模板 `customer_profile_pipeline__<节点id>.txt`：输入 records 全文（按渠道分节、
  关键段前置），输出 `claims[]`；
- **三条规则全部在代码侧**：
  - `quote` 由代码按 `span` 从 `record.content` 截取，**截不到即丢弃该断言**；
  - `subject` 为空或 `unknown` 的断言不得支撑身份字段；
  - `claim_type=prediction` 单列，承接第三方打点。

**验收**：探针案 `13926073386` 的「我们单位」在产出里 `subject != customer`；
`13530559591` 的短转写不被丢弃；锚点可回溯率 **100%**（由代码切片保证）。

**2026-10-10 已实现**（阶段二的最后一块，随后开跑 R0）。落地时有三处与原文的偏离，均按
D5 授权执行：

| 项 | 方案原文 | 落地口径 | 理由 |
|---|---|---|---|
| 定位方式 | 模型给 `span` 字符区间，代码按区间切 | **模型给 `anchor` 逐字短句（≥8 字），代码 `find` 定位后算 `span`** | 让模型数中文字符偏移量实测会系统性漂移，而「切不到即丢弃」会因此误杀**本来正确**的断言。两者都兑现「模型不誊抄整段引文、坐标由代码算」，差别只在召回 |
| 空空白容错 | 未提 | 逐字匹配失败后按**忽略空白**再匹配一次 | ASR 断字与空格差异不应误杀正确断言 |
| 丢弃可观测 | 未提 | 被丢弃的断言连原因一并输出（`dropped_detail`） | 静默丢弃会让人误以为「模型没提取到」，而实际是「提取到了但定位失败」，两者处置完全不同 |

**交付物**：
- `templates/customer_profile_pipeline__pipeline_l1_llm.txt`（L1 提示词，口径 B）；
- `customer_profile_pipeline.py` 的 `build_l1_input` / `localize_claims` 与三个节点
  `pipeline_l1_input`（装配）→ `pipeline_l1_llm`（1 次调用，`expect_json`）→
  `pipeline_l1_localize`（代码定坐标）；
- `tests/test_pipeline_l1.py`（28 项用例，纯夹具、不出网）。

**一处必须说明**：L1 装配把渠道按来源档**优先级序号**排序（登记 → 一手 → 公开登记 →
社交 → 预测），不是按档名字母序。按档名排会把 `firsthand` 顶到 `registry` 之前——这个 bug
在写用例时被抓出并修正（`test_l1_input_orders_registry_before_firsthand_before_prediction`）。

## 5. AB 实验设计

### 5.1 两条臂

```
# 基线臂（阶段三落地后在同日同配置条件下才需要重跑，见 D3）
python scripts/run_baseline.py --out-dir experiments/abexperiments \
  --batch-id B-baseline-<日期> --workflow-id customer_profile_entry \
  --transcript-cache-dir experiments/transcript_cache

# 实验臂
python scripts/run_baseline.py --out-dir experiments/abexperiments \
  --batch-id A-pipeline-<日期> --workflow-id customer_profile_pipeline \
  --transcript-cache-dir experiments/transcript_cache
```
