# 客户人设画像 · 落地方案

> 本文回答一个问题：**`端到端方案.md` 的主方案（事实账本四段式）怎么落到代码与实验里。**
>
> 定位：`基线画像质量诊断.md` 是「病」，`方案构想.md` 是「零件」，`端到端方案.md` 是「图纸」，
> 本文是**施工方案**——写清楚改哪些文件、按什么顺序上、每一步怎么验收、AB 实验怎么跑。
>
> 本文的依据全部来自对基线的实测（口径见 `端到端方案.md` §8）。凡属推算的数字标「预估」。

---

## 0. 结论先行

主方案不是重写工作流，而是**在既有工作流群中间插入一条四段式链路，并把下游的「填表 + 成文」
从这里接过去**。落地后：

- 上游取证子流程**保持不变**（它们取数、下载、识别，都是对的）；
- 新增 L0 记录层与 L2 投影层（纯代码，0 token）、L1 取证层与 L3 表达层（各 1 次 LLM）；
- `画像内容生成&回写` 的**输入契约一字不改**，仍收 `evidence_items` / `profile_analysis` /
  `hobby_analysis` / `consumption_style_analysis` 四段，输出仍是一个 `result1`。

**这意味着回写链路、Notes 契约、前端卡片渲染全都不用动**——AB 实验比较的是同一套对外接口下
两套内部实现。

关键工程量集中在两处：

1. **L2 投影规则表**——它是全案的枢纽，也是唯一「写起来最费事」的部分（预估 800–1200 行）；
2. **L1 取证提示词**——它要一次通读全部原文并输出带坐标的断言（预估 150–250 行提示词）。

### 1.1 与现行工作的关系

```

```

| 层 | 实现形态 | 新增/改动 | 预估规模 |

## 2. 分阶段落地计划

主方案的四段**天然可以分开上线**，且每一段都能单独度量。因此按「一次一段、一段一验」推进，
而不是一次性合入。

### 阶段一：L0 记录层 + L4 分诊（最小改动，先拿收益）

**做什么**

1. 新增 `src/customer_profile/workflows/customer_profile_pipeline.py`，只放 L0 与 L4；
2. L0 把入口清单与各渠道原始产物统一成 `records[]`：
   - 从 `GET /api/v1/remote/data/history/{phone}` 的清单取 `channel` / `created_at` /
     `data_type` / `media_urls`；
   - **渠道分级由代码按 `channel` 定**，9 个空渠道直接记 `status=exception`，不进下文；
   - 录音转写**逐字留存**（`content_kind=transcript`），中间不插任何 LLM 摘要；
   - `speaker` 与逐句 `gender` 只作为原文属性附着，不作归属依据。
3. L4 分诊读记录清单，输出 `sufficient` / `thin` / `empty` 三档；
   `thin` / `empty` 走保守模板，不产生具体断言。

**为什么先做这一段**

- 改动最小，但立刻消除两个可观测的缺陷类别：
  **空渠道污染上下文**（9 渠道 × 39 案 = 351 条 E 级噪声不再进入提示词）与
  **稀疏案上的无中生有**；
- 「有录音却输出无录音」这一类自述-输入冲突，在 L0 之后就由记录层说了算，不再靠模型回忆。

**验收标准**

- 9 个空渠道在 `records[]` 里全部为 `status=exception`，且不出现在 L1 上下文（可查留痕）；
- `13530559591` 的 L0 输出里**明确含**那段 256 字符外呼转写的记录；
- 39 案的分诊结果分布合理（预估 `sufficient` ≈ 32、`thin` ≈ 7）。

**回滚成本**：极低。新增一个工作流，不影响既有链路；不想要就不挂上去。

---

### 阶段二：L1 取证层 + L2 投影层（核心，兑现「矛盾不可能发生」）

**做什么**

1. **L1**：新增提示词模板 `customer_profile_pipeline__<L1节点id>.txt`，输入 `records` 全文
   （按渠道分节、关键段前置），输出 `claims[]`：
   ```jsonc
   {
     "claim_id": "c_017",
     "subject": "customer",
     "attribute": "occupation",
     "value": "充电桩行业从业者",
     "record_id": "rec_testdrive_13415100087_0",
     "span": [1042, 1063],
     "claim_type": "fact",
     "confidence": 0.9
   }
   ```
   三条规则**全部在代码侧执行**，不靠提示词：
   - `quote` 由代码按 `span` 从 `record.content` 截取，**截不到就丢弃该条断言**；
   - `subject` 为空或 `unknown` 的断言不得支撑身份字段；
   - `claim_type=prediction` 单列，承接第三方打点。

2. **L2**：新增纯代码投影层，输入 `claims[]`，输出 `facts` + `notes_updates[]` + `to_confirm[]`。
   七个子步骤见 `端到端方案.md` §3.4，其中**规则表是本阶段的主要工作量**：
   - 归属过滤、来源分级、冲突消解、枚举归一、单/多值约束、跨字段规则、缺失即留白；
   - 枚举归一按 `GET /api/v1/remote/config/note-attributes` 的 `items` 查表。
     **该契约实测跨 39 案完全恒定**（签名只有一种，42 字段：
     基础身份 16 / 购车需求 10 / 预算与金融 4 / 决策与节奏 4 / 个人偏好与备注 8），
     因此可以把它固化成一份离线快照表，运行期不必再取。

**验收标准（用基线回放，不花 token）**

把 39 案的既有字段按 L2 规则重算，预期命中并确定性修复 **97 处**：

| 动作 | 预期命中 |
|---|---|
| 清除「仅第三方」身份断言 | 42 |
| 枚举归一 | 38 |
| 年龄两处统一 | 8 |
| 等级两处统一 | 4 |
| 单选多值截断 | 2 |
| 换购无证清理 / 旧车漏填修复 | 1 / 1 |
| 已注销企业清理 | 1 |

**必须接受的一个代价**：约 42 个字段实例会因「只有预测撑腰」而**空出来**，全部转入 `to_confirm`。
这是准确性优先的必然结果，不是缺陷。

**回滚成本**：中。L2 是纯函数，可单独关闭（关闭后回落到 L1 直接出字段）。

---

### 阶段三：L3 表达层（兑现卡片-Notes 同源）

**做什么**

1. `customer_profile_production` 的输入侧改为只读 L2 的 `facts`：
   - 保留原有的 6 个 `template-transform` 预置层（标签库、格式模板、产品卖点、邀约话术）；
   - **11 路 LLM 生成节点收敛**——卡片 9 个 section 与 `reasoning_detail` 由 L2 的 `facts`
     投影后，只留「把事实写成话」这一项 LLM 职责；
   - `reasoning_detail.evidence` 改为只填 `claim_id`，由代码展开成「原话（记录名）」。
2. 卡片里每个具体值（年龄/职业/收入/家庭）必须能在 `facts` 里找到，否则不许写。

**验收标准**

- **卡片-Notes 一致率 100%**（逐字段比对年龄、等级、家庭结构等跨产物字段）；
- 锚点可回溯率 100%（锚点是代码从原文切出的切片，天然满足）；
- 基线里 `summary` 与 `steps` 零语义重叠的 15.0% 应显著下降（模板统一后二者同源）。

**回滚成本**：中高。这一段改了生产工作流的绑定，回滚需要保留旧绑定分支。

---

### 阶段四：备选二的「身份类字段」核验闸门（按预算叠加）

**做什么**：在 L1 与 L2 之间加一条**独立**核验通道，只拿到「断言 + 它声称的出处」，
逐条问主体对不对、有无矛盾、是否过时。先只对**身份类字段与商机等级**启用。

**为什么按预算**：这是唯一能做语义级事实核查的手段，但成本增加 0.5–1 倍（预估）。
在「准确性优先、成本次之」的排序下应做，但不必全字段做。

**验收标准**：基线里 `13926073386`（「单位」误置 + 已注销企业）在核验通道下必须被判不成立。

## 4. 契约保持（不可破）

对外契约**一个字节都不变**，否则 AB 对比不成立：

| 契约 | 保持方式 |
|---|---|
| `basic_notes_updates` 形状 | 仍为 `[{attribute_key, attribute_value, reasoning_detail}]` |
| 42 个字段的 `attribute_key` / 枚举 `items` | 严格按 `note-attributes` 契约；实测恒定的那份固化成离线表 |
| 卡片 9 个 section 及内部字段名 | 不变 |
| `result1` 外层形状 | 仍为 `{phone, batch_id, analysis_result:{…}}` |
| 回写 | 仍走 `@writeback` 开关；`WRITEBACK_ENABLED=false` 时只产出「已跳过」 |
| `batch_id` 入参 | 恒为 `""`（该字段会透传进 `result1`，填批次号会污染对比） |

唯一的变化在内部：字段不再由模型直接写，而由 L2 投影；锚点由 `claim_id` 展开。

## 5. AB 实验设计

### 5.1 实验场地

`experiments/abexperiments/`（与 `experiments/batches/` 平级，同样被 gitignore）。
目录分工见该目录的 `README.md`。

**两臂共用一个转写缓存**（`experiments/transcript_cache/`）：AUC 识别与被优化的工作流逻辑无关，
同一段录音结果必然相同。不共用会让每臂多花数小时在识别上，且引入无意义的差异。

### 5.2 跑批脚本需要的唯一改动

`scripts/run_baseline.py` 的入口工作流是硬编码常量：

```python
ENTRY_WORKFLOW = "customer_profile_entry"
...
"workflow_id": ENTRY_WORKFLOW,     # 写进 manifest
```

`run_one(...)` 本身已支持传入 `workflow_id`（默认取该常量），只是**没有命令行开关**。
因此加一个 `--workflow-id`（缺省保持 `customer_profile_entry`）即可让两个臂走同一个脚本，
**不复制脚本**——复制会让两臂的归档逻辑分叉，产生不可比的产物。

批次目录由 `out_dir / "batches" / batch_id` 拼成，因此：

```
# 基线臂
python scripts/run_baseline.py --out-dir experiments/abexperiments \
  --batch-id B-baseline-<日期> \
  --transcript-cache-dir experiments/transcript_cache

# 实验臂
python scripts/run_baseline.py --out-dir experiments/abexperiments \
  --batch-id A-pipeline-<日期> --workflow-id customer_profile_pipeline \
  --transcript-cache-dir experiments/transcript_cache
```

**注意转写缓存目录必须显式给**：不给时它默认推导为 `<out-dir>/transcript_cache`，
即 `experiments/abexperiments/transcript_cache`——那是个新目录，会把 39 段录音**全部重新识别**
（单条 20–30 分钟）。

### 5.3 可比性的硬要求

| 要求 | 做法 |
|---|---|
| 号码一致 | 同一份 `test_phone_numbers.txt`（39 个虚拟号），`phones_sha256` 两臂比对 |
| 定义一致 | 每案 `result.json` 的 `definition_hash` 必须单值；两臂各自不同是预期的 |
| 提交一致 | `manifest.json` 的 `code_commit` 记录开工提交；跑批期间不得改代码（见 runbook §5） |
| 参数一致 | 并发、超时、导出策略两臂相同 |
| 不回写 | 两臂均 `WRITEBACK_ENABLED=false`；验收查 `request_attempts` 里 `update-profile` 计数为 0 |

### 5.4 分阶段跑批（省时间也省 token）

| 轮次 | 范围 | 目的 | 预估成本 |
|---|---|---|---|
| R0 | 3 案（跑通） | 验证新链路能跑完、产物形状正确 | 极低 |
| R1 | 12 案（探针集） | 逐案核对「已知正确答案」 | 低 |
| R2 | 39 案（全量） | 出正式 AB 对比报告 | 见 §5.6 |

### 5.6 成本口径（实测基线）

| 指标 | 基线实测（39 案） | 主方案（预估） |
|---|---|---|
| LLM 调用 | 897 次（单案 **23.0**） | 单案 2–3 次 |
| prompt tokens | 12,205,817（单案 312,969） | 单案 ≈ 2.5 万 |
| completion tokens | 2,514,067（单案 64,463） | 单案 ≈ 1.5 万 |
| 单案 token 合计 | **377,432** | ≈ 5 万（降约 87%） |
| LLM 耗时合计 | 18,246,309 ms（单案 **467.9 s**） | 十秒级 |
| 全量出网尝试 | 1,208（http 311 + llm 897） | — |

口径说明：

- 基线「LLM 调用 897 次」是 `attempts.json` 里的**尝试**数，含 1 次重试；
  **逻辑调用 896 次，单案 23.0**。早先文档里的「31.0」把 http 尝试一并计入，两者不可混用。
- 基线单案 LLM 耗时 **467.9 s**（此前记为 654 s，为口径含混所致，以本表为准）。
- 主方案一栏全为**预估**，须在 AB 首轮实测替换。

### 5.7 AB 指标（与验收标准逐条对齐）

| 目标 | 指标 | 口径 | 目标 |
|---|---|---|---|
| 准确性 | 事实错误率 | 人工抽检：字段值与原文可坐实的事实不符的比例 | 下降 |
| 准确性 | 无依据确定值率 | 输出确定值但锚点仅指向中间产物 | **0** |
| 自洽性 | 代码规则命中数 | §2 那套规则在产出上的命中数 | **趋零** |
| 自洽性 | 卡片-Notes 一致率 | 逐字段比对 | **100%** |
| 可读性 | 锚点可回溯率 | 锚点能在原文定位的比例 | **100%** |
| 成本 | 单案 tokens / LLM 耗时 | 与 377,432 / 467.9 s 对比 | 降 |

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| L1 抽取召回不足 | 丢信息，字段更空 | 抽取阶段宁多勿漏，筛选交给 L2；探针集逐案核对 |
| L2 规则表工作量超预期 | 阻塞阶段三 | 先做「能确定性修复」的 8 类规则，其余进 `to_confirm` |
| `to_confirm` 变多让销售觉得空洞 | 业务观感 | `to_confirm` 必须给**可行动建议**（如「建议电话确认用车人」），不是空白 |
| 长上下文中间丢失 | L1 漏掉靠后细节 | 输入按渠道分节、关键段前置；实测最大 78,787 字符，单次可容纳 |
| 单点失败 | 一次调用出错即无产出 | `llm_call` 已有 3 次重试；L1/L3 各自独立，L3 失败时仍可只出 Notes |
| 跑批途中改代码 | 批次不可比 | 在固定 commit 的 `git worktree` 里跑（runbook §5） |
