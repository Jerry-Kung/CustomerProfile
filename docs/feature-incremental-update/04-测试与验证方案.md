# 增量画像 · 测试与验证方案

> 2026-11-09（第二版）。回答三件事：UAT 归档里有什么可直接当增量序列用、还缺什么要手工造、怎么量「做对了」。
> 数字来自对 `experiments/uat_data/uat-traces-20261102-20261103` 的一次性扫描（脚本化见 `03` T0-1）。

---

## 1. 现有数据摸底

### 1.1 结论先行

**不需要大规模手工造数据。** 该批次 482 个号码里 202 个有多次运行，相邻运行 310 对，每对都是
「同一客户、两次触发、history 响应各一份、callback 请求体各一份、下一次运行读回的 profile 各一份」。
缺的只是几类边角场景，用改写脚本补（§3）。

| 项 | 数值 |
|---|---|
| 多次运行的号码 | 202（2 次 139、3 次 33、4 次 21、5 次 7、7 次 1、9 次 1） |
| 相邻运行对 | 310 |
| 其中下一次开始早于上一次结束（重叠，剔除） | 33 |
| 两次 history **内容**完全相同的对 | 7 |
| 新增记录仅为文本类的对 | 247 |
| 新增记录含外呼录音的对 | 52 |
| 首次出现试驾录音的对（T3 判据） | 2 |

### 1.2 差分口径的实测依据

按记录 `id` 差分：310 对**全部**显示 `OntologyLeadInfo` / `OntologyAppRegistration` /
`OntologyLeadDistribution` / `OntologyLeadAssignment` 四路「新增 + 移除」——基础渠道每次触发都重抓快照，
`id` 与 `fetched_at` 全变。按时间戳同样误判。

改为「渠道 + 去掉 `fetched_at` 后的内容哈希」后：7 对判为完全相同、其余 303 对的差分只剩真正的
过程资料变化。这就是 `01` §5 的口径来源。

**P0 复核（2026-11-09，`scripts/build_incremental_fixtures.py` 同款键算法全量重扫）**：310 对里
**7 对内容完全相同**这个数是包含 33 对重叠运行的；剔除重叠后，可用序列里的「完全相同」只有 **3 对**
（5417、5852、1161）。另外 4 对（2180、9027、0866、9717）的「相同」是重叠造成的——两次运行时间
交叠，后一次读到的 history 里还没有前一次之后的新数据，不能当作增量序列的 T0 样本。其余分布：
仅文本 224 对、含录音 48 对、首次出现试驾录音 2 对。扫描结果落在
`experiments/incremental/fixture-scan.json`（不入库）。

### 1.3 读回与写入不一致：环境快照不同步，不是缺陷

274 对「回写 200 → 同号码下一次运行 GET /profile」里有 56 对读回内容与刚写入的不一致：39 对读不到刚写的键
（其中 26 对 `basic_notes` 整个为空或只剩 1–2 键、`ai_insight.updated_at` 停在数日前或为 null），
17 对读到的是同号码更早一版写入的值（109 个字段级差异里 35 个与更早回写体逐字相同）。

用户 2026-11-09 核查后的结论：**UAT 归档是当时的快照，此后 UAT 环境已多次更新，不同步由此而来；
写入侧本身是异步落库，有分钟级延迟。** 加上两次画像的间隔通常以小时或天计，该延迟在业务上无实质影响。

**对本方案的影响**：无。本方案不做写入/读回比对，底座直接取接口现值；若读回的是旧值，
后续任何一次增量都会以那份旧值为底座再叠加，与今天全量行为一致。此条仅作为运维背景记录，
不再作为待上报缺陷（前一版按「后台可见性问题」上报的结论作废）。

### 1.4 随机性与成本基线

**同输入两次全量的输出漂移**（7 对内容相同的运行）：

| 号码（尾号） | Notes 字段总数 | 变化字段数 | 等级是否变 |
|---|---|---|---|
| 9027 | 38 | 23 | — |
| 0866 | 45 | 15 | — |
| 2180 | 31 | 12 | 变 |
| 9717 | 42 | 11 | 变 |
| 1161 | 11 | 6 | — |
| 5417 | 7 | 1 | — |
| 5852 | 6 | 1 | — |

7 对里 2 对连商机等级都变了。这是要治的问题，也是增量方案的对照组：**增量 T0 的字段变化数必须为 0**。

**有新增记录的 300 对**：Notes 字段中位数 29，变化字段中位数 12，新增记录中位数 2。新增两条跟进记录
就让四成字段改写，其中大部分不可能是新数据导致的。

**token 与时延**（150 案抽样，单案中位 67.7k token、86 秒）：

| 节点 | 占比 |
|---|---|
| L1 三层（facts / persona / fields） | 57% |
| L3 表达 | 22% |
| 商机定级 | 11% |
| 录音角色标注 | 6% |
| L2 兜底 | 3% |

据此估算：T0 省 100%；T1 / T2 的 L1 只看新记录，输入包从全量缩到几条，L1 的 57% 预计压到 10–15%，
表达在 facts 未变时跳过，整体预期省 50–70%。

**P0 实测（2026-11-09，787 个成功运行，`scripts/analyze_incremental_archive.py cost`）**：按节点
token 占比为 L1 fields 22.1% / L3 表达 21.5% / L1 facts 18.9% / L1 persona 16.5% / 定级 10.6% /
录音角色标注 6.1% / L2 兜底 2.7%。L1 三层合计 **57.5%**，与抽样估算一致；单案 token 中位 68,743，
根运行耗时中位 85.7 秒。时延上 L3 表达占 36.1%，是「事实未变则跳过」最值钱的那一刀。

### 1.5 底座补缺会补多少

接口画像与回传体的字段集合不一致，缺的部分由副本补（`01` §2.4）。已测得的两个数：

- 792 次读回里 176 次（22%）完全没有 `ai_insight` 与 `ai_insight.updated_at`，`basic_notes` 可能整个为空——
  这类客户补缺几乎覆盖整份画像。
- `basic_notes` 每字段只有 `value` / `reasoning_summary` / `is_locked` / `locked_by` / `ai_feedback`
  五个键，**没有 `steps` / `evidence` / `confidence`**；`purchase_intent_level` 616 次有
  `reasoning_detail`，其中 100 次没有 `evidence`。所以证据与置信度基本只能靠副本补。

**P0 实测（2026-11-09，307 对「上一版回传体 + 下一轮接口画像」，按手机号配对）**：

| 项 | 数值 |
|---|---|
| 本轮画像完全没有 `ai_insight.purchase_intent_level` | 8.1% |
| `basic_notes` 整个为空 | 7.5% |
| 每对缺字段数 | 中位 0，最多 37 |
| 字段级补缺率 | 10.8%；307 对里 57 对至少缺一项 |
| A 有值与 B 逐字相同（可沿用副本证据） | 5,636 项 |
| A 有值与 B 不同（只剩 A 的 summary） | 430 项 |

两点需要说清，它们是 P2 的输入：

1. **8.1% ≠ `04` 上文那个 22%。** 22% 是「读回完全没 `ai_insight`」按全部 792 次读回算的；
   这里按**多运行配对**算，只取有上一版回传体的号码，口径不同，不能互相替代。
2. **补缺集中在少数客户身上。** 中位数是 0——多数客户画像完整，缺的那批一次缺几十个字段。
   这正好对上风险清单里「22% 读回覆盖整份画像」的形态：P2 要保证这类客户整份补缺正确，
   而不是逐字段零散修补。

逐字段补缺率最高的一批（样本 ≥5）：`knowledge_of_erev` 17.1%、`purchase_purpose` 17.0%、
`knowledge_of_mengshi` 16.4%、`core_concerns` 16.3%、`license_plate_address` 15.6%。完整表在
`experiments/incremental/archive-stats.md`（不入库）。

### 2.2 夹具内容（每时点）

```
experiments/incremental/<set>/<phone>/
├─ sequence.json         时点清单、相邻差分统计、预期档位、预期变化字段（手工造的才有）
├─ t1/
│  ├─ history.json       GET /data/history 响应原文
│  ├─ profile.json       GET /data/profile 响应原文（本次运行读到的）
│  ├─ callback.json      POST update-profile 请求体（本次运行发出的）
│  ├─ result1.json
│  └─ transcripts/       本时点新增录音的转写（转写缓存格式，键与号码无关）
├─ t2/ ...
```

`experiments/incremental/` 随 `experiments/*` 一并 gitignore；构建脚本可重跑。

### 2.3 回放方式

t1 用现行 pipeline 全量跑（建基线），t2 起走增量入口；每个时点的 HTTP 帧只取该时点的归档，
LLM 真实调用，录音走转写缓存。与 `replay_from_archive.py` 三条口径一致。

**等价性对照组**：每个 t(k) 同时用现行 pipeline 全量跑一遍，作为「同时点全量」。

## 3. 需要手工改造的夹具

每类至少一例，全部由脚本从真实序列改写生成（`build_incremental_fixtures.py --variant`），改写步骤
记录进 `sequence.json`，不手改 JSON。

| 类 | 怎么造 | 验什么 |
|---|---|---|
| 纯 T0 | 把任一序列的 t1 复制为 t2（history / profile 原样、batch_id 换新） | 零 LLM；回传体除 batch_id 外逐字节相同 |
| 补缺 · A 缺失 | 取一条 T0 序列，从 t2 的 `profile.json` 的 `basic_notes` 删掉 3 个键，其余原样 | 这三项用副本补；证据与置信度来自副本 |
| 补缺 · A 与 B 相同 | t2 的 `profile.json` 里某字段值与 t1 `callback.json` 逐字相同 | 沿用副本的 `steps` / `evidence` / `confidence`，而非只剩 summary |
| 补缺 · A 与 B 不同 | t2 的 `profile.json` 里某字段改成另一个值 | 以 A 为准；证据退化只到 summary，可接受 |
| 记录移除 | 取一条 T1 序列，在 t2 的 `history.json` 删掉 t1 存在的一条跟进记录；另造一例带 `operation: removed` | 依赖该记录的底座结论退场；相关字段留白或回退 |
| 阶段跃迁 | 取一条 T1 序列，在 t2 的 `history.json` 加入一条有实质内容的试驾录音（复用归档里已有的 `TestDriveRecordingFile` 原文） | 判 T3，调用全量 |
| 兼容键变化 | 把 t1 基线里的 `compat_key` 改成随机串 | t2 判 T3 |
| 基线缺失 | 不跑 t1，直接从 t2 开始 | 判 T3，并建立基线 |

## 4. 验收指标

全部由 `compare_incremental.py` 产出，每期验收引用同一份定义。

| 指标 | 定义 | 目标 |
|---|---|---|
| **稳定性** | 增量 t(k) 与上一版 t(k−1) 比，**未受新数据影响的字段**变化数 | T0 为 0；T1/T2 为 0（受影响字段由差分记录的渠道 → 字段映射判定，映射作为脚本输出供核读） |
| **等价性** | 增量 t(k) 与「同时点全量重跑」比，字段一致率 | ≥ 同输入两次全量的一致率（T0-3 量出的对照值）；低于它说明增量在丢信息 |
| **等级守卫** | 等级变化的用例里，变更依据能锚定到新增记录的比例 | 100%；锚不到的必须已回退并留痕 |
| **成本** | 单案 LLM token 与端到端时延，按档位分组 | T0 = 0；T1/T2 ≤ 50%（对比同案全量） |
| **补缺正确性** | 构造的三类补缺夹具中，取值与证据符合 `01` §2.4 规则的比例 | 100%（纯代码规则，应当全对） |

**等价性不是追求 100%**：全量重跑自身就有随机性，增量与它的差异里有一部分是对照组在漂。
对照值就是为了把这部分扣掉。

## 5. 单元与集成测试口径

- 固定响应、不出网（现行 `tests/` 约定）。
- 差分、补缺、合并三个纯函数模块用表驱动测试，样本从 §2.1 序列里抽并脱敏
  （手机号 / 姓名 / 地址替换，与 `tests/fixtures/replay/` 的入库规则相同：只有人工复核脱敏的才
  `git add -f`）。
- 端到端用例至少三条：`T0 零调用`、`T3 落基线`、`T1 未受影响字段逐字相同`。
- 规则簇走 `tests/rules/` 既有骨架；孤儿标记与未落地规则守卫自动覆盖。

## 6. UAT 灰度观察项

开关打开后一周，从运行台与 `rules_report.py` 汇总：

- 四档占比（预期 T0 不低于 20%——UAT 同号码重复触发很常见）；
- 逐字段补缺率，以及补缺后证据仍可用的比例；
- token 日均对比开关前一周；
- 等级守卫回退次数与原因分布；
- `RECENT-02` 命中数（为 0 说明进程字段清单或标注段没起作用）。
