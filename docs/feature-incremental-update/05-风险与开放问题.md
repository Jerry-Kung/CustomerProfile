## 1. 已解除的外部确认项（2026-11-09，用户答复）

| 原问题 | 答复 | 落到哪 |
|---|---|---|
| profile 接口有无字段级「人工修改」标记或修改时间 | **没有，且近期无排期** | 不再需要：方案改为「API 画像当底座」，不做文写/读回比对（`01` §2） |
| 部分 Notes 键为何在下一次读回时缺席 | UAT 快照与环境不同步；写入侧异步落库，分钟级延迟 | 不作为缺陷上报；间隔以小时/天计，业务无影响（`04` §1.3） |
| 「这次比上次变了什么」要不要独立回传字段 | **不回传**，内部字段一律不外传 | 不新增键；变更信息只留在运行台（`01` §7） |
| 多行区块销售是否可手改 | **暂不可改** | 底座照旧取接口，不额外处理 |

> **前一版结论作废**：「以回传成功后 GET 读不到新值」为由上报后台可见性缺陷、以及「三方比对 + 滞后读守卫」
> 整套设计，均随本版收回。用户核查后的解释是环境快照不同步与异步落库，且业务间隔足够长。

## 2. 待本项目拍板

### Q1 · 回传体基线的保留期与清理 `[待定]`

- **背景**：基线表按手机号一行、约 6–10 KB。全量客户量级下体积可控，但目前没有删除策略：
  客户销户、长期无触发的号码会一直留着。
- **建议**：缺省不删；随 `retention` 加一条按 `updated_at` 的软清理（如 24 个月），与业务方确认客户档案保留口径后实施。

### Q3 · 「接口值 ≠ 副本值」时证据退化的容忍度 `[待定]`

- **现状**：按 `01` §2.4 规则二，以接口值 A 为准，此时只剩 A 的 `reasoning_summary`，无证据无置信度。
- **影响**：发生在「上一版之后接口侧被人工改过或锁过」的字段上。业务上以 A 为准是对的，但对客展示会变薄。
- **观察**：P3 灰度一周统计这类字段占比。若占比显著（>10%），再讨论是否把副本里的旧证据挂上并标注
  「依据来自上一版」——这属于对客文案变更，需产品确认。
- **解除条件**：灰度数据出来。

## 3. 已知风险

| 风险 | 后果 | 缓解 |
|---|---|---|
| 接口画像本身可能是一份旧值（异步落库、环境不同步） | 增量以旧值为底座再叠加，与今天全量行为一致，不算回归 | 不做特殊处理；间隔以小时/天计时延迟自消；`ai_insight.updated_at` 记入基线供排障 |
| 22% 的读回没有 `ai_insight`、`basic_notes` 可能为空 | 补缺覆盖整份画像，等价于「以副本为底座」 | 补缺规则纯代码、可测；T0-5 量出实际分布 |
| 副本是「我们算出来的」不是「后台落库的」 | 若后台曾拒绝或部分写入，副本与真实状态不一致 | 契约规定回写 200 即成功；差异最终会被下一次接口读回纠正（A 为准） |
| 已消费键集合与实际处理不完全一致（如某次运行中途失败） | 差分判「无新增」，T0 原样回传，漏掉新数据 | 基线只在运行成功后写；失败运行不写，下次仍是旧键集合，会把记录当新增重跑 |
| 兼容键过严 | 每次提示词微调都让全部客户落 T3，增量形同虚设 | 键只含契约签名 + 规则 ID 集合 + L1 输出 schema 版本 + L3 板块键；措辞不进键 |
| 兼容键过松 | 旧 claim 与新版规则语义不符 | 规则簇增删一律进键；保留「手动触发全量」的运维入口 |
| L1 增量输入包过小触发 thin 口径 | 一条新跟进让 sufficient 案被判 thin、字段大面积留白 | 分诊按合并后全部记录判（`01` §6.1） |
| 已定稿事实清单诱导模型复述旧值 | 新 claims 混入「抄清单」的断言，锚点指不到新记录 | 定位层只在新记录里找锚点，找不到即降级；清单段写明「只用于标注冲突，不得作为取证来源」 |
| 基线表与运行库同库，写放大 | 每案约 6–10 KB，全量客户下需观察体积 | 单行覆盖写，不保留历史；P3 灰度观察；Q1 定清理 |
| 转写不可复用 | T3 重建把历史录音全部重转，成本与时延回到全量 | P4 把转写缓存升为生产设施，键按录音 id |

## 4. 观察项（上线后看）

- 四档占比；T3 占比过高说明兼容键或阶段判据有问题。
- 逐字段补缺率与补缺后证据可用比例（Q3）。
- `RECENT-02` 命中数；为 0 说明清单或标注段无效。
- 等级守卫回退次数；过高说明定级模型在没有新证据时仍频繁改判，需要收紧提示词。
- 基线表体积与更新频率。
- 定期校准是否需要：观察 10 轮以上增量的客户，其等价性指标是否随轮次衰减。

### 4.1 灰度期怎么取数

灰度只看四个数，都要能落到具体命令上，否则「观察一周」等于没观察。

| 观察项 | 取数方式 |
|---|---|
| 四档占比 | `node_executions` 中 `node_id='incremental_dispatch'` 的输出 `tier`，按天分组计数 |
| 补缺字段数 | 同一节点的 `base_stats_json`（`same` / `differ` / `from_b_only`）逐案累加 |
| token 日均 | `request_attempts.usage_json` 按天求和，与灰度前一周同口径对比 |
| 等级回退次数 | `pipeline_level_apply` 节点出参 `level_reverted` 非空的行数；过高说明定级在无新证据时仍改判 |

**存储瘦身之后的读法**：上面四项的**载荷**（节点输出、`usage_json`）在包清空后不在
`node_executions` / `request_attempts` 的列里，而在 `trace-archives/YYYY-MM-DD/<run_id>.json.gz`
（或快照带出的包目录）。两条路都行：

- **走运行台**：`GET /runs/<run_id>` 与 `/graph` 会从包回填，节点行上的 `outputs_json` 就是这里的值；
- **走快照**：`export_snapshot.py` 带出包后，本地起只读运行台按同样方式读（见 runbook §1/§3）。

**`low` 档也留得住这四项**：`NODE_DIAGNOSTIC_FIELDS` 已按节点保留 `tier` / `base_stats_json` /
`level_reverted` 等判定字段（见 `feature-storage-opt/01` §8.1）。阈值：`low` 档下
`request_json` 不留、节点输出只剩诊断键，所以**逐节点的完整对比要 `high` 档**。

**回滚不需要改代码**：`INCREMENTAL_ENABLED=false` 回到全量入口（产物逐字节不变）；
只想收窄档位就改 `INCREMENTAL_TIERS`（置 `T0` 即回到 P1 行为）。两者都只需重建 worker。

**灰度的前置条件**：部署前先确认 `profile_baselines` 已随库发布，且灰度期**不出快照脚本的
旧版本**——旧脚本导出的库没有基线表，本地复现会得出「增量没生效」的错误结论（`03` P3 的
排期约束即为此）。
