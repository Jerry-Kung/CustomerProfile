## 1. 新增模块

### 1.1 `persistence/profile_baselines.py` —— 回传体基线

- **做什么**：按手机号一行，保存上次**实际发出**的 `analysis_result` 与我们需要的少量派生信息。
- **存什么**：

| 列 / 载荷 | 内容 |
|---|---|
| `phone` / `source_run_id` / `updated_at_ms` | 身份与追溯 |
| `compat_key` | 管线兼容键（`01` §4.1），不符即 T3 |
| `stage` / `deal_level` / `deal_level_detail` | 阶段与上一版等级（T3 判据与定级锚点） |
| `consumed_keys_json` | 已消费记录的身份键集合（`01` §5），约几百字节到几 KB |
| `callback_json` | 回传体全文，约 6–10 KB |

- **为什么单独一张表**：回传体是业务数据，寿命与客户相同；`workflow_runs.outputs_json` 在
  `finalize_tree` 收尾时会被置空，运行包 30 天清理（`TRACE_RETENTION_DAYS`）。放错了表等于没存。
- **接口面**：`load(phone)`、`save(phone, baseline)`、`delete(phone)`，全部走 `Store` 的单连接线程。
- **建表**走 `schema.py` 的 `CREATE TABLE IF NOT EXISTS`，补列登记到 `store._ADDED_COLUMNS`。

### 1.2 `incremental/diff.py` —— 记录差分

- 输入：基线 `consumed_keys_json` + 本轮 history 响应。
- 输出：`added[]` / `changed[]` / `removed[]` / `unchanged[]`，每条带身份键。
- 身份键算法在**一处**定义（`01` §5）：过程资料用 `source_key + source_version`，基础渠道用
  「渠道 + 去 `fetched_at` 的内容哈希」。`build_records` 复用同一函数。
- 纯函数，零 I/O，便于用归档数据做表驱动测试。

### 1.3 `incremental/base_claims.py` —— 底座组装与补缺

- **做什么**：把接口画像 A 与回传体副本 B 合成一份「上一版已定稿事实」，再转成 claims。
- **补缺规则**（`01` §2.4）：
  1. A 有值且与 B 逐字相同 → 取值用 A，**证据 / 置信度沿用 B**；
  2. A 有值且与 B 不同（或 B 无此项）→ **A 为准**，只有 A 的 `reasoning_summary`；
  3. A 没有该项 → 用 B 的全部信息。
- **归一化**：A 里的枚举键与展示名差异、`_repair_enum_value` 的出口修值，只在「判断 A 与 B 是否逐字相同」
  时使用；复用 `callback_build` 与 `notes_contract` 现有函数，不复制逻辑。
- 输出形状与 `localize_claims` 一致，可直接喂 `project_claims`；来源名「上一版画像」。
- 失败（结构异常、解析失败）→ 返回空底座并留痕，调度层据此落 T3。

### 1.4 `incremental/merge.py` —— 合并账本

- 输入：底座 claims、差分结果、新 claims。
- 输出：合并后的 `claims_json`，形状与现行产出一致。
- 做三件事：源记录已移除的底座 claim 退场；新 claim 追加；每条补 `observed_at`
  （底座取基线更新时间，新记录取记录业务时间，取不到用 `created_at`）。
- **不做冲突消解**，那是 L2 的事。

### 1.5 `workflows/customer_profile_incremental.py` —— 调度入口工作流

- 新 `WORKFLOW_ID = "customer_profile_incremental"`，节点图：
  `start → history(GET) ∥ profile(GET) ∥ baseline(读) → dispatch(code) → [T3: 子运行 pipeline]
  / [T0: 副本换 batch_id 回传] / [T1·T2: 录音子流程(仅新) → L1 三层(仅新) → merge → L2 全段(复用)
  → 定级(带锚点) → L3(可跳过) → callback_build → writeback] → baseline(写) → end`。
- **复用方式**：L2 全段、定级、L3、`callback_build` 的 code 函数**按原名引用**，输入形状不变。
  只有 `build_l1_input`、`build_level_input`、L3 表达节点需要多一个可选入参（见 §2）。
- `dispatch` 节点输出：档位、差分统计、补缺字段数、兼容键比对结果——这就是审计留痕。
- 回滚：入口常量改回 `customer_profile_pipeline`（`api.ENTRY_WORKFLOW_ID` 与前端
  `SubmitRun.tsx` 的 `ENTRY_WORKFLOW_ID` **必须同改**）。

### 1.6 `rules/clusters/recency.py` —— 时近性规则簇

- `RECENT-01`（project，稳态字段）：新弱信号不翻旧强事实——现行来源分级的显式声明，落成规则为可关可留痕。
- `RECENT-02`（project，进程字段）：同档来源后到者胜；带「推翻」标注且更晚的低一档来源降置信后胜并转确认。
- `RECENT-03`（gate，定级守卫）：等级变化必须锚定到本轮新增记录，否则回退上一版；阶段不回退。
- 进程字段清单登记在规则 `scope`（首版见 `05` Q2）。
- 守卫测试（孤儿标记 / 未落地规则）自动覆盖新簇。

## 3. 刻意不动

| 不动什么 | 理由 |
|---|---|
| `customer_profile_pipeline` 节点图与 `definition_hash` | 作 T3 子运行原样调用；基线可比性 |
| `projection.py` 的投影主体 | 增量只喂不同的 claims，不改消解逻辑；时近性以规则簇外挂 |
| 回传契约与 `notes_contract` | 不新增键；档位、差分等内部字段不外传 |
| `callback_build.py` | 始终发完整回传体（与现行一致）；T0 直接复用基线副本，不需要裁剪 |
| `assemble_l3` 同源一致性检查 | 表达跳过时复用基线板块文本，装配照常跑 |
| 执行器 / 调度器 / 队列 | 增量是业务层的事，不碰断点续跑 |

## 7. P1 实施差异（2026-11-09）

落地时与上表不同的四处，都写在这里而不是悄悄改掉：

| 计划 | 实际 | 理由 |
|---|---|---|
| 收尾钩子（`worker.py` / `runner.py`）写基线 | 增量入口的 `incremental_baseline_commit` 节点写 | 写基线要**本次回传体 + 本轮 history 原始响应**两者；收尾钩子手里只有前者，后者要么从 `request_attempts` 反查（存储瘦身后可能已搬进包），要么再抓一次接口。入口节点两样都有，是同一事实来源。代价：入口关闭时不预建基线，P3 灰度前用脚本铺一批全量即可 |
| `build_records` 产出的 record 带身份键 | 未改 `build_records`；差分走 `diff.diff_by_keys` | P1 只需要「键集合有无差异」这一个判据，而基线里只有键。T0 的结论与 `diff_histories` 完全一致。`diff_histories`（带改版判定）在 P2 接底座时启用 |
| 新增模块 6 个 | 多了 `incremental/compat.py`、`incremental/dispatch.py`、`incremental/nodes.py` | 兼容键与档位判定必须可单测，放进工作流模块会让测试要连着定义一起构造；`nodes.py` 是 code 节点的实现，与工作流定义分开 |
| 前端 `SubmitRun.tsx` 的 `ENTRY_WORKFLOW_ID` 与后端同改 | 前端改为从 `GET /runtime` 读 `entry_workflow_id` | 开关切换在运行期发生，两份常量迟早漂移。缺省值保留，只覆盖「运行态未取回」的窗口 |
| 回传体基线表名与列 | 与上表一致；另加 `stage` 的取值来源：P1 按「记录里有无 `TestDriveRecordingFile`」粗判 | `level_stage` 的严格判据（有实质内容的录音）需要记录层，P2 接底座时换过去 |

## 8. P2 实施差异（2026-11-09）

P2 落地时改动面与上表的五处差异，写在这里而不是悄悄改掉：

| 计划 | 实际 | 理由 |
|---|---|---|
| T1/T2 走一条新的增量节点链（取数 → 录音 → L1 → 合并 → L2 → 定级 → L3） | **不建新图**：现行 `customer_profile_pipeline` 加一个可选入参 `incremental_ctx`，空的即非增量、产出逐字节不变；入口的 T1/T2 分支就是一次带上下文的管线子运行 | 取数、听录、OCR 有十几路，复制一份必然各自漂移；而「只看新记录 / 合并底座 / 定级锚点」三处判据都能在现有节点内部读上下文完成，不需要新节点。代价是 `customer_profile_pipeline` 的定义哈希变了（三处函数签名 + start 多一个变量），**T3 子运行仍调同一份定义，可比性不受影响** |
| `build_l1_input` 加 `record_filter` / `settled_facts` 两个参数 | 只加一个 `incremental_ctx` | 两个参数永远是同一个上下文的两半；拆开会让「是不是增量」有两处判据 |
| 合并账本单列一个 code 节点 | 合进 `inject_deterministic`（改名未动，出参多三项） | 注入值（手机号、驾照）也是本轮结论，要参与时近性取舍；单列节点就得把注入结果再传一遍。合并失败时退回「只跑新断言」，不阻断运行 |
| L1 / 定级 / 表达的模板加可选段占位 | **模板一字未改**：定级与 L1 的可选段在输入装配里拼接；表达跳过的判定放在新代码节点 | 模板正文属业务资产，改动须单独确认（`03` T2-2 原话）。拼接段与模板里的其它约束同性质，位置也正确（记录正文之前） |
| 表达路径「带锚点重写」 | **未做**：重写路径就是现行表达，未附上一版板块文本 | 同上——要在表达模板里加占位段。当前只实现「事实未变则跳过」，事实变了照常重写 |
| `RECENT-03` 作为定级 gate 规则 | 规则已登记，判据实现为 `apply_level` 末尾的代码守卫（复用同一函数），不另接规则执行器 | `apply_level` 是纯代码收口，再套一层动作执行器只多一层间接；`rules_report` 的统计口径不变 |

## 9. P3 实施差异（2026-11-09）

| 计划 | 实际 | 理由 |
|---|---|---|
| `export_snapshot.py` / `fetch_run_archive.py` 都导出 `profile_baselines` | 只改 `export_snapshot.py` | `fetch_run_archive` 按 run_id 取「一棵运行树的包」，而基线是按号码一行、不挂任何运行的表。硬塞进包里会破掉「一个包 = 一棵树」的口径；要基线就走整库快照 |
| 基线按时间窗筛选 | 只按号码筛选，不受时间窗影响 | 基线没有历史版本，一个号码只有一行「当前状态」。按时间窗过滤会把「号码当时有基线、但最近一轮不在窗内」的情况漏掉，本地复现于是跑不出 T0 |
| `FORMAT_VERSION` 保持 2 | 升到 3 | 格式确实变了：`counts` 多一个键、库里多一张表。沿用 2 会让「format 2 的快照能不能跑增量」无法从 manifest 判断 |
| 源库没有基线表时报错 | 记 0 行，不报错 | 那是「这份快照对应的时期还没发生过增量」（P1 之前的库），不是损坏。报错会让历史快照无法导出 |
| `replay_incremental.py` 只回放夹具里的 history / profile | 先铺开该时点归档运行的全部出网响应，再用夹具覆盖这两个端点 | 只用两个端点会让极光、朋友圈、录音清单等渠道全部落空，产物「变空」时的第一嫌疑会落在增量上，而真实原因是夹具不全 |
| 转写条目按缓存键重算后播种 | 按缓存格式原样复制 | 键含识别参数；重算会把「某次改了默认参数」变成一次整批静默未命中，而且不报错 |
| 档位从产物倒推 | 直接读 `nodes.json` 里 `incremental_dispatch` 的出参 | 档位是图里的一个节点输出，是唯一直接证据；从产物倒推等于用结论验证结论 |
