## 一、背景：这里的「缺码值」会变成什么故障

我方消费的是 `GET /api/v1/remote/data/history/{phone}` 返回的 `raw_payload`（接口规范 v2026-10-31）。这批本体渠道的载荷是**未经翻译的业务原始码**，下游需要先把码译成中文，再拼进给 LLM 的提示词。

不翻译的后果不是「显示丑一点」，而是：

1. **字段失效**：LLM 看到 `跟进结果：90452`，无法从中获得信息，等于该字段白传。跟进记录的四个字典字段（结果/目的/意向级别/沟通方式）恰恰是判断客户冷热的核心信号。
2. **锚点污染**：证据锚点要求精确到客户原始数据中的一段内容。裸码 `90452` 会被原样抄进锚点与最终 Notes，对客可见。
3. **口径歧义**：同一字段不同码值代表不同业务阶段（如试驾单状态 4 vs 5），译错会把「已试驾未闭环」当成「已完成」，试驾转化率统计虚高。

我方当前策略是**未登记码一律原样输出**（不猜、不丢、不静默变空）。这条兜底保证不会丢数据，但也意味着缺口清单里的字段在补齐前始终处于失效状态。

## 四、请求的数据形式

### 4.1 首选：字典表直出

最省事、最不容易出错的做法是直接导出公共字典表，我方自己映射：

```sql
-- 公共字典全量（跟进域 + 试驾域）
SELECT prefix_id, actual_value, show_name, description, sequence, status
FROM default_catalog.mhero_ods_center.t_ods_common_dictionary
WHERE prefix_id IN (9043, 9044, 9045, 9046, 9303, 9304)
  AND status = 1
ORDER BY prefix_id, sequence DESC;
```

CSV 或 Markdown 表格均可。若还涉及其他 `prefix_id`（如订单状态、战败类型），请在导出时一并带上，并在结果里注明每个 `prefix_id` 的业务含义。

### 4.2 次选：按字段逐条列表

若不便直出字典，按下面的格式逐字段给出即可，一个字段一段：

```markdown
### <接口 channel>.<接口字段名>
- 字典分组：prefix_id = <数字>，字典名「<中文>」
- 是否布尔（0/1）：<是 / 否>
- 值域：
  | 码值 | 中文名 | 备注 |
  |---|---|---|
  | <值> | <中文> | <可选> |
```

### 4.3 必须对齐键名

解码说明中的字段名混用了本体属性名（camelCase，如 `followResult`、`testDriveOrderStatus`）与接口字段名（snake_case，如 `followresult`、`order_status`）。我方消费的是**接口 snake_case 键名**。回填时请以下面这两个文件为准：

- 键名权威：`docs/reference/M2M历史资料接口规范-20261031.md` §4 各渠道字段表
- 我方实际渲染的字段：`src/customer_profile/workflows/ontology_payload.py` 中的 `FIELD_LABELS`

已有示例：`followResult` → `followresult`（不是 `follow_result`）、`testDriveOrderStatus` → `order_status`（不是 `test_drive_order_status`）。**这两处容易按常规 snake_case 规则推错**，请照搬接口规范里的实际键名。

## 五、信息不足时的兜底方式

我方已实现并会长期保留以下兜底，**不需要业务方为此付出额外工作**：

1. **未登记码原样输出**。`_enum_label(channel, key, value)` 查不到时返回 `None`，渲染层直接输出原始值，例如 `试驾类别：3`。不猜测、不改写、不置空。
2. **空值不渲染**。`null` / 空串 / 空数组的字段整行跳过，不会出现「字段：None」。
3. **未知字段不丢**。`FIELD_LABELS` 未登记标签的键，用接口原键名输出，例如 `some_new_key：值`。接口新增字段时不会静默消失。
4. **`removed` 记录不作为证据**。`{"operation": "removed"}` 的载荷被拦截，不会进入提示词。
5. **金额单位**。`*_fen` 字段一律按分换算成元并标注单位，不依赖 `amount_unit` 字段。

因此补充码值可以**分批进行**：先给 P0，再给 P1/P2，任何时候补齐都会立即生效，未补齐的字段保持原样输出而不是报错。**唯一需要避免的做法**是在没有把握时给出「看起来合理」的猜测值——错译比不译危害更大，因为错译会被当成事实写进对客画像。

## 六、补充：请同时确认的两个口径问题

1. **试驾单状态 `4` 与 `5` 的区分**：解码说明 §4.3 指出只有 `5` 是闭环完成，`4` 是「已试驾未完成回访」。我方渲染已按此区分（`4` = 已试驾·未完成回访，`5` = 已完成）。请确认这一区分在业务上成立，因为下游若把它们合并统计，试驾转化率会虚高约 28 个百分点。
2. **意向级别的方向**：`sequence` 数值越大意向越高，而字母序 H→A→B→C→O→F→L 是降序。我方标签已按热到冷排列，请确认无异议。
