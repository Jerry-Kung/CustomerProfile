# M2M 客户历史资料接口规范

## 1. 接口概述

用于获取某手机号在客户画像系统中**已经落库的有效资料**，包括本体基础资料、轮询过程资料、录音资料及外部补充资料。

该接口只查询本地 `customer_data_source_record`，不会实时调用 Ontology MCP，也不会触发画像生成。

| 项目 | 说明 |
|---|---|
| 方法 | `GET` |
| 应用路由 | `/api/v1/remote/data/history/{phone}` |
| 部署示例 | `https://mhero.dfmc.com.cn/customer_profile/m2m_api/api/v1/remote/data/history/{phone}` |
| 鉴权 | `X-API-Key: <M2M_API_KEY>` |
| 返回 | JSON 数组，无分页 |
| 排序 | 按 `created_at` 升序 |
| 查询条件 | `customer_phone = {phone} AND is_valid = 1` |

未知手机号或暂无有效资料时返回 `200` 和空数组 `[]`。

> 本文档以 `develop` 分支最新扁平化入库代码为准。若部署版本早于提交 `2985852`，`raw_payload` 中的 `customers`、`consultants`、`stores` 等字段可能仍为嵌套结构。

### 请求示例

```bash
curl -sS \
  -H 'X-API-Key: <M2M_API_KEY>' \
  'https://mhero.dfmc.com.cn/customer_profile/m2m_api/api/v1/remote/data/history/13720203537'
```

## 2. 响应记录字段

响应是一个数组，每个元素是一条资料记录。

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `id` | integer | 否 | 资料流水 ID |
| `customer_phone` | string | 否 | 客户手机号 |
| `batch_id` | string | 否 | 画像批次号；同一批次资料共享该值 |
| `channel` | string | 否 | 来源渠道编码 |
| `data_type` | string | 否 | `text` / `image` / `audio` |
| `source_key` | string | 是 | 过程资料稳定身份；基础渠道通常为 `null` |
| `source_version` | integer | 是 | 同一过程资料的递增版本；基础渠道通常为 `null` |
| `confidence_score` | number | 是 | 置信度，系统自动资料一般为 `100.0` |
| `operator` | string | 是 | 写入方/场景 |
| `media_urls` | array | 是 | 图片或音频 URL 列表 |
| `raw_payload` | object | 是 | 资料主体数据，结构见第 3 节 |
| `analysis_summary` | object | 是 | 初步分析结果 |
| `process_status` | integer | 否 | `0=待处理`、`1=处理中`、`2=已完成`、`3=失败` |
| `error_msg` | string | 是 | 处理失败原因 |
| `created_at` | datetime | 否 | 创建时间 |
| `updated_at` | datetime | 否 | 最后更新时间 |
| `is_valid` | integer | 否 | 接口只返回 `1`，旧版本记录不会被返回 |

## 3. `raw_payload` 结构

### 3.1 基础渠道

适用于：

- `OntologyLeadInfo`
- `OntologyAppRegistration`
- `OntologyLeadDistribution`
- `OntologyLeadAssignment`

结构：

```json
{
  "records": [{}],
  "fetched_at": "2026-10-31T11:28:02.376050"
}
```

- `records`：该渠道本次全量读取到的记录数组。
- `fetched_at`：本轮基础资料获取时间。
- 每条记录已经扁平化，不再使用 `customers`、`consultants`、`stores`、`sources`、`vehicle_series`、`vehicle_models` 等嵌套集合。

### 3.2 过程资料渠道

适用于：

- `OntologyLeadStage`
- `OntologyLeadFollowRecord`
- `OntologyDefeatRecord`
- `OntologyManualOutboundCall`
- `OntologyTestDriveSchedule`
- `OntologyCustomerChatInfo`
- `OntologyOrder`
- `OntologyOrderFinance`

`raw_payload` 是单条扁平对象，通常包含：

```json
{
  "source_id": "业务主键",
  "source_kind": "stage | follow | order | finance | ...",
  "source_version": 1,
  "customer_phone": "13720203537",
  "customer_name": null
}
```

如果上游确认记录被移除，可能包含：

```json
{
  "operation": "removed",
  "reason": "upstream_removed_or_reassigned"
}
```

### 3.3 录音渠道

适用于：

- `OntologyManualOutboundCallRecordingFile`
- `TestDriveRecordingFile`

`raw_payload`：

```json
{
  "recording_id": "8496879",
  "recording_url": "https://example.com/call.mp3",
  "recording_text": null,
  "call_time": "2026-10-31 10:00:00",
  "source_business_id": "8496879",
  "source_kind": "manual_call",
  "call_kind": "manual",
  "manual_outbound_call_id": "8496879",
  "source_version": 1
}
```

试驾录音使用 `source_kind=test_drive` 和 `test_drive_id`，不包含 `call_kind` / `manual_outbound_call_id`。

### 3.4 外部补充渠道

`DatametInterestPoints`、`RelatedEnterpriseInfo`、`WeChatPhoneSearchScreenshot` 等渠道的 `raw_payload` 由各自采集逻辑定义，不属于本体轮询资料。

## 7. 使用注意事项

1. `raw_payload` 中的 `null` 表示上游源数据确实为空，不是接口遗漏字段。
2. 基础渠道的 `raw_payload.records` 是数组，即使只有一条记录也保留数组结构。
3. 过程资料每次修订会生成新的 `source_version`，旧版本 `is_valid=0`，不会出现在本接口。
4. 同一个 `batch_id` 表示同一轮画像准备或同一轮轮询提交。
5. 金额字段以分为单位，使用前请按 `amount_unit` 转换。
6. 该接口返回的是已落库资料；本体中有新数据但尚未触发画像准备时，接口不会立即返回。
7. `OntologyQuotation` 当前待实现，不会出现在响应中。
