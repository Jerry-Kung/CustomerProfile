# 对外任务接口 · 对接文档

> 面向**前端任务队列**：把待分析的手机号推给画像服务，拿到结果。
>
> 本文只讲**怎么调通**。背后的设计取舍（为什么 401 与 403 分开、为什么未配密钥是 503
> 而不是放行、为什么接单进程不执行工作流）见 `design/对外任务接口.md`；起进程与真回写
> 验收步骤见 `runbooks/部署.md` §9。
>
> 版本：V0.5.5（2026-10-16）。

---

## 1. 一句话流程

前端推一个手机号 → 接口**立刻**返回 200（任务已落库）→ 服务后台异步分析（约 21 分钟）
→ 分析完成后由**回写接口**把结果写进业务系统 → 前端从业务系统那侧看到画像。

**前端不需要轮询本接口。** 本接口只在「收单」时被调用一次，不提供查询、不提供进度。

```
前端任务队列 ──POST /api/v1/tasks──▶ 对外任务接口(8099) ──落库──▶ 队列
                                                                  │
                                                          worker 领取执行
                                                                  │
                        业务系统 ◀──POST update-profile── 回写接口（结果送到这里）
                            │
                     前端从这里读结果
```

## 2. 接口一览

| 项 | 值 |
|---|---|
| 服务 | 对外任务接口（`python -m customer_profile.inbound`） |
| 地址 | `http://<部署主机>:8099` |
| 方法 | `POST` |
| 路径 | `/api/v1/tasks` |
| 鉴权 | 请求头 `X-API-Key: <INBOUND_API_KEY>` |
| Content-Type | `application/json` |
| 超时建议 | 10 s（接口只做落库，正常在毫秒级返回） |

**一次请求只推一个手机号。** 需要批量就循环发；服务端会排队执行（见 §7）。

### 2.1 存活探针

`GET /health` 不需要鉴权，返回 `{"status":"ok","interface":"inbound","workflow_id":"…"}`。
用于上线前确认端口可达。**它不报告密钥是否配置**——那是未鉴权方不该知道的信息。

## 3. 请求

```http
POST /api/v1/tasks HTTP/1.1
Host: <部署主机>:8099
X-API-Key: <INBOUND_API_KEY>
Content-Type: application/json

{
  "phone_number": "13415100087",
  "batch_id": "batch-20261016-01"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `phone_number` | string | 是 | 11 位中国大陆手机号，须匹配 `^1[3-9]\d{9}$` |
| `batch_id` | string | 是 | 批次号，不能为空或纯空白 |

**`batch_id` 必须填，而且要填得能认出这次任务。** 它会**原样**出现在回写体的
`batch_id` 字段里，前端就是靠它判断「这条画像结果属于哪一批任务」。填错或留空，
结果就对不上来源。

> 注意是 **11 位**手机号，不是 13 位。接口与运行台提交页、号码收集脚本用同一个
> 正则，13 位会被 422 拒掉。

## 4. 响应

### 200 · 接收成功

```json
{
  "status": "accepted",
  "run_id": "c2846ca7c73643acaa3da7bbfabf0f9d",
  "workflow_id": "customer_profile_pipeline",
  "phone_number": "13415100087",
  "batch_id": "batch-20261016-01"
}
```

**拿到 200 就代表任务已经落盘入库**，此刻服务重启任务也不会丢。可以放心把这条标记为
「已提交」。

`run_id` **仅供排查**，前端不必保存、不必用它来查结果。业务上的对应关系是
`batch_id` + `phone_number`。

### 错误响应

错误体统一为 `{"detail": "<原因>"}`。

| 状态 | 含义 | 前端该怎么做 |
|---|---|---|
| `401` | 没带 `X-API-Key` 请求头 | 检查请求头是否漏配 |
| `403` | 密钥错了 | 检查密钥取值；**不要重试**，重试还是 403 |
| `422` | 手机号格式不对，或 `batch_id` 为空 | 修数据后重发；**重试无意义** |
| `429` | 待跑队列已满（缺省上限 50 条） | 按响应头 `Retry-After`（30 秒）等待后重发 |
| `503` | 服务端未配置密钥，接口整体关闭 | 找我们开通；**不是前端的问题** |
| `500` | 服务端内部异常 | 可重试一次；仍失败请联系我们并附上响应体 |

**只有 429 和 500 值得自动重试**，且要退避。401 / 403 / 422 / 503 重试不会变好。

## 5. 调用示例

### curl

```bash
curl -X POST http://<部署主机>:8099/api/v1/tasks \
  -H 'Content-Type: application/json' \
  -H "X-API-Key: $INBOUND_API_KEY" \
  -d '{"phone_number":"13415100087","batch_id":"batch-20261016-01"}'
```

### Python

```python
import requests

resp = requests.post(
    "http://<部署主机>:8099/api/v1/tasks",
    headers={"X-API-Key": INBOUND_API_KEY},
    json={"phone_number": "13415100087", "batch_id": "batch-20261016-01"},
    timeout=10,
)
if resp.status_code == 200:
    accepted = resp.json()         # 已落库
elif resp.status_code == 429:
    wait = int(resp.headers.get("Retry-After", 30))
    ...
else:
    raise RuntimeError(f"{resp.status_code}: {resp.text}")
```

### JavaScript

```javascript
const resp = await fetch("http://<部署主机>:8099/api/v1/tasks", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-API-Key": INBOUND_API_KEY,
  },
  body: JSON.stringify({ phone_number: "13415100087", batch_id: "batch-20261016-01" }),
});
if (!resp.ok) throw new Error(`${resp.status}: ${await resp.text()}`);
const accepted = await resp.json();
```

## 6. 结果怎么拿到

**不在本接口拿。** 分析完成后，服务端把画像通过回写接口
（`POST /api/v1/remote/callback/update-profile`）写进业务系统，前端从业务系统那侧读取。

回写体顶层是三个键：

```json
{
  "phone": "13415100087",
  "batch_id": "batch-20261016-01",
  "analysis_result": { "...": "画像六区块" }
}
```

`batch_id` 与推送时的**逐字一致**，`phone` 就是推送的手机号。前端用这两个值把结果
对应回原来的任务。画像六区块的完整结构见 `AI画像远程回传接口数据结构说明.md`。

> **时序预期**：单号耗时约 21 分钟（受录音、模型响应影响可能更长）。前端应把它当作
> 「分钟级异步任务」设计，不要在推送后立刻查结果。

## 7. 三条要知道的服务端行为

1. **当前是单进程串行执行。** worker 领一个跑完再领下一个。批量推 100 个号码不是并发
   100 个，而是排队——后面的可能要等很久。**推之前请和我们确认当天的量级**，必要时
   我们会加 worker 进程。
2. **队列有上限。** 待跑超过 `MAX_QUEUED_RUNS`（缺省 50）就会返回 429。批量推送时请
   处理 429 并退避，不要死循环重试。
3. **任务进来就不再受前端影响。** 推送成功后，前端关掉、超时、重发同样的号码，都不会
   取消已在执行的任务；重发只会**再算一次**。所以请自己做好「已提交」的去重。

## 8. 联调自检清单

- [ ] `GET /health` 返回 200，说明端口通。
- [ ] 用一个测试号码 + 一个能认出来的 `batch_id` 推一条，拿到 200 和 `run_id`。
- [ ] 故意漏掉 `X-API-Key` → 应得到 **401**；用一个错的密钥 → 应得到 **403**。
- [ ] 推一个 13 位号码 → 应得到 **422**（这条能验证校验生效，也确认是 11 位口径）。
- [ ] 约 21 分钟后，在业务系统那侧看到该号码的画像，且 `batch_id` 与推送值一致。
- [ ] 批量推送时 429 有被正确处理（退避而非重试风暴）。
