# 下一轮架构蓝图（Brainstorming）

> 定位：为下一轮迭代定方向、排雷、划边界。**不是施工图**，不含字段级设计与代码。
> 现状口径见 `../design/客户人设画像管线设计.md`；本文只讲「往哪走、为什么、先做什么」。
> 触发时间：2026-10-22，业务逻辑高频合入后的一次架构体检。

---

## 1. 结论先说

四个工作方向看似独立，实际压在**同一块地基**上。地基不修，四条线都会变成「每条线各加一层补丁」。

| 方向 | 表层的需求 | 底下的真问题 |
|---|---|---|
| 更丰富的输入 | 多接几路数据 | 上下文无预算、取证不可分片 |
| 更多更细的规则 | 加校验 | 规则没有「身份」，散落在提示词/代码/审查三处 |
| 专家知识与知识库 | 灌数据 | 没有知识层，模型拿旧知识填空且无法标注出处 |
| 增量更新 | 少跑一次 | 没有字段级 provenance（来源与时间），无从判断「什么变了」 |

三条判断：

1. **规则层必须建，但形态不是「规则引擎」。** 一份规则要同时喂给代码和提示词，所以它是「声明式规则表 + 双投影」，不是 Drools。
2. **知识库要做，但先做「可引用」再谈「可检索」。** 「产品参数由模型编造」这条缺陷的根因是缺出处，不是缺向量库。
3. **增量更新的切分点不在「哪些字段要更新」，而在「哪些证据要重取」。** 取证贵、投影便宜，投影必须全跑。

还有一个前置动作：**字段级 provenance 是三条线共同的地基**，应该排在最前面，而不是随增量一起做。

---

## 2. 现状体检：结构性问题

按「会不会挡住未来方向」排序，不按代码行数。

### 2.1 管线是一个 3000 行的「四合一」单文件（挡全部四条线）

`workflows/customer_profile_pipeline.py` 3028 行，里面同时有四类东西：

- 渠道登记表（`CHANNELS`，14 路）
- L0/L4/L1/L2/定级各层的节点函数
- 图接线（40 个节点的 `NodeDef` 与 binding）
- 业务规则（确定性注入、定级收口、审查判据）

节点之间以 **JSON 字符串** 传递（`records_json` / `claims_json` / `facts_json`），每个 code 节点都在「解析字符串 → 干活 → `json.dumps`」。这是低代码节点图的遗产：图是表达约束，不是我们的约束。

**后果**：新增一路输入源 = 改渠道表 + 改 L0 装配 + 改 L1 输入 + 改模板 + 改图接线，五处联动。四条方向都要加输入源或加规则，成本会线性叠加成平方。

### 2.2 规则散落三处，且没有身份

当前规则存在于三个互不知道对方存在的地方：

| 载体 | 现状 | 问题 |
|---|---|---|
| 提示词正文 | `pipeline_l1_facts` 14 处、`l1_fields` 11 处、`level_assess` 15 处、`l3_express` 16 处带「必须/不得/一律/若…则」 | 无编号、无作用域、无测试映射；改动靠全批人工核读 |
| 代码守卫 | `projection._apply_cross_field_rules` 只有 2 条半（置换、注销企业、等级归一）+ `_non_income_tag` + `_salesperson_marked` + `income_band` 特例 | 每条都是特例分支，没有统一的「条件→动作」形态 |
| 审查层 | `review_notes` 四条机器判据 | **能判但不拦**，判出违规照样进最终 Notes |

最典型的证据是收入档位规则的漂移：`N档收入 → 金额区间` 这条规则先是写在投影层，后来前移进取数节点，同时又在 L1 提示词里补了一段「不得自行换算」。**同一条业务规则，三个落点，没有一处是它的家。**

### 2.3 上下文没有预算，取证不可分片（挡方向 1）

`build_evidence_input` 只按 `status=ok` 过滤渠道，**没有任何长度预算、截断或分层**。定级链路更是直接吃全量原始记录。

现在全案 7.09M token、单案中位 117s，还能撑住。一旦接入聊天记录、到店记录、销售手工总结（这三类都是长文本且高频），L1 与定级两处会同时爆，而且是「输入被静默截断 → 结论变差」这种最难归因的爆法。

### 2.4 表达层只有一次 LLM，没有「按人分化」的输入（挡方向 2、3）

L3 用一次 LLM 把同一份 facts 写成 9 个板块。这个设计解决了同源问题，但带来一个副作用：**模型手里只有 facts，没有任何「写得好」的素材**。审核报告里「沟通策略同模板复读、且与案情相反，20/39 案逐字复用」正是这个结构的必然结果——不同客户的 facts 长得很像，模型只能写出很像的话。

规则层与知识层的第二个价值就在这里：它们是表达层的**输入源**，不只是校验器。

### 2.5 增量更新没有任何地基（挡方向 4）

- `facts` 是扁平的「字段→值」，没有「什么时候、从哪条记录得知」。
- `records` 有 `created_at`，但没有稳定内容指纹，无法判断「这条记录上次见过了」。
- 回写契约是**先删后建**；「区块缺失或为 null 时保留原值」是**区块级**语义，不是字段级。
- 没有「旧画像」作为输入参与新运行，二次画像 = 全量重跑。

所以增量不是加一个 diff 函数，而是要先有**版本化画像 + 字段级来源**。

### 2.6 双轨残留造成的真实耦合

`customer_profile_production`（1185 行 / 12 个 LLM 节点）在语义上已被 L3 取代，但 L3 仍按**原名**引用它的 6 个资产模板（标签库、证据格式、画像格式、产品信息、产品速查、邀约策略）。也就是说：**想归档 production，得先给这 6 份资产搬家**。这不是坏设计，是没做完的迁移。

### 2.7 两个让守卫失效的已知缺陷

- `review_notes` 判出违规不落执行动作（设计文档 §7 已列，最高 ROI）。
- L3 同源守卫窗口 12 字 → 114/115 是误报，真问题被淹。**一个误报率 99% 的守卫等于没有守卫**，比没有更糟（它让人以为守住了）。

## 3. 目标架构

一句话：**把「图」降级为接线，把「规则」「知识」「来源」升为一级公民。**

```
              ┌──────────────────────────────────────────────┐
  输入源 ──▶  │ 接入层 Source Adapter                         │
  (15+ 路)    │  结构化 Record：id / 时间 / 角色 / 内容哈希     │
              │  / 来源分档 / 是否增量                          │
              └───────────────────┬──────────────────────────┘
                                  ▼
              ┌──────────────────────────────────────────────┐
              │ 取证层（分片 Map + 代码 Reduce）               │◀── 知识层（按需检索）
              │  按渠道/分片小上下文取证 → Claim[]             │    · 字典（品牌/车型/人群）
              │  · 每片有 token 预算，超了再切                  │    · 知识（车型参数/卖点）
              └───────────────────┬──────────────────────────┘    · 经验（策略/话术）
                                  ▼
              ┌──────────────────────────────────────────────┐
              │ 规则层 Rule Registry                          │
              │  一份规则 → 双投影：                           │
              │   (a) 提示词片段（影响推断）                    │
              │   (b) 校验/执行函数（拦截、修正、降级）          │
              └───────────────────┬──────────────────────────┘
                                  ▼
              ┌──────────────────────────────────────────────┐
              │ 投影层 Projection（代码，全量跑）               │
              │  归属 → 来源分级 → 冲突 → 枚举 → 跨字段 → 留白  │
              │  输出 facts（带 provenance）                    │
              └───────────────────┬──────────────────────────┘
                                  ▼
              ┌──────────────────────────────────────────────┐
              │ 表达层 Expression                              │
              │  facts + 规则片段 + 知识命中 + 客户分群 → 文案   │
              └───────────────────┬──────────────────────────┘
                                  ▼
              ┌──────────────────────────────────────────────┐
              │ 增量层 Profile Store                           │
              │  版本 / 字段 provenance / 差异计划 / 部分回写    │
              └──────────────────────────────────────────────┘
```

## 4. 四条方向的落地思路

### 4.1 规则层：一份规则，双投影

**要解决的不是「规则多」，而是「规则没有身份」。**

规则的最小定义（概念层面，不是字段设计）：

```
id          稳定编号，测试与日志都引用它（如 R-INCOME-01）
scope       作用于哪个阶段、哪些字段、哪些断言类型
when        条件：对 claims/facts 的谓词，或给模型的自然语言条件
then        动作：reject / downgrade / rewrite / require_confirm / annotate
severity    block（拦）/ repair（修）/ warn（只提示）
message     对客可读的解释（写进 reasoning_detail 或 to_confirm）
tests       至少一条正例、一条反例
```

**关键判断：同一条规则有两种消费者，各取所需。**

- 「网约车司机年收入应在 10 万量级」——**只能交给 LLM 判**（代码要判就得先建一张职业收入表，而职业有几万种、同一职业方差跨两个数量级，那张表建不出来也维护不住）；提示词同时让模型在取证/成文时自己往合理量级靠。
- 「不得把销售的话当客户的话」——主战场在代码（角色标注已解决），提示词只做兜底。

所以规则层不是「把提示词里的句子搬到代码里」，而是**一处登记、两处投影**：提示词片段由登记表按 scope 拼装，校验函数由登记表按 severity 调度。这样规则增删不再需要在三个地方同步。

**规则分三类，执行语义不同**：

| 类 | 例子 | 动作 |
|---|---|---|
| 一致性 contradiction | 有旧车 ⇒ 换购；注销企业 ⇒ 不填在职 | block/repair：字段间互斥，代码可判 |
| 合理性 plausibility | 职业↔收入量级、年龄↔驾龄、预算↔车型档次 | downgrade/require_confirm：这是**条件先验**，不是硬事实，只能收敛不能证伪 |
| 表达 expression | 不写内部字段名、不写裸渠道名、证据须可回指 | repair/block：作用于对客产出 |

**不要做的**：不要引入通用规则引擎（Drools、JSONLogic 之类），也不要一开始就做规则 DSL。先用 Python 函数 + 一张登记表，让规则的「身份、分类、测试」立起来。规则数到 100 条再谈 DSL。

**反直觉但重要的一点**：合理性规则（职业↔收入）不该写成「网约车 ⇒ 10 万」这样的 if，**也不该写成「职业 ⇒ 收入合理区间」的先验表**——后者等于把一件模型天然擅长、我们建不起的事，用一张永远不全、永远过时的表顶替。正确形态是把它写成**失效模式描述**交给 LLM 检查（「职业与年收入可能明显不自洽」），默认降级 + 转人工。规则多到几百条时撑得住的不是「更全的表」，而是「按字段簇分组、有编号、有命中统计的检查清单」。详见 `规则层设计.md`。

### 4.2 输入层：Source Adapter + 分片取证

新增一路数据源应该只做三件事：写一个 adapter、登记渠道元数据、提供分片策略。**不改图、不改 L1 提示词结构。**

分片取证是上下文问题的正解。现在 L1 是「一次吃全部渠道」，未来改成：

```
渠道记录 → 按渠道（必要时按时间/长度再切）分片 → 每片一次取证 → 代码合并 Claim[]
```

合并层已经存在（1a/1c 并集），思路可直接复用。收益有三：单次上下文可预测、某一片失败不拖垮全案、新增渠道只增加片数不增加单片长度。

定级链路同理，但它需要全局视角。建议：**分片取证先产出 Claim[]，定级读 Claim[] + 关键原文摘录，而不是读全量原文**。这同时降低了定级这个「断档领先重要」字段的成本与抖动。

### 4.3 知识层：先可引用，后可检索

知识分三类，管理方式完全不同：

| 类 | 形态 | 用法 | 优先级 |
|---|---|---|---|
| 字典 | 结构化 JSON（品牌/车型/人群标签/枚举） | 代码精确匹配，作为候选集注入提示词 | 高（同时解决 L-001 人群标签漂移） |
| 知识 | 版本化文档（车型参数、卖点、竞品对比） | 按品牌/车型名命中后注入，不检索全文 | 高（「编造产品参数」是已确认严重缺陷） |
| 经验 | 模板资产（策略、话术、邀约） | 按客户分群**选择**，不做检索 | 中（先解决复读问题） |

**硬口径：知识层的每一条产出都必须带出处。** `facts` 里来自知识层的值要标 `basis=knowledge`，证据写「车型知识库 vX」，和「客户原话」「第三方标签」一样进入来源分级。否则知识层会变成一个新的编造来源——那是把「模型旧知识」换成「我们的旧数据」，问题没有解决。

**不要做的**：一开始就上向量库。当前的数据量（几十个品牌、几百个车型）用字典 + 名称匹配就够，向量检索是输入源爆炸之后的事。

### 4.4 增量层：重取证据，重跑投影

正确的切分：

```
新任务（二次画像）
  ├─ 载入旧画像（facts + provenance + 版本）
  ├─ 记录去重：内容哈希 + 时间，识别真正新增的记录
  ├─ 只对「有新记录的渠道」跑取证（Map）
  ├─ 合并 claims：旧 claims 按时间衰减，新旧冲突按来源分级裁决
  ├─ 全量跑投影（代码，便宜，必须全跑——跨字段规则需要全局视图）
  ├─ 差异计划：字段级 diff → 哪些 Notes 需要写
  └─ 部分回写（依赖字段级更新语义）
```

**三条关键取舍**：

1. **省的是 LLM，不是代码。** 投影必须全跑。否则「只更新变化字段」会让跨字段规则看到残缺的 facts，制造新的矛盾——这正是 v2 之前「卡片说 A、Notes 说 B」的老病。
2. **增量必须建立在 provenance 上。** 没有「这个值是哪条记录、什么时候给的」，「变没变」无从判断。所以 provenance 要先做，不能等增量。
3. **回写契约要单独确认。** 「区块缺失保留原值」是区块级，「先删后建」是整块替换。字段级部分更新需要和业务方确认语义，否则增量省下的成本会在回写上以「覆盖掉人工修正」的形式还回来。

## 5. 排雷清单（先做，与方向解耦）

按 ROI 排序，都是「判据现成、只差执行」或「守卫已失效」的类型。

1. **L2 审查从「能判」到「能拦」**。判据现成，缺的是「判决 → 装配动作」这条线。落地方式不需要新架构：审查层输出带动作的判决（reject/downgrade/confirm），装配层执行。这是规则层的最小原型，做完再抽。
2. **修 L3 同源守卫**。12 字窗口导致 114/115 误报，真问题被淹。守卫误报率 99% 等于没有守卫。
3. **production 资产搬家**。6 份资产模板从 production 的 node_id 命名迁到独立 assets 目录，解除 L3 对 production 的名义耦合，之后 production 才可降级为归档臂。
4. **渠道表去重**。`手机号归属地信息` 与 `关联企业信息` 共用 `RelatedEnterpriseInfo` manifest channel（设计文档 §7 已记），属于结构性重复，接新输入源前必须理顺。
5. **拆分 pipeline.py**。按「接线 / 记录 / 取证 / 定级 / 审查」拆模块，保留对外的节点函数导出面。**不为拆而拆**，与规则层、输入层的落地同步进行。
6. **收敛字符串解析**。`_records_of` / `_claims_payload` 一类重复解析在多个节点各有一份，`text_utils` 只收敛了一部分；这类「同名不同义」是过去已发生过一次的事故类型。

## 6. 路线图与依赖

```
阶段 0  地基    字段级 provenance + 审查能拦 + 守卫修复 + 资产搬家
        ↓
阶段 1  规则层  登记表 + 三类动作 + 职业↔收入等首批合理性规则 + 规则命中的核读清单
        ↓
阶段 2  输入层  Source Adapter + 分片取证 + 上下文预算
        ↓
阶段 3  知识层  字典 → 车型知识 → 经验资产（均带出处）
        ↓
阶段 4  增量层  画像版本 + 差异计划 + 部分回写
```

依赖关系：

- provenance 是阶段 1（规则解释）、阶段 3（知识出处）、阶段 4（增量判断）的共同前置，必须先做。
- 规则层不需要等输入层；它先落地还能给输入层提供「每片取证后立刻校验」的挂点。
- 知识层可以并行，车型知识最急（编造参数是已确认严重缺陷）。
- 增量放最后，因为它同时依赖 provenance、规则层（合并时的冲突裁决）与回写契约确认。

**不建议的排法**：先做增量。它看起来最省成本，实际会在一个没有 provenance 的系统上做出「能跑但不敢信」的 diff。

## 7. 质量反馈回路（长期最贵的一项）

现状：39 案人工核读 26 案，是唯一的质量门。这不是流程问题，是**没有结构化的反馈通道**。

规则层落地后应顺带解决三件事：

1. **规则命中可观测**：每批跑完统计每条规则命中次数与动作分布。命中率长期为 0 的规则要么失效、要么条件写错。
2. **核读范围可收窄**：只核读「命中某规则」或「触发 to_confirm」的案子，而不是整批。
3. **规则级回归**：每条规则的 tests 进入测试集，提示词改动前先跑规则测试，而不是跑全批。

这是让「规则从 20 条长到 200 条」仍可控的唯一办法。没有它，规则层会变成第二个提示词垃圾场。

## 8. 明确不做
