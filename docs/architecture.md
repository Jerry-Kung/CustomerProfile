# 系统架构

> 本文记录**稳定的系统级信息**：系统边界、模块职责、分层、数据流、外部依赖与关键技术约束。
> 不重复代码可读出的内容（函数签名、端点表、字段清单）。文档分工见 `README.md`。

## 1. 这个系统做什么

把 Dify 上的 19 个工作流（客户人设画像分析）迁移为**普通 Python 工程**，并用一个
可留痕的执行器跑起来。对外只暴露一件事：**给定一个手机号，产出该客户的画像 JSON，
并按回写契约写到 Notes 服务**。

迁移原则见 `specs/V0迁移规划.md` §6：产出的是人写的代码，不是 Dify 节点图的逐节点转写；
Dify 的「节点 + 连线」是低代码平台的表达约束，不被继承。

## 2. 进程形态

**两个可独立部署的进程，共用一个 SQLite 文件。**

```
                 ┌──────────────────────────┐
   HTTP 调用方 → │ API 进程（FastAPI）       │
                 │  · 提交任务（写队列）      │
                 │  · 只读查询（运行/图/尝试）│
                 │  · 可选：内联消费者        │
                 └───────────┬──────────────┘
                             │  workflow_runs（同一个 SQLite 文件）
                 ┌───────────┴──────────────┐
                 │ worker 进程               │
                 │  · 领取队列任务            │
                 │  · 执行工作流              │
                 └──────────────────────────┘
```

- **API 进程**只负责提交与查询。它不执行工作流（除非 `INLINE_WORKER=true`）。
- **worker 进程**（`python -m customer_profile.worker`）从队列领取并执行。
- **为什么不用 FastAPI `BackgroundTasks`**：它依附请求生命周期与同一事件循环，既不能
  在进程重启后存活，也无法与 API 分离部署。而「任务先持久化入队再返回 run_id」
  （`Dify迁移任务说明.md` §4）要求任务的生命周期独立于任何一次 HTTP 请求。
- **为什么不用 Redis/Celery 等中间件**：规划 §5 约束 7 明确禁止「未实际需要的重型框架」。
  SQLite 的单语句条件 UPDATE 足以提供原子领取，不需要 broker。

### 2.1 内联消费者（`INLINE_WORKER`）

缺省 `true`：API 进程同时消费队列。这样单机部署与测试不必额外起进程，且
「POST /runs 之后立刻能查到并跑完」的既有契约成立。生产按上面的双进程形态部署时置
`false`（差异 W27）。

## 3. 任务队列

**队列复用 `workflow_runs` 表**（差异 W26）：入队即写一行 `status='queued'`，worker
领取即转为 `running`。不新建队列表——那会让「运行」有两个事实来源，且需要跨表同步。

关键字段：`queued_at_ms` / `claimed_at_ms` / `claimed_by` / `lease_expires_at_ms`。

### 3.1 原子领取与租约

领取是**单条** `UPDATE ... WHERE status='queued' ... RETURNING`。SQLite 的写事务是
串行的，因此两个 worker 同时执行时只有一个能把某行从 `queued` 改成 `running`，
另一个的 `WHERE` 不再命中。这比「先 SELECT 再 UPDATE」安全：后者之间的窗口会让两个
worker 领到同一个任务并把它跑两遍。

领取时写租约（`WORKER_LEASE_MS`，缺省 60s），运行期间靠心跳（`WORKER_HEARTBEAT_MS`，
缺省 20s）续租。主入口一次运行实测约 1282s，远超缺省租约——不续租就会被判为过期。

### 3.2 重启恢复：只标 running，不标 queued

启动时把残留的 `running` 标为 `interrupted`（保留已完成结果，交人工），**但不动
`queued`**（差异 W24）。若把 `queued` 一并标成中断，「worker 重启不丢任务」这条验收
标准直接不成立——重启后所有还没开始的任务都变成需要人工处理的中断态。

**过期租约不自动重领**（差异 W28）：重领会把一条跑到一半的运行**整条重跑**。根目录
文档明确「不做任意节点断点自动续跑」，且「worker 停机/取消/客户端断开不证明外部接口
未完成副作用」——在幂等回写落地前，自动重跑会重复触发外部副作用。
`Store.requeue_expired_leases` 保留为显式动作。

## 4. 并发与限额

四层闸门，粒度各不相同，**不能互相替代**：

| 闸门 | 配置 | 粒度 | 超额行为 |
|---|---|---|---|
| 队列深度 | `MAX_QUEUED_RUNS` | 全局待跑任务数 | 提交被拒（HTTP 429）|
| 运行名额 | `MAX_ACTIVE_RUNS` | 本进程同时执行的运行数 | 仅进程内路径生效（差异 W23）|
| 请求并发 | `MAX_CONCURRENT_REQUESTS` | 全局同时出网请求数（LLM+HTTP+AUC 共用）| 等待 |
| 速率限额 | `LLM_RPM_LIMIT` / `LLM_TPM_LIMIT` | 每分钟请求数 / token 数 | 等待（令牌桶）|

前两者是「队列/进程容量」，后两者分别是「同时打出去几个」与「一分钟总共几个」——
维度不同，故并存不合并（差异 W37）。

**速率限额作用在每次真实出网那一层**（`llm.py` 的 `_single_attempt`），不是调用点：
放在 `llm_call` 的循环外层会让 3 次尝试只记 1 个请求，配额被系统性低估 3 倍（差异 W31）。
TPM 用「出网前按 prompt 长度预扣 + 拿到 usage 后校正」（差异 W32）。

**多 worker 的配额是显式分配**：限额器是进程内的，`LLM_RPM_LIMIT` 是全局额度，按
`WORKER_REPLICAS` 等分（差异 W35）。不可整除时启动即报错，避免「RPM=60 配 4 个 worker
实际打到 240」的静默超发。不做跨进程共享配额（需中间件，差异 W36）。

## 5. 留痕的四层

对齐 `Dify迁移任务说明.md` §6，全部落 SQLite：

| 层 | 表 | 要点 |
|---|---|---|
| 工作流运行 | `workflow_runs` | 含子运行（`parent_run_id` 自引用）与队列字段 |
| 节点执行 | `node_executions` | 唯一键 `(run_id, node_id, call_path)`；迭代各轮靠 `call_path` 区分 |
| 请求尝试 | `request_attempts` | 每次外部尝试一行，含实际请求、响应、usage、耗时 |
| 版本快照 | `definition_versions` | 历史运行展示的是**当时**的图与提示词；新版本不覆盖旧运行 |

两条刻意的口径：**子运行与父运行共表**（树形自引用便于下钻）；**定义快照随运行一起存**
（V0.4 的「历史运行显示旧图」依赖它）。

`node_executions.attempt_count` 是**派生列**（收尾时数来源表），不是自增。自增强调
「每次尝试恰好加一」，一旦某条路径漏记就永久偏移且从行上看不出错。

## 6. 外部依赖

| 服务 | 端点 | 用途 |
|---|---|---|
| LLM | `.env` 的 `LLM_BASE_URL`（OpenAI 兼容）| 全部模型调用。**必须支持多模态**（12 个 vision 节点）|
| Notes / 回写 | `118.145.238.50:8084` | 画像回写、Notes 模板、历史数据 |
| mhero 中台 | `mhero.dfmc.com.cn` | 客户画像与人工确认 Notes |
| AUC 语音 | `openspeech.bytedance.com` | 录音识别。**2026-09-23 由内网自建改为火山引擎云服务**（差异 W14）|

凭据一律从 `.env` 注入，不进 Git、不进日志、不出现在 `GET /runtime` 的返回值里
（该端点由测试断言不含凭据字段）。`X-API-Key` 在 DSL 中曾为明文，按
`specs/ledger/secrets_report.md` 的口径视为已泄露，建议轮换。

## 7. 数据库与部署的硬约束

- **SQLite 文件不可放在网络挂载**（NFS/SMB）。WAL 依赖共享内存（`-shm`），网络文件系统上
  会锁失效并可能损坏数据库。
- `PRAGMA busy_timeout` 必须设置（`SQLITE_BUSY_TIMEOUT_MS`，缺省 5000）。API 与 worker
  是两个进程、各持一个连接，不设它时写相遇会直接报 `database is locked` 而不是等一会儿。
- **表结构变更靠最小补列机制**（差异 W25）：`CREATE TABLE IF NOT EXISTS` 对已存在的表
  不会补列，故 `store.connect()` 里读 `PRAGMA table_info` 后按需 `ALTER TABLE ADD COLUMN`。
  不引入 alembic 等迁移框架。新增列登记在 `store._ADDED_COLUMNS`。
- SQLite 连接有**唯一所有者**：一个专属工作线程，所有读写排进其队列顺序执行。原因是
  `sqlite3.Connection` 不是线程安全的（多线程共用在 Windows + Python 3.14 上实测段错误，
  不是可捕获的异常）。

## 8. 已知的边界与未做的事

明确不做（有意的范围约束，不是遗漏）：

- 不做任意节点断点自动续跑（根目录文档 §139；差异 W28）。
- 不做多 API 实例的水平扩展，不做调度公平性。
- 不做跨进程共享配额（差异 W36）。
- 不做 SSE/WebSocket 进度推送；前端用轮询。
- 无登录鉴权——前端只读运行台，唯一的写操作是提交任务（V0.5.1）与人工终结（V0.5.4）。

待办与缺口见 `specs/V0迁移规划.md` §2.3，以及各版本交付报告的「未完成项」。
