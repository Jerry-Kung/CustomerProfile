# 运行台 UI 优化（计划）

> 依据 `docs/design/Workflow_UI_Implementation_Guide.md` 与 `docs/design/运行台示例.png`。
> 本文是**开发期临时产出**（docs/README 对 `specs/` 的定位），收口后按需归档或删除。

## 1. 目标与边界

把运行详情页从「纵向展开列表」改为「顶部运行概览 + 左侧节点与结果摘要 + 右侧节点详情」，
达到：状态一眼可见、节点产出容易理解、详情方便阅读、技术与原有能力仍然可达。

**不做**：不改工作流执行逻辑、提示词、存储模型、通信协议；不引路由库；不引 UI 组件库；
不引 Markdown 解析依赖；不新增 SSE/推送（沿用 2s 轮询）。

**后端零改动**。展示所需数据现有接口已全部具备，唯一缺口是前端客户端未调用的
`GET /runs/{id}`（运行级 `inputs_json` / `outputs_json`），补一个客户端方法即可。

## 2. 现状核对（已实测，非推断）

| 事实 | 核对结果 | 对实现的影响 |
|---|---|---|
| 前端栈 | Vite 8 + React 19 + TS，无路由、无 UI 库、无 MD 库 | 组件自建，样式走原生 CSS |
| 产物 | `frontend/dist/` 入库，FastAPI 经 `SERVE_UI` 挂载 | 改完必须 `npm run build` 并提交 dist |
| 构建基线 | `npm run build` 通过（21 modules, 172ms） | 以此为回归基准 |
| 节点命名 | 真实标题含「（新）SubAgent - 」「 - 工具」等开发前缀 | 展示层清洗；实测清洗后不产生新重名 |
| 输出形态 | llm→`{text}`；tool→`{result}` 或 `{}`；http→`{body,status,files}`；code→`{result}`；template→`{output}`；aggregator→`{output}` 或 `{}` | 摘要按类型分级提取 + 通用降级 |
| 空输出 | succeeded 1724 条中 142 条输出为 `{}`；另有 143 处合法**空串**产出 | 空串**不得**判为「无数据」（`执行语义口径.md` P4） |
| 子流程 | tool 类节点输出常为 `{}`，真实产出在子运行 | 摘要走「子流程已执行，结果见子流程」 |
| 运行级产出 | `/runs/{id}` 的 `outputs_json` 有完整最终结果（如 `result1` 内含 `analysis_result`） | 「聚合结果」入口有真实数据可依 |
| 来源定位 | 全部输出中**无**来源定位字段 | 「查看来源」链接不做（设计文档 §5.1 的前提不成立） |
| 脱敏 | 列表页现有规范是明文 `business_ref` | 概览沿用明文，不自行引入脱敏规则 |

## 3. 口径决策

1. **排序**：改为按**完成时刻**（`started_at_ms + duration_ms`）升序，缺字段者回退到
   `started_at_ms` 并置后。两者均为已落库事实，非伪造；界面明确标注排序口径。
2. **执行状态与结果状态分离**（设计文档 §4.3）：
   - `succeeded` + 有非空字段 → 成功 · 已获取信息
   - `succeeded` + 输出 `{}`/null → 成功 · 未记录输出（**不**断言「无数据」）
   - `succeeded` + 空串 → 成功（空串是合法产出）
   - `skipped` → 已跳过（分支未走）；`blocked` → 被阻断（前置失败）；`failed` → 失败 + 原因
3. **摘要提取**：按 `text` → `result` → `output` → `body` 顺序取首个可读字段；
   字符串可解析为 JSON 时**只解一层**；长文本取首行截断；无法可靠提取则
   「已生成输出，查看详情」。不调 LLM、不改写原始结果。
4. **Markdown**：自建轻量渲染器输出 React 元素（**不经** `dangerouslySetInnerHTML`，
   结构上无 XSS 面），覆盖标题/列表/表格/引用/代码/强调。不引新依赖。
5. **选中标识**：沿用 `node_id:call_path`（迭代各轮可区分），轮询刷新不重置选中。
6. **范围控制**：设计图中的「查看来源」「重试」等无真实能力的入口一律不做；
   「查看聚合结果」「复制」有真实数据支撑，实现。

## 7. 实施记录（完成后回填）

### 7.1 相对计划的实现调整

| 项 | 计划 | 实际 | 原因 |
|---|---|---|---|
| 客户端补接口 | 新增 `runDetail()` | 同 | 已实测 `/runs/{id}` 最大约 0.72 MB，可直接取用 |
| 排序键 | 缺 `started_at_ms` 者置后 | **扩展为 `0` 也置后** | 实测未执行节点（`blocked` / `skipped`）库里记的是 `started_at_ms = 0` 而非 null，只判 null 会把「输出（被阻断）」顶到时间线第 01 位 |
| 摘要兜底 | 主载荷取不到则给中性描述 | **增加逐字段兜底** | 实测 `{phone_number, batch_id}`、`{profile_result, hobby_result, style_result}` 这类多字段输出无已知正文键，原逻辑会误报「本次输出为空」 |
| 数组渲染 | 未细化 | **对象元素走摘要** | 直接 `String(对象)` 会渲染成 `[object Object]`，等于丢内容还装作展示了 |
| 节点详情标签 | 三标签 | 同；`原始数据` 内合并请求记录 | 「请求记录」属原始数据范畴，不再单列一组 |
| 空字符串 | 未细化 | **显示为「（空字符串）」** | 空串是合法产出（执行语义口径 P4），渲染成空白会与「未渲染」混淆 |

### 7.2 验证范围（真实数据）

以本机库 `data/customer_profile.db` 的 219 条运行、5 个真实工作流为样例，用 headless Chrome 走 CDP 截图核对：

- 已完成运行（`customer_profile_entry`，5 节点）：概览、列表摘要、三标签、聚合结果浮层
- 失败运行：错误横幅、被阻断节点排序、失败节点摘要带子工作流错误
- 已结束的子运行跳转与返回
- 长文本与 Markdown（证据线索、人设特征的深层 JSON）
- 1366 / 1680 / 1920 三种宽度

### 7.3 未做（与计划的偏离一致）

「查看来源」（无来源字段）、「导出结果」（降为复制）、业务标识脱敏（沿用现有明文规范）、
「部分来源暂无数据」措辞（无可靠依据）。首屏未做虚拟滚动——实测单次运行节点数为 5～30，
不构成性能问题。
