## 0. 先纠正三个前提

这三条会直接决定改动面的大小，先摆出来，避免按错误的假设排期。

### 0.1 high/low 档的运行时数据**本来就不在数据库里**

存储瘦身之后，节点输入输出、请求体与响应正文已经搬进 `trace-archives/YYYY-MM-DD/<run_id>.json.gz`，
库里只剩骨架（`docs/design/存储瘦身方案.md` §3.2）。本次实测本地库 9.6 MB、79 个包共 28 MB。

因此**包不需要迁移，存放位置也不变**。切库只影响骨架。用户提到的「压缩包太大时本地存放」
在现状下已经是事实，且 MySQL 不承担任何包存储职责——包继续留在本地卷。

### 0.2 `experiments/` 下的批次 `trace.db` 不是运行时库

`experiments/uat_data/*/trace.db` 与 `experiments/batches/*/trace.db` 是**按批次自包含的证据归档**，
`scripts/ingest_trace_export.py` / `ingest_uat_export.py` 按 `persistence/schema.py` 的 DDL 重建，
`run_baseline.py` / `replay_from_archive.py` / `replay_incremental.py` 从它读。

它们**不迁移，继续用 SQLite**。理由：批次目录要「拷走即归档」（ADR 0003），MySQL schema
不具备这个性质；而且这些库只读、按批次隔离、与运行时负载无关。

这决定了下面的核心架构选择：**双后端并存**，而不是把 SQLite 从代码里彻底移除。

### 0.3 现有 `.env` 的 `MYSQL_DATABASE` 指向的是**生产业务库**

实测 `customer_profile` schema 下已有 45 张表，包括 `customer_profile_main`、`customer_invite_main`、
`customer_profile_tasks` 等业务表，以及 task-backend 的迁移表。当前连接账号是 `root@%`。

**不能把运行时四张表放进这个 schema。** 需要新建独立 schema（见 §3.1）。

## 1. 范围与不变量

### 1.1 在范围内

| 面 | 内容 |
|---|---|
| 运行时库 | `workflow_runs` / `node_executions` / `request_attempts` / `definition_versions` / `profile_baselines` |
| 存储层 | `persistence/store.py`、`persistence/schema.py`、`persistence/profile_baselines.py`、`persistence/tracker.py` |
| 配置与装配 | `settings.py`、`runner.py` 的 `_database_path` 硬闸门 |
| 方言片段 | `workflow_scope.py` 的 `GLOB` |
| 取数链 | `export_snapshot.py`、`fetch_run_archive.py`（源改为可指向 MySQL，**产物仍是 SQLite**） |
| 部署 | `compose.yaml`、`Dockerfile`、健康检查、备份口径、运维文档 |
| 测试 | `tests/` 中 16 个文件约 90 处引用 |

### 1.2 明确不在范围内

- `experiments/` 批次库与回放脚本的读写方式；
- `ingest_trace_export.py` / `ingest_uat_export.py` 重建 `trace.db` 的逻辑；
- 前端（实测只走 HTTP，零改动）；
- task-backend（已是 MySQL，本次不动）；
- 归档包的格式、目录结构、保留期策略；
- 不引入 ORM、不引入 Redis（ADR 0001 继续有效）。

### 1.3 不变量（改动中必须一直成立）

1. **队列原子领取**：两个 worker 并发时，同一 `run_id` 只能被一方领到。改用 InnoDB 行锁实现，不退回「先查后写」。
2. **续租与恢复语义不变**：租约过期不自动重领；`interrupted` 只由启动恢复或人工终结。
3. **留痕 fail_soft 不变**：写留痕失败不能让业务运行失败；但失败必须可观测。
4. **包是载荷唯一副本**：先写包成功、再清库内载荷的顺序不变。
5. **`payload_state` 的三种状态可区分**：`in_db` / `packed` / `purged` 不能因为换库退化成「空 = 没有」。
6. **本地复现链路零改动**：快照产物仍是 SQLite 文件，`DATABASE_URL=sqlite:///...` 仍可打开。

## 2. 目标架构

### 2.1 双后端，按 URL 前缀选择

```
DATABASE_URL=sqlite:///./data/customer_profile.db      → SQLite 后端（保留，用于实验/快照/本地复现）
DATABASE_URL=mysql://user:pass@host:3306/schema        → MySQL 后端（运行时）
```

`runner._database_path()` 现在遇到非 `sqlite:///` 直接抛 `V0.2 仅支持 SQLite`，改为按 scheme 分派。

### 2.2 依赖注入点

`Store` 的构造从「一个路径」改为「一个后端工厂」：

```
Store(backend=SqliteBackend(path) | MySqlBackend(dsn, pool_size=...), archive_dir=...)
```

`_ConnectionThread`（独占线程 + 命令队列）**保留**。它解决的是 `Future` 取消竞态——
2026-11 那次「容器 Up、执行停止」的直接原因——与用哪种数据库无关。

`setup` 回调的内容由后端提供：SQLite 是 PRAGMA 序列，MySQL 是会话参数 + 迁移检查。

### 2.3 连接模型

保持「一次数据库操作 = 在工作线程上执行、拿到一个连接、用完归还」的串行模型：

- 引入连接池（`mysql.connector.pooling.MySQLConnectionPool`，初始 4、上限 8）；
- 每次 work 借一个连接，`finally` 归还前 `is_connected()` 检查；
- 串行不变 → 不会因为并发引入新的死锁面；将来要并发，把工作线程数改成 N 即可。

**为什么保留串行**：主入口实测约 1282 s，一次运行约 600–1000 次库操作。按到实例的实测 RTT
约 36 ms 计算，串行额外开销约 22–36 s，占 2–3%，可接受；而并发的收益在这个量级上换不回
排查成本。

### 2.4 断连自愈（新增，必须做）

SQLite 是本地文件，不会断。MySQL 是远程，网络抖动会断。当前 fail_soft 会把断连**静默吞掉**，
这与「容器 Up、执行停止」那类故障同性质。处置：

| 机制 | 做法 |
|---|---|
| 自动重连 | 归还连接前检测；操作抛 `2013/2006/2055` 时丢弃该连接、重取一个 |
| 有界重试 | **只对幂等语句**（upsert、UPDATE、SELECT）重试一次；纯 INSERT 只重连不重试，避免重复行 |
| 健康暴露 | liveness JSON 增加 `db_last_ok_at_ms` / `db_error`，健康检查一并判定 |
| 计数告警 | 连续 N 次 DB 失败打印 ERROR 并让 worker 停止领取（不是退出进程） |

### 2.5 schema 变更机制

| 后端 | 机制 | 理由 |
|---|---|---|
| SQLite（批次/快照） | 沿用 `SCHEMA_STATEMENTS` + `_ADDED_COLUMNS` + `PRAGMA table_info` | 库随代码重建，声明式最省事 |
| MySQL（运行时） | `schema_migrations` 版本表 + `db/migrations/*.sql` 有序文件 | 长期演进的生产库需要可审计的变更记录；task-backend 已有同类成熟做法可参照 |

MySQL 侧建表语句不再依赖「`CREATE TABLE IF NOT EXISTS` 不补列」这个怪癖——
那正是 `_ADDED_COLUMNS` 存在的原因。

## 3. 实例与环境准备（P0，不改代码）

### 3.1 独立 schema

```sql
CREATE DATABASE customer_profile_runtime
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_0900_as_cs;
```

**用 `as_cs`（大小写敏感）而不是实例缺省的 `ai_ci`**。SQLite 的 TEXT 比较是二进制语义，
`ai_ci` 会让 `'Running' = 'running'`、`'ABC' = 'abc'`，与现状不一致，属于隐蔽的行为漂移。

### 3.2 最小权限账号

当前用 `root@%`，且实例上 root 可从多个公网地址登录，属既有安全债。运行时库应建：

```sql
CREATE USER 'cp_runtime'@'%' IDENTIFIED BY '<rotate>';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES
  ON customer_profile_runtime.* TO 'cp_runtime'@'%';
```

DDL 权限仅用于迁移；若希望运行账号不带 DDL，可拆成 `cp_migrate` 与 `cp_runtime` 两个账号，
迁移由 `runtime-migrate` 容器以 `cp_migrate` 执行（与 `backend-migrate` 同形，但**挂在正常启动链上**，
见 §9.1）。

### 3.3 变量命名：不要复用 `MYSQL_*`

`.env` 里的 `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_DATABASE`
已被 task-backend 的 `load_mysql_config()` 强制读取。运行时若复用同一组，两边会连同一个
schema——而这正是 §0.3 要避免的。

推荐：运行时只用一条 `DATABASE_URL`：

```
DATABASE_URL=mysql://cp_runtime:<password>@<mysql-host>:3306/customer_profile_runtime?charset=utf8mb4
```

好处：单点配置、可直接切回 `sqlite:///`、不与 task-backend 抢变量、密码不散落在五个键里。

### 3.5 UAT 网络不可达（2026-11-12 用户确认）

UAT 在内网、使用内网 MySQL 实例，**不能直连** `<mysql-host>:3306`；本地也访问不到 UAT 的库。

因此**不要求 UAT 复用本次开发用的实例**，改为交付一件可搬运的东西：

| 环境 | 库 | 落地方式 |
|---|---|---|
| 本地开发 / 验证 | `<mysql-host>:3306` 上的 `customer_profile_runtime` | 本方案直接开发调试 |
| UAT | UAT 内网的 MySQL | 随 docker 部署执行**初始化脚本**，建 schema + 表 + `schema_migrations` 记录 |
| 生产 | 生产内网 MySQL | 同上 |

初始化脚本的设计约束（据此实现）：

1. **幂等**：可重复执行，已存在的对象不报错（`CREATE TABLE IF NOT EXISTS` + 迁移版本表）。
2. **不假设实例地址**：只读 `DATABASE_URL`，不写死主机。
3. **不假设字符集可改**：显式在每个 `CREATE TABLE` 上写 `CHARSET/COLLATE`，不依赖库级缺省。
4. **不假设账号有 DDL 权限**：脚本可由 DBA 以管理员账号手工执行；容器内执行是便利路径，不是唯一路径。
5. **可核对**：执行后打印表清单与迁移版本，便于与代码期望版本比对。

这也意味着 `runtime-migrate` 容器不能是「UAT 唯一的建表途径」——必须同时提供一个
纯 SQL 的等价产物，供无法跑容器的场合交给 DBA。

### 3.6 实例参数核对结果

| 参数 | 实测值 | 影响 |
|---|---|---|
| `max_allowed_packet` | 64 MB | 单行最大载荷实测 572 KB，充足 |
| `innodb_buffer_pool_size` | 128 MB | **与业务库共用**，我们的写入会挤占缓存 |
| `max_connections` | 500 | 充足 |
| `sql_mode` | 含 `STRICT_TRANS_TABLES`、`ONLY_FULL_GROUP_BY` | 超长/空串会**报错而非截断**，列宽必须按实测设足 |
| `lower_case_table_names` | 0 | 表名大小写敏感，与代码一致 |
| `transaction_isolation` | REPEATABLE-READ | 领取用 `FOR UPDATE SKIP LOCKED`，见 §4.3 |
| `log_bin` / `binlog_format` | ON / ROW | 大 TEXT 写入会产生大量 binlog，需评估实例磁盘 |
| `wait_timeout` | 28800 s | 池内空闲连接不会轻易被掐 |

### 3.5 待确认：UAT 到实例的网络可达性

UAT 部署在内网、运行台出网不可达（`docs/runbooks/内网取数与本地复现.md` 开篇）。
若 UAT 机器**不能**直连 `<mysql-host>:3306`，则本方案在 UAT 上无法直接落地，
需要在 UAT 网络内另起实例，或改用跳板/内网映射。

**这是开工前必须先确认的一条。**

## 4. 方言差异清单（实现时逐条对照）

### 4.1 DDL 映射

| SQLite | MySQL | 说明 |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT UNSIGNED NOT NULL AUTO_INCREMENT` | 三张表 |
| `TEXT`（键列） | `VARCHAR(n)` + 合适字符集 | 见下表 |
| `TEXT`（载荷列） | `LONGTEXT NULL` | 最长实测 572 KB |
| `INTEGER`（毫秒） | `BIGINT` | **不改成 DATETIME**：避免时区与精度漂移，代码零改动 |
| `INTEGER`（布尔） | `TINYINT(1) NOT NULL DEFAULT 0` | `is_replay` / `replayed` |
| `TEXT NOT NULL DEFAULT '[]'` | `LONGTEXT NULL` + 应用层兜底 | MySQL 的 TEXT 不接受字面量默认值 |
| 部分索引 `WHERE parent_run_id IS NULL` | 普通复合索引 `(status, created_at_ms)` | MySQL 无部分索引 |
| `PRAGMA foreign_keys=ON` | **不建外键** | 见 §4.2 |

键列长度（按实测最大值给余量，`ascii` 字符集只存英文标识）：

| 列 | 实测最大 | 建议类型 |
|---|---|---|
| `workflow_runs.run_id` | 32 | `VARCHAR(48) CHARACTER SET ascii COLLATE ascii_bin` |
| `workflow_runs.workflow_id` | 27 | `VARCHAR(128)` |
| `workflow_runs.business_ref` | 11 | `VARCHAR(128)` |
| `workflow_runs.call_path` | 6 | `VARCHAR(256)` |
| `node_executions.node_id` | 30 | `VARCHAR(96) ascii` |
| `node_executions.call_path` | 34 | `VARCHAR(384)` |
| `request_attempts.target` | 168 | `VARCHAR(1024)` |
| `definition_versions.definition_hash` | 64 | `CHAR(64) ascii` |
| `profile_baselines.phone` | — | `VARCHAR(32) ascii` PK |

唯一键 `(run_id, node_id, call_path)` 按上表合计约 1.7 KB，低于 InnoDB DYNAMIC 的 3072 字节上限。

### 4.2 不建外键（有意差异，需在文档中写明）

SQLite 版本开了 `foreign_keys=ON`。MySQL 版本建议**不建**：

- 留痕层是 fail_soft，子运行的写可能晚于父运行到达；外键会把「暂时缺父行」变成硬失败；
- 外键会在 DDL 变更与批量清理时引入额外锁与顺序约束；
- task-backend 的现有 migrations 同样不用外键，风格一致。

代价：孤儿行不再被数据库拦下。现状数据里没有孤儿（`execution_trace` 走递归 CTE 自然过滤），
可接受；如需兜底，用一条定期巡检 SQL 而不是外键。

### 4.3 SQL 重写点

| 位置 | SQLite 写法 | MySQL 写法 |
|---|---|---|
| `store.insert_run` | `ON CONFLICT (run_id) DO UPDATE SET ... = excluded.x` | `INSERT ... AS new ON DUPLICATE KEY UPDATE x = new.x`（8.0.19+ 别名语法，8.2.0 可用；**不要用已弃用的 `VALUES(x)`**） |
| `store.upsert_node_execution` | 同上，三列唯一键 | 同上 |
| `store.enqueue_run_once` | `ON CONFLICT DO NOTHING` + `rowcount==1` | `ON DUPLICATE KEY UPDATE run_id = run_id` + `rowcount==1`。**不要用 `INSERT IGNORE`**——在 STRICT 模式下它会把「超长」降级为告警并截断 |
| `store.claim_next_queued_run` | 单条 `UPDATE ... RETURNING` | 事务内 `SELECT ... FOR UPDATE SKIP LOCKED` → `UPDATE ... WHERE run_id=? AND status='queued'` → 回查。见下 |
| `store.mark_running_as_interrupted` | `UPDATE ... RETURNING run_id` | 事务内先 `SELECT run_id ... FOR UPDATE` 再 `UPDATE`，返回行数 |
| `store.abandon_run` / `renew_lease` | 依赖 `rowcount` | **必须开 `client_flags=CLIENT.FOUND_ROWS`**，否则「匹配但值未变」返回 0，与 SQLite 的 `changes()` 语义不一致 |
| `store.execution_trace` / `_root_run_id` / `finalize_tree` | `WITH RECURSIVE ... UNION ...` | MySQL 8 支持，但建议改 `UNION ALL`（`UNION` 的 DISTINCT 在递归里开销大）；树深 ≤ 3，`cte_max_recursion_depth` 无虞 |
| `workflow_scope.scope_predicate` | `workflow_id GLOB 'invitation_*'` | `LEFT(workflow_id, 11) = 'invitation_'`（不用 `LIKE`，避免 `_` 通配与转义符问题） |
| `store._apply_migrations` | `PRAGMA table_info` | `information_schema.columns`（仅 SQLite 后端继续用原逻辑） |
| `cursor.lastrowid` | 可用 | MySQL 上有效，保持 |

**领取语句的目标形态**：

```sql
START TRANSACTION;
SELECT run_id FROM workflow_runs
 WHERE status='queued' AND parent_run_id IS NULL AND <scope predicate>
 ORDER BY created_at_ms LIMIT 1
 FOR UPDATE SKIP LOCKED;
UPDATE workflow_runs
   SET status='running', claimed_at_ms=?, claimed_by=?, lease_expires_at_ms=?
 WHERE run_id=? AND status='queued';
SELECT run_id, workflow_id, business_ref, inputs_json, definition_version_id,
       is_replay, claimed_by, claimed_at_ms, lease_expires_at_ms
  FROM workflow_runs WHERE run_id=?;
COMMIT;
```

`SKIP LOCKED` 让多 worker 不互相等待，是 MySQL 上比 SQLite 串行写事务更正确的队列模式。
`ORDER BY` 与 `LIMIT 1` 在 `idx_runs_queue` 上只锁一行。

### 4.4 事务模型差异

- SQLite 代码用 `connection.execute("BEGIN")` + `finally: rollback()` 包住多表读。MySQL 需要
  `START TRANSACTION`，且 **DDL 会隐式提交当前事务**——建表/迁移必须走独立连接或独立事务，
  不能与业务事务混在同一个 work 回调里。
- mysql-connector 缺省 `autocommit=False`，`commit()` 是显式的；这与 SQLite 隐式事务不同，
  所有写路径要确认有 `commit()`（现有代码已有，但新增代码要遵守）。
- 隔离级别保持 RR。领取用 `SKIP LOCKED` 已规避间隙锁的主要冲突面。

## 7. 内网取数 / 快照链路

现状（`docs/runbooks/内网取数与本地复现.md`）：快照 = 骨架库 `.db` + 包目录 + `manifest.json`，
本地用 `DATABASE_URL=sqlite:///...` 起只读运行台复现。

切 MySQL 后的处理：**读取侧换成 MySQL，写出侧仍是 SQLite**。

```
内网/公网 MySQL ──(START TRANSACTION WITH CONSISTENT SNAPSHOT)──▶ export_snapshot.py ──▶ snap.db + archives/
```

好处：
- 本地复现、`tests/test_export_snapshot.py`、runbook §3 的操作全部不用改；
- 快照仍然是「一个文件 + 一个目录」，可以过堡垒机、可以拷进拷出；
- 不需要在本地起 MySQL。

`manifest.json` 的 `format` 升到 4，增加 `source.backend = "mysql"`、`source.dsn_schema`（不含密码）、
`source.snapshot_gtid`（若可取得），便于事后对齐「这份快照取自哪个库的哪个时刻」。

同步要改的文档：`内网取数与本地复现.md` §1（不再有 `-wal/-shm` 之说，改述为「从库直读」）、
§2（不再需要 `.db` 伴生文件说明）、§3（本地起服务不变）。

**注意**：§3.5 的网络可达性若为否，这条链路反而更简单（继续从本机 SQLite 取），
但运行时库也无法落在该实例上。

## 9. 部署与运维

### 9.1 compose

| 项 | 改动 |
|---|---|
| `DATABASE_URL` | 从 `x-environment` 移除硬编码，改由 `.env` 注入（现状会覆盖 env_file） |
| `profile-data` 卷 | **保留**（归档包所在） |
| worker 健康检查 | 沿用 `liveness --check`，判定条件增加 DB 新鲜度 |
| `runtime-migrate` | **挂在正常启动链上**（不是 maintenance profile）：`restart: "no"`，四个运行服务 `depends_on: service_completed_successfully` |
| 网络 | 容器需能访问内网 MySQL；`extra_hosts` 不适用 |

### 9.1.1 自动初始化（2026-11-12 追加需求）

用户要求「每次部署 docker 时自动运行、自动检测表是否满足业务需要、不满足时自动建表」，
因此 `runtime-migrate` 从「运维记得跑一次」改为启动链上的一环。三条实现口径：

1. **自检不是比版本表，而是比实际结构。** `mysql_schema.inspect()` 解析 `MYSQL_DDL` 得到
   期望的「表→列」，与 `information_schema.columns` 比对。版本行只证明「有人跑过脚本」，
   不证明表还在——手工删过表时版本行照样在，服务会正常启动到第一次写才炸。
2. **只补缺的，不重建。** 缺表 `CREATE TABLE`、缺列 `ADD COLUMN`，已存在的一律不动。
   因此对已有数据的库也是安全的（已实测：补列后原有行仍在）。
3. **并发安全靠 `GET_LOCK`。** 四个服务与初始化容器可能同时启动；`CREATE TABLE IF NOT
   EXISTS` 在并发下会撞 `Table already exists`。实测 6 进程同时初始化：全部成功、
   只有一个真正建表。

`runtime-migrate` 对 SQLite 后端也生效（`--allow-sqlite` 时执行 SQLite 的幂等建表），
让部署链对两种后端做同一件事：服务启动前结构就已就绪。

### 9.1.2 不引入配置开关（2026-11-12 用户决定）

初版曾引入 `DB_MIGRATE_ON_CONNECT` 与 `DB_REQUIRE_SCHEMA_VERSION` 两个环境变量，用户以
「环境变量数量已接近失控、运维无力承担」为由要求移除。这个判断是对的：两者管的都是
**代码自己就能决定的事**，交给运维等于让他们抄一遍代码里的常量。

| 原变量 | 现在怎么定 |
|---|---|
| `DB_MIGRATE_ON_CONNECT` | 按后端类型写死：SQLite 服务进程自建，MySQL 服务进程一律不建（表由 `runtime-migrate` 建） |
| `DB_REQUIRE_SCHEMA_VERSION` | 校验**无条件开启**，期望值直接取代码里的 `SCHEMA_VERSION` |

顺带清掉了同样是本方案引入、且**从未真正接通**的 `DB_CONNECT_TIMEOUT_S`
（`build_backend` 一直用的是函数默认值）。结论：`DATABASE_URL` 是这套后端配置里唯一
需要运维填的项。

### 9.2 启动顺序

`runtime-migrate`（一次性，成功退出）→ `runtime-profile-api` / `runtime-profile-worker` /
`runtime-invitation-*` 并行启动。
运行服务启动时**不再**自己建表，且**无条件**校验结构：不符即拒绝启动并列出缺哪些表、
哪些列。这比「谁先起谁建表、补列靠吞异常」更可解释。

### 9.3 备份口径变更

| 旧 | 新 |
|---|---|
| 停写 → `tar` 整个卷 | 停写 → `mysqldump --single-transaction` + `tar` 包目录 |
| 无需外部依赖 | 需要 `mysqldump` 客户端与实例访问权 |

`docs/runbooks/部署.md` §1.3 整节重写。

### 9.4 健康检查语义

| 现象 | 现状 | 切换后 |
|---|---|---|
| 数据库线程死亡 | 容器 Up、`/health` ok、积压无人处理 | 同上，但 liveness 带 `db_last_ok_at_ms`，过期即 unhealthy |
| 连不上 MySQL | 不可能发生 | 启动期：拒绝启动（比 Up 着但什么都不做更好）；运行期：停止领取 + 记 ERROR |
| 池耗尽 | 无此概念 | 借连接超时记 ERROR，不静默 |

### 11.3 实施中发现的方言坑（都已修复，记下来避免重犯）

| 现象 | 原因 | 处置 |
|---|---|---|
| `UPDATE … WHERE run_id IN (SELECT … LIMIT n)` 报「MySQL doesn't yet support」 | MySQL 不支持带 LIMIT 的 IN 子查询 | `requeue_expired_leases` 拆成「先查候选 → 按主键批量更新」 |
| `error = COALESCE(error \|\| ' \| ', '') \|\| ?` 结果变成 0/1 | MySQL 的 `\|\|` 缺省是逻辑或（未开 `PIPES_AS_CONCAT`） | 走 `dialect.append_error_sql()`，MySQL 侧用 `CONCAT` |
| `renew_lease` 在该续租时返回 False | 驱动缺省 `rowcount` 是「实际改变行数」，值没变就是 0 | 连接开 `CLIENT_FOUND_ROWS`，与 SQLite 的 `changes()` 对齐 |
| `enqueue_run_once` 无法区分「插入」与「已存在」 | 开了 `FOUND_ROWS` 后两者都可能返回 1 | 改回纯 `INSERT` + 捕获唯一键冲突，两种后端语义一致 |
| 迁移对账报「目标比源大 30%」 | SQLite `LENGTH(TEXT)` 数**字符**，MySQL 数**字节** | 两边统一比**字节**（源侧 `LENGTH(CAST(x AS BLOB))`） |
| 某条 `response_text` 源侧长度只有 1/12 | 文本含内嵌 `NUL`，SQLite 的 `LENGTH` 在第一个 NUL 处截断 | 同上；数据本身完整，是核对口径错了 |
| DSN 密码含 `@ # /` 时解析成「缺少主机」 | `urlsplit` 把未编码的 `@` 当分隔符 | 按**最后一个** `@` 切凭据，`#` 不走 fragment |
| 版本不匹配时服务照常启动 | 建连错误被延后到「第一次操作」 | `Store.connect()` 立即抛出启动期错误 |

### 11.4 收尾补完的三项（2026-11-12）

| 项 | 内容 | 验证 |
|---|---|---|
| `fetch_run_archive.py` | 加 `--source-url mysql://…`；包目录位置不变，源库只用于定位所属根运行 | 用真实 run_id 与「已打包」合成行各跑一次，`rc=0` 并正确复制；「从未打包」诊断照旧 |

| 健康检查 | 存活信号写入 `db`（`db_alive` / `db_last_ok_at_ms` / `db_error`），`--check` 一并判定 | 四种情形实测：DB 断开→unhealthy、DB 正常→healthy、旧信号无 `db`→healthy、信号过期→unhealthy |

### 11.5 仍未做（明确不在本轮）

- **连接池**：当前是单连接串行（见 §2.3）。实测 RTT ≈ 36 ms、一次运行多 22–36 s（占 2–3%），
  压测若显示写入占比超过 10% 再引入；
- `mysqldump` 未随镜像分发：备份在宿主机或由 DBA 执行，脚本只调用本机客户端并检查非空；
- 迁移账号拆分（`cp_migrate` 与 `cp_runtime` 两个账号）已在 runbook 写好，但当前开发实例
  仍用同一个账号，生产落地时按 runbook 建。

P1 是纯重构、P2 是新增后端，两者都不改变缺省行为。真正的「切换」只发生在 P6，且是配置项级别。

### 11.1 为什么先 P1 再 P2

把方言差异先收敛到一层、并证明 SQLite 行为不变，再引入第二种后端。反过来做（直接写 MySQL 版本、
SQLite 顺手改）会让「测试变红」同时有三种可能原因：重构错了、方言错了、环境错了。

### 11.2 回退方案

任一时点把 `DATABASE_URL` 改回 `sqlite:///...` 即回到今天的行为，**不需要回滚代码**。
前提是 P1 之后 SQLite 后端一直存活——这也是 §1.2 把批次库排除在迁移之外的原因之一。

## 12. 风险

| 风险 | 影响 | 处置 |
|---|---|---|
| UAT 到实例不可达 | 方案在 UAT 无法落地 | §3.5，开工前确认；不可达则 UAT 另起实例 |

| 严格模式下的列宽不足 | 写入直接失败（不是截断） | 列宽按 §4.1 实测值给余量；迁移前跑一次全表长度扫描 |
| `rowcount` 语义差异 | `abandon_run` / `renew_lease` 误判「没改到」 | 开 `FOUND_ROWS`；契约测试覆盖「值未变」分支 |

| root 账号与公网暴露 | 安全面 | 新账号最小权限；root 轮换是独立事项，本次至少在文档中标注 |
| 双后端导致两份 SQL 分叉 | 长期维护成本 | 方言收敛到单一模块；契约测试双跑；批次库路径不改代码 |
