# 增量画像 · 策略与方案

> 2026-11-09 规划稿（第二版，按「API 画像当底座」结论重写）。
> 本文讲**为什么这么分层、每档各干什么、结论被什么约束住**。实现细节见 `02`，分期见 `03`，验证见 `04`。

---

## 1. 一句话概括

**同一个手机号第二次及以后的画像任务，以 `GET /profile/{phone}` 取回的当前画像为底座，
只对「新进来的客户数据」做推理，其余结论沿用底座。没有新数据就不动，数据多就多改。**

两条硬要求：

| 要求 | 含义 | 怎么保证 |
|---|---|---|
| 前向兼容 | 不受新数据影响的结论必须与上一版逐字一致 | 这些结论进 L2 时是「上一版已定稿事实」，不是重新生成的 |
| 成本节约 | 不重跑完整推理链 | 取证层只看新记录；定级与表达带上一版锚点、有守卫地重跑或跳过 |

---

## 2. 底座从哪来：接口优先，副本补缺

### 2.1 为什么不再维护本地版本链

前一版方案以本地运行留痕为底座。2026-11-09 重新评估后放弃，三条理由：

1. **留痕会消失。** 存储瘦身后 SQLite 只留骨架，`low` 档切片里没有 claims；运行包 30 天清理
   （`TRACE_RETENTION_DAYS=30`）。把业务能力绑在排障数据上，长期不可靠。
2. **销售手工修改是边角场景。** 销售工作繁忙，很少主动改我们给出的 Notes；真要改，通常会顺手
   上锁（`is_locked=1`，后台会保护）。为「改了但不上锁」付出三方比对、归一化、假阳性治理的成本，
   收益不成比例。
3. **不识别它不构成行为回归。** 当前每次全量跑，回写本来就会覆盖未锁定字段；增量沿用同一行为，
   只是不再假装能区分「人工改的」和「我们上次写的」。

**结论：不维护版本链，不做三方比对，不做人工修改识别。** 上一版方案里的滞后读守卫、状态机、
`callback_sent` 基线一并删除。

### 2.2 两种来源与优先级

| 来源 | 内容 | 用途 |
|---|---|---|
| **A. 接口画像** `GET /profile/{phone}` | `basic_notes`（每字段 `value` / `reasoning_summary` / `is_locked` / `ai_feedback`）、`ai_insight`、`purchase_decisions`、`deal_battle`、`decision_psychology`、`main_summary` | **底座主体**；字段有值即以此为准 |
| **B. 回传体副本** | 我们上一次**实际发出**的 `analysis_result`（与根运行 `result1` 逐字节相同） | **只用来补缺**：接口画像里没有的字段/键，用副本补 |

优先级唯一条款：**新增项与已有项以 A 为准；A 缺失的项用 B 补。**

### 2.3 副本为什么必须落骨架

接口返回的证据信息不完整。792 次读回实测：`basic_notes` 每个字段只有上面五个键，
**没有 `steps`、没有 `evidence`、没有 `confidence`**；`ai_insight.purchase_intent_level`
有 `reasoning_detail` 但 616 次里 100 次没有 `evidence`。另外 176/792 次读回完全没有
`ai_insight` 与 `ai_insight.updated_at`（22%），`basic_notes` 可能整个为空。

如果底座只来自 A，那些本轮未被新数据影响的字段回写时只剩一句 `reasoning_summary`，
证据锚点与置信度整体丢失，销售点开「AI 推断原因」会退化——不报错，很难发现。

因此副本 B 是**业务数据**，必须进骨架、不随 trace 清理：

- 存 `profile_baselines` 表，按手机号一行（不是版本链），含：回传体 JSON、已消费记录身份键集合、
  管线兼容键、阶段、上一版等级与推理链、来源 run_id、更新时间。单行约 6–10 KB。
- **不放进 `workflow_runs.outputs_json`**：那列在收尾时会被置空（`finalize_tree` 搬包后清空），
  包 30 天后删除。骨架表不受这条清理影响。

### 2.4 补缺与证据沿用的细则

按字段分三种情形，纯代码判定：

| 情形 | 取值 | 证据 / 置信度 |
|---|---|---|
| A 有值，且与 B 的取值**逐字相同** | A（等于 B） | **沿用 B 的 `steps` / `evidence` / `confidence`**——值没变，说明这条结论没被新数据影响，用当时的证据是准确的 |
| A 有值，与 B 不同（或 B 没有该字段） | **A 为准** | 只有 `reasoning_summary`；置信度取 A 无则留空，不臆造 |
| A **没有该字段** | B | 沿用 B 的全部信息 |

第二种情形是这套方案唯一的质量让步，写清楚在此，不藏在实现里。它发生在「上一版之后接口侧
被别的来源改过」的时刻——多数是人工上锁或人工修改，此时以 A 为准本来就是正确的业务选择。

## 3. 整体形态

```
                 任务（phone, batch_id）
                        │
             ┌──────────▼──────────┐
             │  画像调度（纯代码）    │  读基线（副本 + 已消费键）；拉 history；拉 profile
             │  差分 + 底座组装 + 分档 │  产出：档位 + 新增/改版/移除记录 + 底座事实
             └──────────┬──────────┘
        ┌───────┬───────┼────────┐
        T0      T1       T2       T3
     原样回传  新文本   新录音    全量重建
     0 LLM    L1(新)   转写+L1(新) 现行 pipeline 子运行
                 │        │
                 └────────┘
                      ▼
          底座事实 → claims（0 token，来源标「上一版画像」）
                      ▼
          合并账本（底座 claims + 新 claims）
                      ▼
          L2 投影 / 兜底 / 应用 / 枚举映射 / 审查 / 规则层（现行代码，不改）
                      ▼
          商机定级（带上一版锚点 + 守卫）  L3 表达（事实未变则跳过）
                      ▼
          回传体构造 → 回写 → 基线更新（副本换新、已消费键并入）
```

调度层做成**新的入口工作流**（暂名 `customer_profile_incremental`），现行 `customer_profile_pipeline`
一字不动，作为 T3 的子运行被调用。与录音链路改「变体」同一理由：不动原件，基线可比性与
`definition_hash` 不受影响，回退只改入口常量。

## 4. 分档

判定顺序自上而下，先命中先生效：

| 档 | 判据 | 做什么 | LLM 次数 |
|---|---|---|---|
| **T3 全量重建** | 无基线；基线兼容键不符；**阶段跃迁**（上一版 `lead`、本轮 `opportunity`） | 调用现行 pipeline 子运行；写新基线 | 现行全量（约 6 次 + 录音） |
| **T2 含录音增量** | 新增记录含录音渠道 | 只转写新录音；新记录跑 L1；合并重跑 L2；定级与表达按 §6 | 角色标注 1 + L1 3 + 定级 1 + 表达 0/1 |
| **T1 文本增量** | 新增/改版记录仅文本 | 同上，无转写 | L1 3 + 定级 1 + 表达 0/1 |
| **T0 无变化** | 记录身份键集合无差异 | 副本换 `batch_id` 原样回传 | 0 |

三条说明：

- **「数据少小改、数据多大改」是自然结果**：L1 只看新记录，新记录越多 claims 越多，被推翻的字段越多。
- **T3 只认阶段跃迁一条**（用户拍板 2026-11-09）：「首次出现有实质内容的试驾录音」复用 `level_stage`
  判据；空录音、转写失败不会误触发。锁单、交付若日后成为定级分界，往同一判据里加。
- **调度判定留痕**：档位、各类记录数、补缺字段数、兼容键比对结果，作为运行树里一个代码节点的输出。
  任务侧不带增量语义，销售问「这次为什么没变」只能从这里回答。

### 4.1 兼容键

基线记录 `pipeline_compat_key` = 契约签名 + 规则登记表 ID 集合 + L1 输出 schema 版本 + L3 板块键集合的联合哈希。
不同即 T3。只收「会改变 claims 形状或字段语义」的部分，**提示词措辞调整不进键**——否则每次微调
都让全部客户落 T3，增量形同虚设。

## 5. 记录差分：为什么还要一个小小的「已消费键集合」

底座是接口画像，但「哪些记录是新的」接口没给。有两个可选判据：

1. **`ai_insight.updated_at` 作界**：晚于它的过程资料算新增。310 对相邻运行实测 298 对正确，
   12 对误判且全是**多判**（实际无新记录却判有），没有漏判。但 176/792 次读回没有这个字段（22%），
   且基础渠道的 `update_time` 每次抓取都刷新，会持续误判。
2. **已消费记录的身份键集合**：基线里存一份键集合，本轮 history 与之作差。几百字节到几 KB。

采用 2，理由：它对 22% 无 `updated_at` 的客户照常工作，也不受基础渠道刷新的干扰。键算法：

- 过程资料（跟进、订单、录音、聊天等，带 `source_key`）：`渠道 + source_key + source_version`。
- 基础渠道（`source_key` 为空，每次触发重抓快照）：`渠道 + 去掉 fetched_at 后的内容哈希`。
  直接按 `id` 差分会把 310 对相邻运行**全部**判成「有新增」，这是实测过的坑。
- 键消失视为移除，依赖该记录的结论退场；键出现但内容哈希相同视为无变化。

`GET /batch/{batch_id}` 可作交叉核对，**不作真源**：两次画像之间可能有多个批次，上一次任务也可能失败。

## 6. 三处 LLM 怎么关进笼子

150 案抽样的 token 占比：L1 三层 57%、L3 表达 22%、定级 11%、录音角色标注 6%、兜底 3%。

### 6.1 L1 取证：只看新记录，附「已定稿事实清单」

- 输入包只装新增与改版记录，与现行 `build_l1_input` 同形，差别只在记录筛选。
- 末尾附一份紧凑的已定稿事实清单（字段 → 取值，不含证据与推理）。用途只有一个：新记录与旧事实冲突时，
  模型**明确标出**「本条推翻 `<字段>`」。标注进 claim 的新属性，由 L2 时近性规则消费。
- 定位层、确定性注入照旧跑，只对新 claims。
- **thin/empty 分诊按合并后的全部记录判**，不按增量记录判——否则一条新跟进会把 sufficient 案判成 thin。

### 6.2 L2：合并账本 + 一条新规则簇

L2 现行代码不改，新增两样：

1. **底座 claims（0 token）**：把底座事实逐条转成 claim，来源标「上一版画像」，归「人工/系统登记」档，
   带 `observed_at`（取基线更新时间）。证据沿用 §2.4 的规则。
2. **时近性规则簇 `RECENT-xx`**（code 通道，走现行规则层）：
   - **稳态字段**（基础身份类）：新来的弱信号不得翻掉旧的强事实，沿用现行来源分级与置信档。
   - **进程字段**（预算、意向车型、进度、计划购车时间、情绪、抗性等）：同档来源后到者胜；
     低一档来源若带「推翻」标注且更晚，降置信后仍胜并转 `to_confirm`。
   - 两类归属登记在规则 `scope`；首版清单见 `05` Q2。
3. 旧低置信推断被新事实坐实自然升档，是 L2 跑合并账本的副产品。

### 6.3 商机定级：重跑但带锚点与守卫

- T1/T2 一律重跑那 1 次 LLM，输入多一段「上一版等级与推理链」，要求说明变更依据。
- 代码收口两条守卫：等级变化必须能锚定到本轮新增记录，锚不到就回退上一版并留痕；阶段只能前进不能后退。
- T3 没有锚点，按现行逻辑跑。

### 6.4 L3 表达：事实没变就不写

- 合并后的 `facts` 与底座 `facts`（来自副本）逐字节相同 → 跳过表达，复用副本里的板块文本。
- 有差异 → 全量重写但带锚点：把上一版板块文本给模型，要求「事实未变的板块措辞不改」；
  装配层仍逐条核对引用取值能否在 facts 里找到出处。
- 板块级局部重写放到 P4。

## 7. 已拍板的口径（2026-11-09）

| 事项 | 结论 | 后果 |
|---|---|---|
| 任务侧是否带增量语义 | **不带**，我们自判 | 调度层必须留痕判定依据 |
| 底座 | **`GET /profile` 取回的画像**，API 为准、副本补缺 | §2；不做版本链 |
| 销售静默修改 | **不识别**，作为边角场景接受 | 不做三方比对、不做滞后读守卫；与当前全量行为一致，无回归 |
| 回传体副本 | **落骨架归档**，用于补缺与证据沿用 | §2.3；不随 trace 清理 |
| T0 是否回传 | **要**，副本原样回传换 `batch_id` | 任务闭环 |
| 并发 | 间隔以小时/天计，**不做防护** | 单任务内无状态机，天然无顺序问题 |
| 全量校准触发 | **首次出现试驾录音**（阶段跃迁） | 复用 `level_stage` 判据；定期校准本期不做 |
| 变更信息外传 | **不回传**任何内部字段，也不新增回传键 | 档位、差分只留在运行台 |
| 多行区块人工修改 | 不可手改 | 底座照旧读接口，不额外处理 |

## 8. 与现行设计原则的对照

| 原则（管线设计 §6） | 本方案怎么遵守 |
|---|---|
| 能写成代码的约束不交给模型 | 差分、底座组装、补缺、合并、定级守卫、表达跳过全是代码 |
| 改链路用变体不就地改 | 新入口工作流，现行 pipeline 原样作 T3 子运行 |
| 规则升为一等公民 | 时近性是新规则簇，可单条关闭、有 trace |
| 失败不阻断 | 基线缺失/损坏 → T3；补缺失败 → 用 A 原样；规则守卫失败不阻断 |
| 对客产出真人可读 | 回传体不出现「T1」「claims」「上一版」等内部词 |

## 9. 本期不做

- 不做本地版本链、三方比对、人工修改识别、滞后读守卫。
- 不做任意节点断点续跑。
- 不做跨任务并发防护。
- 不做板块级局部重写（P4）。
- 不做定期全量校准。
- 不改回传契约，不新增回传键。
