# 提交臂切换与「极光数据」卡死修复方案

> 状态：**已收口**（2026-10-16 实施，回归用例 `tests/test_iteration_call_path.py`）｜分支：`dev-business-opt01`

本轮处理两件互相独立的事，合在一份方案里只因为它们是同一次反馈：

1. 「提交任务」页面提交的仍是旧臂，且该臂已无用；
2. 业务测试臂的运行里，「极光数据」节点永远停在「运行中」。

---

## 一、「极光数据」卡在运行中

### 1.1 现象与复现

`4793fef1644d47928f4f55bc49c4d1ef`（业务测试臂，2026-10-16 08:54:36 起）顶层状态
`succeeded`，40 个节点成功，唯独 `pipeline_jiguang`（极光数据）显示「运行中」。

全库同现象共 4 处：本 run 与 `dce58637…` 各 1–2 处，另一处在
`human_corrected_info` 的运行里。

### 1.2 根因

**`_RunRecord.call_path` 被当成跨节点的可变字段，且并发下被兄弟节点读到。**

- `scheduler.py` `_execute_node` 为循环体节点临时改写 `record.call_path`，
  在**整个 await 期间**（含外部调用）保持覆盖值，执行完再还原。
- `record` 是整个运行共用的一份句柄，运行内各节点由 `_execute_graph` 并发投递，
  兄弟节点因此会读到被污染的值。
- `tracker.py` `node_finished` 用 `execution.call_path or run.call_path` 取值。
  顶层节点的 `execution.call_path` 是空串（falsy），于是回落到 `run.call_path`——
  正值污染窗口时，终态就被写进**另一条调用路径**。
- 它自己那条由 `node_started` 写下的行（`call_path=''`，`status=running`）
  此后再无人更新，永久停在「运行中」。

同一机理还制造了两个附带错误：

- 兄弟迭代节点 `pipeline_test_drive_iter` 的终态被写进
  `/iter:pipeline_outbound_iter/0`；
- 嵌套迭代的路径被拼成 `/0/0/iter:X/0/iter:X/0`（覆盖值被当成基路径叠加）。

### 1.3 修法

**把「本次执行的调用路径」从共享句柄上摘下来，改为随执行实例传递。**

1. `_execute_node` 在构造 `NodeExecution` 时即定死 `call_path`，全程不再改写；
2. 该路径通过 `RunRecorder.node_started(run, node, call_path)` 显式传给留痕层，
   不再依赖读 `run.call_path`；
3. `RunTracker.node_finished` 改读 `execution.call_path`，去掉 `or run.call_path`
   这个会静默回落的兜底；
4. 循环体路径由 `ContextVar` 携带（每个 `asyncio.Task` 自带一份上下文副本），
   `run_iteration_body_node` 从它取基路径再拼 `/iter:<id>/<n>`。嵌套随之正确，
   因为内层读到的是外层已定死的路径。

选 `ContextVar` 而不是给 `RunContext` 加字段：`RunContext` 是 `slots=True`，
且顶层节点共用一个上下文实例，往上写同样是共享状态。

**不变的契约**：`call_path` 的取值口径（顶层空串、循环体 `/iter:<id>/<n>`）、
`node_executions` 的唯一键 `(run_id, node_id, call_path)`、`_next_call_path` 的
子运行路径分配，全部不动。

### 1.4 验收

- **A1** 新增回归用例：顶层慢节点与循环体并发时，该节点
  `node_started` 与 `node_finished` 的 `call_path` 相等，且始终为空串。
  修复前该用例必须失败。
- **A2** 既有 `tests/test_iteration*.py`、`tests/test_persistence.py` 全绿。
- **A3** 库内 4 处孤儿行按 1.5 修好，运行详情页不再出现「运行中」。

### 1.5 历史数据修复

孤儿行是**真实执行**的记录，只是终态写错了地方，与错位行成对。修法是合并：
把错位行的终态字段回填到孤儿行、删除错位行。涉及 4 处（`pipeline_jiguang` ×2、
`pipeline_test_drive_iter` ×1、`human_corrected_info` 一个节点 ×1）。

**动手前先整库备份**（`data/customer_profile.db.bak-<日期>`），修复脚本留存可回放。

## 二、提交臂切换

### 2.1 现状

- 「提交任务」写死 `customer_profile_entry`（显示名「客户初始画像」，基线臂）。
- 后端手机号校验也挂在同一个常量上（`api.py` `ENTRY_WORKFLOW_ID`），
  所以只改前端会让校验**静默失效**。

### 2.2 处置

| 项 | 处置 |
|---|---|
| 提交入口 | 前端与后端常量一起改指 `customer_profile_pipeline`（业务测试臂） |
| `customer_profile_entry` | 从 `WORKFLOW_MODULES` 摘除，不再加载、不再出现在 `/workflows`、不可提交、不可跑批 |
| 该臂历史运行 | 连同其子运行树一并清除（先备份） |
| 模块文件 | **保留**，见下 |
| `evidence_subagent` / `profile_features_analysis` | 保留。摘除入口后成为无引用模块，但仍是 AB 基线可复位的前提 |

**为什么不 `git rm` 模块文件**：那会连带删改 4 个测试文件与整份《AB实验》runbook，
且基线臂是《跑批可靠性》里点名的「选错臂」防线的对照物。摘出注册表已达成
「提交与运行面不再出现该臂」，且 `run_baseline.py --workflow-id customer_profile_entry`
会在开跑前的 ID 校验处**立即报错**（正是想要的防错）。需要彻底删除时另行提出。

### 2.3 连带改动

- `scripts/run_baseline.py`：缺省臂改为业务测试臂。原缺省是基线臂，且已被
  《跑批可靠性》记为「漏传参数会整批白烧」的坑；缺省指向当前唯一在用的臂。
  提示文案同步更新，并**保留**显式指定两臂的能力说明（基线臂摘除后跑批需另行恢复）。
- 文档：`runbooks/部署.md`、`experiments/docs/AB实验.md`、`history/跑批可靠性-分析与改进清单.md`
  中「主入口 = customer_profile_entry」的表述同步。
- `changelog.md` 追加一条。

### 2.4 验收

- **B1** 提交页提交后，运行列表出现的工作流是业务测试臂。
- **B2** 手机号校验对业务测试臂仍生效（422 两条用例继续通过）。
- **B3** `/workflows` 不再返回 `customer_profile_entry`。
- **B4** 运行列表中不再有该臂的历史运行；业务测试臂历史不受影响。
- **B5** 后端测试全绿。

## 三、不做什么

- 不删 `evidence_subagent` / `profile_features_analysis` / `customer_profile_production`。
  前两者是基线臂的组成部分，`customer_profile_production` 还被
  `customer_profile_l3` 引用其模板资源。
- 不改任何节点正文、提示词与定义结构。
- 不做「多臂下拉」之类的提交页改造：本轮只切臂。
