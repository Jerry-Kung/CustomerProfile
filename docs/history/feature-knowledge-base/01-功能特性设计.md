# 功能特性设计

## 1. 这套东西提供什么

一句话：**把「我们在卖什么」变成代码能查、模型能读、换伙伴能换的一份资产。**

拆成六个能力，按依赖顺序排列：

| 能力 | 输入 | 输出 | 消费点 | 类型 |
|---|---|---|---|---|
| K1 知识加载与校验 | 知识包目录 | 只读知识目录（进程内缓存） | 全部 | 纯代码 |
| K2 品牌与车型解析 | 任意称谓 | 规范名 + 归属判定 | 取证层、投影层 | 纯代码 |
| K3 取证侧视图 | 知识目录 | 《本方品牌与在售车型》清单 | L1 事实层提示词 | 渲染 |
| K4 表达侧视图 | 知识目录 + 本案 facts | 本案相关的车型简报 | L3 表达层提示词 | 渲染 + 筛选 |
| K5 意向车型闭集与分流 | 断言账本 + 知识目录 | 归属正确的字段 | 投影层 | 纯代码 |
| K6 运行台只读展示 | 知识目录 | `GET /knowledge` + 前端页 | 人 | 接口 + 页面 |
| K7 竞品资料（骨架） | 竞品库目录 + 本案 facts | 客户提到的那几台竞品 | L3 表达层提示词 | 渲染 + 筛选 |

K1 是基础设施。K2 归一，K5 分流——**K5 是本轮业务价值最高的一块**：它把「意向车型」从
开放提取改成闭集选择，同时保证客户提到的非在售车型不会凭空消失。K3、K4 是知识进入
模型的两条路径。K6 只给人看，不参与运行。K7 是第 4 期的骨架：结构与接线已就位，
**内容待业务方提供资料来源**，默认不启用，行为与没有它时逐字节一致。

## 2. K1 · 知识加载与校验

**形态**：`src/customer_profile/knowledge/` 包，进程内单例，首次访问时加载并缓存。
运行期无写接口，也不监听文件变化。内容一旦加载即冻结，与「写入即冻结」一致。

**输入是「知识包」目录**：一个包 = 一个合作方的一组知识。包自带清单 `pack.json`，
声明身份与生效期。加载器只认清单，不扫目录——没有清单的文件不生效，避免往目录丢个
文件就意外上线。

**校验在加载时一次做完，失败即抛**。启动期报错优于运行期静默：

1. 清单必填项齐全；
2. `model_id` 包内唯一；
3. **别名全局唯一**（含 ASR 变体），且不与任何规范名撞车；
4. 清单声明的文件都存在；
5. 价格区间合法、`as_of` 可解析、版本价落在区间内；
6. 表达层三字段非空。

**为什么用 JSON 不用 YAML**：生产依赖 `requirements.txt` 里没有 PyYAML，只有
`scripts/requirements.txt` 有。为读几份知识文件给镜像加一个依赖不值得；JSON 有 stdlib、
有 schema 工具，且条目由脚本生成、人只做复核。

**为什么不复用 `TemplateRepository`**：那个的契约是「正文不可改、改正文即改运行行为、
需评审」；知识包要能整体替换。两种资源的生命周期不同，走两条通道，在渲染时汇合。

## 3. K2 · 品牌与车型解析

三个纯函数，无 IO、可单测：

```
resolve_brand(text)  -> pack_id | competitor_id | None
resolve_model(text)  -> model_id | None
is_our_brand(text)   -> bool
```

**匹配优先级**（命中即停）：规范名精确 → 别名精确 → ASR 变体精确 → 归一化后精确
（去空格、全半角统一、大小写统一）。

**明确不做模糊匹配。** 不做编辑距离、不做子串包含。`坦克700` 与 `坦克500` 子串上互为
包含，模糊匹配会把两台车归成一个。知识库的价值在答得准，不在答得多。未命中返回 `None`，
上层按既有口径处理（L1 照写、投影层不归一）。

**用途**：给 K5 提供「这台车是不是我方在售车型」这一个判断。K3 视图的清单也由此派生。

## 4. K3 · 取证侧视图

**给谁**：L1 事实层提示词。

**给多少**：本方品牌名 + 在售车型规范名与别名。**不给价格、配置、卖点。**
规模约 200–300 字。

理由：L1 的任务是**归类**（意向／对比／自用／试驾），不是讲解。给它配置参数只会诱使它
把参数写进结论，而参数不是客户说的。

**这一份视图同时服务两件事**：归属判断（K5 的事前引导）与意向车型闭集（客户必须在
清单里选）。因此清单必须完整——漏一个别名，就等于让客户说出的合法车型被判成非在售。

**渲染形态**：

```
## 本方品牌与在售车型（用于归属与取值判断，不是事实来源）
本方品牌：东风猛士（别名：猛士）
在售车型：猛士X700（X700）、猛士M817（M817 / 猛士817）、猛士917（917 / M917）
- 意向车型只能从上列在售车型中选；客户提到的其它任何车型都不是意向车型。
- 客户已拥有 / 正在开 / 打算置换的车写 old_car_model，不进意向车型。
```

**与提示词正文的分工**：正文只留「怎么判断」的方法论，不出现具体品牌名。换伙伴只换
知识包，提示词一字不动。

## 5. K4 · 表达侧视图

**给谁**：L3 表达层。**替代**现有的 `product_info` 与 `product_info_short` 两份资产。

**筛选逻辑**：

```
输入：本案 facts
1. intended_model / competing_model / test_driven_models / old_car_model
   逐个 resolve_model，命中本方车型的进「本案相关」
2. 取 facts 的预算区间，把价格带重叠的本方车型补进「参考」
3. 「本案相关」给完整条目（参数 + 卖点 + 场景）
   「参考」只给一行速览（名称 + 价格带 + 一句话定位）
4. 一个都没命中 → 全系速览
```

**产出**：一段 Markdown，作为模板变量 `{{ product_brief }}` 注入。

**为什么按案筛**：当前把约 3000 字无差别塞进去，模型得在长文里自己找该推哪台。
筛后单案预计 300–800 字，候选由代码给定，模型只负责措辞。

**硬边界**：视图里的价格是**知识**不是**事实**。视图文本必须自述这一区别——
可用于说明产品，不得当作客户已表达的偏好写入事实。

## 6. K5 · 意向车型闭集与分流

这是本轮新增的业务核心。目标两条：

1. `intended_model` **只能取在售车型清单里的值**；
2. 客户提到的清单外车型**不得丢弃**，要落到正确的字段上。

### 6.1 为什么需要一个分流，而不只是加一条过滤

若只做「不在清单就剔除」，客户说「我在看坦克700」会得到一个空的意向车型、也没有竞品——
这是把信息弄丢。业务口径要求的是**重新归位**：那台车不是意向车型，但它一定是
**对比车型**或**置换车型**。

分流的前提是一个干净的划分，而知识库恰好给出了它：

| 客户说的车 | 归属 | 依据 |
|---|---|---|
| 本方在售车型 + 客户在考虑 | `intended_model` | 闭集内 |
| 本方在售车型 + 客户已拥有/在开 | `old_car_model` | 自用车优先（既有 §5 口径） |
| 非本方车型 + 拿来比较 | `competing_brand` / `competing_model` | 竞品位 |
| 非本方车型 + 客户已拥有/在开 | `old_car_model` / `owned_brand_model` | 自用车优先 |

**本方车型永不进竞品位，非本方车型永不进意向位。** 两条边界互补，合起来把四类字段
划成互斥的四个格子。

### 6.2 三层落地，各管一段

| 层 | 手段 | 管什么 |
|---|---|---|
| 提示词（K3 视图） | 闭集清单 + 上面那张划分表 | 事前引导。让模型在取证时就按闭集选，减少事后返工 |
| L1 取证 | 不变 | 仍按原文写，包括写法未归一的称谓 |
| L2 投影（K5 本体） | 代码判定 | 事后校正。`intended_model` 的值 `resolve_model` 未命中 → 剔除并尝试分流 |

**代码守最后一道**，理由与枚举映射通道一致：模型给的取值只当建议。

### 6.3 分流的具体规则

对 `intended_model` 的每个取值 `v`：

1. `resolve_model(v)` 命中 → 保留；不命中则继续；
2. 该值同时出现在 `old_car_model` / `owned_brand_model` 里（说明是自用车）→ 从意向位移除；
3. `resolve_brand(v)` 命中本方品牌但型号不认识（如写了个未在售的旧款）→ 从意向位移除，
   记 `to_confirm`「该车型不在当前在售清单内，请确认客户意向」；
4. `resolve_brand(v)` 命中竞品 → 从意向位移除，**并入 `competing_model`**（同值不重复添加）；
5. 完全不认识的称谓 → 从意向位移除，记 `to_confirm`。**不擅自并入竞品位**——
   未知不等于竞品，客户可能说的是自己那台车。

**为什么第 3 条要转确认而不是直接丢**：客户说「我想买个老款 917」，值是真话，只是
不在售。丢掉了销售就看不到这条线索。

**为什么第 5 条不并入竞品**：与既有 L1 提示词的「拿不准就写竞品位」口径不同。
那条针对的是模型抽取时的判断，这里针对的是**代码事后校正**——代码不知道语境，
把未知称谓塞进竞品位等于制造事实。

### 6.4 留痕与开关

整条通道登记为规则 `KB-02`（code 通道），走既有执行器与 `RULES_DISABLED` 开关。
每次剔除/分流记一条 trace，说明原值、去向、原因。没有 trace 的话，
「客户明明说了想买 XX，Notes 里却没有」就无从排查。

### 6.5 已知代价

客户确实在考虑竞品车型时（「我就想买坦克700」），`intended_model` 会为空，
信息落在 `competing_model`。这是业务口径要求的结果，但销售看到的卡片会少一句
「客户想买什么」。**缓解**：L3 表达层可以从 `competing_model` 组织出
「客户目前在对比 X」的表述——表达层的输入有 facts 全量，不需要额外机制。

## 7. K6 · 运行台只读展示

**目的**：让人能回答「当前系统认的在售车型是哪几款、价格对不对」。这是知识库唯一
需要人工肉眼核对的地方——内容写错了不会报错，只会让输出慢慢偏掉。

**接口**：`GET /knowledge`，只读、无参数、进程常量现拼，与 `/rules`、`/standards`
同一定位。

返回形状：

```json
{
  "pack_id": "dfms-mengshi",
  "display_name": "东风猛士",
  "vendor": "东风猛士科技",
  "effective_from": "2026-10-29",
  "content_signature": "sha256:...",
  "brands": [{"canonical": "东风猛士", "aliases": ["猛士"]}],
  "models": [
    {
      "model_id": "dfms-x700",
      "canonical_name": "猛士X700",
      "aliases": ["X700"],
      "series": "X",
      "status": "on_sale",
      "price": {"min_wan": 21.98, "max_wan": 27.98, "as_of": "2026-10-29"},
      "powertrain": ["phev", "erev"],
      "positioning": "...",
      "configs": [{"name": "325KM 后驱 Pro", "price_wan": 21.98, "powertrain": []}],
      "highlights": [{"title": "...", "text": "..."}]
    }
  ],
  "validation": {"ok": true, "checks": [...]}
}
```

`content_signature` 是 `models.json` 的 sha256：**换了知识就要能看出来**，
与批次可比性同一诉求。

`validation.checks` 把加载期跑过的每条校验连同结果一起返回。页面因此能显示
「这份包是校验通过的」而不是「它加载成功了」。

**页面**：运行台新增「知识库」标签页，与「参考标准表」同构——顶部一行摘要
（包名、车型数、生效日、指纹前 8 位），下面按车型分块的只读卡片，
展开看版本表与卖点。

**静态**：不加筛选、不加编辑、不加刷新按钮。要改内容就改文件重启，
页面刷新一次即可。**没有写接口**——这是硬约束，不是暂未实现。

## 8. 替换合作伙伴

动作三步：放入新知识包目录 → 改 `KNOWLEDGE_PACK` 配置 → 重启（加载期校验通过即生效）。

不改：代码、提示词正文、测试。

**配置**：新增 `Settings.knowledge_pack`，缺省 `dfms-mengshi`；可选
`KNOWLEDGE_PACKS_DIR` 供测试注入临时包。

**完整性检查**：加载期额外跑「本方品牌一致性」——提示词正文里若仍出现旧品牌名，
由构建期守卫 `scripts/scan_brand_names.py` 报错，而不是等跑批才发现。

## 9. 与既有机制的边界

| 既有机制 | 本次关系 |
|---|---|
| `TemplateRepository` | 不动。知识走另一条通道，渲染结果作为变量喂进去 |
| 规则层三通道 | K5 登记为 `KB-02` 规则，复用执行器与开关；其余知识解析**不**做成规则。规则层管「违反口径要不要拦」，知识解析管「这东西是什么」 |
| 枚举映射通道 | 复用骨架（关闭即零 token、失败不阻断、代码复核模型输出），不共用开关 |
| `notes_contract` / `internal_fields` | 不动。知识不碰字段定义 |
| 参考标准表 | 不动。它是规则的视图，不是知识的视图 |

## 10. 明确不做的事

- **不做语义检索 / 向量库**。知识规模是「几款车」，不是「几千篇文档」，检索层是纯成本。
- **不做热更新**。内容冻结，改就重启。
- **不做知识版本迁移工具**。换包是全量替换，没有增量合并。
- **不做多包并存路由**。同一时刻只有一个生效包。
- **不自动抽取知识**。原始素材到结构化那一步由人发起单独任务完成，产物经确认才入库。
- **不做过期自动告警**。时效是人的事，只在加载期校验格式。
- **知识页不做编辑**。只读是定论，不是第一版。
- **竞品库不参与归属判定**。`resolve_brand` 仍是唯一的三方归属入口（本方 / 竞品 / 未知）；
  竞品库只提供资料。两处共用词表会让「这个品牌算不算竞品」出现第二个判据。
- **竞品资料不写贬损话术**。条目里的「应对要点」只能基于已登记的事实，不扩展到攻击性表述。
