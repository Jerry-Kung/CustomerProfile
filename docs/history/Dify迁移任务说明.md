# 用户画像工作流：Dify → Python 迁移任务说明

用途：交给 Claude Code 作为项目需求与实施约束。本文是迁移规划，尚未实现或验证目标服务。附件分析仅针对 Dify_dsl_example.yml；完整项目须继续盘点所有入口及递归引用的子工作流。

## 1. 项目目标与边界

将现有 Dify 用户画像项目迁移为独立 Python 服务，以 Python 代码定义工作流，以受控并发调度执行，以持久化记录支持排错，以只读前端查看拓扑与运行详情。迁移完成后运行链路不依赖 Dify、Dify 插件守护进程或 Dify 内部数据库。

优先完成等价迁移，再单独进行性能、提示词和业务逻辑优化。首期只支持实际工作流用到的能力，不开发通用低代码平台、画布编辑器、插件市场或自主 Agent。

原始 DSL 是迁移基线，迁移后的 Python 定义是运行时唯一事实来源。不要长期维护两套业务定义。允许脚本辅助提取模板、节点、连线和代码，但不要求建设通用 YAML 转 Python 编译器，也不在运行时 exec YAML 中的任意代码。

## 2. 已确认的样例事实

| 项目 | 结果 |
|---|---|
| 主图规模 | 41 个节点，55 条连线 |
| 节点分布 | start 1、end 1、template-transform 18、code 7、http-request 2、tool 11、llm 1 |
| 拓扑 | 有向无环图；全部节点从入口可达；存在分叉与多路汇合 |
| 子工作流引用 | 11 个 tool 节点均引用同一个 provider_id，provider_type=workflow |
| 子工作流显示名 | Gemini（异常输出重试版） |
| 工具名 | gemini_retry_2_times；不能根据名称推断实际模型或重试算法 |
| 子工作流入参 | input_prompt 与 output_json；本例 output_json 是字符串 'false' |
| 直接 LLM 节点 | JSON 修复；导出配置的模型名 qwen3.8-flash，temperature=0.7 |
| HTTP | 一个获取 Notes 模板的 GET，一个回写画像的 POST |
| 代码节点 | 7 个均为 Python，仅看到 json/re 标准库导入 |
| 输出 | result1 字段，值为最终 merged_json 的字符串 |
| DSL version | 0.6.0；不能据此确定部署的 Dify 产品版本 |

关键缺口：外部子工作流只有引用和调用参数，未包含其内部图、模型参数、输出契约和异常恢复逻辑。需导出该子工作流，并继续递归检查。主图的 1 个直接 LLM 节点不代表只有 1 次模型调用。

附件 HTTP headers 含明文 X-API-Key。迁移资料应先脱敏，运行时从环境变量读取；真实密钥不得进入 Git、执行日志或前端。若该密钥仍有效，建议轮换。本文没有复制密钥值。

## 3. 还原要求与验收定义

### 3.1 必须保留

- 原节点 ID、标题、类型、边、控制依赖及输入输出映射；Python 函数可起可读名称，但保留 original_node_id。
- 模板文本、换行、变量绑定、消息角色与顺序、模型参数、输出字段和类型。
- 子工作流输入输出契约、调用层级、重试条件、尝试上限及默认值。
- HTTP 方法、路径、请求编码、业务 body、必要 headers 与响应提取方式；鉴权改为环境配置注入。
- 代码节点的确定性逻辑、空值和异常行为；先直接提取为普通 Python 函数，避免迁移时顺手重构。
- 工作流最终 result1 是字符串的现有契约；若要改为对象，必须作为单独 API 版本变更。

图中有一些连接承担执行顺序约束，即使下游未直接消费该节点输出也不能删除。例如“录音类证据提取”前面连接了多个预置节点。还应保留“录音类证据提取”等看似可省略的节点，优化另开变更。

### 3.2 不可误用的“100%”

结构覆盖、接口类型、固定输入下的确定性输出可以严格比较。真实 LLM 调用存在随机性和服务端变化，不能承诺逐字一致。先用固定上游响应回放验证流程等价，再用真实模型验证 JSON 合法率、字段完整度、业务质量、耗时和费用。

未能从 DSL 确认的运行语义必须写入差异清单，并通过实际部署版本或 Dify 执行记录确认。例如 HTTP 非 2xx 是否使节点失败、timeout=0 的含义、retry_interval 的单位及插件默认参数。不得直接将这些数值原样传给 Python HTTP 库。

未经明确决策，不更换模型、不修改提示词、不合并节点、不增加 JSON 修复次数、不更改空值兜底、不调整回写成功判定。

## 4. 推荐技术方案

| 模块 | 首期建议 | 责任 |
|---|---|---|
| API | FastAPI + Pydantic | 入参校验、任务提交与查询、兼容现有调用方 |
| 工作流 | Python 中显式定义节点、依赖和输入绑定 | 唯一可执行定义；可导出给前端 |
| 调度 | asyncio + graphlib 或简单就绪队列 | 依赖检查、并发、超时、取消、状态归档 |
| 外部请求 | 复用 httpx.AsyncClient；按需要封装模型 SDK | 模型/HTTP 适配与统一观测 |
| 模板 | Jinja2 等薄封装 | 对照 Dify 实际渲染；显式定义缺失变量行为 |
| 持久化 | SQLite 开发验证，生产优先既有 MySQL | 任务队列、执行记录、版本与结果 |
| 前端 | React + TypeScript + React Flow，只读 | 图形查看、节点选中、历史运行详情 |
| 部署 | Docker Compose | API、单个执行 worker、数据库；前端构建为静态资源 |

初期不引入 Redis/Celery、Airflow、Temporal 或完整 Agent 框架。若后来出现跨机器调度、长期暂停恢复或大规模多 worker，再单独评估。数据库访问层可用 SQLAlchemy；不必为未用数据库建设复杂适配体系。

生产第一版建议 API 与单个执行 worker 分开，worker 内异步处理多个任务。任务先持久化入队再返回 run_id。不要把耗时画像流程只放在 Web 请求或 FastAPI BackgroundTasks 中。

## 5. 工作流定义与执行

### 5.1 单一来源

每个节点的最小信息为：稳定 ID、显示名、类型、前置节点、输入绑定、执行函数/配置、可选展示坐标。拓扑给调度器和前端共同使用，不能手工再维护一张展示图。原 DSL 的 position 可直接作为第一版布局。

提示词和预置资料可以独立保存为文本资源并受 Git 管理。这仍属于代码项目，不要求将长提示词硬编码进 Python。迁移前后应按 YAML 解析后的字符串比较，注意 CRLF 和末尾换行。

两套变量机制要分别处理：Dify 的 {{#node_id.output#}} 引用以及模板的 {{ variable }} 渲染。不得用通用字符串 replace 粗暴替换全部内容。节点结果按类型保存，JSON 字符串与 JSON 对象不能任意互换。

### 5.2 并发语义

- 对本例无条件 DAG，节点全部直接前置节点成功、输入可用后即可启动。
- 某节点完成就及时释放其下游，不采用全图逐层等待的统一屏障。
- 多前置汇合节点只执行一次；一个分支未完成时不能读取其输出。
- 每个 run 有独立上下文，禁止跨客户共享可变中间结果。
- 同时限制活动任务数、所有任务的实际 LLM/HTTP 请求数，以及模型服务方的 RPM/TPM；并发上限不等于速率限制。
- 子工作流父节点等待期间不占用其内部 LLM 所需的同一信号量，避免父子相互等待。子工作流内部每次真实请求计入统一限额。
- 初期单 worker 可在进程内实现限流。未来扩展多进程时需要共享配额或明确分配，不能每个进程都使用完整“全局”限额。

启动前校验节点 ID 唯一、边合法、无环、入口可达、变量生产者存在及路径有效。若变量引用来源不在已有祖先链中，先报告不一致，不自动加边改变原图。

其他工作流若发现条件、循环或迭代节点，应明确补入范围。条件汇合不能套用“所有前置必须成功”的规则；只为实际出现的控制流实现必要语义。

### 5.3 子工作流

将 gemini_retry_2_times 实现为被多个节点复用的 Python 子工作流定义，不能仅按名称替换成单次模型请求。使用 parent_run_id、parent_node_execution_id 和调用路径区分 11 次调用；同一个静态节点 ID 不足以唯一定位动态执行。

先核对子流程实际模型、调用次数、JSON 校验、重试/修复策略及返回 result 的规则。图中保留父节点；详情可进入子运行，查看内部节点及每次尝试。

## 6. 执行记录

记录从第一版执行器即接入，不能仅使用 print 或日志文件。

| 层级 | 必需内容 |
|---|---|
| 工作流运行 | run_id、业务请求标识、流程版本、输入、最终输出、状态、开始结束时间、耗时、错误 |
| 节点执行 | run_id、节点 ID、调用路径、实际输入输出、状态、排队/执行时间、错误、父子关联 |
| 请求尝试 | attempt_no、实际模型/接口、请求与响应、耗时、错误码、服务方 request_id、token usage |
| 版本快照 | 当次图结构、提示词/配置版本或内容哈希、代码提交标识、依赖锁定信息 |

LLM 记录包括完成变量替换后真正发出的 messages、可见模型输出、解析结果与格式错误。仅保存 prompt 模板或最终合格输出是不够的。只记录 API 实际返回的内容，不要求模型暴露隐藏思维过程。费用缺少计费依据时标记估算；usage 缺失时标记未知，不伪造为 0。

HTTP 记录应保留非敏感请求信息、业务 payload、响应状态/必要响应体。Authorization、X-API-Key 等密钥始终屏蔽。客户个人信息详情按权限展示，列表用脱敏标识，设定保留期、清理和备份策略。大文本可压缩或用持久化内容引用，不能悄悄截断唯一副本。

历史运行图必须按当时版本显示；新版本不能覆盖旧运行中的提示词和结构。静态资源、外部 Notes 模板也要保存当次取用结果，以便回放。

基本状态至少区分排队、运行、成功、失败、取消、阻塞/跳过和中断。节点事件及状态变更需持久化；记录失败时不得假报“完整留痕成功”。

## 7. HTTP 回写、失败与恢复

### 7.1 副作用必须明确

画像生成成功和回写成功是两个事实，分别记录，整体成功要求满足已确认的回写成功条件。HTTP 200 不一定意味着业务成功，应确认回写接口响应协议。当前 end 输出仍是最终 merged_json，并不返回回写响应。

GET 可按确认后的策略重试；POST 的超时可能发生在服务端已完成写入之后，不能直接按“未写入”处理。优先与接收方约定幂等键，同一逻辑回写重试使用同一键；新业务版本生成新键，并防止旧批次晚到覆盖新画像。具体幂等键范围需结合客户、批次、业务版本确定，不能只用手机号。

若接收方不支持幂等或状态查询，不承诺 exactly-once。模糊结果标记为“回写状态待确认”，提供核查/有条件重试；不自动重跑全图。幂等协议属于显式生产加固变更，需列入迁移差异。

### 7.2 重试与失败传播

区别传输重试、模型输出不合格后的重新生成、JSON 修复和人工重跑。为总尝试次数设定明确上限，避免 SDK、HTTP 封装、节点、子工作流多层重试乘法叠加。既有子工作流行为先还原，再讨论统一策略。

对于无恢复路径的关键失败，阻止依赖它的下游及最终回写，保留已完成结果。是否立即取消独立运行分支应根据原系统记录确认；没有证据时将选择明确写入差异表。重试等待不能无限占用有限外部请求名额。

### 7.3 服务重启

已接受任务必须存在数据库。初期可以将进程中断时运行中的任务标记 interrupted，保留结果并提供人工处理，不必立即实现任意节点断点自动续跑。worker 停机、请求取消或客户端断开，并不能证明外部接口未完成副作用。

“回写失败后复用已保存结果重试回写”比全图自动恢复更优先。恢复时需绑定同一结果与工作流版本。新建重跑记录，保留与原运行的关系，不能覆盖旧记录。

## 8. 只读前端范围

1. 工作流结构：缩放、平移、节点点击、查看配置、查看子工作流；初版复用 DSL 坐标。
2. 任务列表：状态、业务标识、开始时间、耗时、错误摘要，支持基本筛选分页。
3. 运行详情：将节点状态叠加到当次版本的图上；点击查看输入输出、实际 messages、错误和重试。
4. 执行顺序：简要时间线或开始结束时间；图表达依赖，不把并发执行伪装成单一线性顺序。

前端构建后为静态文件，由后端或静态服务器托管；运行记录通过只读 API 获取。静态页面并不意味着没有后端数据。首版轮询状态即可，暂不做 WebSocket、在线编辑或拖拽保存。需要独立离线 HTML 报告时可后续新增，不作为主运行台替代品。

## 9. 迁移验证与上线

### 9.1 资料准备

- 各入口实际生产版本 DSL；区分草稿与已发布版本，并记录对应部署版本。
- 递归引用的子工作流；模型实际服务商、模型名、参数及运行时默认值。
- 代表性 Dify 执行记录：真实输入、各节点输入输出、HTTP 读响应、最终结果与失败案例。
- 现有调用方协议：同步/异步、超时、鉴权、字段、错误结构、是否使用流式或任务查询。
- 回写接口成功判定、幂等能力、批次覆盖规则及测试环境。
- 峰值请求率、单任务模型调用数和 tokens、期望时延、配额、留痕保留时间。

缺少子工作流时可以开发通用调度及本地固定响应模式，但必须标记“未完成等价验证”，不能虚构实现。

### 9.2 两类验收

结构与回放：对照所有节点/边/变量映射；固定 LLM 和外部读取响应，检查模板、确定性代码、请求 payload、最终接口是否等价。冻结时间等非确定性因素；JSON 对象可结构比较，JSON 字符串是否字节比较需按现有契约明确。写接口在回放中截获请求，不触达生产。

真实业务验收：用代表性样本比较 JSON 合法率、关键字段、业务质量、错误率、耗时与用量。第一次可取 20–50 条具有代表性的样本作为功能回归起点，不把它当成充分统计证明。样本覆盖信息完整、信息稀少、无录音、格式异常和已知失败。

核心工程验证只覆盖明确风险：多前置汇合、分支无全局屏障、并发限额、多客户上下文隔离、子工作流留痕、失败阻断、回写结果不确定、任务重启中断、历史版本可查看。达到验收条件即收敛，不建设镜像实现式测试或未经要求的极端场景矩阵。

### 9.3 切换步骤

固定响应回放 → 测试环境端到端 → 只生成结果的影子运行 → 少量受控切流 → 完成切换。

影子运行不向生产回写；切流时同一业务请求只有一个权威写入方。保留 Dify 导出、旧记录和回退方式，直到新系统验收完成。回退需要考虑已写入的业务结果，而不只是切换请求路由。

## 10. 里程碑

| 版本 | 聚焦目标 | 可验收成果 |
|---|---|---|
| V0.1 | 迁移盘点 | 所有工作流与递归依赖清单、节点映射、未决差异、脱敏资料；缺失不伪装完成 |
| V0.2 | 最小执行与留痕 | 小型真实拓扑覆盖分叉/汇合/子流程；有限并发、持久化记录、固定响应回放通过 |
| V0.3 | 样例端到端迁移 | 完整 41 节点/55 边及补齐后的子流程；测试接口跑通；逐节点差异与契约回归通过 |

## 11. 给 Claude Code 的执行要求

先完成 V0.1 的盘点并输出具体迁移映射与缺口，再实施执行器与业务迁移。遇到缺失子流程或未知行为时，完成其他不受影响的工作，列出精确缺口；不要根据节点名称、历史猜测或提示词自行补造业务。

始终遵守：

1. 原 DSL 是基线，Python 是迁移后的唯一运行定义；不改原始资料，不提交真实密钥。
2. 保留节点身份、依赖、提示词、类型和子工作流语义；任何有意差异单独说明。
3. 并发依据依赖就绪，不逐层等待；全局请求限额覆盖子工作流。
4. 每个节点和每次外部尝试都有记录；已完成结果持久化，历史版本可追溯。
5. 前端从相同工作流定义获取图，不维护第二份拓扑。
6. 用固定响应验证流程，用真实样本验证模型效果；测试和影子模式禁止生产回写。
7. 不引入未实际需要的重型框架、通用平台、复杂恢复机制和大量极端场景测试。
8. 每个里程碑报告“实现内容、等价证据、已知差异、未完成项、下一步”，满足验收即结束该版本。
