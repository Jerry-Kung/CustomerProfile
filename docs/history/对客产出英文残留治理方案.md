## 3. 根因

三处，彼此独立：

### 3.1 `unknown` 作为非法枚举值进入 facts

L1 在无线索时对枚举字段给 `value = "unknown"`、`basis = inferred_low`
（实测 `payment_method` / `license_plate_status` / `driver_license_status`）。
`unknown` 只在 `knowledge_of_*` / `electronic_ecosystem` 是合法键，其余字段不是。

- `HARD-01` 的占位串表只有中文「未知」，没有英文 `unknown`，拦不住；
- `HARD-02` 判非法枚举，但值已降级为 `inferred_low` 时只记 warning，不拦；
- `_label()` 查不到展示名，原样返回 `unknown`，于是拼进正文。

### 3.2 多值枚举在正文拼接时未逐项翻译

`callback_build._FactView.text()` 走 `_as_text`（`as_display_text`），
对 `power||appearance` 这类多值串按顿号直接连，**没有逐项查展示名**；
只有 `items()` 做了逐项翻译。而 `detail()` 拼「已定稿事实：…」用的是 `text()`。

`customer_profile/readable.py` 的 `readable_value()` 早已正确实现了这条（多值逐项 `_enum_display`），
但 `callback_build` 没有复用它。

### 3.3 编外枚举的展示名存在，但没被走到

`emotion`（`guard_against`→防备强 等）、`personality_and_preferences`、
`communication_rhythm` 在 `INTERNAL_ENUM_SPECS` 里都有中文展示名，
只是同样卡在 3.2 那条路径上。

> 结论：**没有一条缺陷需要模型来判断**。三处都是确定性映射缺失。

## 4. 规则设计

### 4.1 判据：键集合，不是英文正则

核心决定：**用「该字段的合法枚举键」作为唯一判据**，不用「含英文字母」判断。

理由：

- 误伤率为零。品牌名、车型名、技术缩写、等级代号都不是任何字段的枚举键；
- 不依赖需要持续维护的例外词表；
- 展示名映射来自 `internal_fields.display_map()`，与契约同源，不手抄。

英文正则只用于**离线扫描脚本**发现新形态并报告，不进入拦截判据。

### 4.2 登记两条规则

| 编号 | 内容类 | 通道 | 阶段 | 动作 | 判据 |
|---|---|---|---|---|---|
| `EXPR-01` | hard | code | gate | rewrite | 正文中出现的**合法枚举键**→ 替换为该字段的中文展示名 |
| `EXPR-03` | hard | code | gate | reject / rewrite | 枚举字段取值是**非法英文占位串**（`unknown` 等）：该条 Notes 整条删除；facts 侧归一为缺失 |
| `EXPR-01` | — | prompt | extract / express | annotate | 提示词正文：对客文字一律中文，枚举只填键、正文不出现键 |
| `EXPR-01` | — | llm_checker | express | annotate | 二期：语义层判「是否还有英文表述」，只出报告不拦 |

`EXPR-02` 已存在（证据位不得出现结论型措辞），编号顺延不复用。
`EXPR-03` 与 `HARD-01` 的分工：`HARD-01` 管中文占位串，`EXPR-03` 管英文占位串，
两者共用同一张表（§4.3）。

**`attribute_value` 不在作用范围内**——那是契约枚举键，见 §7 待拍板 1。

### 4.3 占位串表合并

把 `unknown` / `n/a` / `none` / `null` 并入 `hard.PLACEHOLDER_VALUES`，
但判据加一道前置：**该取值是本字段的合法枚举键时，不当作占位串**。
否则 `knowledge_of_mengshi = unknown`（合法，「未知」）会被误删。

### 4.4 动作语义

- 合法键 → `rewrite`（确定性映射，0 token，不改置信档）；
- 非法占位串 → `reject`（Notes 条目整条删除，同 `HARD-01`）；
  同时 `target=field` 把 facts 里的该值清掉，避免下游 `callback_build` 再拼出 `unknown`；
- 映射不到、又不是占位串的英文串 → 不拦，只记 trace（`annotate`），交人工核读。
  **宁可漏一个，不误删一条**。这正是白名单能安全成立的前提。

### 4.5 落点

| 规则 | 代码落点 | 说明 |
|---|---|---|
| `EXPR-01` 正文替换 | `rules/clusters/expression.py` 新增 `check_prose_keys()`，接入 `customer_profile_pipeline.review_notes`（gate 段） | 复用已有的 `rules.apply` 与 `RuleTrace` |
| `EXPR-01` 提示词 | `rules/texts/expression.txt`（新文件），经 `rules.render` 渲染进 L1《目标字段清单》之后与 L3 表达指令 | 与 `SPEC-*` 同一机制 |
| `EXPR-03` 占位串 | `rules/clusters/hard.py` 的 `check_notes()`（与 `HARD-01` 同函数，加分支） | 判据共享，避免第二份表 |

### 4.6 上游根因修复（与规则并行，互不替代）

| 位置 | 改动 |
|---|---|
| `callback_build._FactView.text()` | 多值字段改走逐项翻译（复用 `readable.readable_value`），不再直接连英文键 |
| `readable.readable_value()` | 已是正确实现，本次只做 `callback_build` 侧接入 |

> 规则是兜底，根因修复让规则大多数时候无事可做。
> 只做规则不做修复，trace 里会长期挂着同一条规则的命中，等于把缺陷固化成了常态。

## 7. 已拍板的口径（2026-10-27）

| 事项 | 决定 |
|---|---|
| `attribute_value` 里的英文枚举键 | **保留**。契约 `field_type=enum` 的设计：键供回写与前端 `display_name` 映射。本次只治理正文文字，`attribute_value` 不进作用范围 |

由此锁定的两条设计后果：

- 英文残留的判据**只能是「是不是某个字段的合法枚举键」**。一旦改为「出现英文字母就拦」，
  与「保留 to B / max版」直接冲突。这条决定了 §4.1 不是取舍而是唯一可行解。
- 前端若仍在页面上显示 `unmarried_no_child` 这类**现行合法键**，那是前端未做键→展示名映射，
  **不在本次范围内**。验收时只对正文（`summary` / `steps` / `evidence` / `label`）判定。
  > **2026-10-27 补充**：`unmarried` / `replacement` / `commute` 不是本方案说的形态，而是
  > **已废弃的枚举键**——它们在现行契约里没有展示名可映射。那类由
  > `docs/history/旧版枚举键与production臂整改方案.md` 处置（归一层别名 + `ENUM-01` 剔除）。
