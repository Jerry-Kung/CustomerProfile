# Customer Profile V0.5 工作台任务触发入口（设计）

> 版本：V0.5　状态：v0.5.1 已实现（2026-09-24）
> 依据：用户 2026-09-24 需求、`docs/specs/V0.4只读运行台.md`、`ledger/differences.md`。
> 上游缺口：迁移规划 §3 里 V0.5 原定的「生产运行保障」本次**后移**，见 differences W19。

## 1. 目标与范围

在 V0.4 只读运行台上增加**任务触发入口**：在运行台输入 `phone_number` 提交任务，
就地观察完整的运行过程与结果。

**明确不做**（用户 2026-09-24 确认）：持久化队列、独立 worker、影子运行模式、幂等回写、
SSE/WebSocket、登录鉴权。

## 2. 现状：缺口比「加一个入口」小

需求听上去是「新增提交能力」，但盘点后只有两处真缺口：

| 能力 | 现状 |
|---|---|
| 提交端点 | **已存在**（`POST /runs`，V0.2 起）。V0.4 明确「不改动」它，不是删除 |
| 先落库再返回 run_id | **已满足**（`Service.wait_until_recorded`） |
| 过程与结果展示 | **已具备**（`/runs/{id}/graph` + 节点尝试 + 子运行下钻 + 时间线） |
| 提交后跳详情并轮询 | **已具备**（`RunDetail` 运行中 2s 轮询，终态即停） |
| 前端提交能力 | **缺**：`api/client.ts` 只有 `getJson`，无任何写方法 |
| 并发闸门 | **缺**：`MAX_ACTIVE_RUNS` 只声明、**无读取方**（见 §3.1） |

因此本次**不新增提交端点**，只补前端写路径与一个后端闸门。

## 3. 关键设计决策

### 3.1 `MAX_ACTIVE_RUNS` 由死配置改为生效，满则拒绝而非排队

此前 `Settings.max_active_runs` 只在 `settings.py` 声明、`.env.example` 写了语义，
但全仓**无任何读取方**——唯一真正生效的并发限制是 `Scheduler._active_slot`
（`MAX_ACTIVE_NODES`，限制**一次运行内部**同时执行的节点数）。工作台一开提交入口，
重复提交就会堆叠真实模型调用。

新实现（`runner.py` 的 `RunSlotGate`）：

- 放在**服务层**而非路由层：并发上限属「一次进程能承受多少」，与 HTTP 形态无关，
  这样对 CLI 与 API 同样生效。
- **满则抛 `RunSlotUnavailable`，由 API 翻成 HTTP 429**，不排队。排队会让调用方拿到
  `run_id` 却迟迟不开始，看上去像提交失败；拒绝是可解释的即时反馈。
- **用计数器而非 `asyncio.Semaphore`**：这里的申请严格非阻塞（满了立刻抛，从不等待），
  而 `Semaphore` 没有非阻塞 `acquire`，用它就得动 `_value` 私有属性。不需要排队时，
  一个整数就够。
- **子运行不占名额**：它们由 `SubWorkflowRunner` 直接调 `Scheduler.run`，不走 `Service.submit`。
  主入口一次会扇出十几个子运行，若子运行也申请名额，上限一低就自锁。
- `MAX_ACTIVE_RUNS=` 空串按「未设置」处理（既有 `_blank_means_unset` 校验器），此时不装闸门。

### 3.2 手机号在提交前校验，且只对主入口

此前**没有任何前端校验**：`start` 节点的必填性在执行期才由 `execute_start` 检查，
于是少传或传错手机号会变成一个**失败的运行**，而不是可解释的 4xx。

- 正则与 `scripts/smoke_run.py` 的脱敏正则同一形状，此处锚定整串：`^1[3-9]\d{9}$`。
- **只对 `customer_profile_entry` 生效**：其它工作流（录音类要 `customer_data` /
  `data_source`）入参契约不同，一并约束会挡掉它们的合法调用。
- 理由不只是「格式好看」：手机号会进 `business_ref` 与多个下游 HTTP 路径
  （`/data/history/{phone}`、`/data/profile/{phone}`），空串或带斜杠的值会在外部服务上
  变成难以归因的 404。

### 3.3 提交后跳详情页，不就地显示进度

`RunDetail` 已能表达过程（依赖图 + 时间线 + 每次尝试）且支持子运行下钻。另做一套
「提交后就地看进度」的简化视图等于维护第二份展示逻辑，还看不到下钻。

主入口一次真实运行实测约 **1282 s**（`ledger/v0.3_smoke_report.md`），轮询会持续
二十余分钟——这进一步支持「跳详情页」而非「留在表单页看状态」。

### 3.4 「没有回写」必须在界面上可见

`WRITEBACK_ENABLED=false`（差异 W10）时，回写节点只产出「已跳过」的可解释结果，
**而运行仍显示 succeeded**。因此新增只读端点 `GET /runtime`，报出
`writeback_enabled` / `replay_mode` / `llm_model` / 并发上限，前端在提交页显著标出
「回写已关闭（不回写生产库）」。

不加这个端点，界面上「成功」会被读成「已写进生产库」——而实际上没有任何生产副作用。
这正是 `smoke_run.py` 在报告里显式记 `writeback_enabled` 的理由，只是那份记录在 CLI 里，
运行台上看不到。

**该端点不返回任何凭据**：只报配置项，三个 API Key 一律不出现（由测试断言）。

### 3.5 `business_ref` 取手机号

列表页有「业务标识」筛选；子运行会从 `inputs["phone_number"]` 自动派生 `business_ref`
（`subworkflow.py`）。父运行若不设，列表里父运行显示 `—` 而子运行带着号码，检索会漏掉父运行。

## 4. API 增量

| 端点 | 变化 |
|---|---|
| `GET /runtime` | **新增**（只读）：回放模式、回写开关、模型名、并发上限与占用 |
| `POST /runs` | **行为变化**：新增主入口手机号校验（422）与并发满拒绝（429）。**入参形状与成功返回值不变** |

对外契约（`result1` 为字符串、异步提交返回 run_id）不变。

## 5. 前端增量

| 文件 | 变化 |
|---|---|
| `api/client.ts` | 新增 `postJson`、`submitRun`、`runtime`，类型 `SubmitResult` / `RuntimeInfo` |
| `components/SubmitRun.tsx` | **新增**：手机号 + 批次号表单，提交中禁用按钮，错误就地显示 |
| `App.tsx` | 新增「提交任务」标签页；提交成功后 `setRunStack([runId])` 并切到任务列表页 |
| `index.css` | 提交表单与运行态面板样式，沿用既有 token |

**提交中禁用按钮**：真实运行约二十一分钟，重复点击会堆叠真实模型调用（后端会以 429 拒绝
后来者，但禁用是最容易做对的一道闸门）。
