# 规则层设计

> 定位：把「规则」从散落在提示词、代码、审查层三处的句子，升为有身份、有通道、有留痕的一等公民。
> 不含字段级实现；状态机、具体函数签名留给施工计划。
> 上游蓝图见 `下一轮架构蓝图.md` §4.1。

---

## 1. 真问题

不是「规则多」，是**规则没有身份**。

同一条收入规则现在有三个落点：极光取数节点里换算、投影层里兜底、L1 提示词里补一句「不得自行换算」。
三个地方都不知道彼此存在。判断一条规则是否生效、是否失效、是否互相打架，目前只能靠全批人工核读。

规则层要交付三件事：

1. **一处登记**：一条规则只有一个定义处，提示词片段与校验函数从它派生。
2. **一处留痕**：每次规则触发都记录「哪条、对哪个字段、改了什么、为什么」。
3. **一处关闭**：单条规则可灰度、可回滚，不必回滚整批提示词。

## 2. 先修正分类：内容类 × 执行通道是两维

你给的三类是**规则内容**的分类，很准。但「固定约束大多能转写代码、金标准更适合放提示词」这个对应关系只对了一半——真正的维度有两个：

| 内容类 | 说明 | 由谁执行 |
|---|---|---|
| A 硬约束 | 输出形态、取值合法性、身份归属 | 几乎全部代码 |
| B 金标准 | 某字段该怎么填、参考哪些源、怎么写证据 | 提示词为主，代码兜底 |
| C 一致性 | 字段间、产品间、事实与表达间的矛盾 | **两档**：可判定→代码；不可判定→LLM 检查 |

反例说明为什么不能一一对应：

- **「职业↔收入量级」看起来是 C 类，实际只能交给 LLM 判断**。职业种类以万计，且同一职业的收入方差可以跨两个数量级（软件开发从几万到几百万）。建一张「职业 → 合理收入区间」的先验表，代价远超它带来的收益，且表一过时就会稳定地判错。这类**开放集合、高方差**的判断，正确形态是 checker 通道：让模型带着规则描述去看两个字段是否自洽，判不出就留白。
- **「不要直接把意向车型的价格当成预算区间」看起来是 B 类（金标准），实际可以代码判**——因为意向车型是个**封闭集合**，知识库里已经有一份车型价格数据，直接比对即可，不需要新建任何东西。
- **「不写英文表达」是 A 类，但代码判不全**：`Model Y`、`BMW`、`OTA` 都是合法英文。纯正则必误伤，需要一份**例外词表**——但这是几行人工补的词，不是一份需要持续维护的业务白名单。
- **「联系客服电话直填手机号」是 A 类，代码可判**，因为它读的是我们自己产生的入参，不是外部世界。

四类例子的区分不取决于「能不能写成 if」，而取决于**判断所需的知识是不是我们已经拥有的、封闭的**。知识是封闭的（车型价、入参、我们在用的枚举）→ 代码。知识是开放的（职业收入分布、常识合理性、语义矛盾）→ LLM。

所以规则记录里，**内容类**与**执行通道**必须分开存：

```
content_kind:  hard | spec | consistency      规则说什么
channel:       code | prompt | llm_checker      谁来执行
```

一条 C 类规则可以同时挂多个通道：例如「预算与意向车型价格矛盾」既可以在知识库命中车型价时由代码直判，也可以在没命中时交给 checker。这不是重复，是同一个定义的两个投影——正是规则层要提供的能力。

### 2.1 建表还是交给 LLM：一条明确的判据

**默认交给 LLM。只有在同时满足下面三条时，才为规则建白名单 / 先验表：**

1. **集合是封闭且我们拥有的**：枚举键、契约字段名、内部字段键、我们自己产生的入参。这些本来就存在，不是为规则新建的。
2. **建表成本低于它替代的 LLM 调用成本**：几十行的词表换掉每案一次调用，划算；需要业务专家持续维护的职业收入分布，不划算。
3. **表不会因为外部世界变化而迅速失真**：车型价格表相对稳定；职业收入分布随经济周期漂移。

任何一条不满足，就走 `prompt` 或 `llm_checker`。**规则层不承担「把世界整理成表」的职责**——那是把建模成本转嫁给业务方；而且转嫁出去之后，没人能保证那张表是对的。而「稳定地、静默地把错的东西当成对的」，恰恰是规则层最该避免的失败形态。

## 3. 规则的最小身份

每条规则是一条记录，至少含这些字段（概念层，不是最终字段名）：

```
id            稳定编号，如 INCOME-01 / EXPR-03。测试、日志、核读清单都引用它
version       规则版本。改条件或改阈值即升版，便于"这条规则什么时候开始生效的"
title         一句话，人能读
content_kind  hard | spec | consistency
channel       code | prompt | llm_checker（可多值）
scope         作用字段：[annual_income] / 字段簇 [income_cluster] / 全局 *
stage         生效阶段：extract（取证前给口径）/ project（投影时校验）/ express（成文后）/ gate（出闸前最终守门）
when          条件。code 通道是 Python 谓词；prompt 通道是自然语言条件；checker 通道是"失效模式"描述
then          动作：reject / downgrade / rewrite / require_confirm / annotate / refuse
severity      block（拦）/ repair（修）/ warn（只记）
message       对内解释（进 rule_trace）与对客解释（进 reasoning_detail 或 to_confirm）分开写
owner         业务方 / 工程 / 双方。金标准类规则的正文由业务专家出，工程只负责编码
status        proposed | active | deprecated
tests         必填：至少一条正例、一条反例。没有测试的规则不允许 active
```

**为什么 `stage` 和 `channel` 要分开**：同一条 A 类规则可能既要在 `project` 阶段拦（值不合法），又要在 `gate` 阶段做最后一道检查（表达层可能又写脏了）。分期执行是常态。

## 4. 三条执行通道

### 4.1 code 通道：确定性守卫

适用：A 类全部；C 类里能写成谓词的部分。

执行时机：投影层（字段级）、装配前（跨产物）、出闸前（final gate）。

形态：普通 Python 函数，输入是 `facts` + `basis` + `records` 摘要，输出是**动作列表**而不是直接改 `facts`：

```
[{"rule": "INCOME-01", "attribute": "annual_income",
  "action": "downgrade", "reason": "职业为网约车司机（fact），年收入 30-50 万超出该职业常见区间",
  "to_confirm": "确认客户是否有第二收入来源"}]
```

由统一的执行器按优先级应用动作。**规则自己不改状态**——这是保证动作可排序、可留痕、可回放的前提。

### 4.2 prompt 通道：金标准注入

适用：B 类全部；C 类里「只有提示词能推」的部分（例如从职业推收入方向）。

执行时机：**两个注入点**，不是一处：

| 注入点 | 注入什么 | 目的 |
|---|---|---|
| L1 取证输入 | 字段的取证口径、来源方向、反例 | 让模型一开始就别从错的地方找 |
| L3 表达输入 | 字段之间该怎么组织、哪些话不能说、示例 | 让模型写得好，而不只是没写错 |

现状里 `notes_contract.description` 与 `FIELD_SOURCE_NOTES` 已经在做第一件事，但它们是两份并列的散表，且只覆盖了部分字段。规则层应**接管 `FIELD_SOURCE_NOTES`**，把它降级为规则表的一个渲染视图。

关键约束：**提示词片段一律由规则表按 scope 渲染生成，不允许在模板正文里再手写一遍业务规则**。模板正文只保留「角色、任务、输出格式」这类结构性内容。否则又回到三处漂移。

> 这会改变现有工作纪律：`src/customer_profile/templates/README.md` 写的「正文默认不可改」仍然成立，但**新规则一律进规则表、不进模板正文**。模板正文随规则迁移逐段变薄。

### 4.3 llm_checker 通道：失效模式检查

适用：C 类里判不出谓词的部分——语义层面的矛盾、常识层面的不合理、表达层面的失真。

形态：一次结构化调用，输入是「可读化 facts + 待检规则清单 + 相关原文摘录」，输出是逐条的判决：

```
[{"rule": "INCOME-01", "fields": ["occupation", "annual_income"],
  "verdict": "contradiction", "explain": "...", "proposed_action": "downgrade"}]
```

**只要判决，不要新值。** 修复由统一执行器按动作处理；只有「需要重新生成一段措辞」时才起第二次调用（例如沟通策略复读，那是重写，不是裁决）。

四条硬边界：

1. 输入只能是**可读化后的事实**（`readable.py` 已有），不得让 checker 看见内部字段键。
2. 输出必须过代码复核：动作合法、字段存在、不得新增字段值、不得把 `fact` 降成 `inferred_low` 以外的任何改写。
3. 判决必须带 `rule` 编号，否则丢弃——没有编号的判决无法统计、无法回归。
4. 未命中的规则不得出现在输出里，也不得在输入里塞全部规则清单（见 §6 分组）。

## 5. 对你两个提议的评估

### 5.1 派生校验字段：思路对，但要和「编外字段」分开

「设一个『职业年收入』字段，只从职业推，再和年收入比对」——这个做法成立，而且比 LLM 直接比对更稳：它把「推导」和「比对」拆成两步，推导结果可以单独核读。

但要澄清一件事：**它不是编外字段**。现在的编外字段（`old_car_model`、`company`）是**取证产物**——要回原文找、要带锚点、要进 `facts`、能喂给回传区块。派生校验字段是**校验中间产物**——不问原文、不带锚点、不进 `facts`、跑完即弃。两者生命周期完全不同，混在一张表里会让「编外字段是否要取证」这个问题变得无解。

建议分两张登记表：

| | 编外字段 | 派生校验字段 |
|---|---|---|
| 来源 | L1 从原文取证 | 代码或窄 LLM 从已有 facts 推导 |
| 进 facts | 是 | 否（只进校验上下文） |
| 回传 | 否 | 否 |
| 生命周期 | 全流程 | 投影期一次性 |
| 例子 | `company` / `purchase_nature` | `occupation_implied_income` |

> `occupation_implied_income` 只作例子说明形态，不作为必须落地项。它相对「直接让 checker 比对职业与收入」的额外价值在于推导结果可单独核读；如果实现成本高于这个收益，就该直接由 `INCOME-01` 在一次 checker 调用里完成，不引入派生字段。

三条防自证规则：

- 派生字段的输入**只能读被推导的源字段**（职业），不能读目标字段（年收入），否则就是循环论证。
- 派生字段的产出必须标 `derived`，且**不得**被当作证据写进 `reasoning_detail`——它只是检查器，不是结论。
- 推导方式**默认交给 LLM**：派生字段本身就是「用模型的世界知识做一次窄推断」，这正是模型擅长的。不要求为它建职业收入分布表——那是不可能的任务。只有当某个派生关系是封闭的（如「档位 N → 金额区间」这种我们自己定义的映射）才走代码。
- 派生结果**只在本次运行内有效，不沉淀、不缓存**。它是一次性检查器，不是新知识。

### 5.2 LLM + 失效模式：成立，但不要「一次统一判断」

把「XX 与 YY 可能发生类似 XXX 的矛盾」写成失效模式、批量交给模型核查，这个方向对。它对的是当前最贵的一类缺陷：**模型自己不会主动发现矛盾**（审核报告里「事实层与卡片层互相打架」「弱信号被写成确定事实」都是这一类）。

但「所有失效模式一次统一判断」有三个具体问题：

1. **规则一多，单次上下文就变成第二个 L1 爆点**。200 条失效模式塞进一次调用，模型注意力被摊薄，判决质量会随规则数下降——而且下降是静默的。
2. **无法定位归因**。一次调用判出 3 条矛盾，其中哪条是模型真发现的、哪条是它顺着规则清单编的，分不清。规则级命中率统计随之失效。
3. **无法做规则级回归**。新增一条规则，你不知道是它生效了还是干扰了别的规则。

修正方案：**按字段簇分组，每簇一次检查**。

```
收入簇：occupation / annual_income / industry / purpose
车辆簇：intended_model / competing_* / old_car_model / budget
家庭簇：marital_status / children / seating_requirement / primary_driver
时间簇：planned_purchase_time / deal_level / follow_up_frequency
表达簇：communication_strategies / evidence 可读性 / 内部字段名
```

每簇 5–15 条规则，单次输入可控。规则增长时是**簇内增加**，不是全局膨胀。什么时候可以合并成一次：当某簇规则数 ≤5 且输入事实 ≤20 条时可以合并，否则拆开。

**成本闸门：只排除结构上不可能有矛盾的，不做语义粗筛。** 代码层只做极便宜的排除（两字段有一为空、值不是合法枚举、来源同为登记档等），剩下的全部交 LLM。**不要试图用代码先做一轮「疑似矛盾」的语义筛选**——那等于在代码里重写一遍 checker，而且会用更差的信息做同样的判断。checker 的调用次数应当与「簇内有几个相关字段非空」相关，这是确定的、可预算的。

## 6. 字段簇是规则的组织单位

这条是从「规则会到几百条」倒推出来的，不这么组织撑不住。

- 规则按字段簇归属，簇是**检查、渲染、统计、回归**的默认粒度。
- 一个簇 = 一组规则 + 一个代码守卫 + 可选一个 checker 提示词 + 一组测试。
- 新增字段：先归属一个簇；新开簇必须说明为什么不能并进现有簇。

好处很具体：

- 核读清单按簇出（「本批收入簇触发 4 次，请核读这 4 案」），而不是整批。
- 规则失效可按簇定位（收入簇命中率跌到 0 → 多半是上游字段改名了）。
- 提示词注入按簇组装，L1/L3 的输入长度可预测。

## 7. 动作语义与冲突仲裁

### 7.1 动作

| 动作 | 语义 | 用在哪 | 与既有口径的关系 |
|---|---|---|---|
| `reject` | 删掉这条字段 | 硬约束违规、占位串 | 与 `review_notes` 的占位清除同 |
| `downgrade` | 保留值、降置信、转人工 | 合理性不成立、证据不足 | 与「定位失败降级不丢」同口径 |
| `rewrite` | 改成另一个值 | 只在有确定性依据时（如档位→金额区间） | 需 `basis` 降档 |
| `require_confirm` | 不动值、进 `to_confirm` | 两值都好、拿不准 | 与现有 `to_confirm` 同 |
| `annotate` | 只加一条说明 | 对客可读的解释 | 进 `reasoning_detail` |

**默认动作是 `downgrade` 或 `require_confirm`，不是 `reject`。** 这条与项目既有原则一致：丢弃是掉字段的主因。只有契约形态错误（非法枚举、占位串、内部字段名）才 `reject`。

### 7.2 优先级

同一字段被多条规则命中时，按顺序应用：

```
硬约束 > 一致性 > 合理性 > 表达
同层：字段级 scope > 簇级 > 全局
同级：按 rule id 稳定排序（保证可复现）
```

### 7.3 收敛

规则应用后必须复查是否产生新违规（例如 A 规则降级后，B 规则的输入条件变了）。最多迭代 N 轮（建议 3），达到上限即停止并记 `unstable`。**不做无限收敛**——真实系统里不收敛通常意味着两条规则互相打架，那是人的问题，不该由运行时硬转。

## 8. 留痕与可观测

每次运行产出一份 `rule_trace`：

```
rule_id / stage / attribute / before / after / action / severity / reason / source
```

三个用途：

1. **核读清单**：只核读「命中某规则」的字段，而不是整批。
2. **增量更新**：新证据进来时，知道「这个值上次是被哪条规则改的」，判断要不要重判。
3. **规则治理**：按批次统计每条规则的命中率与动作分布。**连续三批命中率为 0 的 `active` 规则，进入待退役清单**——规则层最大的退化方式不是写错，是没人知道它已经失效了。

对客产出（Notes、画像卡）：**规则 id 与内部解释一律不下发**。对客只看到「结论 + 依据 + 需要您确认的地方」，这是 `docs/README.md` 已定的硬约束。规则层的 message 字段因此要写两份：对内（可带 id）、对客（不得带）。

## 9. 规则落点标记：让规则可被「整体摘除」

规则层的前提是「一处登记」，但真实落地时，一条规则的正文必然**同时落在几处**：代码守卫、提示词片段、测试、枚举/词表。问题不在于分散，而在于**分散了却看不出来**——半年后有人要改「收入标签只认收入」这条，得靠记忆去翻 `income_band.py`、`projection.py` 和一个模板文件。漏掉任何一处，就是「规则改了一半」。

因此定一条硬契约：**规则落到代码或提示词里时，落点必须带规则编号**。

### 9.1 标记形态

按落点形态分三种，都用**可被工具检索的固定前缀**，不用自由措辞：

| 落点 | 形态 | 示例 |
|---|---|---|
| Python 代码块 | 注释行 + 编号，紧挨被约束的行 | `# rule: INCOME-01 收入字段只认「预测收入水平」标签` |
| 提示词正文 | HTML 注释包裹整段，模板渲染时不可见 | `<!-- rule: INCOME-01 begin --> … <!-- rule: INCOME-01 end -->` |
| 数据表 / 词表 | 条目级注释或并行登记键 | `{"tag": "预测手机价格", "rule": "INCOME-01", ...}` |

三条约束：

1. **一个落点只挂一个 primary 规则编号**。一条规则落到多处是正常的；一处落点被两条规则共用，说明这两条规则该拆。
2. **编号必须与规则登记表里的 id 逐字一致**。不一致即为漂移，由 §9.3 的检索守卫检出。
3. **提示词用成对标记包裹整段，而不是行内标注**。改规则时要能整段删掉，行内标注做不到这一点。

### 9.2 「删一条规则」的操作步骤

标记存在之后，摘除一条规则应当是机械动作，不需要理解上下文：

```
1. 按编号全局检索 → 得到落点清单（代码 / 提示词 / 测试 / 词表）
2. 逐处删除标记包裹的代码块或提示词段
3. 删掉登记表条目与该规则的正反例测试
4. 跑全量测试；删干净则绿，漏删则 §9.3 的守卫报出孤儿标记
5. 跑一个小批次确认没有别的规则接替了它的行为
```

**关键在第四步**：漏删时守卫必须**报错**，而不是安静地通过。孤儿标记（标记还在、登记表里没这条规则）和不详标记（登记表有、检索不到落点）都是错误，不是警告。

### 9.3 检索守卫

两条静态检查，进测试集，零 token：

- **孤儿标记**：代码/提示词里出现的每个 `rule:` 编号，必须在登记表中存在且 `status=active`。规则退役后残留标记即红。
- **未落地规则**：登记表里每个 `active` 规则，必须至少检索到一处落点。只登记不落地的规则即红——这条能挡住「文档里写了、代码里没做」的典型漂移。

守卫只做「编号存在性」检查，不做语义检查。语义是否一致仍靠测试与核读，但**位置的完整性可以完全机器保证**，这已经覆盖了「改规则时漏改一处」这一类事故的绝大部分。

### 9.4 与现有工作纪律的关系

- 模板正文「不可随意修改」的纪律不变；但**带规则标记的段落在改对应规则时允许修改**，改动范围以标记边界为准，边界外不动。
- 迁移期允许先标后迁：新增标记是零风险动作，可以在规则尚未搬进登记表前先打标，把散落点摸清楚。摸清之后再决定哪些迁走、哪些就地保留。

## 11. 首批规则建议

按「已确认缺陷 × 实现成本」选，六条：

| id | 内容类 | 通道 | 对应的已知缺陷 |
|---|---|---|---|
| `INCOME-01` | consistency | checker（+ 派生字段，可选） | 网约车司机 30–50 万 |
| `SPEC-01` | spec | prompt + checker | 预算优先参考收入/消费而非车型价 |
| `EXPR-01` | hard | code（例外词表） | 英文表达误伤 / 内部字段名 |
| `CONSIST-02` | consistency | checker | 事实层与卡片层互相打架 |
| `MISS-01` | spec | prompt + checker | 地域/距离/语言被丢弃 |
| `PROD-01` | hard + spec | code（知识库命中）+ prompt | 产品参数由模型编造 |

`INCOME-01` 的完整形态可以当**样板**：一条失效模式描述（「职业与年收入可能明显不自洽，例如网约车司机与 30–50 万年收入」）交给 checker，命中后默认 `downgrade` + `require_confirm`，不删值。**不建职业收入表**——那张表的维护成本与失真风险都高于一次额外调用。这条规则示范的是「开放知识交给 LLM」这条主路径，而不是「三种通道协作」。

## 12. 验收与成本

### 12.1 验收指标（按规则统计，不按整批）

| 指标 | 含义 | 目标 |
|---|---|---|
| 命中率 | 本批触发次数 / 涉及字段出现次数 | 不设目标，用作治理信号 |
| 修复率 | 命中后动作被采纳且复核通过 | > 90% |
| 误报率 | 命中但人工核读判为「其实没问题」 | < 10% |
| 回归覆盖 | 有正反例测试的 active 规则占比 | 100% |

### 12.2 成本

- code 通道：0 token，可忽略。
- checker 通道：按簇调用，是**默认执行通道**而非兜底。成本口径按「簇 × 案」预算：每案常规 1 次（全部簇合并为一次调用时可降到 1 次），修复重写另计 1 次。**上限：每案 ≤ 2 次**，超出记 `checker_budget_exceeded` 交人工。用同模型调用时，按当前单案成本量级估算，额外 1 次调用的开销远低于人工维护任何一张业务表。
- prompt 通道：规则片段进 L1/L3 输入会增大提示词。规则迁移后 L1 输入增长上限建议不超过 30%，超出说明该规则更适合 checker（按需、不占常驻上下文）而不是 prompt。

## 13. 明确不做

- **不做通用规则引擎 / DSL**。规则到 100 条且出现「同形规则大量复制」时再议。
- **不做规则的可视化编排**。规则由工程师写、业务方出正文，走代码评审。
- **不让 checker 产出新字段值**。只裁决，不生成。
- **不在本轮改回传契约**。
- **不把规则塞进一个 `rules.py`**——按簇分文件，否则就是第二个 `pipeline.py`。

## 14. 遗留的开放问题

1. **规则正文的评审流程**：金标准类规则由业务专家写，谁签字生效？是否复用现有「提示词改动须单独确认」的纪律。
2. **例外词表的边界**：`EXPR-01` 需要的英文例外词表（品牌名、技术缩写）用一次性清单即可，不设维护流程；若日后发现需要持续扩充，说明它该改走 checker。
3. **checker 的模型选择**：与主流程同一模型，还是单独一个更便宜/更严的模型。建议先同模型，量起来再拆。
4. **派生字段是否跨运行缓存**：目前建议不缓存（只影响本批次），避免把某次推导沉淀成事实。
