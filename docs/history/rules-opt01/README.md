## 1. 这一轮做什么

把「规则」从散落在提示词、代码、审查层三处的句子，升为有身份、有通道、有留痕的一等公民。
分阶段目标见 `下一轮架构蓝图.md` §6；规则层本身的设计见 `规则层设计.md`。

**本轮范围建议（对齐蓝图阶段 0 + 阶段 1）**：

1. 规则登记表与三条执行通道（code / prompt / llm_checker）的最小实现；
2. 现有散落规则中「判据现成」的一批迁入（`规则层设计.md` §10 的迁移表）；
3. 规则落点标记与两道检索守卫（`规则层设计.md` §9）；
4. L2 审查从「能判」到「能拦」。

**不在本轮**（除非需求方另行确认）：输入层分片取证、知识层、增量更新、回传契约变更。

## 2. 必须先建立的共识

- **默认交给 LLM，不把建模成本转嫁给业务方。** 只有「集合封闭且我们本来就拥有」的
  才建表（枚举键、契约字段、内部字段键、入参）。理由与判据见 `规则层设计.md` §2.1。
- **不建职业收入表这类开放知识表**。职业有几万种、同职业方差跨两个数量级。
- **规则自己不改状态**，只输出动作，由统一执行器按优先级应用。
- **默认动作是降级 / 转人工，不是删除**。
- **对客产出不得出现规则 id 与内部解释**（`docs/README.md` 硬约束）。
- **成本让位于准确性，但每案 checker 调用上限 2 次**。

## 3. 实验基线与质量门

基线批次：`experiments/batches/rules-opt01-baseline-8-20261026/`（8 个号码，见其 README）。

**性质要先看清**：它来自 UAT 快照，代码版本未知、写回开启，**不是受控复现基线**。
因此比对口径是「质量对照」而非「逐字相同」：

| 看什么 | 怎么判 |
|---|---|
| 字段覆盖 | Notes 条数与非空数不低于基线（8 案各自对照，不看总数） |
| 商机等级 | 与基线同档，或变化有可解释的规则依据 |
| 规则命中 | 新规则在本批的命中数与动作分布，逐案记录 `rule_trace` |
| 可读性 | 证据位无裸渠道名、推理链非「来自 X」、无内部字段名与英文取值 |
| 不引入新矛盾 | 职业↔收入、预算↔车型、旧车↔购车性质等跨字段一致性 |

若需要严格可比，先在当前 HEAD 上重跑这 8 个号码生成受控基线；该动作消耗真实 token，
由需求方决定是否执行。

## 4. 已知的工程约束（来自项目既有纪律）

- 提示词正文改动属业务优化，须单独确认；新规则一律进登记表，不进模板正文。
- 模板正文「唯一运行期来源」不变，由 `TemplateRepository` 加载，缺文件即报错。
- 按「最小且完整的修改」推进，小任务直接做，跨模块改动先出计划。
- 不删除、不改写 `experiments/` 下的任何基线目录；禁止 `git clean -xdf/-X`。
- 文档改动同步更新 `docs/changelog.md`（功能落地时）。

## 5. 建议的开工顺序

1. 规则登记表的数据形态 + 一条样板规则（`INCOME-01`）跑通三通道；
2. 落点标记与检索守卫（先标后迁，把散落点摸清）；
3. 按 `规则层设计.md` §10 的迁移表逐条搬家，一次一条、迁完补测试；
4. 接 L2 审查的动作执行，让「能判」变成「能拦」；
5. 用基线 8 案对照，出核读清单与差异说明。

## 6. 待拍板事项

1. `SPEC-01` / `MISS-01` 这类金标准规则，是 prompt + checker 双通道，还是单走 checker。
2. checker 用主流程同一模型，还是单独一个更严/更便宜的模型。
3. 金标准类规则的正文由谁签字生效，是否复用「提示词改动须单独确认」的纪律。
4. 是否重跑受控基线（消耗 token）。
