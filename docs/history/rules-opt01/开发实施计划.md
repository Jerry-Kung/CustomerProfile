两个必须先记住的事实：

- **`review_notes` 与 `validate_l3` 的 `unbacked_fact` 是同一判据的两份实现**。迁移时先合并，再登记；否则规则层会继承「改一处漏一处」这个原始病。
- **契约归一不是规则**。`d_enum` / `d_enum_partial`、单多值约束、`serialize_value`、`enum_key_guide`、`field_inference_guide` 全部来自契约快照（`notes_contract`）或字段类型，不承载业务判断，**不迁**。判据：删掉它，契约仍然完整 → 它是契约施工；删掉它业务上会出错 → 它是规则。

## 2. 目标形态

### 2.1 目录

```
src/customer_profile/rules/
├─ __init__.py          导出 registry / executor / render / guard 的公开面
├─ registry.py          Rule 定义、登记表装载、启动期自检（id 唯一、tests 必填、status 合法）
├─ actions.py           Action 数据结构 + 统一执行器（优先级、收敛、留痕）
├─ trace.py             RuleTrace 条目与收集器；序列化成 rule_trace_json
├─ render.py            prompt 通道：按 scope/stage 取规则正文，渲染成片段
├─ guard.py             两道检索守卫（孤儿标记 / 未落地规则）的检索原语
├─ clusters/
│   ├─ __init__.py      簇清单与注册顺序（顺序即同级排序的次级键）
│   ├─ identity.py      IDENT-* / ATTE-*
│   ├─ income.py        INCOME-*
│   ├─ consistency.py   CONSIST-*
│   ├─ level.py         LEVEL-*
│   ├─ hard.py          HARD-*（契约形态与占位）
│   ├─ expression.py    EXPR-*
│   └─ spec.py          SPEC-* / MISS-*（prompt 为主）
└─ texts/               prompt 通道的规则正文，按簇一个文件
    ├─ income.txt
    ├─ consistency.txt
    ├─ spec.txt
    └─ …
```

**依赖方向**：`rules` 只能依赖 `notes_contract` / `internal_fields` / `text_utils` / `income_band`，**不得**导入 `projection` 或任何 `workflows.*`。`projection` 与 `workflows` 可以导入 `rules`。这条是防循环导入的硬约束，也是「规则层不反向依赖管线」的体现。

`clusters/*.py` 只允许出现三类内容：规则登记条目、规则谓词/检查函数、该簇的测试夹具引用。**每个文件不超过 200 行**，超了说明簇该拆。

### 2.2 Rule 定义

```python
@dataclass(frozen=True, slots=True)
class Rule:
    id: str                     # "INCOME-01"
    version: int                # 改条件或阈值即 +1
    title: str                  # 一句话，人能读
    content_kind: str           # "hard" | "spec" | "consistency"
    channels: tuple[str, ...]   # ("code",) / ("prompt",) / ("code", "llm_checker")
    scope: tuple[str, ...]      # 字段名或字段簇名；("*",) 表示全局
    stages: tuple[str, ...]     # "extract" | "project" | "express" | "gate"
    severity: str               # "block" | "repair" | "warn"
    default_action: str         # reject | downgrade | rewrite | require_confirm | annotate
    message_internal: str       # 进 rule_trace，可带 id
    message_customer: str       # 进 to_confirm / reasoning_detail，不得带 id
    owner: str                  # "business" | "engineering" | "both"
    status: str                 # "proposed" | "active" | "deprecated"
    legacy_codes: tuple[str, ...] = ()   # 迁移前的裸串，仅用于跨批次对账
```

- **规则正文不进 Python 字符串**：prompt 通道的正文放 `texts/<簇>.txt`，用成对标记包裹（§4），`render()` 按 id 切出整段。代码通道的 `message_internal` 一句话即可。
- **`default_action` 与 `message_customer` 是把 `then` / `message` 拆开后的安定形态**：一个规则只声明默认动作，实际动作可由谓词按情形上调或下调（如 INCOME-01 命中后 `downgrade` + `require_confirm` 两条）。
- 登记表在**启动期自检**：id 唯一、`active` 必须有正反例测试、`channels` 与 `stages` 非空、`legacy_codes` 不重复。自检失败直接抛，不带病开图。

### 2.3 Action 与执行器

```python
@dataclass(frozen=True, slots=True)
class Action:
    rule: str
    attribute: str
    action: str                 # reject | downgrade | rewrite | require_confirm | annotate
    severity: str
    reason: str                 # 对内
    customer_reason: str = ""   # 对客；空则不出现在 to_confirm
    value: Any = None           # rewrite 的新值
    stage: str = "project"
```

执行器 `apply(projection, actions, *, max_rounds=3) -> ApplyResult`：

- 排序：`硬约束 > 一致性 > 合理性 > 表达` → 字段级 scope > 簇级 > 全局 → rule id 字典序；
- 每轮应用后复查：若产生新的可执行动作则再跑一轮，**最多 3 轮**，超限记 `unstable` 并停机（设计 §7.3）；
- 每条动作落一条 `RuleTrace`，字段 `rule_id / stage / attribute / before / after / action / severity / reason / source`；
- **规则函数自己不碰 `Projection`**：一律返回 `list[Action]`，由执行器改状态。这是迁移期最容易被破坏的一条——迁一条就要保证这条被守住。

### 2.4 留痕出口

`project_claims` 新增输出 `rule_trace_json`（与 `rejected_json` / `to_confirm_json` 并列），下游节点按需透传，最终由批次导出脚本读取。已有 `rejected` / `downgraded` / `to_confirm` 的结构**本轮不变**（它们进 `result1` 与回传体，改形状是契约变更）。trace 是**追加**，不是替换。

## 3. 三条通道的落地形态

### 3.1 code：`clusters/<簇>.py` 里的纯谓词

```python
def check_identity(claims, facts, context) -> list[Action]: ...
def check_consistency(facts, context) -> list[Action]: ...
def check_level(facts, stage, assess) -> list[Action]: ...
```

接入点只有两个：`projection.project_claims`（project 阶段）与 `pipeline.apply_level`（gate 阶段）。迁移方式是**「先包后替」**：

1. 把内联分支原样抽成一个函数，返回 `Action` 列表，执行器套上去；
2. 全量测试绿（行为不变）后，再把条件表驱动化、补正反例；
3. 最后加标记（§4），删掉旧分支。

### 3.2 prompt：`render(scope, stage) -> str`

两个注入点（设计 §4.2）：

| 注入点 | 现有挂载处 | 本轮做法 |
|---|---|---|
| L1 取证输入 | `pipeline.l1_guide()` 已经把 `FIELD_SOURCE_NOTES` 渲染进字段清单 | 换成 `rules.render.field_notes(stage="extract")` 的视图，**输出文本逐字不变**才是合格的迁移（已按此落地） |
| L3 表达输入 | `l3_express` 模板正文 | **本轮不动模板正文**。模板改正文属业务优化，须单独确认；先让 L3 侧规则在登记表里 `status=proposed`，等确认后再挂变量 |

约束：**新规则一律进登记表，不进模板正文**；`FIELD_SOURCE_NOTES` 迁移完成后**删除常量**，不留第二份（这是「一处登记」的最低检验）。

### 3.3 llm_checker：新增一对节点

```
L2_REVIEW (code) ──▶ RULE_CHECK (llm) ──▶ RULE_APPLY (code) ──▶ LEVEL_INPUT
```

- 输入只有**可读化事实**（`readable.py` 渲染后）+ 本簇待检规则（编号、失效模式描述、涉及字段）+ 必要的原文摘录；**不得**见内部字段键（设计 §4.3 硬边界 1）。
- 输出逐条 `{rule, fields, verdict, explain, proposed_action}`。`RULE_APPLY` 过代码复核：编号必须在本次输入清单里、字段必须存在、动作必须在白名单内、**不得携带新值**；不合格条目丢弃并计数。
- 分组：按字段簇（收入 / 车辆 / 家庭 / 时间 / 表达）组装，单次输入 ≤15 条规则；**每案 checker 调用上限 2 次**，超出记 `checker_budget_exceeded` 并把剩余簇转人工。
- 失败语义：一次调用失败**不阻断**管线（规则层不能让它成为新的单点），记 `checker_failed` 后管线照常往下走，人工核读清单里带上该案。

新增开关：`RULE_CHECKER_ENABLED`（缺省 `false`，先离线跑通再开）、`RULES_DISABLED`（逗号分隔的规则 id，用于单条灰度/回滚）。

## 4. 落点标记与守卫

形态按设计 §9.1：

- Python：`# rule: <ID>` 紧挨被约束的行；一个函数承载多条时，每段前各一行；
- 提示词：`<!-- rule: <ID> begin --> … <!-- rule: <ID> end -->`，成对、整段；
- 数据表：条目级 `{"tag": …, "rule": "<ID>"}`，或并行登记键。

`guard.py` 只做编号存在性检查，两条，进 `tests/rules/test_guard.py`：

1. **孤儿标记**：扫描 `src/**/*.py` 与 `src/customer_profile/templates/*.txt`，出现的每个 `rule:` 编号必须在登记表里且 `status=active`；
2. **未落地**：登记表里每个 `active` 规则，至少检索到一处落点（代码标记、texts 文件里的成对标段、或数据表登记键）。

另提供 `scripts/rules_index.py`：按编号或簇输出落点清单，供「删一条规则」的机械操作（设计 §9.2）使用。

**标记的写入顺序**：先标后迁是允许的，且是推荐路径——先把现有三处摸清并打标（零语义风险），再逐条搬进登记表。但标记一旦打上，守卫就要跟着上，**不允许长时间存在「标了但守卫没开」的中间态**。

## 6. 任务分解

每个里程碑可独立提交、独立回滚。**M0 不合并任何规则迁移**，先让基座与守卫立住。

### M0 · 基座（无行为变化）——**已完成**（2026-10-26）

- 新增 `rules/` 包：`registry` / `actions` / `trace` / `render` / `guard`，`clusters/` 暂为空。
- `Rule` / `Action` / `RuleTrace` 落地；登记表启动期自检；`RULES_DISABLED` 由 `RuleRegistry.without()` 承担单条灰度。
- `project_claims` 增出 `rule_trace_json`（当前恒为空列表）。
- 新增 `rules_disabled` / `rule_checker_enabled` 两个设置项，缺省关闭。
- 验收已过：全量 `pytest` 绿；`tests/rules/` 46 个用例覆盖登记表自检、执行器排序/收敛/留痕、守卫三形态识别。

**落地时与计划的偏差（后续里程碑须知）**：

1. 守卫的检索前缀收窄为三种**带形态限定**的正则（`# rule: <ID>`、`<!-- rule: <ID> begin/end -->`、`{"rule": "<ID>"}`），且只认大写短横线编号。裸查 `rule:` 会把源码里大量的断言留痕字典（`"rule": "a_attribution"`）全当落点。
2. 内容类优先级定为 `hard(0) > consistency(1) > spec(2)`：表达类规则记 `hard`，先清形态、后判语义。见 `rules/actions.py` 的 `KIND_PRIORITY` 注释。
3. `Action.value` 为 ``None`` 的 `rewrite` 不执行（计 noop），避免把字段改写成空值。

- 现有三处代码落点全部打标：`projection.py` 8 处、`customer_profile_pipeline.py` 7 处、`income_band.py` 1 处。
- 守卫接进测试集：`tests/rules/test_guard.py` 用临时目录钉住检索原语，`tests/rules/test_guard_repo.py` 对真实代码树跑两道检查，另加「引用的测试真实存在」与「落点集合 == active 集合」两条。

### M5 · checker 通道——**已完成**（2026-10-26）

- 新增 `RULE_CHECK`（llm）+ `RULE_APPLY`（code）两节点，插入 `L2_REVIEW` 与 `LEVEL_INPUT` 之间；`LEVEL_INPUT` 的 `after` 改为新节点。
- 簇组装、预算（≤2 次/案）、代码复核、失败不阻断。
- 首批只挂 `INCOME-01`；跑通后依次加 `CONSIST-02` → `SPEC-01` → `MISS-01` → `PROD-01`（prompt 侧）。
- 验收：回放 8 个基线案，`INCOME-01` 在「网约车司机 / 30–50 万」形态上必须命中；无标签、无职业的案不得命中；单案 checker 调用 ≤2。

**落地实况**：

- `RULE_CHECK` 实际是 **code 节点**，不是计划写的 llm 节点。原因是调度器对失败节点会阻塞整棵下游子树（`scheduler._block_descendants`）——做成 llm 节点，一次调用失败就挡掉定级、表达与回传，与「checker 失败不阻断」直接冲突。现在由 code 节点内部调用统一 LLM 层并吞掉异常，失败只记 `checker_status=failed`。
- LLM 客户端通过 `rt.extra['code_functions']` 注入（`runner._checker_functions`），与节点复用同一客户端，共享限额、重试与留痕。code 函数本身可不传 `llm` 直调，便于单测。
- `RULE_CHECKER_ENABLED` 缺省 false，关闭时**在发起调用之前**返回（`checker_status=disabled`，0 次调用）。
- 送检清单只给**中文字段名**与当前取值，不含内部字段键；作用域内不足两个字段有确定取值的规则不送检（没有可比对的信息，问了也只答「判不了」）。
- 代码复核四条：编号须在送检清单内、字段须属于该规则作用域、动作须在白名单（`downgrade` / `require_confirm`）、**不得携带新值**。丢弃逐条留痕（`checker_dropped_json`）。
- `INCOME-01` 的默认动作只做 `downgrade`，未同时发 `require_confirm`：`to_confirm` 在回传链路里没有消费方，发出去是空接线。
- 离线回放脚本 `scripts/probe_checker.py`：缺省只组装送检清单与提示词规模，**不调用模型**；`--live` 才真调。

**落地时的决定（后续里程碑须知）**：

1. **checker 的动作白名单不含 `reject` / `rewrite`**。`reject` 要删条目、`rewrite` 要带新值，两者都要求掌握确定证据；checker 只有可读化事实。
2. **送检字段不足两个时整条规则不送**。这条判据比「字段都在即可」严格，避免为一条注定「判不了」的规则付费。
3. **一个簇一次调用**。M5 只有一个簇；后续加簇时按 `CHECKER_BUDGET` 卡上限，超了说明组装粒度不对，先拆簇再谈加规则。
4. **失败不写回任何东西**，只留 `checker_status` / `checker_calls` / `checker_error`。核读清单据此挑案。

**落地实况**：

- **同源批次去重**：`uat-18-20261026` 与 `rules-opt01-baseline-8-20261026` 是同一次运行的两个视图（按 `source_snapshot_sha256` 认亲），只取案件多的那份。不认亲的话，一次运行会被算成两批，零命中连击虚增。

**落地时的决定（后续里程碑须知）**：

## 9. 待拍板事项与建议默认值

以下四项取自 `README.md` §6。**不阻塞 M0–M3**（那三个里程碑不依赖它们），M5 开工前必须有结论。

## 10. 风险清单

1. **迁移把行为改坏而无报错**。投影层「错了不报错、只悄悄写错字段」（`tests/test_projection.py` 开头原话）。对策：先包后替 + 离线对账 + 一次一条。
2. **标记流于形式**。守卫只查编号存在性，查不出「标在错的段落上」。对策：标记以整段/整行为界，解释写在标记同一行；语义靠测试与核读，不指望守卫。
3. **checker 静默变差**。随规则增多而注意力摊薄。对策：按簇分组、单次 <=15 条、命中统计进 M6 报告；某簇判决质量下滑可从报告里看出来。
4. **模板正文迁移越界**。改正文属业务优化。对策：M4 只动 `l1_guide` 的渲染来源，正文迁移单独立项、单独确认。
5. **`review_notes` / `validate_l3` 双实现残留**。对策：M3 第一件事就是合并，未合并前不得新增 gate 规则。
6. **依赖方向被破坏**。`rules` 反向导入 `projection` 会立刻成环。对策：`rules` 只吃普通 dict / duck-typed 对象；如确需类型，用 `Protocol` 局部声明，不在 `rules` 里 import `projection`。

## 11. 开工第一步

这一步跑绿了，后面每个里程碑都是「往登记表里加一条 + 在簇文件里写一个谓词 + 打一处标记」。
