# 规则层离线重跑验证报告（uat-18）

> 2026-10-26 · 分支 `dev-rules-opt01` · 结论：**未发现由规则层引起的劣化**。

## 1. 为什么要离线重跑

第一次在线重跑（`uat-18-20261026-rerun`）与归档结果差异巨大：Notes 从 43 条掉到 1 条，
商机等级从 C 变「待识别」。排查发现输入侧已经变了——`GET /data/history/{phone}` 全部返回
`[]`，`profile` 换成了另一种结构，录音文件也取不到。**两批输入不同，比出来的差异没有意义。**

归档的 `runs/<手机号>/attempts.json` 保存了当次全部出网请求体与响应全文，包括录音识别结果。
因此改走离线重跑：取数层用归档原始响应回放，模型层保持真实调用。这样「新代码 vs 未改代码」
的比较建立在**同一份输入**上。

## 2. 三个批次的构成

| 批次 | 代码 | 取数层 | 模型层 |
|---|---|---|---|
| `uat-18-20261026` | UAT 当时的版本（含规则层之前） | 真实接口（2026-10-26 当日） | 真实调用 |
| `uat-18-20261026-replay` | 当前工作区（`2f5eab8` + 规则层未提交改动） | 归档回放 | 真实调用 |
| `head-ctrl-replay` | `2f5eab8`（**不含**规则层，独立 worktree） | 归档回放 | 真实调用 |

两批回放的 `fixture.json` **逐字节相同**（sha256 `d9a7779f…`，784539 字节，34 个端点 /
50 帧 / 36 条转写条目），因此两臂的输入完全一致，只剩代码这一个变量。

回放的三条口径写在 `scripts/replay_from_archive.py` 的模块说明里，要点是：只回放 HTTP
（LLM 真实调用）、录音走转写缓存而非回放帧（`/submit_analyze` 路径不含号码，合并后会跨案
串号）、图片从归档 LLM 请求的 data URI 还原原始字节（PNG 头在 `response_text` 里已被改写）。

## 4. 规则层确实生效

`scripts/rules_report.py --batch uat-18-20261026-replay` 报出 **141 次命中**，逐规则如下：

| 规则 | 通道 | 命中 | 动作 |
|---|---|---|---|
| IDENT-03 | code | 62 | downgrade |
| HARD-01 | code | 36 | reject |
| ATTE-01 | code | 19 | downgrade |
| HARD-02 | code | 13 | downgrade |
| HARD-03 | code | 7 | downgrade |
| CONSIST-01 | code | 4 | reject 2 / require_confirm 2 |

这直接解除了 L-009 的前两条：`pipeline_rule_check` / `pipeline_rule_apply` 两个节点在 16
个案子里全部 `succeeded` 并有产物，`checker_status` 16/16 为 `disabled`（`RULE_CHECKER_ENABLED`
缺省关闭，符合预期）；`rules_report.py` 报出非零命中且与 `rule_trace` 逐条对得上。

落地的证据不是「记了一条」，而是档位真的改了。以 13367265521 的 `driver_license_status` 为例：

- `pipeline_l2_project`：`fact`

  「标为事实但指不出原文」）

18271918797 上 HARD-01 的 24 次 `reject` 也确实把「未知」占位串挡在了最终 Notes 之外：
该号最终 Notes 里没有任何一条是占位值。

其它写侧保障同样成立：16 个案子的出网记录里 **没有一次** `update-profile` 请求
（`WRITEBACK_ENABLED=false` 被遵守），也没有任何回放未命中（`replay_miss` = 0）。

## 5. 逐案判断

商机等级：新代码与对照组 16 案中 **14 案一致**，2 案不同：

| 手机号 | 归档 | 对照 | 新代码 | 判断 |
|---|---|---|---|---|
| 13207117251 | A | A | B | 对照也判 A，新代码判 B |
| 15327825930 | 待识别 | 待识别 | C | 对照也是待识别，新代码判 C |

两案都查到了根因，**都不是规则层造成的**：

- **13207117251**：等级评估的输入事实有 15 项不同（`residence_address` 武汉 vs 鄂州、
  `test_driven_models` 未知 vs 猛士车型、`life_key_nodes` 空 vs `buying_car` 等），
  属于 L1 抽取在 `temperature=0.5` 下的采样差异。该号唯一的规则命中是 CONSIST-01
  （对 `purchase_nature` 的 `rewrite`），而 `purchase_nature` 并不在等级评估的输入差异项里。
- **15327825930**：输入事实同样有 5 项不同（`emotion` 空 vs `guard_against`、
  `communication_rhythm` 空 vs `procrastination`、`residence_address` 写法不同）。规则层
  只做了 IDENT-03 / ATTE-01 的降级，两处证据在对照组里本来就有内容。

两个案子在规则层上线前后都没有被 `rule_clamped` 拦截，等级判定的差异来自模型采样，
与规则无关。

## 6. 唯一一条硬信号及其归因

`17652815077` 的 Notes 从 42 条降到 30 条，是三者中唯一触发对比工具「硬指标」告警的。

归因结论：**不是规则层造成的，是上游取数失败。**

- 归档里该号的两次录音识别本来就全部失败：一次提交返回 401（`Invalid X-Api-Key`），
  随后查询报「找不到本次提交的 task_id」。因此归档里没有该号的转写条目。
- 离线重跑时转写缓存无条目可用，`submit_analyze` 落到回放的兜底 transport（一律返回 599），
  两条录音同样没有原文。整个新批次里只有这 2 次缓存未命中，全部属于这个号码。
- 逐节点核对：丢掉的 13 项（`budget_range`、`competing_brand`、`credit_status` 等）在
  `pipeline_l2_project` 阶段就已经不存在，不是被规则摘掉的。

对照组同号是 26 条——**比新代码的 30 条还少**。也就是说这次下降是上游识别失败导致的，
新代码反而比未改代码的对照组多保住了 4 项。

## 7. 观察到的其它现象（不构成劣化）

**规则零命中面较大。** 登记表里 12 条 active 的 code 规则在 16 个案子上零命中
（`IDENT-01`、`IDENT-02`、`INCOME-02`、`INCOME-03`、`LEVEL-01`–`04`、`CONSIST-03`、`EXPR-02`），
`INCOME-01`（llm_checker 通道）因开关缺省关闭同样为 0。这一批 16 个号码里，触发条件本身
较少出现（如收入倒挂、等级越界），不足以判定规则写错。需要多批数据累积后再判断是否退役。

**一条旧裸串尚未归一。** `rules_report.py` 报出 `name_source_whitelist` 3 次未归一到新编号，
说明还有散落判据没迁进登记表。

**`13367265521` 比对照组少 2 条 Notes（45 → 43）。** 该号 9 次 IDENT-03 降级 + 2 次 HARD-01
拒收，属于规则层按设计收紧；两组占位值均为 0，缺证据的高置信项也未增加。

## 8. 结论

三条解除条件全部满足：

1. 流水跑通，`pipeline_rule_apply` 有产物、`checker_status` 有值——16/16 成立；
2. `rules_report.py` 报出非零命中（141 次）且与 `rule_trace` 对得上——成立；
3. 逐案对照 Notes 条数与商机等级不低于对照基线——Notes 总量 327 vs 328（差 1 条），
   等级 14/16 一致、2 处差异均归因于 L1 采样；唯一的硬告警（`17652815077`）由上游识别失败
   引起，对照组更差。

**规则层在当前代码上没有造成结果劣化。**
