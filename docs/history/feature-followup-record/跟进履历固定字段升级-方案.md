# 跟进履历固定字段契约升级（1124 版）代码更新方案

> 状态：**已实施（2026-11-24）**，验证见 `验证记录.md`。
> 新契约：`docs/reference/AI画像回传接口变更说明-客户跟进履历-1124.md`
> 旧契约：`docs/history/AI画像回传接口变更说明-客户跟进履历-20261113.md`（已归档）
> 现有实现：`src/customer_profile/follow_up.py`、`src/customer_profile/callback_build.py`

## 1. 结论先行

本次契约变更只动**节点内部字段形状**：把原先塞在 `extra_info` 里的六项固定属性
（跟进人、关联车型、意向级别、跟进结果、转商机、下次跟进时间）提升为节点的一级字段，
并给它们加了长度/类型校验。接口地址、鉴权、顶层结构、回写语义、版本判定、
无数据不出键的约定**全部不变**。

因此本仓库的改动集中在 `follow_up.py`（装配 + 自检）与其单测；`callback_build.py`
的七键组装与"有内容才出键"逻辑不需要改；落库、DDL、查询接口、快照都在业务方仓库
（`cdp-m2m`），不在本次修改范围。

## 3. 字段映射（代码侧取值口径）

六项全部从**节点的最新一条记录**（`members[-1]`）确定性取，与现有 `extra_info`
"标签反映这组跟进最终状态"的口径一致；时间轴位置仍取首条（`followed_at` 不动）。

| 回传字段 | 记录字段 | 处理 |
|---|---|---|
| `follow_up_by` | `跟进顾问姓名` | 去占位串，≤100 |
| `related_model` | `意向车型名称` | 去占位串/裸码，≤100 |
| `intent_level` | `意向级别` | 去占位串，≤50 |
| `follow_up_result` | `跟进结果` | 去占位串，≤100 |
| `converted_to_opportunity` | `是否转商机` | 已解码为"是/否"，≤50；布尔值转"是/否" |
| `next_follow_up_at` | `下次跟进时间` | `parse_time` 归一；零点折成日期，≤100 |

`extra_info` 保留三项：`跟进渠道`、`参与人`、`战败类型`。其中 `参与人` 在合并节点里
仍列出全部顾问；`follow_up_by` 取最新一条的顾问（单值语义），二者分工不同。

**取值缺失/为占位串时不出这个键**，与契约"可为空"一致；既不出空串，也不编造。

## 4. 代码修改点

### 4.1 `src/customer_profile/follow_up.py`

1. 新增契约常量：`MAX_FOLLOW_UP_BY_CHARS=100`、`MAX_RELATED_MODEL_CHARS=100`、
   `MAX_INTENT_LEVEL_CHARS=50`、`MAX_FOLLOW_UP_RESULT_CHARS=100`、
   `MAX_CONVERTED_CHARS=50`、`MAX_NEXT_FOLLOW_UP_CHARS=100`。
2. `fallback_extra()` 收窄为只产出 `跟进渠道` / `参与人` / `战败类型`。
3. 新增 `fixed_fields(item) -> dict`：按 §3 映射产出六项一级字段。
4. `_node()`：`node.update(fixed_fields(tail))`，再接原有 `extra_info` 装配与渠道冲突守卫。
5. 新增 `promote_fixed_fields(entry) -> dict`（自检内的归一函数）：
   - 一级字段缺失时，按契约别名从 `extra_info` 提取：
     | 字段 | `extra_info` 别名 |
     |---|---|
     | `follow_up_by` | `跟进人` / `销售顾问` |
     | `related_model` | `关联车型` |
     | `intent_level` | `意向级别` / `意向等级` |
     | `follow_up_result` | `跟进结果` |
     | `converted_to_opportunity` | `转商机` / `是否转商机` |
     | `next_follow_up_at` | `下次跟进时间` / `下次跟进` / **`下一步跟进`**（我们旧版输出的键，仅作兼容） |
   - 提取后把这些键从 `extra_info` 副本中删除，保证出口不重复；
   - 一级字段优先于 `extra_info` 别名。
6. `sanitize()`：对每个保留节点先走 `promote_fixed_fields`，再逐字段校验——
   去空白、去空串、按上限截断；`converted_to_opportunity` 接受布尔（`true→是`、
   `false→否`），其他非字符串类型丢弃；`extra_info` 仍按 64KB 整体丢弃。
7. 模块文档补一节「固定字段为什么仍由代码产出」：这六项都能从记录字段确定性取到，
   进模型只会多一种"抄错码值"的失败模式；一级字段与 `extra_info` 的分工由服务端
   契约的"提取并去重"语义固定。

### 4.2 提示词模板（已落地）

`templates/customer_profile_pipeline__pipeline_follow_up.txt`：

- §六 增一句：六项固定字段同样由程序生成、模型不要输出。解析侧本就只读
  `records/node_name/summary/next_step`，此改动只省 token、防误解。
- §四 增一条保真规则：记录只表达「打算」（如「太晚了再联系」「明天跟进一遍」）且没有
  沟通结果时，必须写成「计划改日再联系」，不得写成已联系。真实案例核读发现的问题，
  见 `验证记录.md` §5。

### 4.3 `src/customer_profile/callback_build.py`

**不改逻辑**。`build_follow_up_history()` 继续透传节点（本模块不重推导、不改写）；
只更新 docstring，说明节点现在带六项一级字段，组装层无需感知。

### 4.4 不动的部分

- 七键结构、`if follow_up: 出键` 的无数据语义、`MAX_NODES` 截断；
- 记录解析、排序、时间归一、模型分组、兜底装配；
- `runner.py` 的注入（节点签名不变）；
- L0 记录层、L1/L2/L3、Notes、增量底座与 `profile_readback`；
- 增量 T0 原样回传（旧形状节点由服务端兼容提取四个字段，见 §7 风险 2）。

## 7. 风险与已定口径

1. **合并节点的 `follow_up_by`**：取最新一条记录的顾问，不拼多人。理由：六项固定
   属性统一"反映最终状态"，多人信息已由 `参与人` 承载。若业务方要求拼多人，
   只需改一处取值函数。
2. **T0 重放旧回传体**：旧节点缺少一级字段，服务端按契约从 `extra_info` 兼容提取
   `related_model` / `intent_level` / `follow_up_result` / `converted_to_opportunity`；
   我们旧键 `下一步跟进` 不在服务端别名表里，`next_follow_up_at` 会缺一档，直到该客户
   下一次真实更新。影响仅限展示，不改变正确性，**接受**。
   - 实测补充：`follow_up_by` 在旧版输出里没有单独键（顾问只出现在 `参与人` 里），
     服务端与本仓库自检都无法可靠反推，同样缺一档。不从 `参与人` 猜测——合并节点的
     首位顾问是**最早**那位，猜成 `follow_up_by` 会把跟进人标错。
3. **不改 T0 副本**：避免为了让旧产物多一个字段而触碰增量链路。
4. **不加开关**：本次仍是契约内字段形状升级，沿用"始终执行、回退靠代码"的既有口径。
