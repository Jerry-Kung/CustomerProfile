## 已拍板的口径（2026-11-05）

| 事项 | 结论 |
|---|---|
| UAT 跑哪一档 | 只跑 `high` 与 `low`；`none` 不实现，配置层直接拒绝 |
| 存量数据 | **不迁移**，就地清理载荷、保留骨架与根输出 |
| 取数链 | **合并为一条**：包是运行时数据的唯一搬运单位 |
| 对比脚本 | 批次 manifest 标注档位；`low` 批次不得当作完整输入做 A/B |

## 总览

| 期次 | 主题 | 目标 | 依赖 | 主要产出 |
|---|---|---|---|---|
| P0 | 止血 | 存量库回收空间；新库不再累积 freelist | 无 | 一条运维命令、一个 PRAGMA |
| P1 | 写包与瘦身 | 收尾搬运、两档写入矩阵、媒体外化、`end` 节点 | P0 | `persistence/archive.py`、tracker/store 改造 |
| P2 | 读路径与补收尾 | 回填、`SELECT *` 收口、崩溃行补收尾 | P1 | api 读取层、响应新增字段 |
| P3 | UAT 取数链 | 快照、导出、入库、取包脚本全部支持新形态 | P1 | `export_snapshot.py` v2、`fetch_run_archive.py`、runbook |

工作量粗估：P0 半天；P1 三到四天；P2 两天；P3 一天半；P4 一天。

## P0 · 止血（零代码风险）· 已完成 2026-11-05

实测结果：

| 项 | 结果 |
|---|---|
| 存量库 | 63.5 MB → 9.6 MB；freelist 13746 → 0；`integrity_check` = ok；`auto_vacuum` = 2 |
| 备份 | `data/customer_profile.db.bak-20261105`（与原库 sha256 一致） |

| WAL | `wal_autocheckpoint` = 1000 未改动；写入 2000×8 KB 过程中 `-wal` 稳定在约 4 MB 封顶，关闭后归零。**不常驻，不需要补 PRAGMA** |


### T0-1 存量库空间回收

- 本机 `data/customer_profile.db` 63.5 MB 中 53.7 MB 是 freelist，从未 `VACUUM`。
- 命令：`sqlite3 data/customer_profile.db "PRAGMA auto_vacuum=INCREMENTAL; VACUUM;"`
- 验收：`PRAGMA freelist_count;` 显著下降；`PRAGMA integrity_check;` 为 `ok`；库可用。
- 回滚：操作前先 `cp` 一份带日期的备份（在 `.gitignore` 的 `data/` 下，不提交）。

### T0-2 新库设增量回收

- `Store._ConnectionThread._run` 建连时，在 `journal_mode=WAL` 之前执行
  `PRAGMA auto_vacuum=INCREMENTAL`。`auto_vacuum` 只在建库时生效，对已建库需先 `VACUUM`。
- 验收：新建临时库后 `PRAGMA auto_vacuum;` 返回 2。既有库未 VACUUM 时返回 0，属预期。
- 改动文件：`src/customer_profile/persistence/store.py`（约 3 行）。

### T0-3 确认 WAL 不常驻

- 现有 `journal_mode=WAL` 未覆盖 `wal_autocheckpoint`，用 SQLite 缺省（1000 页）。
- 验收：跑一单后 `-wal` 回落接近 0，不需要改代码。若实测常驻，再补
  `PRAGMA wal_autocheckpoint` 并把实测值记进任务书。

## P1 · 写包与瘦身写入 · 已完成 2026-11-05

落地结果：

| 项 | 结果 |
|---|---|
| 配置 | `TRACE_PERSIST_MODE` 只接受 `high`/`low`，`none` 与未知值拒绝启动；旧布尔开关映射到新档位 |
| 包模块 | `persistence/archive.py`：`DIAGNOSTIC_FIELDS` 单处常量、媒体外化、原子写盘（tmp→fsync→replace） |
| 收尾搬运 | `Store.finalize_tree`：读树→裁剪→写盘**成功后**才清载荷；失败保留 `in_db` |
| 两档 | `high` 全留（`end` 节点与子运行 `customer_data` 除外）；`low` 只留 `response_text`、根输出、`l0_records` 原样输入、10 个诊断键 |
| 读回填 | 本轮一并完成 T2-2（否则清库后运行台会成片空节点）：`get_run`/`list_node_executions`/`list_attempts`/`execution_trace` 按包回填 |
| 响应字段 | `payload_state` / `payload_missing` / `payload_truncated` 已上 `RunDetail`、`RunGraph` 与节点/尝试行 |

端到端实测（真实工作流 `human_corrected_info`，回放模式）：

- `high`：状态 `packed`，包 1.8 KB，回填后 4/4 节点输出与打包前一致；
- `low`：包 1.7 KB，`omitted` 含 `node_outputs` 与 `requests`，节点行带 `payload_truncated=low`。

### T1-1 配置项

`settings.py`：

- `trace_persist_mode: Literal["high","low"] = "high"`（env `TRACE_PERSIST_MODE`）。
  **只接受 `high` / `low`**；`none` 与任何未知值都**拒绝启动**，报错文本列出合法取值。
  不实现静默回落——「以为开了 `low` 其实还在存全量」是最难查的一类问题。
- 旧布尔变量兼容：`TRACE_PERSIST_ENABLED` 已存在时 `true→high`、`false→low`；
  同时存在时以 `TRACE_PERSIST_MODE` 为准并 WARN。
- `trace_archive_dir: Path | None = None`，缺省 `<DATA_DIR>/trace-archives`；
  `trace_retention_days: int = 30`；`trace_archive_compress_level: int = 6`。
- `.env.example` 追加说明（取值语义、`none` 为何不可用、旧变量映射、目录必须落在数据卷）。

验收：`test_model_configuration.py` 增四例——非法值抛错、`none` 被拒、旧布尔映射、
目录缺省值。

### T1-2 包写入模块（新文件 `persistence/archive.py`）

只做三件事：**裁剪、媒体外化、序列化落盘**。不碰数据库。

- `DIAGNOSTIC_FIELDS`：设计稿 §8 的 10 个键，单处常量。
- `build_package(tree, mode, media_index) -> dict`：按设计稿 §5.2 裁剪，产出 §4 的结构。
- `write_package(pkg, path)`：`tmp → fsync → os.replace`，返回字节数与 sha256。
- `externalize_media(value, media_index) -> (value, stats)`：递归把 `data:` URI 换成引用；
  签名参数检测（`Signature` / `Expires` / `X-Amz-` / `token`）在此实现。

验收（`tests/test_archive_package.py`，纯函数，不连库）：
- 两档矩阵逐项断言：包里有什么、`omitted` 内容、`low` 切片只含 10 个键。
- 媒体：data URI 被替换、sha256 与原文一致、查不到 URL 时 `url: null` 且计数。
- 签名参数命中时 `url_may_expire` 为真。

### T1-3 收尾搬运

`persistence/tracker.py` + `persistence/store.py`：

- 新增 `Store.finalize_tree(root_run_id, mode, archive_dir)`：在一个读事务里读回整棵树
  （复用 `execution_trace` 的递归 CTE），交给 `archive.build_package`，**写盘成功后**
  在同一连接的写事务里清空载荷列并置 `payload_state='packed'`。
- 清空范围：该树全部 `node_executions.inputs_json/outputs_json`、
  `request_attempts.request_json/response_text/usage_json`、全部在树的
  `workflow_runs.outputs_json`（含根——两档都进包）。
- 顺序不变量见设计稿 §3：先写盘成功，再清空。
- 失败：不动库，`payload_state` 留 `in_db`，ERROR 日志，不影响业务运行。
- `RunTracker.run_finished`：仅当根运行（`parent_run_id is None`）且终态时触发；
  调用放在现有 `try/except` 内。`Store.abandon_run` 成功后触发同一条。

验收（`tests/test_archive_write.py`）：
- 合成树打包后，包内节点与尝试载荷与库内一致。
- `high`：库内载荷列全空、状态 `packed`、包内有根输出。
- `low`：包里无 `request_json`、有 `response_text` 与切片。
- 写盘失败（只读目录模拟）：库内载荷**仍在**、状态 `in_db`、业务运行仍成功。
- 子运行收尾不触发搬运。

### T1-4 子运行输入去重与 `end` 节点

- 打包时：`parent_run_id` 非空的运行，删除入参中的重复键。键集合用常量
  `REPEATED_INPUT_KEYS = {"customer_data"}`、阈值 `REPEATED_INPUT_MIN_BYTES = 4096`，
  显式列出，不做通用启发式。
- 打包时：`node_type == "end"` 的节点，`outputs_json` 记为 `null`，输入照常保留。

验收：
- 子运行入参里不再有 `customer_data`，其余字段完整。
- `end` 节点输出为 `null`，同运行的 `outputs_json` 完整。

  目前**没有**定时扫描重试，需要手工触发 `Store.finalize_tree`。在两档下这只是占空间，
  不丢数据；若要自动收口再按原设计实现 `sweep_unpacked_trees` + CAS 置 `archiving`。

### T2-2 回填

- `Store` 读方法按 `payload_state` 分派：`in_db` 直读列；`packed` 用包覆盖；
  `purged` 返回骨架并带标记。
- `packed` 但包缺失：记 ERROR，返回骨架并置 `payload_missing`。

接入点：`api.py` 的 `/runs/{id}`、`/graph`、`/nodes/{node}/attempts`、`trace_api.py`。

- 包文件删除后 `payload_missing=true` 且记 ERROR。

### T2-3 崩溃行补收尾

- `Store.sweep_unpacked_trees(older_than_ms, limit)`：扫终态超过 1 小时、
  `payload_state='in_db'` 的根运行，逐个走 `finalize_tree`。
- 入口：`worker.py` 主循环按小时节流调用一次。
- 搬运前先 CAS 置 `archiving`，成功改 `packed`，保证内联与独立 worker 并发时只搬一次。

验收：`tests/test_archive_sweep.py` — 遗留 `in_db` 被搬运；并发两次调用只搬一次。

## P4 · 存量清理 + 保留期 · 已完成 2026-11-05

| 项 | 结果 |
|---|---|
| 清理脚本 | 新增 `purge_legacy_payloads.py`：只扫终态、保留根输出、`VACUUM INTO` 备份后才动手 |
| 保留期 | `persistence/retention.py` + worker 主循环按天节流；只删包，骨架不动 |
| 端到端 | 真实工作流 `high`/`low` 各跑一单：均 `packed`、回填后节点输出与打包前一致；清理脚本 dry-run / 无备份拒绝 / 正式执行 / 重跑幂等四项均实测通过 |

### T4-1 存量就地清理（新 `scripts/purge_legacy_payloads.py`）

**不迁移**。旧行不写包，直接清空载荷并打标。

- 扫 `payload_state IS NULL` 的**终态**根运行；`queued`/`running` 一律跳过并报告。
- 对每棵树：清空节点输入输出、尝试请求体与响应、子运行输出；**保留**骨架全列、
  非载荷列（错误、耗时、目标 URL、状态码）、`definition_versions`、
  以及**根运行的 `outputs_json`**。置 `payload_state='purged'`、写 `archived_at_ms`。
- 默认 `--dry-run`；正式执行要求 `--backup <path>`，先 `VACUUM INTO` 备份再动。
- 分块提交（每 N 棵树一次），可中断续跑（已清理的行状态为 `purged`）。
- 完成后 `VACUUM`。

验收：拿 `experiments/uat_data/uat-traces-20261102-20261103/trace.db` 的副本跑：
- 清后行数与 `payload_state` 分布符合预期，库体积显著下降；
- 随机抽 5 棵：骨架列逐字段不变、根输出仍在、节点与尝试载荷为空；
- `/graph`、`/runs`、`/traces/export` 不报错，且明确带 `purged`；
- 重跑一次为 no-op。

### T4-2 保留期

`worker.py`：主循环按天节流一次，调用 `retention.run_once(settings)`：

- 删 `trace_archive_dir` 下早于 `now - retention_days` 的日期目录，空目录一并清。
- 删完执行 `PRAGMA incremental_vacuum`。
- 结果写 INFO 日志（删了几个包、释放估算）。
- 骨架不删——两档都保留运行、节点、尝试的非载荷列。

验收：`tests/test_retention.py` — 过期删除、未过期保留、骨架行数不变、空日期目录被清理。

| P0 | 从备份恢复库文件 |
| P1 / P2 | 置 `TRACE_PERSIST_MODE=high`；读路径对 `packed` 行仍走包，不受档位切换影响 |
| P3 | 脚本为新增参数，去掉即回到旧行为 |
| P4 | 包保留 30 天；清理前有整库备份，可从备份恢复 |

**P1 合并前先具备「包可读回」的能力（T2-2）。** 否则一旦清空库内载荷而包读不出来，
运行台会显示成批空节点。这是本轮唯一的单向门。
