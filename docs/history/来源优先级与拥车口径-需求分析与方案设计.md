## 一、需求来源

业务方在测试环境（`158****1947` 最新一次运行）发现画像卡内部自相矛盾：

- 「现车信息」「当前用车」判为**无车**，「人生关键节点」判为**买车中**；
- 同一张卡上「置换车型」写着**有置换需求，置换车型为别克威朗**。

业务方的判断：有旧车可置换就不可能是无车。且「无车」来自第三方画像标签，
「置换」来自录音中客户亲口所述，**一手信息应当压过第三方推断**。

### 业务方追加的三条约束（原文要点）

1. **不只要修「无车」一条**，需要通用规则：多来源冲突时按
   客户原话 > 销售描述 > 第三方标签取舍，第三方标签在前两类都缺失时兜底。
   适用 Notes 字段：行业、职业、家庭结构（三类都缺时允许受控推断）、
   人生关键节点、现车信息、驾照情况（驾照已有单独处理）。
2. **跨字段规则要直接改口径**：存在旧车/拥车/置换证据时，「无车」类取值直接改成
   「有车」，且**信源与推理链一并指向该证据**，先保证输出无内部矛盾。
3. **第三方标签可以降档，但不允许静默丢弃**：有第三方标签值可填的字段，
   不允许留白置空丢出去。

### 已拍板事项

- 拍板点一：来源档位放在冲突消解排序的**首位**（高于置信档）。
- 拍板点二：冲突中被压过的一方**降档保留**，不置空（前端已有低置信标记）。

## 二、根因分析（四层，均已代码定位）

### 层一 · 转写失败被当成成功

`extract_auc_result` 取不到 AUC 响应时不抛错，把异常拼成 `解析失败: <异常>` 往下传。
该串非空，记录层判 `status=ok`、`content_kind=transcript`，于是**报错文本冒充
「一手录音原文」进入 L1 提示词**，客户亲口说的旧车年份与车型整段丢失。

`_transcript_parts` 原有 `_looks_like_sentinel` 兜底，但它按「短串 + 子串命中」判，
上限 60 字符；而失败串长度取决于异常全文，会远超上限，因此拦不住。

### 层二 · 第三方标签压过一手证据

冲突消解排序键原为 `(effective_basis, 来源档)`。而 `effective_basis` 会把
「第三方预测 + 自称 fact」抬成 `inferred_high`，于是**任何自评 `inferred_low`
的一手断言都输给第三方预测**。「无车」正是这样胜出的。

### 层三 · 跨字段无约束

没有任何规则禁止 `current_vehicle_info=无车` 与「置换证据」同时成立。

### 层四 · L2 兜底沿错值外推

兜底模板允许拿同组字段当依据：无车 ⇒ 首购 ⇒ 无置换需求 ⇒ 置换车型为空。
一个错值被复制成四五条「有理有据」的结论。

### 附带发现（两个既有缺陷）

- **`REGISTRY_CHANNELS` 漏登记注入渠道**：`客户留资手机号` / `试驾与置换记录`
  不在登记档名单里，HARD-03 会把每次注入的驾照判成「标为事实却指不出原文」
  并降为 `inferred_low`，注入时宣告的 `fact` 当场被自家人推翻。
- **参考标准表「标准推理路径」列是空壳**：该列只做展示，不参与提示词渲染。
  业务方建议的「把优先级规则写进标准推理路径」按当时实现**根本到不了模型**。

- **拦截点必须在记录层**，不能只改提示词。报错文本一旦进了提示词，

- **改写取值必须同时改证据指向**，否则会出现「值是有车、证据写着无车」的新矛盾。

## 五、失败的真正原因（重开必读）

### 5.1 验证样本本身不可用

- 本次验证所用批次 `fallback-floor-20261028-6` 的 6 个号码，
  录音位 **100% 是空或「解析失败」报错串**。
- 用户报障的 `158****1947` **不在任何归档批次里**。

对照臂之所以全是 `sufficient` 档、兜底全 `ok`，是因为那条 135 字符的
`解析失败: the JSON object must be str...` 被当成一手录音证据在跑。
**基线自身有病，所有对比都建立在噪声上。**

> ⚠️ **归因曾出错，务必看「五之二」节。** 首次实施时把这里读成「录音识别链路有故障，
> 报错文本冒充证据」，于是去修转写失败过滤。真实原因是**这批数据的录音压根没送去识别**
> ——回放批次没播种到任何转写缓存，请求落到回放守卫的 599 上。
> AUC 服务本身一直是好的，实测可正常出转写。

### 5.2 过滤报错串触发既有 `thin` 档连锁

`triage()` 判档只看「`status=ok` 且有内容」：

- 过滤报错串 → 录音位真空 → 无一手交互 → 掉 `thin`；
- `thin` 档按既有判据（`_thin_keeps` / `_thin_keep_candidates`）清掉非登记档字段、
  收窄兜底候选 → 候选归零 → 兜底 `no_candidate`；
- 结果：Notes 塌方。

每一环都是既有代码的正确行为，合起来就是输出塌方。**改在第二环，塌方发生在第五环。**

### 5.3 方法教训

**先证明测试数据能复现问题，再改代码。** 本次在无法复现报障案的样本上连做三轮修复，
每次都验出新的连锁反应。六项改动没有一项拿到过有效验证。

**更要紧的是：看见报错串要先问它是谁写的。** 本次那个 `解析失败: ...` 是我们自己的
代码在 `json.loads(None)` 时生成的，与 AUC 服务无关。把它当成「上游故障」的证据，
就等于在自己的诊断产物上做根因分析——越查越偏，且每修一处都会引出新的连锁反应。

## 五之二、录音识别链路（AUC）调查结论（2026-10-30）

> 本节独立的回答一个问题：**录音解析是不是一直坏的？** 结论：不是。

### 5.5.1 实测：AUC 现在是好的

用真实 key 各跑一次完整链路（提交 + 轮询），两个不同来源的录音都出了转写：

| 录音来源 | 提交 | 轮询 | 识别结果 |
|---|---|---|---|
| `dfms.tos-cn-beijing.volces.com`（mp3） | 200 / `20000000` | 19 次，21.8 秒 | 42 条 utterances |
| `online-business-cos.m-hero.com`（wav） | 200 / `20000000` | 8 次，9.8 秒 | 12 条 utterances |

归档里全部 820 次录音请求用的都是 m-hero 域名，没有一条用过 TOS 域名。

### 5.5.2 归档时间线（820 次调用的全部事实）

| 时间 | 结果 | 真实原因 |
|---|---|---|
| 10-22 ~ 10-23 上午 | 37 次 `200` | 真实成功，产出 9 个号码的真实转写 |
| 10-23 09:36 起 | 1 次 `401` | `Invalid X-Api-Key`，key 开始失效 |
| 10-26 全天 | 212 次 `401` | 同上。**这就是业务方提到的 key 失效窗口** |
| 10-28 全天 | 10 个批次 596 次 `599` | 见下，不是 AUC 故障 |
| 10-29 | 4 个批次 32 次 `200` | 转写缓存命中（`replayed=1`） |
| 10-30 | 72 次 `599` | 本次三臂，同下 |

### 5.5.3 `599` 是我们自己造的

`599` 不是合法 HTTP 状态码，由 `runner.py` 的回放守卫生成：**回放模式下任何未命中
固定响应的请求都拿 599**，目的是保证回放永远不出网。10-28 之后每一个批次的
`manifest.json` 里 `kind` 都是 `archive-replay`。

### 5.5.4 报错串的完整成因链

回放脚本要从源批次还原转写缓存，而源头就断了：

1. `fallback-floor-20261028-6` 的源头是 `uat-all-tasks-20261026-20261027`；
2. 该源批次 43 个 run 有提交记录，**查询成功 0 个**（全在 10-26 被 401 拒掉）；
3. 因此播种条目数为 **0**，日志原文 `transcript cache: 0 entries seeded`；
4. 每次录音都 miss → 落到回放守卫 599 → 提交失败返回 `None`；
5. `parse_task_params(None)` → `解析失败: the JSON object must be str...`（代码实测可复现）；
6. 该串一路流进 `transcript_bundle.content`，记录层判 `status=ok`。

**一句话：那串报错不是「AUC 坏了」的信号，而是「这个回放批次根本没有录音数据」的产物。**

### 5.5.5 真正需要修的三处

| # | 问题 | 位置 | 处置建议 |
|---|---|---|---|
| 1 | 回放脚本不拦「零播种」 | `scripts/replay_from_archive.py` | 源批次转写条目为 0 时应拒绝开跑，或至少不把录音渠道当有效输入。当前只打一行日志就继续，导致 596 次调用建立在空数据上 |
| 2 | `None` 被转成内容串 | `workflows/shared_code.py::parse_task_params` / `extract_auc_result` | 迁移前原样设计（「让错误出现在日志里，比空值好排查」），但它让失败沿着正文字段流进提示词。至少要让它与真正的内容在记录层可区分 |
| 3 | key 轮换无记录 | `.env` / `docs/runbooks/` | 10-23~10-26 的 401 没有留下任何运维记录，`.env` 到 10-30 15:07 才被改过 |

### 5.5.6 可用的验证样本

`uat-18-20261026` 是**真实出网**跑出来的批次（`replayed=0`，37 次成功提交），
其中 9 个号码有真实转写，最长 26209 字符。**重开时应以这批为准**，不要再用
`fallback-floor-*` / `verify-*` 这些回放批次。

可用号码：`131****2128`、`133****5521`、`153****2822`、`159****9760`、
`180****7750`、`182****8797`、`192****8215`、`199****0792`
（`176****5077` 是一次 401 + 一次成功，需挑成功的录音）。

## 六、重开建议

### 6.1 前置条件（缺一不可）

1. **拿到能复现报障的样本**：`158****1947` 的原始取数记录；拿不到就用
   `uat-18-20261026`（真实出网、9 个号码有真实转写，见 5.5.6）。
   **不要用任何 `archive-replay` 批次做验证。**
2. **先单独验证基线的病**：确认该样本在改动前的代码上确实产出「无车 + 有置换车型」，
   而不是靠报错串撑出来的假 `sufficient`。
3. **先确认录音位是真转写**：跑一遍 `pipeline_l0_records`，看录音渠道的
   `content_kind` 与内容前 20 字——是「解析失败」就说明这批数据没被送进 AUC，
   立刻停手换样本。

### 6.2 真正的第一处改动

不是提示词，是 **L4 分诊的「一手渠道」判据**：

> `status=ok 且有内容` ≠ 有证据。报错串不能算一手交互。

这一条不修，后续所有改动都在噪声上做实验。建议把「录音位的正文是否为失败串」
纳入 `triage()` 与 `build_records` 的同口径判据，并补一条回归测试：
**只有报错串的案件必须判 `thin` 或以下，不得判 `sufficient`。**

### 6.3 改动顺序建议

0. **先修数据地基**：5.5.5 的三处（回放零播种守门、`None` 不转内容串、key 轮换留痕）。
   这一条不做，后面每一步都还可能踩同一块坑；
1. 分诊判据修正 + 回归测试（本轮缺的地基）；
2. 层一转写失败过滤（与 1 同批，因为二者判据同源）；
3. 层二排序键（可用构造的 `Claim` 对做单元验证，不必等真实数据）；
4. 层三 `CONSIST-05`（需真实「无车 + 置换」样本才能验命中）；
5. 层四兜底模板（改一句即可，但须在三臂里看兜底状态不能退化）；
6. 附带缺陷：`REGISTRY_CHANNELS`（本轮证明**无效**，需重查 HARD-03 的实际判据路径）；
7. 参考标准表渲染改造（与本议题正交，可独立推进）。

## 八、重开方案 v2（2026-10-30 制定，待批准）

### 8.1 本轮的五条铁律

从首轮失败里提炼，后面的任务设计全部据此：

1. **先证样本，再改代码。** 每次真实跑批前先看 `pipeline_l0_records` 的录音位：
   `content_kind=transcript` 且正文前 20 字不是「解析失败」。不是就停手换样本。
   首轮在六次跑批里都没做这一步。
2. **一次只动一层。** 首轮六项改打包上，塌方后无法判断是谁造成的。
3. **判据同源。** 记录层、分诊层、HARD-03 必须共用同一个「失败串 / 占位串」判定函数。
   首轮 `REGISTRY_CHANNELS` 改了无效，根因就是同一概念在四处各写一份、改一处不生效。
4. **纯代码改动先离线验。** 排序键与跨字段改写都是纯函数，用归档 run 的 L0/L1 产物

**T-09 · `HARD-03` 降档路径定位（附带缺陷一）**

首轮补了 `REGISTRY_CHANNELS` 却无效。本轮在 uat-18 上读到三条硬事实，把范围收窄了：

**(a) 两条通道的输入根本不同，补渠道名改不到 gate 那条。**
`is_unbacked_fact(has_quote, channel)` 有两个调用点，喂给它的 `channel` 来源不一样：

- Notes 侧（`review_notes` → `hard_rules.check_notes`）：`channel = entry.get("record_channel")`；
- 断言侧（`validate_l3`）：`channel = claim.get("record_channel")`。

而投影层写 Notes 更新项时**只写三个键**（`attribute_key` / `attribute_value` /
`reasoning_detail`），**`record_channel` 在那里根本不存在**。全批 18 个 run 实测相同：
Notes 条目的键集合恒为这三个。也就是说 gate 侧读渠道名恒得空串，
`is_unbacked_fact` 实际退化成「只看有没有原文标记」。首轮补 `REGISTRY_CHANNELS`
打在断言侧，对 gate 侧那条路径毫无作用——**这才是「补了无效」的直接机制**。

**(b) 但 gate 侧实测又没把驾照降下去，与 (a) 不闭合。**
全批 `driver_license_status` 的 `unbacked_fact` 计数恒为 0，且多数案该字段停在 `fact`；
其证据串是 `["到店试驾记录", "到店试驾或有旧车，驾驶资格成立"]`，不含 `QUOTE_MARKERS`
（`：` / `「` / `“`）。按 (a) 的推理它**应当**被判无锚点并降档，却没有。
说明还有一处我们没看到的传递：可能是 `L2_ENUM_MAP` 在关闭态下回填了这个键，
也可能 `review_notes` 的 `basis` 与 `notes` 不是同一版。**这两条都是推测，未证实。**

**(c) `176****5077` 的降档与驾照无关，不要混为一谈。**
该案 `current_vehicle_info` 在「L1 代码定坐标」被降为 `inferred_low`，`downgraded_detail`
给出的理由是 `anchor_not_found`（锚点为空），不是渠道对不上。**这是「无车」错值的来路之一，
但它不是 HARD-03 的降档。**

**任务做法**：先单步复现 (b) 的不闭合——在 `L2_PROJECT → L2_ENUM_MAP → L2_REVIEW`
三处各打一次点，打印 `notes` 条目的键集合与 `basis`，确认 `review_notes` 真正收到的是什么。
**在 (b) 解释清楚之前不许动 `REGISTRY_CHANNELS`，也不许给 Notes 条目加 `record_channel`
——那会同时改变回写出口的读法（`callback_build.py:327` 也读这个键）。**

## 十、真实跑批验证（2026-10-30）

### 10.1 测量方法

**样本**：从本地取数接口现取 12 个号码中挑 6 个，条件是「取数非空 + 两条录音转写全部命中
归档缓存」。这 6 个在跑批前**不在任何归档批次里**，因此取数、录音都是真实链路。

**两臂**：

- 新臂 = 当前工作区（含本轮七项改动）；
- 旧臂 = `HEAD`（`d4c7483`）的独立工作树，**真旧代码**。

两臂共用同一份转写归档，`WRITEBACK_ENABLED=false`、`REPLAY_MODE=off`，并发同为 4。

**为什么旧臂不能靠 `RULES_DISABLED` 造**：`RULES_DISABLED` 只作用于投影层与 gate 的
**动作**，管不住**提示词渲染**。实测 `RULES_DISABLED=SPEC-19` 时 `l1_guide()` 仍是
8944 字符、全局规则仍在提示词里。用配置开关造出来的「对照臂」提示词与实验臂逐字相同，
比出来的差异全是模型随机性。这一条要记在验证协议里。

### 10.3 质量：规则层

| 指标 | 旧臂 | 新臂 |
|---|---|---|
| `unbacked_fact`（无锚点 fact） | 6（6 案各 1） | **0** |
| `placeholder_removed`（占位串剔除） | 0 | 6（2 案各 3） |
| `HARD-03` 命中 | 6/6 案 | 0 |

- **`HARD-03` 从 6/6 降到 0 是本轮要的效果。** 旧臂每案都把 `driver_license_status`
  判成「标为事实但指不出原文」并降档，原因是 gate 拿不到来源渠道（Notes 条目只有三键）。
  新臂补了独立渠道映射后，这个字段的来源可判定，不再误降。这是**误报被消除**，
  不是规则失效——两臂该字段的置信档都是 `fact`，只是旧臂多报了一次降档。
- **`placeholder_removed` 6 条是新臂多出来的**：`industry` 取值「未知/未提及」、
  `occupation` 取值「未知（普通个人用户…）」被 HARD-01 当成占位串剔除。方向上是对的
  （这两个字段本来就是填「未知」凑数），但**这条差异没有做隔离实验**，不能断言它由本轮
  哪一项改动带来，只能记录为观测到的差异。

### 10.4 拥车口径：字段取值

新臂在拥车字段上统一带了「有车（…）」前缀，旧臂是裸车型名。逐案差异：

| 号码 | 旧臂 | 新臂 |
|---|---|---|
| 134****9943 | 比亚迪海鸥（车龄未提及） | 有车（比亚迪海鸥） |
| 137****0972 | 无该字段 | 旧车车况差、残值低，电池损坏，估值约2万 |
| 137****6409 | 比亚迪，车龄3年半，纯电… | 有车（比亚迪，车龄3年半，约7万公里） |
| 138****4651 | 埃安Y（2022年购入）；另有乐道一台；曾拥有宝马X1… | 比亚迪元，车龄约7年 |
| 166****8554 | 起亚K2，车龄约11年 | 有车（起亚K3，车龄约11年） |
| 158****1947 | 别克威朗（2019年上牌，车龄约19年） | 有车（别克威朗，2019年上牌） |

三处判读要分开看：

1. **`138****4651` 新臂更准。** 原文里「比亚迪元」是**正在置换的那台**，
   「埃安Y / 乐道 / 宝马X1」是客户过去开过或家里另有的车。旧臂把三台车串成一条现车信息，
   新臂只留现车。这是「拥车与置换一组不得互相外推」那条口径生效的实例。
2. **`166****8554` 新臂更准。** 原文是销售问「应该是K3吧？K2？」客户答「十一」年，
   K3 与 K2 都出现过；旧臂取 K2，新臂取 K3。差异来自模型随机性，方向上不算劣化，但
   **这张案不足以证明新臂更准**，只是改值。
3. **`158****1947` 旧臂的「车龄约19年」是错的**——原文「旧车19年」指 2019 年上牌。
   新臂写成「2019年上牌」，没有把年份读成车龄。

### 10.5 原报障案：结构性矛盾是否还在

号码 `158****1947`，用**已归档的录音转写**（两条共 2532 句，缓存全命中，全程未调 AUC）。

- 本次取数里**仍然带着**那条第三方标签「预测是否有车＝无车（置信度 0.578653）」，
  且它照常进入了 L1 与定级节点的请求体；
- 旧臂与新臂都在有这条标签的前提下，把现车信息判成「有车（别克威朗，2019年上牌）」；
- 两臂的 `trade_in_requirement` 均为 `yes`、`trade_in_model` 均为「别克威朗」。

**结论：「无车」与「置换别克威朗」这个组合不再出现。** 但要说清根因有两层：

- 先前那次 `无车` 的出处在 18173 的历史运行里可以逐字读到：`current_vehicle_info`
  的 `record_channel` 是「第三方画像数据」、`basis` 为 `inferred_low`，依据写着
  「第三方画像标签『预测是否有车』给出『无车』（置信度 0.578653）」。
- 也就是说，这个矛盾是**低置信第三方标签压过了一手录音**。本轮 `SORT_TIER_FIRST`
  正是冲着这个机制去的，但本次两案都没走到需要它出手的地步——L1 自己就选了录音。
  **所以这组样本证明「现象没复现」，不证明「排序开关救了它」。**

另外，「别克威朗」这个车型名本身不是错译：原文是「威蓝威蓝7」（ASR 变体），
客户先说了「别克」，销售提「昂科威、英朗」，客户否认昂科威后说的是「威蓝7」。
