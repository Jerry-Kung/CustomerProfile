# 留痕存储瘦身 · 设计稿

> 2026-11-05。本稿把 `../design/存储瘦身方案.md`（下称「方案稿」）的测量结论落成**可实现的契约**。
> 方案稿回答「为什么这样切」，本稿回答「代码里怎么切、切完谁还能读到什么」。
> 任务拆解与验收见 `02-任务书.md`。

## 1. 范围与边界

**改**：留痕四张表的**载荷列**如何写、搬到哪、读的时候怎么回填；UAT 取数链（快照脚本、
`/traces/export`、新增取包脚本）。

**不改**：

| 不做 | 理由 |
|---|---|
| 不删列、不改表设计 | 迁移期新旧行混存，读路径必须能同时读两种形态；删除列需要重建表，收益为零 |
| 不改前端 | 读路径在服务端回填，`/runs`、`/graph`、`/nodes` 的返回形状保持不变 |
| 不做镜像节点去重（方案稿 §6.1 的 E 项） | 方案稿明确「本轮未采纳」，需先确认详情页不依赖 `sub_run_id` 节点的输出 |
| 不改 `definition_versions` | 共同的重建依据，体积可忽略 |
| 不改回放（`replay.py`、fixture 格式） | 与留痕存储无关；包不是回放入口 |
| **不做存量迁移** | 2026-11-05 拍板：旧数据不搬进包，就地清理载荷、保留骨架 |
| **不实现 `none` 档** | 2026-11-05 拍板：UAT 只跑 `high` 与 `low`；`none` 保留为设计预置，配置层直接拒绝 |

## 3. 目标形态与三条不变量

SQLite 只留骨架（运行、节点、尝试的非载荷列与定义快照），运行时数据按**主任务树**打成
一个 gzip 包，多模态只留 URL 与哈希。

三条不变量，任何实现选择都不能破坏：

1. **永不销毁唯一副本**。打包写盘成功（含 fsync/rename）之前，不得清空任何载荷列；
   包写失败就保留库内载荷并记 ERROR，状态留在 `in_db`。
2. **API 返回形状不变**。前端与 `ingest_trace_export.py` 都不感知包的存在；回填在服务端完成。
3. **空不等同于「没发生」**。载荷不在库里时，读路径必须能说明「搬进包了 / 该档丢弃了 /
   包丢了」，不允许静默返回空对象让人误判成「节点没有输出」。

## 4. 包格式（`package_version = 1`）

路径：`<TRACE_ARCHIVE_DIR>/YYYY-MM-DD/<root_run_id>.json.gz`。日期取根运行 `created_at_ms`
的东八区日期；gzip 级别 6。一个包覆盖**整棵运行树**（根 + 全部后代 + 它们的节点与尝试）。

顶层结构：

```json
{
  "manifest": {
    "package_version": 1,
    "persist_mode": "high",
    "root_run_id": "...",
    "workflow_id": "customer_profile_pipeline",
    "business_ref": "cdp:13800000000:B20261105",
    "status": "succeeded",
    "timestamps": {
      "created_at": "2026-11-05T15:49:44.123+08:00",
      "started_at": "2026-11-05T15:49:45.010+08:00",
      "finished_at": "2026-11-05T16:11:07.884+08:00"
    },
    "written_at": "2026-11-05T16:11:08.201+08:00",
    "code_commit": "84c5f74",
    "counts": {"runs": 11, "nodes": 250, "attempts": 96},
    "definition_version_ids": [42],
    "media": {"count": 3, "url_may_expire": false},
    "omitted": ["node_outputs", "requests"],
    "unresolved_media": 0
  },
  "runs": [ ... ],
  "nodes": [ ... ],
  "attempts": [ ... ],
  "definitions": {"42": { ... }}
}
```

- `runs` / `nodes` / `attempts` 的字段名与库列名一致（`inputs_json` 等已解析为对象），
  回填时按键覆盖，不需要另一套映射表。
- `omitted` 列出该档**按模式省略**了什么：`high` 通常只有 `end_node_outputs`；`low` 另含
  `node_outputs` 与 `requests`（`request_json`）。
- `timestamps` 是人可直接读的 ISO8601（`+08:00`）；毫秒列仍在 `runs`/`nodes` 里，
  节点绝对结束时刻由 `started_at_ms + duration_ms` 派生，不另存列（方案稿 §3.1）。
- `media.url_may_expire` 为真时同时写一条 WARN 日志；`unresolved_media > 0` 表示有媒体
  找不到来源 URL（见 §7）。

## 5. 写入路径

### 5.1 统一落库，收尾搬运

**运行期间照旧把载荷写进 SQLite，根运行收尾时一次性搬运。** 这不是方案稿 §5.L1.6 字面上的
「写入端按模式跳过」，是刻意选的路（裁定理由见 §9.1）：

```
节点执行 / 请求尝试 ──写库（现状不变）──> SQLite
                                              │
                        根运行 run_finished    │
                                              ▼
              ┌─────────────── 读回整棵树 ───────────────┐
              │  按模式裁剪（high / low）                 │
              │  媒体外化（data: → _media 引用）          │
              │  end 节点输出丢弃；子运行输入去重          │
              └────────────────┬─────────────────────────┘
                               ▼
                     gzip 写包（tmp → fsync → rename）
                               │
              成功 ──> 清空该树载荷列，payload_state='packed'
              失败 ──> 不清空，payload_state='in_db'，记 ERROR
```

换来三件事：

- **运行中可实时查看**。一次画像跑二十余分钟，`/graph` 与节点详情在跑的时候就能看中间产物，
  这是现有排障习惯（「卡在哪一步」）。
- **崩溃后证据仍在**。进程被打断的运行不会有包，但载荷在库里，重启后能看到它跑到哪。
- **一套写入规则**。两档只在**收尾**处分叉，不需要在写入端堆两套判断。

代价是单次运行内一次临时写放大（约 2 MB/主任务），由 `auto_vacuum=INCREMENTAL` 增量回收
（§11）。方案稿「直写包」的做法记为后续可选优化（§9.1）。

### 5.2 两档的收尾行为

| | `high` | `low` |
|---|---|---|
| 写包 | 是 | 是 |
| 包内节点输入输出 | 全部（`end` 节点除外） | 不留；只留诊断切片 |
| 包内 `request_json` | 全部 | 不留 |
| 包内 `response_text` | 全部 | 全部 |
| 包内 `usage_json` / `provider_request_id` | 留 | 留 |
| 错误文本、耗时、状态码、目标 URL | 骨架全留 | 骨架全留 |
| 根 `outputs_json` | 进包，清列 | 进包，清列 |
| 子运行 `outputs_json` | 进包，清列 | 进包，清列 |
| 清空后根 `payload_state` | `packed` | `packed` |

`none` 档不在本轮实现范围。配置层只接受 `high` / `low`，`none` 视为保留字并**拒绝启动**——
这样「以为跑了 `none` 其实在写包」和「以为写了包其实什么都没有」都不会发生。

`low` 的包内**必须**有四样（方案稿 §4.1）：`response_text`（全树）、根运行输出、
`pipeline_l0_records` 节点输出（原样输入）、诊断切片。这四样决定「为什么」还能不能回答。

### 5.3 `end` 节点与子运行输入

- **`end` 节点不存输出**（`high` 也砍）。抽样 60/60 与根运行 `outputs_json` 逐字节相同。
  读路径发现节点无输出且 `node_type == "end"` 时，用所在运行的 `outputs_json` 填充。
- **子运行的 `inputs` 去掉 `customer_data`**（连同其它超过阈值的重复入参，阈值常量化）。
  真正的客户数据快照在 `pipeline_l0_records` 的输出里；`workflow_runs.inputs_json` 只有
  手机号与批次号，不要误以为它承载了输入（方案稿 §5.L1.3）。`high` 档同样执行这一条。

### 5.4 失败、中断与补收尾

- **包写失败**：保持 `in_db`，ERROR 日志带 `run_id`，不影响业务运行（沿用留痕的 fail-soft 口径）。
- **进程硬崩**：库内载荷完整、`payload_state='in_db'`。由补收尾扫描处理（P2）：
  扫终态已超过 1 小时仍是 `in_db` 的树，按当前模式搬运。P2 之前这些行只是占空间，不会丢。
- **人工终结**（`abandon_run`）：终结后触发一次收尾搬运——这些运行正是最需要包的那一类。
- **跨进程**：包由**收尾的那一侧**写（独立 worker 或内联消费者），两侧共用同一目录。

## 6. 读取路径

### 6.1 回填算法

```
读 /runs/{id}、/graph、/nodes/.../attempts、/traces/export
  1. 从库取骨架（显式列清单，不带载荷列）
  2. 取该运行的 payload_state
     - in_db  → 载荷列直接读（存量旧行与崩溃行）
     - packed → 解析根运行 → 载入包 → 覆盖 nodes/attempts/runs 的载荷字段
     - purged → 存量清理过的行：载荷已就地清空，返回骨架并带 payload_state="purged"
  3. 包缺失（文件被删/路径不对）→ 记 ERROR，返回骨架 + payload_missing=true
```

- 根运行解析用一次递归 CTE（`root_run_id`），结果按 `run_id → root` 缓存。
- 包解析结果按根运行做小的 LRU（容量 4）。包解压后约数 MB，宁可重复解也不要常驻太多。
- 包读取走 `asyncio.to_thread`，不占用 SQLite 专属线程，也不阻塞事件循环。

### 6.2 响应新增字段（只增不改）

| 字段 | 位置 | 取值 |
|---|---|---|
| `payload_state` | `RunDetail` / `RunGraph` / 导出记录 | `in_db` / `packed` / `purged` |
| `payload_missing` | 回填失败时的节点与尝试块 | `true` |
| `payload_truncated` | `low` 档下的节点行 | `"low"` |
| `payload_state` | `/traces/export` 每行 | 同上，供入库脚本标注 |

前端可以忽略这些字段；`ingest_trace_export.py` 读到 `payload_state="purged"` 时在批次
`manifest.json` 里记「本批为清理前的骨架，无运行时数据」，不假装节点输出为空是正常结果。

### 6.3 `SELECT *` 的收口（本轮未做）

计划把 `list_runs`、`list_node_executions`、`list_attempts`、`list_child_runs` 改为显式列
清单。理由不是体积而是**形状**：列表页把 400 KB 的节点输出拖进来只为显示一行状态，两档
都受益。`execution_trace` 需要全量载荷（导出与回填），保留按表取列。

**实现阶段判定为可选优化，未做**：回填按行覆盖，越界列会被丢弃，正确性不受影响；
未做的代价只是列表查询多读几个大字段。`SELECT *` 还带来一处好处——新增列（如本轮补的
三列）不必逐个改查询。若后续列表页出现卡顿再按上面收口。

## 7. 多模态外化

`data:` URI 在包内一律替换为引用：

```json
{"_media": "image/png", "bytes": 233791, "sha256": "…", "url": "https://…", "source": "download"}
```

覆盖两处：节点输出里的 `files` 类字段，以及请求尝试 `request_json` 里 LLM 消息的
`image_url.url`。

**URL 怎么来。** 盘上唯一可靠的对应关系在下载那一刻：`HttpAttempt.response_bytes` 在
内存里，`_files_of` 用同一份字节生成 data URI。因此在 `attempt_recorded` 时对
`response_bytes` 算 sha256，记进本树的 `{sha256 → 请求 URL}` 索引；打包时按内容哈希查回
来源。查不到时写 `"url": null` 并计数 `unresolved_media`，**不猜**。

- 索引里的 URL 是**服务相对路径**（留痕与回放都按相对路径寻址）。业务原图地址在
  `pipeline_l0_records` 输出的 `media_urls` 里，包里同时保留了那份节点输出（`low` 及以上），
  所以 `2026-11-02` 那类「录音/截图来自哪」的追查不受影响。
- 签名类参数（`Signature` / `Expires` / `X-Amz-` / `token`）命中时 WARN 并在 manifest 标
  `url_may_expire`。
- `sha256` 用于下载后校验：取不到时明确报「媒体已不可达」，不静默当成空数据。

## 8. 诊断切片（`low`）

字段清单集中在**一处常量**（`persistence/archive.py` 的 `DIAGNOSTIC_FIELDS`），不得散落在
写包逻辑里：

`notes_updates_json`、`facts_json`、`candidates_json`、`to_confirm_json`、`rule_trace_json`、
`rejected_json`、`checker_status`、`enum_illegal`、`unbacked_fact`、`placeholder_removed`

实现口径：切片不是独立段，而是把节点输出**裁剪成只含这些键的对象**再放进 `nodes[].outputs_json`，
同时给该节点行标 `payload_truncated="low"`。这样读路径只有一种形状，前端无需分支。

明确排除 `callback_json`（与根输出逐字节相同，方案稿 §4.1.1）。保留 `notes_updates_json`
的理由同样在方案稿：40 个样本里 36 个与根输出的 `basic_notes_updates` 字段集合不同，
「某个字段为什么没进最终 Notes」只能在这一层回答。

## 9. 与方案稿的口径裁定

### 9.1 写侧不跳过，收尾搬运

方案稿 §5.L1.6 写「写入端按模式跳过」。本稿改为**照旧落库、收尾搬运**，理由见 §5.1：
运行中实时可看、崩溃不丢证据。代价是单次运行内一次临时写放大约 2 MB/主任务，
由增量回收吃掉。若后续观察到写放大成为瓶颈，再评估「直写包」——届时需要同步放弃
运行中查看能力，或另建内存态提供。

### 9.2 新增三列，走既有补列机制

`workflow_runs` 新增 `payload_state TEXT`、`payload_mode TEXT`、`archived_at_ms INTEGER`，
登记在 `store._ADDED_COLUMNS`（既有最小补列机制，架构文档 §7）。方案稿的「不动表结构」按
「不改表设计、不删列」理解：没有标记列，读路径就无法区分「已搬进包」与「本来就没有」，
而这正是方案稿最在意的静默误判。

`payload_mode` 是实现阶段补的第三列：`/traces/export` 的 `X-Trace-Payload` 响应头必须在
**开始推流前**定值，而那时还没读包。把档位随搬运一起落在行上，导出侧一次查询即可决定
标 `full` 还是 `sliced`，不必为了几个字节的响应头把每个包解一遍。

### 9.3 `none` 档本轮不落地

方案稿设计了三档，实装只做 `high` / `low`（2026-11-05 拍板）。原因：`none` 取消了包，
排障只能「用当前输入重跑一次」，而当前输入与当时的差异会让重跑结论不可比；UAT 是主要的
问题回归环境，这个代价不划算。方案稿里 `none` 的体积与清理规则保持有效，未来若生产存储
吃紧再按那份设计施工，届时需要同时补「导出不含运行时数据」的标注。

## 10. UAT 取数链

本期一旦在 UAT 翻到「骨架 + 包」，**取数脚本不同步更新就会取到没有载荷的库**。
按 2026-11-05 的拍板，取数链**合并为一条**：包是运行时数据的唯一搬运单位，库只负责骨架。

### 10.1 为什么合并

原先有三条并行的搬运路径：拷库（`export_snapshot.py`）、导出 JSONL（`/traces/export`）、
入库重组（`ingest_trace_export.py`）。翻包之后，前两者都拿不到载荷，必须各自补一套回填，
而回填逻辑一旦有偏差，两条链的产出会不一致——同一棵运行在运行台看得到、在批次归档里看不到，
这类问题最难查。

合并后的口径：

| 想要什么 | 走哪条 |
|---|---|
| 在本地运行台复现某段时间 | 快照：骨架库 + 包目录，`TRACE_ARCHIVE_DIR` 指过去 |
| 把 UAT 当功能验证/回归输入 | 任务导出：`/traces/export` **回填后**再导出，结构不变 |
| 只想看一案 | 取包脚本 `fetch_run_archive.py` |
| 客户原始资料 | 不受影响，仍走 `GET /api/v1/remote/data/history/{phone}` |

### 10.2 快照（`scripts/export_snapshot.py`）

- 新增 `--archive-dir`（缺省 `TRACE_ARCHIVE_DIR`，再缺省 `DATA_DIR/trace-archives`）。
- 对每个选中根运行：
  - `payload_state='packed'` → 复制对应包到 `<out-dir>/<name>.archives/YYYY-MM-DD/<run_id>.json.gz`，
    逐个校验 sha256；
  - `payload_state='in_db'` → 行内载荷原样拷（翻包之前的历史运行）；
  - `payload_state='purged'` → 只拷骨架，manifest 计数，不算错误。
- `manifest.json` 升到 `format: 2`，新增 `archives: {count, bytes, missing: [...]}`。
  `missing` 只登记「应为 `packed` 但包文件不在」的运行，非空时以非零码退出并逐条打印。
- `--dry-run` 额外报告「选中运行里有多少需要包、多少已 purged」。

### 10.3 本地复现

骨架库与包目录是两个并列输入，`TRACE_ARCHIVE_DIR` 指向后者：

```
set DATABASE_URL=sqlite:///D:/uat/snap-1.db
set TRACE_ARCHIVE_DIR=D:/uat/snap-1.archives
set INLINE_WORKER=false
```

## 11. 保留期与空间回收

| 项 | 规则 | 参数 |
|---|---|---|
| 包 | 30 天后删除 | `TRACE_RETENTION_DAYS=30` |
| 骨架（运行、节点、尝试） | 永久保留 | — |
| 包目录 | 按日期目录整目录删，空目录一并删 | — |

挂在 worker 主循环里按天节流一次（已有秒级轮询，不引入外部 cron）。API 进程不做删除，
避免多进程重复扫。

空间回收：

- 存量库一次性 `PRAGMA auto_vacuum=INCREMENTAL; VACUUM;`（T0-1 / T4-1）。
- 新库在 `connect()` 建表前设 `auto_vacuum=INCREMENTAL`。
- 每日清理后执行一次 `PRAGMA incremental_vacuum`；WAL 靠自动 checkpoint，不常驻。

## 11.1 存量数据的处置：就地清理，不迁移

2026-11-05 拍板：**旧数据不搬进包**。理由是不值得为历史行写一次完整迁移与回灌通道——
旧行的问题已经被查过了，而迁移引入的「包写一半、库已清空」风险要长期背着。

执行口径：

- 一次性脚本把 `payload_state` 仍为空的终态运行就地打标 `purged`，并清空载荷列
  （节点输入输出、尝试请求体与响应、非根运行输出），然后 `VACUUM`。
- **保留**：骨架全部列、错误、耗时、尝试的目标 URL/状态码、`definition_versions`、
  以及根运行的 `outputs_json`（最终画像是我们唯一写出的东西，profile 接口给不了当时的值）。
- 清理之后这些运行仍可列出、可看状态与错误，但节点详情为空且明确标 `purged`。
- 旧批次归档（`experiments/uat_data/`）不受影响：它们是**已经导出**的副本，与库无关。
- 迁移前的库文件先留一份带日期的备份（`data/` 已在 gitignore 内）。

因此不再需要 `--restore` 回灌通道，也不需要「新旧混存」的迁移窗口；
读到 `purged` 的分支保留，用于如实交代「这行没有载荷」。

## 12. 回归面

必须新增或扩展的测试（细节见任务书）：

- 包往返：库 → 包 → 回填，节点与尝试的载荷**逐字段相等**（媒体外化字段单独断言）。
- 两档矩阵：`high`/`low` 各自包里有什么、库里剩什么。
- `end` 节点：包内无输出，回填后与运行输出一致。
- 失败保护：包写失败时载荷仍在库、状态仍 `in_db`。
- 读路径：`/graph`、`/nodes/.../attempts`、`/traces/export` 在 `packed` / `in_db` / `purged` 下的返回。
- 快照脚本：包被带出、缺失被列出、`format: 2` manifest 字段齐全。
- 存量清理：清后骨架完整、根输出保留、`purged` 标记正确、可重跑幂等。

## 13. 风险

| 风险 | 影响 | 处置 |
|---|---|---|
| UAT 已翻包、取数脚本仍取旧格式 | 本地复现看不到节点载荷，误判为「管线没产出」 | P3 与 P1 同批发布；manifest 里 `missing` 显式报错 |
| 包写盘失败被静默 | 唯一副本被清空 | 不变量 1：先成功再清空；失败保留 `in_db` |

| `low` 档被当成完整批次复用 | 对比结论把「被裁」读成「没产出」 | 导出带 `X-Trace-Payload: sliced`；批次 manifest 标注档位 |
