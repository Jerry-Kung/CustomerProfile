# ADR 0002：多 worker 的模型配额用「显式分配」，不做共享

- 状态：已采纳（V0.5.3）
- 相关：差异 W35、W36；`docs/architecture.md` §4

## 背景

规划 §3 V0.5 的验收标准含一条：**「配额在多 worker 场景下语义明确（共享配额或显式分配）」**。
它要求的是「说清楚」，而不是默许每个 worker 各自使用完整的全局限额。

本项目的限额（`LLM_RPM_LIMIT` / `LLM_TPM_LIMIT`）是**进程内**令牌桶。若不加约束地起 4 个
worker，配置写着 RPM=60，实际会打到 240——限额静默失效，且没有任何提示。这与本版本要消灭
的「死配置」是同一类问题：**声明了却与运行无关**。

## 备选方案

| 方案 | 结论 |
|---|---|
| 跨进程共享配额（队列表里令牌行 / 集中式配额服务）| **否决。** 需要跨进程协调与轮询等待，即引入调度中间件；与规划 §5 约束 7 冲突。而且要为一个当前不存在的部署形态（单 worker）付这个成本 |
| 每个 worker 都用完整全局限额 | **否决。** 这正是验收标准要排除的：「语义明确」的前提是语义本身正确 |
| 起多 worker 时由运维自行折算 | **否决。** 把一致性寄托在运维记忆上，且没有任何机制阻止错误配置 |
| **显式分配：全局限额按 worker 数等分，不可整除则启动报错** | **采纳** |

## 采纳方案与理由

- `LLM_RPM_LIMIT` / `LLM_TPM_LIMIT` 的语义是**全局额度**（写在 `.env` 里，是部署级配置）。
- 每个进程实际使用的限额 = 全局额度 ÷ `WORKER_REPLICAS`。折算在
  `runner._per_process_quota_settings` 一处完成，不散落在各 worker 里。
- **不可整除时启动即报错**（`Settings._limits_split_evenly_across_workers`）。宁可拒绝启动，
  也不要运行时静默超发：`RPM=60` 配 4 个 worker 实际打到 240 这种事，出问题时的表现是
  「模型服务方限流/封禁」，而排查方向会指向代码而非配置。
- 单 worker（缺省）时折算为恒等变换，配置项含义与直觉一致。

相关实现细节见 ADR 0001 之外的差异条目：令牌桶而非固定窗口（W30）、接线在每次真实出网那一层
（W31）、TPM 预扣加校正（W32）、回放不耗额度（W33）、超容报错而非死等（W34）、
并发与速率并存不合并（W37）。

## 代价与后续

- **不是严格的全局限额**：多 worker 场景下，某一进程空闲时它的额度不会被别的进程用掉。
  对当前负载（单 worker、一次运行二十余分钟）这不构成浪费。
- **扩容需要同时改两个数**：`WORKER_REPLICAS` 与限额。校验器保证两者一致，但改配置的人
  必须同时想到它们——这也是把它写进 `.env.example` 与本文的原因。
- 若日后确实需要共享配额，第一步是在队列表里加令牌行并让 worker 轮询申领；届时本文需要
  被重新评估，而不是叠加实现。
