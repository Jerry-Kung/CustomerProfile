# ADR 0003：基线实验用「批次独立 SQLite」与「批次目录冻结」

- 状态：已采纳（V0.6）
- 相关：`docs/runbooks/基线实验.md`（留痕层 `fail_soft`）

## 背景

V0.6 要建立**数据基线**：拿一批固定手机号各跑一遍真实工作流，把结果与全部中间节点输出
归档，供日后判断「改了工作流之后输出质量有没有崩」。

留痕已经全量落 SQLite（四张表，见 `docs/architecture.md` §3），所以「归档」看起来只要
把库复制走就行。但有两处不能凭直觉决定：**归档写进哪个库**、以及**归档能否事后编辑**。

## 决策一：批次写自己的 `trace.db`，不复用 `data/customer_profile.db`

### 备选方案

| 方案 | 结论 |
|---|---|
| 直接写生产库 `data/customer_profile.db` | **否决。** 三条理由见下 |
| 批次完成后从生产库把该批 run 抽出来另存 | **否决。** 抽取本身要遍历整棵树，且生产库随时可能被清理；「先写进去再捞出来」比「一开始就分开写」多一次失败机会 |
| **批次独立库 `experiments/batches/<id>/trace.db`** | **采纳** |

### 理由

- **`data/` 的语义是「可重建」。** `docs/runbooks/部署.md` 与 `.gitignore` 都把它归为运行期
  数据。而基线的定义要求它**长期留存**。同一个目录承载两种相反的语义，日后必然有人按
  「可重建」把它删掉。
- **写并发会静默丢留痕。** `data/customer_profile.db` 是 API 与 worker 共用的库（WAL、单写者）。
  基线要连续写几个小时，与在跑的 worker 抢写者锁。而留痕层是 `fail_soft`——写超时**不会让
  运行失败**，只会少记几行。这比直接报错更糟：一批本该完整的痕迹，事后才发现有洞，且无从
  判断洞在哪。
- **归档退化成一条复制命令。** 批次目录自包含，拷走即完成持久化，不依赖 `data/` 是否还在。

### 代价

- `definition_versions` 的 version_id 从 1 重排，与生产库不连续。跨库比对必须用
  `definition_hash` 与 `code_commit`，**不能**拿 version_id 对号。这一点写进了
  `manifest.json`（`"trace_db": "batch-local"`）与 runbook。
- 每批次多一份库文件（约 120 MB）。相对该批次 600 MB 的产物总量，这是小头。
- 想跨批次比对时需要在两个库之间手工 join。当前不做自动比对，所以未构成实际负担。

### 附带效果（重要）

独立库顺带消灭了一个**改坏生产留痕**的风险：`build_service` 在 `interrupt_on_start` 为真
（缺省）时会调 `store.mark_running_as_interrupted()`，把库里残留的 `running` 全标成中断。
若基线脚本指向共享库而恰好有 worker 在跑，脚本一启动就会把对方**正在执行**的运行标成
中断——「看起来正常、实际改坏状态」。指向独立库后，这一步只作用于本批次的残留。

即便如此，脚本里仍显式设 `interrupt_on_start=False`，并在续跑时自己调
`mark_running_as_interrupted()`：作用域明确，不依赖「恰好指向了独立库」这个巧合。

## 决策二：批次目录一经写入即冻结

### 备选方案

| 方案 | 结论 |
|---|---|
| 允许就地修正产物（补字段、改状态、重算哈希） | **否决。** 见下 |
| **只增不改：补跑写进同批次，但已有产物不编辑** | **采纳** |

### 理由

基线的全部价值在于「它当时的输出就是这样」。一旦允许事后编辑，**任何差异都能被解释成
「大概是后来手改的」**——基线就失去了作为证据的能力。这与本项目在别处已经采纳过的原则
同向：`docs/history/prompts/` 的评审副本一旦失真，就用测试断言把它钉成会失败的事实，而不是
留一句没人验证的声明。

具体到操作：

- **允许**：用同一个 `--batch-id` 补跑失败的号码（新增目录、更新汇总）。
- **不允许**：手工编辑 `runs/*/result.json`、改写 `manifest.json` 的字段、修改已有节点输出。

需要别的视图（例如按节点聚合、跨批次对比）时，**写到新目录**，不要改源批次。

### 代价

- 产物里若发现了错误（例如某个字段本该记录却没记），不能在原批次里补——只能重跑一个新
  批次。这是刻意的成本，换来的是「批次即证据」。
- `manifest.json` 是唯一的例外：它在批次**收尾时**会被更新一次（补 `finished_at`、
  `bytes_written`、遗留临时文件清单）。这些字段描述的是「这一批次怎么结束的」，只有收尾时
  才知道，属于同一批次的事实补全，不是对已有结论的修改。
