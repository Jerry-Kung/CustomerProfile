# Customer Profile V0.4 只读运行台（设计）

> 状态：已评审，进入实现。上游依据：`V0迁移规划.md` §3 V0.4、`Dify迁移任务说明.md` §8。

## 1. 目标与范围

V0.4 交付一个只读运行台：能看工作流结构、看任务列表、看运行详情，包括子运行与每次请求尝试。

**明确不做**：不做编辑、不做重跑、不做拖拽保存、不做 WebSocket（首版轮询）、不做独立离线 HTML 报告。

## 2. 核心设计决策

### 2.1 图的形状只来自定义快照，不来自当前 Python 定义

`definition_versions` 表已在每次运行开始时由 `tracker.register_definition()` 写入 `asdict()` 快照。
因此「历史运行展示当时的图与提示词版本」不是 V0.4 需要新建的机制，而是既成事实。

推论：详情页与结构页取图走 `/definition-versions/{id}`，**不读**当前进程内的 `WorkflowDef`。
结构页在「尚未有运行」时才回落到当前定义。

### 2.2 布局为纯函数，在导出时按需计算，不落库

**决策（用户 2026-09-23）**：放弃复用 DSL 坐标，采用自动布局。

原因：`NodeDef.coords` 字段虽已预留，但迁移时 285 个节点只填了 22 个（17 个工作流每图仅 1 个）。
回填会产生一份与 DSL 强相关的派生物，与「纯代码构建、与 Dify 解关联」的初衷相悖。

**算法**：按 `predecessors` 求最长路径分层。层号决定 x，同层内顺序决定 y。

用有界松弛（Bellman-Ford 形式的最长路径），不用 `WorkflowDef.structural_order()`。
后者基于 `graphlib.TopologicalSorter`，在带环图上抛 `CycleError`。

> **修订（2026-09-23，实现时实测）**：本设计初稿称「截图类工作流的迭代节点确实带环」，
> 这一判断**不成立**。实测 20 个已迁移定义**全部无环**（逐个调用 `structural_order()`
> 均成功）：迭代节点引用其循环体，循环体不反向引用迭代节点。
>
> 实现过程中据此走过两条弯路，均被实测否定：先是按 DFS 回边剔除，在自造环图上把链中间
> 切断、环上节点错位；再是改用有界松弛并声称「带环时退化为忽略回边」，而实测环上节点被
> 推到第 10 层——松弛在环上不收敛到有意义的层号。
>
> 最终口径：**布局按 DAG 设计，不为环做特殊语义。** 松弛轮数上限 `n-1`，带环时有限但层号
> 无意义，图难看、不崩、不死循环。环普查由 `tests/test_layout.py::test_no_real_workflow_is_cyclic`
> 断言——引入环时它会直接失败，逼出真实原因，而不是让一张失真的图静默通过。

**接口**：

```
layout(definition: WorkflowDef) -> dict[str, tuple[float, float]]
```

纯函数，无副作用、无 IO。有 `coords` 的节点优先用其值（保留手工钉位置的能力），其余自动排版。

**已知代价**：扇出图上会变宽。证据汇总图出度 14、画像生成图出度 7，分层算法会把它们摊成很宽的一行。
缓解手段是同层内按扇出子树排序并加最小间距；接受它不如 Dify 原版美观。

### 2.3 并发不伪装成线性顺序

迁移说明 §8.4 的明确要求。图用边表达依赖，时间线用横向条形按真实起止时间绘制，两者并排。
这是本运行台与通用 DAG 查看器的区别所在。

### 2.4 后端计算布局

前端只保留一套 React Flow 渲染逻辑，布局算法留在 Python 侧以便被测试覆盖。
前端不做布局计算。

## 3. API 增量

现有端点保留。新增三个，全部挂在现有 `/runs` 族下：

| 端点 | 用途 | 备注 |
|---|---|---|
| `GET /runs/{run_id}/graph` | 详情页主数据 | 一次返回定义快照 + 节点状态 + 子运行映射，避免前端多次往返 |
| `GET /definition-versions/{version_id}` | 历史版本查看 | 快照单独可查 |
| `GET /runs/{run_id}/timeline` | 执行顺序视图 | 按节点起止时间排序，标出并发段 |

`GET /runs` 补齐筛选与排序：已有 `workflow_id` / `status` / `business_ref` / `include_children` / `limit` / `offset`；
新增时间范围与 `order_by`。

`GET /workflows/{id}/topology` 返回值增加布局坐标（在 `asdict()` 基础上附加 `layout` 字段）。

**不改动的端点**：`POST /runs`、`POST /runs/{run_id}/cancel`、`GET /health`、`GET /runs/{run_id}`。
对外契约（`result1` 为字符串）不变。

## 4. 前端结构

独立目录 `frontend/`，Vite + React + TypeScript + React Flow。

| 路由 | 内容 |
|---|---|
| 工作流结构 | 缩放、平移、节点点击看配置、叶子卡片进入子工作流 |
| 任务列表 | 状态、业务标识、开始时间、耗时、错误摘要，筛选分页 |
| 运行详情 | 节点状态叠加到当次版本的图上；输入输出、messages、错误与重试；子运行下钻 |

**子工作流表示**：结构图上作为叶子卡片，不展开；详情页点带 `sub_run_id` 的节点下钻到子运行，
在那里能看到 17 处 `Gemini` 调用的每一次尝试。

**轮询**：详情页 2s，列表页 5s；运行进入终态后停止轮询。

**构建产物**：`frontend/dist/` **入库**（决策：运行台要能在未安装 node 的机器上直接启动）。
由 FastAPI 以 `SERVE_UI` 开关挂载，缺省关闭——路由依赖构建产物存在，而测试不应依赖它。

## 5. 安全

**凭据**：已由 `execution/http.py:31` 的 `redact_headers` 在落库前掩码，请求头与响应头均覆盖。
由 `test_auc.py` 与 `test_human_corrected_info.py` 钉住。V0.4 不新增此项工作。

**客户业务数据**（手机号、通话内容、截图内容）：**原文返回**（用户 2026-09-23 决策），
鉴权由部署侧承担。

前端侧的边界约束（写入代码规范，由实现遵守）：

- 不额外记录日志到外部；
- 不把数据发往任何第三方服务；
- Vite 构建不引入会把数据外发的 SDK。

运行台是内部工具，但不是无边界的数据出口。

## 6. 子任务拆分

按依赖顺序，每步可独立验收：

| 子任务 | 内容 | 验收 |
|---|---|---|
| `v0.4.1` | 布局纯函数 + `/runs/{run_id}/graph` + `/definition-versions/{id}` + 前端脚手架与拓扑渲染 | 285 节点出图；同一份定义布局稳定；历史版本的图与当时一致 |
| `v0.4.2` | 任务列表页 + `GET /runs` 筛选分页与时间范围 | 状态、业务标识、耗时、错误摘要可见、可筛、可分页 |

每个子任务结束报告：实现内容、等价证据、已知差异、未完成项、下一步。

## 7. 验收标准（对齐迁移说明 §3 V0.4）

- 前端拓扑与后端工作流定义来自**同一份定义**，不存在第二份拓扑。
- 历史运行展示的是当时的图与提示词版本，新版本不覆盖旧运行的展示。
- 子运行可下钻，能看到 17 处 `Gemini` 调用的每一次尝试。
- 前端展示的图在带环定义上不崩、不死循环（布局按 DAG 设计，环由环普查测试拦截）。
- 密钥始终屏蔽。
