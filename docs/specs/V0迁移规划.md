## 1. 范围与现状

### 1.1 资产盘点结论

`dify_dsl_data/` 共 19 份 DSL，全部 `kind: app`、`mode: workflow`、`version: 0.6.0`。递归解析后的依赖关系如下：

- **主入口**：`（新）客户初始画像（生产环境）`，只有 6 个节点、6 条边，本身只是调度壳。

- V0 的真实迁移规模不是「41 节点主图」，而是**工作流图 19 个、节点总数 293 个、边总数 324 条**（DSL 基线；含被复用的子流程；见 §1.2 与 §7）。

### 1.3 迁移的真实难点（按风险排序）

1. **命名体系错位**（低风险，本地可解）：`tool` 节点用英文 `tool_name` 引用，本地文件按中文显示名命名，需建映射表（§1.1 已给出）。
2. **迭代节点**：8 个 `iteration` + 8 个 `iteration-start`，严格一一对应，分布在 8 个工作流（7 个截图/录音类子流程 + 1 个音频识别子流程），属 Dify 版式迭代，语义需精确还原（默认串行、逐项、失败传播）。
3. **条件分支**：共 26 个 `if-else` 节点，且存在「条件分支两侧汇聚到同一 aggregator」的写法（人设特征判断、截图类工作流的多文件分支），并非教科书式的二选一。
4. **变量聚合器分组**：23 个 `variable-aggregator` 中有 1 个开启了 `group_enabled`（人设特征判断的「特征结果聚合」），输出 `hobby` / `consumption` 两个 group，下游 code 节点再取 `.output`。这是 Dify 的非直观语义，必须逐项还原。
5. **扇出/汇合语义**：证据汇总图的「获取全量用户数据」出度 14，画像生成图的「用户输入」出度 7。汇合点是「全部完成才执行」还是「先到先得」，必须按实际拓扑与 Dify 行为判定。
6. **HTTP 外部依赖**：4 个不同的外部服务（AUC 语音 `192.168.0.5:5005`、Notes/回写 `118.145.238.50:8084`、mhero 中台 `mhero.dfmc.com.cn`、以及图片直链）。其中回写接口有副作用，`retry_config` 未声明幂等能力。**【2026-09-23 更新】**AUC 语音的内网服务长期不可达，已按用户决定改接火山引擎云服务（`openspeech.bytedance.com`），由 `execution/auc.py` 适配，见差异 W14。
7. **多模态模型选型**（原「模型供应商异构」，已由 §6.4.4 收敛）：DSL 原有三套模型标识，按 §6.4.4 全部归一为 `.env` 中的单一模型。**剩余风险只有一条**：全项目 12 个 vision 节点（截图解析）要求该统一模型具备多模态能力，选型时须确认。
8. **提示词体积**：46 个 template-transform 中单模板最长 14539 字符（标签库预置），合计约 8 万字符，需外置为资源文件并做逐字符比对。
9. **明文密钥**：**实测为 5 处 HTTP 节点、2 个密钥值**（原文写「4 处」，口径混淆了节点数与密钥值数，已在 `ledger/secrets_report.md` 更正）；header 含明文 `X-API-Key`（真实值已在本次盘点中屏蔽，未写入任何文档）。**需在 V0.1 内完成轮换建议与脱敏**。

## 3. V0 版本拆解

拆解原则：每个子版本有**独立可验证的产出**，且不依赖后续版本。V0.1 是纯盘点（无代码），V0.2 起交付可运行代码。

### V0.1 迁移盘点与基线固化

**目标**：把 DSL 变成可核对的结构化基线，把所有未知项显式列出，不做任何业务实现。

**交付物**

1. `docs/specs/` 下的**基线映射表**：19 个工作流 × 全部 293 个 DSL 节点（原 ID、标题、类型、直接前置、输入绑定、输出来源），含 18 个 `tool_name` ↔ 19 个文件名的映射。**同时给出 §6 优化后的 Python 实现计数与逐项对应关系**（两份数字，见 §6.7）。
2. **变量引用台账**：所有 `{{#node_id.field#}}` 引用的生产者与消费者，标记「顺序依赖但无数据消费」的边。
3. **差异清单 v1**：DSL 无法确认的运行语义（Q1/Q2/Q4–Q8 + HTTP 参数语义 + 迭代语义 + aggregator 分组语义）+ 已确认的有意差异（Q3 的双节点删除、Q9 的输入源）。
4. **资源清单**：提示词/模板清单（长度、变量名、字符哈希），不含正文入库。
5. **脱敏确认**：确认仓库内无明文密钥，输出轮换建议。

**验收标准**

- 映射表中的节点总数、边总数与脚本从 DSL 提取的结果逐项一致（可用脚本复核）。
- 差异清单中每一条都标注「已确认 / 待确认 / 缺省采用」，不存在空白项。

## 6. 工程优化规则（用户 2026-09-22 明确要求，覆盖前述默认还原原则）

> **优先级**：本节规则与 `Dify迁移任务说明.md` 第 3 节的「必须保留 / 不得合并节点」条款冲突时，**以本节为准**。用户已明确授权在迁移中同步做工程化改造。默认还原原则仅在**本节未覆盖**的范围内继续适用。

### 6.1 优化基线

迁移产出的 Python 是**正常的、人类可读的代码工程**，不是对 Dify 节点图的逐节点转写。Dify 的「节点 + 连线」是低代码平台的表达约束，其建模方式不应被继承。执行器与调度层按 §3 V0.2 保留（工作流执行确实是图问题），但**业务逻辑层必须写成人写的代码**。

### 6.2 节点 → Python 映射原则

| Dify 节点 | 迁移后形态 | 要点 |
|---|---|---|
| `start`（变量节点） | 函数入参 / 模块级常量 | 工作流入参 → 函数签名参数；固定预置内容 → 常量或资源文件 |
| `template-transform` | 单一渲染函数 + 外置资源文件 | 见 §6.5，变量绑定与换行必须逐字保留 |
| `code` | 普通 Python 函数 | 原节点代码逻辑**直接提取**，不在迁移中顺手重构；只剥离 Dify 特有的入参加载与返回值包装 |
| `if-else` | 普通 `if / elif / else` | 条件表达式翻译为 Python 表达式，不保留节点 ID 寻址 |
| `iteration` / `iteration-start` | 普通 `for` 循环 | 循环体为函数调用；`parallel_nums` 若需并发用并发原语表达，不建迭代节点 |
| `variable-aggregator`（含 `group_enabled`） | 普通赋值 / 三元表达式 / `if` 兜底 | 分组聚合 → 返回一个普通对象（如 dict / dataclass），下游取属性 |
| `llm` | `llm_call()` 统一函数调用 | 见 §6.4 |
| `http-request` | 显式 HTTP 客户端调用 | 保留方法、路径、body、必要 headers；鉴权从环境变量注入 |
| `tool`（`provider_type=workflow`） | 普通函数调用 | 子工作流 → 函数；`{{#node.field#}}` → 函数实参 |
| `end` | 函数返回值 | 保留 `result1` 为字符串的对外契约 |

**允许并入同一模块**：原图中的短链、纯装饰性节点、仅为绕开平台约束而存在的中间节点，在**行为等价**的前提下可合并为顺序代码。

### 6.3 「Prompt 模板 + Gemini（异常输出重试版）」固定搭配

DSL 中 17 处 `tool` 节点以 `gemini_retry_2_times` 调用 `Gemini（异常输出重试版）` 子流程。该子流程本身只是「同一 LLM 调用 + 异常重试」的封装（11 节点、内部最多 3 次尝试）。按用户要求**统一简化为一次直接的 LLM 调用**：

- 该子流程的 11 个节点、以及引用它的 17 个 `tool` 节点，在 Python 中不再作为独立图存在，改为一次 `llm_call()`。
- **重试机制不丢失，形式改变**：原图用「三个并联 LLM 节点 + 两个异常判定 + 两个条件分支」表达最多 3 次尝试，迁移后下沉为 `llm_call()` 内部的尝试循环（§6.4）。
- 等价性口径变更：从「图形态一致」变为「行为一致」——相同输入下期望输出一致、异常判定规则一致、尝试次数上限一致。
- 运行记录仍须可追溯原节点身份，保留 `original_node_id` 与调用路径。

### 6.4 统一 LLM 调用规范

#### 6.4.1 调用签名

以**一个** `llm_call()` 函数承载全部 LLM 调用，替代所有 `Gemini（异常输出重试版）` 节点与所有直连 `llm` 节点：

```
llm_call(
    prompt,                 # 渲染完成的提示词
    system=None,            # 可选系统提示
    images=None,            # 可选图片输入（多模态节点用）
    expect_json=False,      # 该任务是否要求 JSON 输出
    node_ref=None,          # 记录用：原节点 ID 与调用路径
) -> str | dict
```

#### 6.4.2 异常与重试（统一 3 次）

**所有 LLM 调用一律支持 3 次尝试。** 触发重试的情形：

1. **一般 API 异常**——网络错误、超时、非 2xx、服务端错误。
2. **输出中途异常截断**——判定方法沿用原 DSL「Gemini（异常输出重试版） - 判断结果是否异常」节点的节点代码，规则如下（该节点完整源码是唯一权威依据，此处仅记其口径）：
   - `usage` 三项 tokens 全为 0 → `usage_zero`
   - 去掉首尾空白后 `text` 为空 → `empty_text`
   - `text` 以 `<think>` 开头但不含 `</think>` → `unfinished_think_block`
   - `reasoning_content` 为空、`text` 以 `<think>` 开头且长度 < 500 → `thinking_only_suspected`
3. **需要 JSON 的任务输出不是合法 JSON**——`expect_json=True` 时解析失败即重试。

**判定「该任务需要输出 JSON」的依据**：以**下游消费方的语义**为准——下游 `code` 节点对该输出执行了 JSON 解析、或提示词明确约定输出 JSON，即视为需要。判据是消费侧，不是生产侧声明。

> **盘查结论（供执行参考）**：现有 17 处 `tool` 节点的 `output_json` 入参**全部为 `false`**。因此不能用该入参判断任务是否需要 JSON，须按上面「下游消费方」口径逐个确认。这也是为什么 §6.4.1 把 `expect_json` 设计为**调用点显式声明**，而非从 DSL 参数继承。

#### 6.4.3 次数与层级

- 「3 次尝试」指**最多尝试 3 次**（首次 + 2 次重试）。若业务确认应理解为「首次 + 3 次重试 = 4 次」，以业务确认为准，本规则待确认。
- **重试只在一层实现**（`llm_call()` 内部）。不得出现「SDK 重试 × HTTP 封装重试 × 节点重试 × 子流程重试」的乘法叠加。这与 `Dify迁移任务说明.md` §7.2 的要求一致。

#### 6.4.4 模型与参数（全项目统一）

| 项 | 统一取值 |
|---|---|
| 模型 | **由 `.env` 的 `LLM_MODEL` 决定，全部节点同一款模型** |
| temperature | **0.5**（全项目统一） |
| thinking | **开启**（默认） |
| 其他参数 | **一律不配置**（不设 `max_tokens`、`top_p`、`presence_penalty` 等） |

**对原基线的归一化**（属**有意差异**，须记入差异清单）：

- DSL 中三套模型标识（通义 `qwen3.8-flash` 32 处、火山 `doubao-seed-2-0-pro-260215` 2 处且 `thinking=enabled`、火山 `doubao-seed-2-0-lite-260215` 1 处）**收敛为单一模型**。
- DSL 中四档 temperature（0.2 二十处、0.4 八处、0.7 三处、1 四处）**全部归一为 0.5**。

> ⚠ **硬约束**：全项目 35 个 LLM 节点中共 **12 个为多模态（vision）节点**（分布在朋友圈、微信主页、微信手机号搜索截图、抖音、小红书、支付宝六类截图解析工作流，`vision.enabled=true`，图片以 `files` 变量注入）。因此 `.env` 中统一选定的模型**必须具备多模态能力**，否则这 12 个功能不可用。请在确定模型时确认这一点。

#### 6.4.5 `llm_model` 参数废弃

DSL 中 8 个工作流的 `start` 节点含 `llm_model` 入参，并有 4 个 `if-else` 节点以其为条件。该参数原用于在工作流内切换模型，**现已废弃，不得继续使用**：

- 迁移时删除 `llm_model` 入参，删除与之相关的条件分支。
- 相关分支**任选一支**为默认路径即可——因模型已统一，两支差异仅是模型选择，对业务语义无影响。
- 受影响的 4 个 `if-else` 节点：`人设特征判断` 2 处（`1776760124715`、`17767603231790`）、`外呼录音信息提取`（`1776764239626`）、`试驾录音信息提取`（`1776763992027`）。

### 6.5 模板与提示词的处理

- 保留逐字符等价（含换行与空白），这是提示词效果的前提。
- 外置为资源文件并受 Git 管理；模板语法可简化为统一渲染，**变量绑定关系不得改变**。
- `template-transform` 节点可合并为同一模块的顺序代码；提示词正文仍独立存放。
- 变更口径：**模板语法可改，模板内容不可改**。提示词文本本身的任何改动都属业务优化，须单独提出并获得确认。

### 6.6 不受影响的部分（继续按原基线还原）

- 图结构以外的**业务语义**：节点业务含义、数据流向、提示词内容、子工作流输入输出契约、空数据兜底字符串、`result1` 为字符串的对外契约。
- **执行记录**：§3 与 `Dify迁移任务说明.md` §6 的四层留痕要求不变，且因重试下沉到 `llm_call()`，**「请求尝试」层的记录要求更重要**——每次尝试仍须独立留痕（attempt_no、实际请求与响应、耗时、错误、usage）。原图中「每次尝试」由图结构自然分开，迁移后必须由代码显式记录。
- **HTTP 与回写**：§3 与 Q1/Q2 的约束不变，本次优化不涉及回写协议。
- **安全**：密钥从环境变量读取、不进 Git / 日志 / 前端的要求不变。
