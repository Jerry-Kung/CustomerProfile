# 在售车型条目规范（v1）

本规范定义知识包里一份车型知识的结构。第 1 期实施时以 `knowledge/pack.py`
里的 pydantic 模型为准，本文解释为什么这么定。

**v1 的主要变化**：引入「车型 → 档位」两层结构。每款车有若干档位型号，各档配置与
价格不同，动力形式也可能不同。v0 把「同一车型多个价格」当成数据问题，是误判。

## 1. 文件组织

```
src/customer_profile/knowledge/
  packs/
    dfms-mengshi/
      pack.json           # 包清单：身份、品牌、生效期、价格带矩阵
      models.json         # 全部车型条目
      brand.json          # 品牌别名；竞品位预留给第 4 期
  common/
    invite_strategy.json  # 去品牌化后的通用邀约策略
```

车型与品牌分文件，是因为它们被不同消费点读取：K2 只读 `brand.json` 与车型条目的**标识层**，
K5 读标识层，K4 读参数与表达层。拆开让「取全量」与「取标识」不必共用一条路径。

`common/` 与 `packs/` 同级，因为通用邀约策略跨合作方成立（拍板第二条：留用、去品牌化）。

## 2. 包清单 `pack.json`

| 字段 | 必填 | 说明 |
|---|---|---|
| `pack_id` | 是 | 包唯一标识，如 `dfms-mengshi`，同时是配置值 |
| `display_name` | 是 | 人读名称 |
| `vendor` | 是 | 合作方 |
| `brands` | 是 | 本方品牌规范名列表 |
| `models_file` | 是 | 车型文件名，相对包目录 |
| `brand_file` | 是 | 品牌文件名 |
| `effective_from` | 是 | 生效起始日 `YYYY-MM-DD` |
| `effective_to` | 否 | 失效日，空表示在售 |
| `tiers` | 否 | 产品矩阵分层，见 §2.1 |
| `note` | 否 | 人读备注 |

`effective_from` 必填的理由：车型知识带时间属性（上市、改款、停产），没有时间锚就无法
判断「这个价格现在还算不算数」。加载期只校验格式、不校验时效——过期是人的事，不该让
运行期罢工。

### 2.1 `tiers`：产品矩阵（供 K4 按预算筛）

```json
"tiers": [
  {"tier": "entry",  "label": "走量·轻户外", "models": ["dfms-x700"], "budget_min_wan": 20, "budget_max_wan": 28},
  {"tier": "main",   "label": "主销·硬核",   "models": ["dfms-m817"], "budget_min_wan": 28, "budget_max_wan": 45},
  {"tier": "flagship","label": "旗舰标杆",   "models": ["dfms-917"],  "budget_min_wan": 60, "budget_max_wan": null}
]
```

把矩阵放进**包清单**而不是车型条目：矩阵关系是「三款车之间」的属性，写进单条会让
同一句话抄三遍，改一处漏两处。`budget_max_wan: null` 表示无上限。

## 3. 品牌文件 `brand.json`

```json
{
  "our_brand": {
    "canonical": "东风猛士",
    "aliases": ["猛士", "猛士科技"],
    "asr_variants": []
  },
  "competitors": []
}
```

`competitors` 本轮为空，第 4 期竞品库接入时填。留字段是为了让 `resolve_brand` 从一开始
就有三方归属语义（本方／竞品／未知），日后不必改签名。

## 4. 车型条目 `models.json`

一条 = 一款在售车型（**不是**一个档位）。分三层，与消费点对应。

### 4.1 标识层（K2、K5 用，必填）

| 字段 | 类型 | 说明 |
|---|---|---|
| `model_id` | str | 包内唯一，如 `dfms-m817` |
| `canonical_name` | str | 规范名，如 `猛士M817`；对客出现的就是它 |
| `aliases` | list[str] | 客户真会说的称谓：`M817`、`猛士817` |
| `asr_variants` | list[str] | 转写常见错写 |
| `series` | str | 所属系列 |
| `status` | enum | `on_sale` / `coming` / `discontinued` |

`aliases` 与 `asr_variants` 分开，是因为误判后果不同：把错字当真名会污染归属，
把真名当错字会漏判。前者影响精确度，后者影响召回。

**档位名不进 `aliases`**（默认口径）。客户说「我要 360 Ultra」时，`resolve_model`
仍返回 `dfms-x700`，因为 `360 Ultra` 只在 `configs[].name` 里。若需要按档位名解析，
单独加 `config_aliases`，不与车型别名混在一起——见 `07` Q3。

### 4.2 参数层（K4 筛选用，必填）

| 字段 | 类型 | 说明 |
|---|---|---|
| `price` | object | 见 §4.4 |
| `powertrain` | list[enum] | `bev` / `phev` / `erev` / `ice`；车型级为「该车提供哪些」 |
| `body` | str | 车身形式 |
| `seats` | int | 座位数 |
| `dimensions` | object | `length_mm` / `width_mm` / `height_mm` / `wheelbase_mm`，可选 |
| `configs` | list | 档位列表，见 §4.3 |
| `audience` | list[str] | 目标人群关键词 |
| `scenarios` | list[str] | 适用场景关键词 |

### 4.3 档位 `configs[]`

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 档位名，如 `285KM 四驱 Max`；**用官方写法** |
| `price_wan` | 是 | 该档指导价，万元 |
| `promo_price_wan` | 否 | 限时促销价；与 `price_wan` 并存，不覆盖 |
| `powertrain` | 否 | 该档动力形式；空表示「按车型级处理，逐档待定」 |
| `drive` | 否 | 驱动形式：`前驱` / `后驱` / `四驱` |
| `range_km` | 否 | CLTC 纯电续航 |
| `note` | 否 | 该档的补充说明 |

`powertrain` **允许为空**，这是刻意的：M817 的逐档动力形式目前未确认，
若强制填写就会逼出臆造值。空值的语义是「不知道，别猜」——与全项目「宁可留白」一致。

### 4.4 `price` 的三段结构

| 字段 | 必填 | 说明 |
|---|---|---|
| `min_wan` | 是 | 全系最低指导价（含特别版） |
| `max_wan` | 是 | 全系最高指导价（含特别版、定制版） |
| `core_max_wan` | 否 | **主力价格带上限**，不含定制/限量版；缺省等于 `max_wan` |
| `as_of` | 是 | 价格采集日期 |
| `note` | 否 | 口径说明，如「标准版 63.77–69.90，另有 109.8 万顶配」 |

**为什么需要 `core_max_wan`**：917 全系 63.77–109.80 万，但对客沟通的默认价格带是
63.77–69.90。若只留 `min/max`，K4 按价格带筛车时会把 917 当成「百万级车」推给
80 万预算的客户；若只留 `core`，109.8 万的版本价就会落在区间外导致校验失败。
两段并存才是真实口径。

对外讲述时用 `core_*`，结构校验用 `min/max`。

### 4.5 表达层（K4 渲染用，必填）

| 字段 | 类型 | 说明 |
|---|---|---|
| `positioning` | str | 一句话定位 |
| `highlights` | list | `{title, text}`，每条一个论点 |
| `speech` | str | 散文段落：整车完整推介话术 |

`speech` 就是「散文编进条目属性」的落点（拍板第一条）：卖点叙述本无字段形状，它是
条目 `speech` 的值，随条目一起校验、一起冻结。

`highlights` 建议 5–7 条。超过 7 条会挤占 K4 的注入预算，且模型的注意力会摊薄。

## 5. 校验规则

加载期强制，任一不过即抛：

1. `model_id` 包内唯一；
2. **别名全局唯一**——`aliases` 与 `asr_variants` 合起来，任一字符串不得被两条条目认领；
3. 别名不得与另一条目的 `canonical_name` 相同；
4. `price.min_wan <= core_max_wan <= price.max_wan`，`as_of` 可解析；
5. `configs[].price_wan` 须落在 `[min_wan, max_wan]` 内（容差 0.01）；
6. `status` 在枚举内；`powertrain` 取值在枚举内（**空列表合法**）；
7. 表达层三字段非空；
8. `tiers[].models` 引用的 `model_id` 必须存在（悬空引用）；
9. 每个 `model_id` 至少被一个 tier 覆盖，或显式标注 `tier: null`（死知识检查）。

规则 2 与 3 是这套校验里最有价值的：别名表是污染高发点，两条目声称同一别名时查表结果
就不确定，而这种错在无校验时只会在跑批里以「归属莫名其妙地错」出现。

规则 8 与 9 在第 3 期落地（`03` T3-2），第 1 期先做 1–7。

**不校验的**：`configs[].powertrain` 为空、`aliases` 是否覆盖所有口语说法、
价格是否与实际门店一致。前两项属于「不知道」，第三项属于「人该管的」。

## 6. 与原始素材的关系

素材是**写作稿**，不是条目。它卖点与参数交织、同一参数多处重复。直接注入会把
「哪个数是准的」交给模型。

处理流程（拍板第一条的配套流程）：

1. **拆解整理**（人工发起、单独任务）→ 产出 `05-素材拆解草案-在售车型.md`，逐条落到本
   规范，并标出材料里互相矛盾或缺失的地方；
2. **人工确认** → 逐条核对数字与口径；
3. **定稿入库** → 写入 `packs/dfms-mengshi/models.json`，过校验，冻结。

素材本身不进运行期路径，只在草案里以出处形式留痕。

**素材多份时以新为准**：X700 有旧素材与 `X700车型信息.md` 两份，后者是上市后的正式数据，
旧素材的 X700 段落作废。拆解时在草案里标明来源，避免日后误以为两处都可信。
