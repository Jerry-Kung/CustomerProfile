# 知识库体系顶层设计（v0 策略稿）

> 状态：**策略稿，未实施**。本文只定分层、边界与路线，不含字段级设计与代码。
> 首个落地模块是「在售车型」；后续专家知识（竞品库、区域市场、金融政策等）按同一骨架扩展。

---

## 0. 先看现状：不是缺知识，是错知识在位

走读代码得到三个事实，按严重程度排列。

**① 表达层正在用别家的产品资料写我们自己的画像卡。**
L3 表达层从三份共享资产取料：产品详版（26.6KB）、产品速查（4.8KB）、邀约策略（4.8KB）。
这三份正文通篇是**广汽埃安**——AION Y Plus、AION S MAX、昊铂 GT/HT/SSR、埃安车型话术。
当前管线的本方品牌是东风猛士。也就是说每跑一单，模型都在拿着错的车型矩阵、错的价格带、
错的卖点去组织 `product_preferences`、`communication_strategies` 与邀约建议。
这不是"知识不够用"，是"知识有害"。

**②「本方品牌」在代码里没有定义。**
全仓搜不到一处定义本方品牌的常量或配置。L1 提示词只能让模型自行认定「试驾的那台、
顾问推销的那台所属品牌」。于是 `competing_brand` 那条关键例外——同品牌车型不算竞品——
实际上是一条软约束，取决于模型当次怎么理解。在售车型清单天然就是"本方品牌"的定义域，
这一块知识缺失，直接削弱的是取证准确率。

**③ 提示词里已经给知识库留了位置，但没接上。**
`pipeline_l1_facts` 写着「品牌知识库尚在建设中，建成后会被接入——当前不要因为拿不准
品牌名就整条不写」。这是上一次留下的一个明确挂载点，等着被填。

**规模参考**：6 份共享资产合计约 40KB 正文，全量塞进一次 L3 调用。其中真正"随合作方变化"
的部分（车型、卖点、话术）与"跨合作方不变"的部分（标签库、证据分级、画像格式、邀约方法论）
目前混装在同一批文件里，没有边界。

## 1. 三条设计原则

**原则一：知识不写进提示词正文，只写占位符。**
提示词是"怎么做"的指令，知识是"做什么"的素材。二者混在一份文件里，改一次知识就要
改动一份受评审的提示词资产，且正文不可读、不可校验、不可按需裁剪。
目标形态：模板里只有 `{{ product_brief }}`，正文由代码从知识库渲染后填入。

**原则二：能查表的不问模型。**
凡是"枚举、对照、归属、别名"这类可穷举判断的知识，落成代码可读的结构，0 token、
可校验、可留痕。只有"怎么说才打动人"这类判断才交给模型看正文。
这条与管线既有取向一致（§6 决策表第一条），只是此前没有把业务知识也纳入其中。

**原则三：知识只替换，不叠加。**
同一时刻只能有一个"合作方上下文"生效。换合作伙伴是**换模块**，不是加模块。
多套车型知识并存，等于把"当前在卖什么"这个事实变成需要模型判断的问题。

## 2. 四层架构

```
L0 知识源（人写·git 管理）
    一个模块一个目录，一份清单声明身份、版本、生效范围
        ↓ 编译期（离线，代码执行，失败即中断）
L1 结构化产物（schema 校验后的机器可读形态）
        ↓ 启动期（只读加载、缓存，运行期不可变）
L2 知识目录（按模块 ID 取用，带版本与内容指纹）
        ↓ 按用途渲染（每个消费点只拿到自己那一小块）
L3 消费视图（喂给提示词的文本 / 喂给代码的结构）
```

**为什么分四层而不是"建个知识文件夹让大家读"**：
- 分层把"写得好不好"与"用对没用对"分开。知识源是人写的散文与表格，编译期把它变成
  形状确定的产物；此后任何消费点拿到的都是同一份形状，不会各解析各的。
- 运行期不可变由 L2 保证：加载后不提供写接口，也没有热更新路径。这正好匹配"写入即冻结"
  （内容一旦定稿就不改，改了要专门起任务核实影响面）。
- L3 是防止污染的关键：**消费点拿到的是视图，不是全量**。没有视图层，知识库会退化成
  "又一个越来越大的提示词"。

**与现有模板机制的关系**：现有 `TemplateRepository` 已具备"按名取回逐字原文 + 变量渲染"
的能力，且缺文件即报错。知识源**不要**塞进模板目录——模板目录的契约是"正文不可改、
改正文即改运行行为、需评审"，而知识应当可以整体替换。二者是两种资源，走两条通道，
在 L3 汇合（知识渲染成文本后作为变量喂给模板）。

## 3. 什么该进知识库：三条判据

不是所有"像知识的东西"都该搬。判据按**谁能判对**来分：

| 判据 | 归属 | 例子 |
|---|---|---|
| 可穷举、可校验、答案唯一 | **知识（结构化）→ 代码消费** | 在售车型清单、品牌↔车型对照、ASR 音近别名、价格带 |
| 可穷举，但用途是"措辞素材" | **知识（成文）→ 提示词消费** | 车型卖点描述、竞品应对要点、邀约场景与钩子 |
| 是"怎么做判断"的方法论 | **规则层 / 提示词**，不进知识库 | 定级六步流程、证据分级口径、冲突消解顺序 |
| 是程序参数 | **配置**（`.env` / `Settings`） | 阈值、开关、模型 |

第四条判据用来挡住最常见的污染：把"某个客户群体应该怎么判断"写成知识表。
那类东西一旦进库，就会与规则层重复，且没有留痕通道。

**知识 ≠ 数据**。UAT 样本、转写缓存、批次产物是数据，不进知识库。

## 4. 在售车型模块的形态

### 4.1 一份知识，三个消费点

这是本模块设计的核心：车型知识不是"一段产品介绍"，而是同时服务三种完全不同的用途。

**消费点 A｜本方品牌与在售车型的定义域（代码，0 token）**
- 提供：品牌集合、在售车型的规范名与全部别名。
- 用途：判定客户提到的一台车属于"本方"还是"竞品"；把 ASR 错字与口语别名归一到规范名。
- 影响面：`competing_brand` 的同品牌例外、`owned_brand_model`、`test_driven_models` 的归属。
- 这是**最值得先做**的一块：它把一条软约束变成硬判定。

**消费点 B｜L1 的归一与纠错（代码查表 + 提示词兜底）**
- 提供：品牌/车型别名表（含音近错字）。
- 用途：模型抽出的品牌名先过一遍归一，命中则改写并标 `normalized`；未命中仍按现有
  "以模型原生知识为准"的口径放行。
- 原则：**只补不判**。查表命中只改动写法，不新增结论；未命中也不阻断。与既有枚举映射
  通道的取向完全一致，可复用同一套"失败不阻断、关闭即零 token"骨架。

**消费点 C｜L3 表达的选材（代码筛选 + 提示词消费）**
- 提供：按案筛选后的车型速查与卖点摘要。
- 筛选依据：本案 facts 里命中的意向车型、对比车型、价格带、用车场景。
- 兜底：一个都没命中时给全系速查表；命中时只给命中车型 + 至多一款相邻价位车型。
- 为什么要筛：当前把 40KB 无差别塞进去。筛选后预计单案注入量降到数千字，同时
  "该推荐哪台车"从"模型自己在长文里找"变成"代码已经挑好了候选"。

### 4.2 车型知识的内部结构（只到概念粒度）

一份车型条目需要同时承载"能查的"与"能说的"：
- **标识层**：规范名、别名/口语/音近写法、所属系列、在售状态与生效期。→ 供 A、B 查表。
- **参数层**：价格区间、动力形式、车身形式、关键配置、目标人群。→ 供代码做候选筛选。
- **表达层**：卖点叙述、适用场景、对应邀约钩子。→ 供 C 渲染成文本。

三层同源一份文件，避免"参数在表格里、卖点在不同文档里"的漂移。价格与配置这类
会变的东西标生效期，过期在编译期报警而不是运行期出错。

### 4.3 为什么不用现有那份 `our_models_dfms.txt` 直接当知识

它是一份**写作稿**，不是知识形态：4000 字散文、卖点与参数交织、同一参数在不同段落
重复出现（X700 的续航写了两处、M817 的价格在正文和对比表各一份）。直接注入会把
"哪个数是准的"这个问题交给模型。它的正确用途是**知识源的素材**，编译期人工拆分进
结构化条目后即退役，不再被运行期读取。

## 5. 可替换性：换合作伙伴

这是用户明确提出、且必须在架构层解决的需求。

**做法**：知识目录的顶层不是一个"车型库"，而是**合作方模块**。每个模块自带清单，
声明自己是哪家、卖哪些车、什么时候生效。运行期只认一个"当前生效模块"的标识。

**换人时的动作**：放入新模块目录 → 改一处配置指向新模块 → 启动期校验通过即生效。
全程不改代码、不改提示词。旧模块保留在仓库（历史批次要能复现），但不再被加载。

**必须一起换掉的东西**（否则会出现"埃安车型 + 猛士话术"这种半新半旧状态）：
1. 车型条目（本模块）；
2. 品牌特定的邀约话术与竞品应对；
3. 任何提示词正文里点名的品牌/车型（现有 L1、定级提示词里有"埃安 A27""埃安 YP"这类
   举例，属于**应当抽走**的硬编码）；
4. 回传契约里写死的品牌字段名（`knowledge_of_mengshi` 这类以品牌命名的字段是**契约**，
   不能跟着换）。**本轮已定：暂不处理**，仅在换伙伴时再议；守卫须将其列入豁免。

**审计口径**：合作方模块清单里应能回答"换掉它，还有哪些地方仍写着旧品牌"。
建议做成一条测试：全仓扫品牌名，命中而未在豁免清单内即失败。这条守卫的价值高于
任何文档约定，因为它不可能被忘记。

## 6. 防污染治理：六条硬规则

用户担心的是"知识不断增长把架构撑坏"。以下每条都必须有对应的机器检查，否则只是口号。

1. **一模块一目录一清单**。没有清单的知识文件不加载，加载了不产生任何效果——避免
   往目录里丢个文件就"意外生效"。
2. **知识不引用代码内部字段名**。知识用业务语言写；需要与字段对接的地方，在编译期
   建立映射并校验字段存在。防止字段改名后知识静默失效。
3. **提示词正文里不得出现具体品牌/车型**。品牌信息只能经视图注入。现有正文里的举例
   属历史遗留，迁移时清理。
4. **孤儿双向检测**：知识库里未被任何视图消费的条目要报警（死知识）；视图引用了知识
   库中不存在的键要报错（悬空引用）。与规则层现有的"孤儿标记 / 未落地规则"守卫同构。
5. **模块内唯一**：同一车型在模块内只能有一条规范条目，别名冲突在编译期报错。
   别名表是污染最容易发生的地方——两个条目声称同一个别名，查表结果就不确定了。
6. **版本进留痕**：批次产物记录生效模块的 ID 与内容指纹。理由与 `definition_hash`
   相同——换了知识，两批结果不可直接对比，必须能在产物里看出来。

## 7. 迁移路线

**第 0 期｜止血（最高优先级）**
把三份埃安资产从表达层摘下来，换成在售车型模块的最小视图（只有车型名、价格带、
一句话定位）。目的不是内容丰富，是**停止输出错品牌内容**。同时落地消费点 A——
让"本方品牌"第一次变成代码里的事实。

**第 1 期｜骨架**
建立四层结构与模块清单，把「在售车型」拆成结构化条目（标识/参数/表达三层），
接上消费点 B 与 C。完成后 L1 那句"品牌知识库尚在建设中"可以改口。

**第 2 期｜收编**
把 6 份共享资产按「随合作方变 / 跨合作方不变」切开：标签库、证据分级、画像格式、
邀约方法论属通用，进通用模块；车型卖点、品牌话术进合作方模块。这一步会暴露
「方法论与话术其实是混写的」——拆开是本次最重要的结构性收益。

两份资产的实际处置见 §8 第二条：**邀约策略留用但去品牌化**（清掉「广汽埃安」字眼、
改通用指代、纯产品内容挪去合作方模块、竞品名保留）；**产品详版与速查版不迁移**，
它们的内容全部归合作方模块，由在售车型条目重写。

**第 3 期｜治理**
补齐六条守卫，纳入测试集；把知识版本写进批次留痕。

**第 4 期｜扩展**
竞品库、区域市场、金融政策按同一骨架接入。竞品库要特别注意：它是"对外部世界的认识"，
变化快于合作方模块，生效期与更新节奏与车型知识不同，可能需要独立的版本策略。

## 8. 已拍板事项（2026-10-29）

三条都已定，后续模块按此执行。

**一、知识源写成结构化条目；散文编进条目的属性字段。**
不做「整份散文 + 编译期由模型抽取」的路线——那条路每次改知识都要过模型，结果不可复现，
与「写入即冻结」冲突。散文不是被排除，而是**归位**：卖点叙述、话术这类本来就没有字段形状
的内容，成为某个条目的一个属性值，随条目一起校验、一起冻结。

**配套说明（决定流程而不只是格式）**：专家给的第一手材料形式不固定——可能是一份产品文档、
几张截图、一段口述整理。因此知识入库分两步，不合成一步：

1. **拆解整理**（人工发起、单独起任务）：把原始材料读成条目草案，逐条落到约定结构上，
   并标出材料里互相矛盾或缺失的地方。这一步的产物是**人可读的草案**，不进运行期。
2. **定稿入库**：草案经确认后写入知识源目录，编译期校验通过即冻结。

两步分开的理由：拆解是「理解材料」，入库是「确定事实」，混在一起会让「我理解得对不对」
与「这份数据对不对」无法分别复核。原始材料不进运行期路径，只在草案里以出处形式留痕。

**二、埃安邀约策略可以留用，但必须清除全部「广汽埃安」字眼，换成通用话术。**
具体操作：
- 策略类别、目标客户画像、触发标签、邀约动作／场景、优先级——跨品牌成立，原样保留；
- 话术示例里的「埃安车型」改为「这款车／这台车」这类通用指代，涉及具体车型参数的表述
  删除或抽象；
- 品牌定位、主力车型速览、价格区间这类纯产品内容**不留在通用模块**，归入合作方模块；
- 文中出现的竞品（比亚迪、特斯拉、小鹏）属于「外部世界」，清品牌字眼时不要顺手删掉，
  它们在第 4 期会进竞品库。

**三、`knowledge_of_mengshi` 这类品牌命名字段本轮不动。**
换伙伴时再讨论。据此，§5「必须一起换掉」清单里的契约层一项降级为「已知风险，暂不处理」，
不进入任何守卫的失败条件——守卫扫品牌名时必须把它们列入豁免，否则每次跑都在报一个
已知且已接受的问题。

## 9. 与现有架构的接缝

| 现有构件 | 接缝方式 |
|---|---|
| `TemplateRepository` | 模板只管指令，知识经变量注入；两条通道在渲染时汇合 |
| 共享资产（6 份） | 拆分为通用模块 + 合作方模块，正文不动、组织方式变 |
| 规则层三通道 | 消费点 A/B 走 code 通道形态（只出动作、失败不阻断、关闭即零 token） |
| 枚举映射通道 | 归一与纠错复用其骨架与开关习惯，不新建机制 |
| 批次留痕 | 增记知识模块 ID 与内容指纹 |
| 参考标准表 | 未来可作为"知识在字段口径上的投影"入口，当前不动 |
