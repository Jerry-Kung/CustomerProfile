# 客户跟进履历（follow_up_history）

> 状态：**已批准（2026-11-16）**，按 `任务书.md` 开工。
> 业务契约原文：`docs/reference/AI画像回传接口变更说明-客户跟进履历.md`
> 契约要点只在此引用，不复述。

## 1. 需求与边界

画像 v2 回传体 `analysis_result` 新增 `follow_up_history`：把销售顾问对这位客户的
历史跟进动作梳理成时间线。它服务的是「销售交接/续跟时快速看懂这个客户被跟到哪一步」，
与客户自身人设（性格、家庭、偏好）相关性弱，因此**不进 L1 取证、不进 Notes 契约**，
单独一条旁支，与 `pipeline` 的九板块链条并行。

数据源只有一个渠道：L0 记录层里的 `OntologyLeadFollowRecord`（中文名「销售跟进记录」），
`multi="all"` 逐条展开，渠道移除标记已由 `_manifest_index` 拦掉。

## 2. 数据实况（UAT 20261102–20261103 批次实测，791 案）

| 项 | 实测 |
|---|---|
| 有跟进记录的案例 | 546 / 791（69%），其余 245 案渠道整体缺失 |
| 单案条数分布 | 1 条 289、2 条 159、3 条 58、4 条 23、5 条 11、6 条 4、9 条 1、10 条 1 |
| `followcontent` 长度 | 中位 13 字，p90 44 字，最长 178 字（销售手写简写：「电话没接通。」「用户忙无法接通」） |
| `arrivetime`（到店时间） | **全空**，不能作为「到店」节点的判据 |
| 字段全空但仍有一条内容 | 158 条（目的/方式/结果三个枚举皆 `null`） |
| 同一客户经手多名顾问 | 91 案 |
| 同分钟多条记录 | 15 案（排序需要稳定 tiebreak） |
| 含战败 / 转商机 | 83 条 `followresult=90453` 暂败；67 条 `changebusinessopportunity=1` |
| 意向级别、车型 | 枚举可解码；车型名实测有 `Max+` / `MAX+` / `Ultra` / `PRO` 等写法不一 |

两条直接结论：

1. **原始内容极短**，直接抄进卡片就是一堆「电话没接通」。要让销售看懂，必须补上
   「什么时候、以什么方式、跟到了什么结果、下一步是什么」——这部分关键信息其实
   在枚举字段里（沟通方式、跟进目的、跟进结果、下次跟进时间），可**确定性取到**。
2. 业务文档示例里的「首次到店」「首次试驾」这类节点名，**不能从数据里直接取**，
   需要一层归纳。

## 3. 方案

### 3.1 分工：代码管结构，模型管措辞

沿用「能写成代码的约束不交给模型」的既有原则：

| 归代码（0 token、可验证） | 归模型（1 次调用） |
|---|---|
| 取哪些记录、排序、时间归一 | 节点命名（首次邀约 / 试驾邀约 / 价格沟通 / 战败跟进……） |
| `id` / `sequence` 生成与唯一性 | `contents` 的整合与可读化（把简写补成整句） |
| 上限（≤100 节点、≤20 条内容、≤1000 字） | 同一次事件的多条记录合并成一个节点 |
| `extra_info` 全量（渠道/参与人/关联车型/跟进结果/意向级别/下一步） | — |
| 时间格式合法（非法即 400，整次回写回滚） | — |
| 未被采纳的记录兜底成节点（不丢记录） | — |

**模型不输出 `extra_info`**：那六个键全都能从枚举与记录字段确定性取到，交给模型只会
引入「把代码抄错」这一种新失败模式。

### 3.2 落点：code 节点承载，不用 `llm` 节点

用户提的「单独一次 LLM 调用、无数据则跳过」，用**同一个 code 节点内部**实现，
而不是 `if-else` + `llm` 节点。理由是本仓库已经付出过代价的那条：

> 调度器对失败节点会阻塞整棵下游子树。做成 `llm` 节点，一次调用失败就挡掉回传，
> 把「履历没生成」升级成「整案失败」。（`docs/design/客户人设画像管线设计.md` §6）

本节点与 `L2 兜底裁决`/`checker` 同骨架：无数据在发起调用前就返回（零 token），
失败吞成状态位、不抛。`node_ref` 由 `execute_code` 注入，尝试留痕与 `llm` 节点一致。

### 3.3 图变化（`customer_profile_pipeline`）

一处新增、一处改绑：

```
L0 记录层 ──► 跟进履历整理（code，1 次 LLM）
                     │
L3 校验与表达 ──► 回传体构造 ──► 画像回写
                   ▲
                   └── follow_up_json
```

- 新节点 `pipeline_follow_up`（code，`after=(L0_RECORDS,)`），出参
  `follow_up_json` / `follow_status` / `follow_calls` / `follow_error` /
  `record_count` / `node_count` / `dropped_indexes` / `fallback_used`。
- `pipeline_callback_build` 增加入参 `follow_up_json`，`after` 改为
  `(PRODUCTION, pipeline_follow_up)`。
- 它接在 L0 之后而不是回传前，是为了与 L1/L2/L3 并行，不增加关键路径时延。

### 3.4 取数与字段来源

输入用 L0 的 `records_json`（不直接读 `history_body`）——移除标记、排序、
「哪个渠道活着」这些判定 L0 已经做过一遍，第二条取数口就是第二套口径。

记录里没有原始 `raw_payload`，只有渲染后的正文（`render_record` 的
`字段中文名：值` 逐行格式）。因此在该节点内做一次**受控的行解析**取回
跟进目的/沟通方式/跟进结果/意向级别/车型/创建时间/顾问/下次跟进时间；解析不到的键
留空，不猜。此格式由 `render_record` 生成，属于我们自己的稳定契约，用单测钉住。

**时间口径**：用记录正文里的「跟进创建时间」（业务事件时刻），不用 L0 的
`created_at`（落库时刻，实测差几分钟）。排序也按业务时刻重排。

### 3.5 契约风险的本地收口（最重要）

契约写明「校验失败返回 400，本次画像回写**整体回滚**」。也就是说一条不合法的
`followed_at` 会让整个画像（含定级、Notes、九板块）作废。因此回传前必须逐条自检：

1. `followed_at` 只在解析成功时输出，统一成 `YYYY-MM-DDTHH:MM:SS` 或 `YYYY-MM-DD`；
   解析失败**整条丢弃该字段**，不输出原串。
2. `node_name` 非空、≤100；`contents` 剔除空串、每条 ≤1000、最多 20 条；单条节点
   内容全空则给它一条兜底陈述（「暂无更详细的跟进说明」），不输出空数组。
3. `id` 全局唯一、≤50；`sequence` 正整数且唯一，按时间升序重排为 1..N。
4. `extra_info` 只保留标量与字符串列表，序列化超 64KB 整体丢弃该键。
5. **无数据时整个 `follow_up_history` 键不出现**，绝不输出 `[]`——按契约 §3.4，
   `[]` 的语义是「清空该客户全部履历」，而我们只是这次没取到数据。

第 5 条是本方案唯一会**破坏性**影响线上数据的点，`callback_build` 里要有一条用例
正面钉住它。

### 3.6 无数据 / 失败 / 增量

| 情形 | 行为 |
|---|---|
| 渠道不存在，或渠道在但全部 `exception` | 不发起调用，不出键 |
| 模型调用失败 | **代码兜底**：按记录 1:1 出节点，名取「沟通方式+跟进目的」，内容取记录原文；仍出键 |
| 模型返回的节点只覆盖部分记录 | 未覆盖的记录由代码补成节点，追加在对应时间位置 |
| 增量 T0 原样回传 | 上一版回传体里有什么就发什么，本次不动 |

T0 那一行需要业务方知悉：**上线后历史没变过的客户，区块会一直是缺失的**，
直到该客户出现新记录触发 T1/T2/T3。这不影响正确性（缺失＝保留），但会影响
「覆盖率」类指标的口径。

| `13135664256` | 0 条跟进记录，但录音等其他渠道齐全 | 跳过分支 + 确认不因其他渠道误触发 |

| `13121132715` | 6 条，含战败 + 转商机 + 订单 + 试驾/外呼录音 | 最强边界，跨渠道一致性 |
| `18986162155` | 9 条，3 名顾问，同分钟重复，6 个录音 | **上限与合并**：同分钟合并、多人多顾问 |

回放注意：本批自 2026-10-28 起录音位在 `archive-replay` 里可能为空或 599（转写缓存
未播种），而跟进履历分支只读文本渠道，不受影响；但带录音的两案（`13121132715`、
`18986162155`）整体产物会与 UAT 不同，只看履历区块、不横向比九板块。

先跑前三个（无录音、体量小）通结构，再跑全八个。逐案人工核读：节点排序是否与
`createtime` 一致、有无无中生有的动作、`extra_info` 有无未解码的裸码值或内部键名
（`docs/README.md` 的对客产出红线）。

## 6. 验收标准

1. 无跟进记录的案例：回传体不含 `follow_up_history`，节点零 LLM 调用（`follow_calls=0`）。
2. 有记录的案例：节点数 ≥1、≤100，`sequence` 连续 1..N，`id` 唯一。
3. 全部 `followed_at` 通过契约 §3.3 的格式校验（本地自检为零告警）。
4. 每条输入记录都能在同一次输出里找到落点（`dropped_indexes` 为空，或补节点兜底）。
5. 模型调用失败时仍产出可用区块（`fallback_used=true`），且整条回写链路不受影响。
6. `contents` / `extra_info` 内不出现英文键名、规则编号、枚举裸码、`未知渠道` 类占位串。
7. 既有用例全绿；`callback_build` 六键断言改为七键。

## 7. 已定口径（2026-11-16 拍板）

1. **不加开关**。用户明确要求移除 `FOLLOW_UP_ENABLED`，不入环境变量；本特性在业务测试臂上始终执行。
2. **模型失败保留代码兜底**（§3.6）：按记录 1:1 出节点，履历比精修重要。
3. **`contents` 两段式**：第一段原样保留销售原始记录，第二段是模型补的可读陈述。
4. **节点 `id`** 按契约缺省 `fu-{sequence}`。
