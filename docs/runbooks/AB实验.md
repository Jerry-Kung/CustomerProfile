# AB 实验

> 用途：把「客户人设画像输出质量优化」的新旧两条链路放在**同一批号码、同一套配置**下
> 各跑一遍，产出可逐案比对的两臂批次。
> 实验设计与指标口径见 `../business_opt01/落地方案.md`；跑批脚本的通用用法见
> `./基线实验.md`（本文件只讲**两臂**相关的部分，不重复那份的通用流程）。

## 1. 它解决什么问题

`基线实验.md` 讲的是「改动前后质量有没有崩」，对照物是**历史批次**。AB 实验更进一步：
两条链路要**同时**跑，逐案比对「同一个客户，两套实现各给出什么画像」。

因此它比基线多一条硬要求：**两臂之间除了被测的那一处，其余必须完全一致**。
不一致就不是 AB，是两次互不相干的实验，结论无法归因。

## 2. 两条臂

| 臂 | `--workflow-id` | 说明 |
|---|---|---|
| 基线臂 | `customer_profile_entry` | 现行主入口（`证据线索汇总 → 人设特征判断 → 画像内容生成与回写`） |
| 业务测试臂 | `customer_profile_pipeline` | 事实账本管线（`L0 记录 → L1 取证 → L2 投影 → L4 分诊 → 成文`）。该臂的实验已完成并通过核验，2026-10-15 起对外口径由「实验臂」改为「业务测试臂」；`workflow_id` 不动 |

两臂**共用同一个跑批脚本** `scripts/run_baseline.py`，只用 `--workflow-id` 区分。
这是刻意的：复制脚本会让两臂的归档逻辑分叉，产出不可比的产物。

## 3. 操作流程

### 3.1 跑业务测试臂

```
python scripts/run_baseline.py \
  --out-dir experiments/abexperiments \
  --batch-id A-pipeline-<日期> \
  --workflow-id customer_profile_pipeline \
  --transcript-cache-dir experiments/transcript_cache
```

`--workflow-id` 拼错会在**开跑前**报错退出（脚本先核对 ID 是否已定义，不建服务、不出网），
不会跑几十个号码之后才失败。这比在跑批中途以「子工作流未注册」暴露要便宜得多。

### 3.2 跑基线臂

分两种场合，别混：

- **阶段一/二期间不必重跑。** 用已冻结的历史批次
  `experiments/batches/baseline-39-dsv41-noThink/` 作为对照物即可——那时两臂共用的
  `customer_profile_production` 还没被改。
- **阶段三落地后必须重跑一次。** 阶段三要改 production，一改基线臂也跟着变。此时在
  **分支点 commit** 的 worktree 里跑，保证基线臂拿到的是改动前的 production：

```
git worktree add ../cp-baseline <dev-business-opt01 的 HEAD>
# 把 .env 拷进 worktree，然后在里面跑第 3.1 节的基线臂命令（--out-dir 指向同一场地）
```

### 3.3 转写缓存必须显式给

```
--transcript-cache-dir experiments/transcript_cache
```

不给会默认推导成 `<out-dir>/transcript_cache`，即
`experiments/abexperiments/transcript_cache`——一个空目录，会让 39 段录音**全部重新识别**
（单条 20–30 分钟）。共享缓存与批次同级、两臂共用：AUC 识别与被优化的工作流逻辑无关，
同一段录音结果必然相同，不共用只是白花几小时并引入无意义的差异。

`--no-transcript-cache` 关的是**读取**（本次不复用），写入仍默认进行；要连写入也关，
再加 `--no-cache-write`。

### 3.4 分轮推进

不要一上来就跑全量 39 案。

| 轮次 | 范围 | 目的 |
|---|---|---|
| R0 | 3 案 | 新链路能跑完、产物形状正确 |
| R1 | 13 案（探针集） | 逐案核对「已知正确答案」，名单见 `落地方案.md` §5.4 |
| R2 | 39 案 | 出正式 AB 对比报告 |

**R0 起就要真实出网**（LLM + AUC + mhero）。AUC 走共享缓存，主要成本在 LLM。

**轮次记录**：

- **R0**（2026-10-10，3 案，实验臂 3/3 `succeeded`）：结论与三条质量问题见
  `../business_opt01/R0结果.md`。该文件同时记录了**判据 3 未满足**的一个实例：
  跑批时被测代码尚未提交，`manifest.code_commit` 记的是 HEAD 而实际执行的是工作区代码，
  批次不可从所记提交复原。跑 R1 前须先提交。
- **R1**（2026-10-10，13 案，提交 `e0eb935`）：**判据 3 首次通过**。但 Notes 从基线的 360
  掉到 158，根因是**三个工程缺陷**（锚点长度门过严、空产出清空字段、枚举键附录位置不当），
  已由 `b6a7023` 修复。结论见 `../business_opt01/R1结果.md`。
- **R1b**（2026-10-10，13 案，提交 `b6a7023`）：修复后复跑，13/13 `succeeded`，
  四条判据全过。Notes 回到 **192**，定位丢失 237→30。**R1 首轮的数字不可对外引用**
  （它测的是带缺陷的实现），只引 R1b。

**跑批前提醒**：R1 的教训是「判据全绿不等于质量达标」——R1 的四条判据当时只有 3 条通过，
但即便全过，Notes 腰斩仍是缺陷。**每轮跑完除了核 §4 的四条判据，还要比 Notes 字段总数**，
它是最早暴露问题的指标。

## 4. 可比性：四条底线（跑完必须逐条核）

| # | 要求 | 判据 | 怎么核 |
|---|---|---|---|
| 1 | 号码一致 | 两臂 `phones_sha256` 相同 | 比 `manifest.json` 的该字段 |
| 2 | 定义单值 | 每臂内 39 案 `definition_hash` 只有一个值 | 见 `基线实验.md` §5 的 PowerShell 单行 |
| 3 | 代码冻结 | 跑批期间不改代码 | 在固定 commit 的 worktree 里跑；看 `manifest.code_commit` |
| 4 | 不回写 | 两臂 `WRITEBACK_ENABLED=false` | 查 `request_attempts` 里 `update-profile` 为 0（命令见 `基线实验.md` §8） |

**第 2 条两臂之间不同是预期的**——那是被测的那一处。**每臂内部**必须单值。

第 3 条要特别留意：AB 两臂各自都要跑数小时，而开发期改代码是常态。前半批用旧图、
后半批用新图，整批不可比，且症状隐蔽（每份产物看起来都正常）。跑批期间**冻结代码**。

## 5. 产物与目录

```
experiments/abexperiments/
├─ batches/
│  ├─ B-baseline-<日期>/  基线臂（结构与 experiments/batches/ 完全一致）
│  └─ A-pipeline-<日期>/  业务测试臂
└─ compare/               逐案比对表与指标汇总
```

单批次的内部结构（`manifest.json` / `summary.md` / `trace.db` / `runs/<号码>/…`）与
`基线实验.md` §4 逐字相同——两臂跑的是同一个脚本，没有第二套归档格式。

**`manifest.json` 的 `workflow_id` 记的是实际使用的入口工作流**，不是缺省常量。
写死常量会让业务测试臂的批次声称自己跑的是基线图，第 1、2 条判据随之失效。

## 6. 不放进这个目录的东西

- **不放代码。** 脚本在 `scripts/`，工作流定义在 `src/customer_profile/workflows/`。
- **不放文档结论。** 结论写 `docs/`。本目录被 gitignore，放这儿等于不存在。
- **不放真实客户数据的手工副本。** 批次产物本身已含 PII，靠目录级 gitignore 兜住；
  再单独导出散落副本会绕开这层保护。

## 7. 禁用命令

`git clean -xdf` / `git clean -X` 会**一并删除**整个 `experiments/`（含历史基线与共享
转写缓存）。**禁用这两条命令。** 详见 `基线实验.md` §7。

## 8. 常见问题

**「实验臂跑完是 succeeded，能下结论了吗？」**
不能。`succeeded` 只说明运行没失败，不说明新链路**走到了该走的分支**——`基线实验.md` §9
讲的 `skipped` 陷阱在这里同样成立。先核 §4 的四条底线，再看产物。

**「两臂的 `definition_hash` 不同，是不是跑错了？」**
不是。两臂本来就是两张图，定义哈希**应当**不同。要看的是**每臂内部**是否单值。

**「指标算出来和方案里的预估对不上？」**
预估（如单案 5 万 token、十秒级耗时）是设计目标，**以 R2 实测替换**。探针集里逐案核对的
「已知正确答案」才是判定质量的主要依据。
