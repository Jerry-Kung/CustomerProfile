# 部署与运行

> 面向运维。记录**操作方法、约束与坑**，不重复代码可读出的内容。
> 系统形态见 `../architecture.md`。

## 1. 依赖与安装

```
pip install -r requirements.txt
cp .env.example .env    # 然后填入真实端点与凭据
```

`.env` 位于仓库根目录，已被 gitignore。**它是部署侧发现配置项的唯一入口**——
`settings.py` 里每个字段都应在 `.env.example` 里有对应行（`WRITEBACK_ENABLED` 曾遗漏过，
模板与代码不同步的代价是那一项在部署时不可知）。

## 2. 两个进程

```
# API（提交与查询）
python -m customer_profile.main
#   等价于 uvicorn customer_profile.main:app --host 0.0.0.0 --port 8000

# worker（执行；可独立部署，也可与 API 同机）
python -m customer_profile.worker
```

**先起 worker 还是先起 API 都可以**，两者只在数据库层面耦合。

### 2.1 单机最简形态

`INLINE_WORKER=true`（缺省）时 API 进程自己消费队列，**不需要单独起 worker**。
适合开发、测试与小规模使用。

### 2.2 生产形态（API 与执行分离）

`Dify迁移任务说明.md` §4 要求「API 与单个执行 worker 分开」。做法：

```
INLINE_WORKER=false     # API 只提交与查询，不执行
```

然后单独起一个 `python -m customer_profile.worker`。多个 worker 时同时设置
`WORKER_REPLICAS`，**并确保 `LLM_RPM_LIMIT` / `LLM_TPM_LIMIT` 能被它整除**，否则启动即报错
（见 ADR 0002 与 `../adr/0002-配额用显式分配而非共享.md`）。

## 3. 数据库：三条硬约束

- **SQLite 文件不可放在网络挂载**（NFS / SMB / 某些同步盘）。WAL 依赖共享内存文件
  （`-shm`），网络文件系统上会锁失效，**可能损坏数据库**。用本地卷。
- `SQLITE_BUSY_TIMEOUT_MS` 保持非 0（缺省 5000）。API 与 worker 各持一个连接，不设它时
  写相遇会直接抛 `database is locked` 而不是等一会儿。
- **备份时连 `-wal` / `-shm` 一起拷**，或先停进程。只拷 `.db` 会丢掉尚未 checkpoint 的
  最新事务——任务队列的入队记录就在这些事务里。

## 4. 表结构变更

项目**不使用迁移框架**。新增列登记在 `persistence/store.py` 的 `_ADDED_COLUMNS`，由
`Store.connect()` 在启动时按 `PRAGMA table_info` 判断后补列（幂等）。

对运维的含义：**升级代码后重启进程即完成补列**，不需要手工 DDL。两个进程同时启动时，
后来者可能拿到 `duplicate column name`——那是正常的，已被吞掉。

## 5. 停机

- **API**：`SIGINT` / `SIGTERM`。它会先等在飞运行收敛（最长 60s），再关闭存储。
- **worker**：`SIGINT` / `SIGTERM`。收到后**停止领取新任务**，等在飞运行自然结束。
  正在跑的任务不会被中断——一次画像流程二十余分钟，中途砍断会留下需要人工处理的状态。
  直接 `kill -9` 的后果见「故障定位」。

## 6. 提交任务

```
curl -X POST localhost:8000/runs \
  -H 'content-type: application/json' \
  -d '{"workflow_id":"customer_profile_entry","inputs":{"phone_number":"13800000000"},"business_ref":"13800000000"}'
```

返回 `run_id`。**任务在返回前已落库**（`status=queued`），因此进程此刻挂掉任务也不会丢。

入参校验只对主入口 `customer_profile_entry` 生效（手机号须匹配 `^1[3-9]\d{9}$`），
其它工作流入参契约不同。

## 7. 运行台

`SERVE_UI=true` 时后端在 `/` 托管 `frontend/dist` 的构建产物。要求先跑过
`cd frontend && npm run build`；未构建时打印告警并**跳过而非启动失败**（可选功能不应成为
硬依赖）。

`GET /runtime` 报告当前运行态：回放模式、**回写开关**、模型名、队列深度、并发与配额上限。
它**不返回任何凭据**（由测试断言）。

**注意 `writeback_enabled`**：为 false 时回写节点不发请求，但运行仍显示 `succeeded`。
界面上「成功」不等于「已写进生产库」——这一条是 `/runtime` 存在的主要理由。

## 8. 回放模式

`REPLAY_MODE=fixture` 时 LLM 与 HTTP 全部走本地固定响应，**物理上不出网**（transport 兜底
返回 599）。用于确定性验证。此时任何写请求都不会真的发出，回写自然被拦下。

`REPLAY_STRICT=true`（缺省）时未命中固定响应直接失败——静默返回空响应会让「没跑通」看起来
像「跑通了」。
