# 部署与运行

> 面向运维。记录**操作方法、约束与坑**，不重复代码可读出的内容。
> 系统形态见 `../architecture.md`。

## 1. 依赖与安装

两条路径，配置口径相同（都读仓库根目录的 `.env`）：

**方式 A：装容器（推荐用于测试环境与生产）**

```
cp .env.example .env       # 填入真实端点与凭据
docker compose up -d --build
docker compose ps
docker compose logs -f worker
```

**方式 B：直接跑进程（开发与排障）**

```
pip install -r requirements.txt
cp .env.example .env    # 然后填入真实端点与凭据
```

`.env` 位于仓库根目录，已被 gitignore。**它是部署侧发现配置项的唯一入口**——
`settings.py` 里每个字段都应在 `.env.example` 里有对应行（`WRITEBACK_ENABLED` 曾遗漏过，
模板与代码不同步的代价是那一项在部署时不可知）。

### 1.1 容器部署要点

`Dockerfile` 产出一个镜像，`docker-compose.yml` 用三个服务共用它，各自的 `command` 就是
§2 的三个进程。apt 与 pip 均走清华源。

- **配置来源**：compose 用 `env_file: .env` 注入，与 `settings.py` 自己读 `.env` 取值一致。
  **改 `.env` 后要 `docker compose up -d` 重建容器**（环境变量在容器启动时固定），
  `restart` 不够。compose 只覆盖随形态变化的两项：`SERVE_UI=true`（镜像里已带前端构建产物）
  与 API 服务的 `INLINE_WORKER=false`（执行交给独立 worker 服务，不让两个消费者抢同一队列）。
- **数据卷**：命名卷 `cp-data` 挂到容器内 `/app/data`，全库位置就是
  `/app/data/customer_profile.db`。**它落在本机磁盘，不可改成网络挂载**（§3 第一条）。
  宿主机与容器互换数据：

  ```
  docker compose cp data/customer_profile.db api:/app/data/customer_profile.db
  docker compose cp api:/app/data/customer_profile.db ./data/
  ```

  拷的时候连 `-wal` / `-shm` 一起带，或先停服务（同 §3）。
- **停止宽限期是刻意分开的**：`api` 90s、`inbound` 30s，`worker` **30 分钟**。
  一次画像约 21 分钟，用缺省的 10 秒会把在飞运行砍成 interrupted（§5）。改小它等于放弃优雅停机。
- **端口**：8000 是内部只读面、无鉴权，只该在内网暴露；8099 对外写面强制密钥。
  compose 里两条 `ports` 都是全接口绑定，若宿主直接对公网，把 8099 改成只绑内网地址。
- **镜像里没有 ffmpeg**（`Dockerfile.example` 里有，是照抄会误带的一项）：本项目音频走云端
  URL，仓库内无 ffmpeg / ffprobe / pydub 调用。
- **前端改动要先构建再建镜像**：镜像 `COPY frontend/dist`，容器内不做 npm 构建。
  只改后端时 `--build` 会命中缓存，很快。

## 2. 三个进程

```
# API（提交与查询、托管运行台）
python -m customer_profile.main
#   等价于 uvicorn customer_profile.main:app --host 0.0.0.0 --port 8000

# worker（执行；可独立部署，也可与 API 同机）
python -m customer_profile.worker

# 对外任务接口（接收前端任务队列推送；只接单，不执行、不查询）
python -m customer_profile.inbound
#   等价于 uvicorn customer_profile.inbound:app --host 0.0.0.0 --port 8099
```

**先起 worker 还是先起 API 都可以**，三者只在数据库层面耦合。容器部署时三者是
compose 服务 `api` / `worker` / `inbound`，`command` 与上面三条命令一一对应。

`main`（8000）是**内部只读面**，`inbound`（8099）是**对外写面**。分两个进程而不是
一个应用挂两个端口，是因为两者的暴露范围与生命周期不同：对外写面出问题不该拖住
运行台，反之亦然。两者的鉴权口径也不同——8000 无鉴权（只在内网），8099 强制密钥。

### 2.1 单机最简形态

`INLINE_WORKER=true`（缺省）时 API 进程自己消费队列，**不需要单独起 worker**。
适合开发、测试与小规模使用。

### 2.2 生产形态（API 与执行分离）

生产形态要求「API 与执行 worker 分开」。做法：

```
INLINE_WORKER=false     # API 只提交与查询，不执行
```

然后单独起一个 `python -m customer_profile.worker`。多个 worker 时同时设置
`WORKER_REPLICAS`，**并确保 `LLM_RPM_LIMIT` / `LLM_TPM_LIMIT` 能被它整除**，否则启动即报错
（见 ADR 0002 与 `../adr/0002-配额用显式分配而非共享.md`）。

## 3. 数据库：三条硬约束

- **SQLite 文件不可放在网络挂载**（NFS / SMB / 某些同步盘）。WAL 依赖共享内存文件
  （`-shm`），网络文件系统上会锁失效，**可能损坏数据库**。用本地卷。
- `SQLITE_BUSY_TIMEOUT_MS` 保持非 0（缺省 5000）。API 与 worker 各持一个连接，不设它时
  写相遇会直接抛 `database is locked` 而不是等一会儿。
- **备份时连 `-wal` / `-shm` 一起拷**，或先停进程。只拷 `.db` 会丢掉尚未 checkpoint 的
  最新事务——任务队列的入队记录就在这些事务里。

## 4. 表结构变更

项目**不使用迁移框架**。新增列登记在 `persistence/store.py` 的 `_ADDED_COLUMNS`，由
`Store.connect()` 在启动时按 `PRAGMA table_info` 判断后补列（幂等）。

对运维的含义：**升级代码后重启进程即完成补列**，不需要手工 DDL。两个进程同时启动时，
后来者可能拿到 `duplicate column name`——那是正常的，已被吞掉。

## 5. 停机

- **API**：`SIGINT` / `SIGTERM`。它会先等在飞运行收敛（最长 60s），再关闭存储。
- **worker**：`SIGINT` / `SIGTERM`。收到后**停止领取新任务**，等在飞运行自然结束。
  正在跑的任务不会被中断——一次画像流程二十余分钟，中途砍断会留下需要人工处理的状态。
  直接 `kill -9` 的后果见「故障定位」。

## 6. 提交任务

```
curl -X POST localhost:8000/runs \
  -H 'content-type: application/json' \
  -d '{"workflow_id":"customer_profile_pipeline","inputs":{"phone_number":"13800000000"},"business_ref":"13800000000"}'
```

返回 `run_id`。**任务在返回前已落库**（`status=queued`），因此进程此刻挂掉任务也不会丢。

入参校验只对主入口 `customer_profile_pipeline`（业务测试臂）生效（手机号须匹配
`^1[3-9]\d{9}$`），其它工作流入参契约不同。主入口于 2026-10-16 由基线臂
`customer_profile_entry` 改指本臂；该臂已从注册表摘除，提交它会得到 404。

## 7. 运行台

`SERVE_UI=true` 时后端在 `/` 托管 `frontend/dist` 的构建产物。要求先跑过
`cd frontend && npm run build`；未构建时打印告警并**跳过而非启动失败**（可选功能不应成为
硬依赖）。

`GET /runtime` 报告当前运行态：回放模式、**回写开关**、模型名、队列深度、并发与配额上限。
它**不返回任何凭据**（由测试断言）。

**注意 `writeback_enabled`**：为 false 时回写节点不发请求，但运行仍显示 `succeeded`。
界面上「成功」不等于「已写进生产库」——这一条是 `/runtime` 存在的主要理由。

## 8. 回放模式

`REPLAY_MODE=fixture` 时 LLM 与 HTTP 全部走本地固定响应，**物理上不出网**（transport 兜底
返回 599）。用于确定性验证。此时任何写请求都不会真的发出，回写自然被拦下。

`REPLAY_STRICT=true`（缺省）时未命中固定响应直接失败——静默返回空响应会让「没跑通」看起来
像「跑通了」。

## 9. 对外任务接口（V0.5.5）

前端任务队列按此接口推送单号任务。契约、响应码与「前端为什么必须拿到同一个 batch_id」
见 `../design/对外任务接口.md`；此处只记运维要点。

```
curl -X POST localhost:8099/api/v1/tasks \
  -H 'content-type: application/json' \
  -H 'X-API-Key: <INBOUND_API_KEY>' \
  -d '{"phone_number":"13415100087","batch_id":"batch-20261016-01"}'
```

返回 `{"status":"accepted","run_id":"…","workflow_id":"customer_profile_pipeline",…}`。
**拿到 200 即表示任务已落库**，与 8000 的 `POST /runs` 同一契约。

### 9.1 三条运维注意

- **密钥独立，且未配置即关闭接口。** 用 `INBOUND_API_KEY`，**不复用** `PROFILE_API_KEY`
  （后者是出站回写凭据）。置空时全部请求返回 **503**——接口关闭，而不是「不校验」。
  换密钥后**重启本进程**（配置在启动时读取）。

  生成新密钥用脚本，不要手敲：

  ```
  python scripts/gen_inbound_key.py            # 只打印一个密钥
  python scripts/gen_inbound_key.py --write    # 生成并写入 .env；已有非空值时拒绝
  python scripts/gen_inbound_key.py --write --force   # 换密钥：覆盖已有值
  ```

  脚本产出的值必须**同时**给前端任务队列一份——两端不一致时对方的请求会全部 403。
  因此换密钥是双方一起做的事，脚本默认拒绝覆盖已有值正是为此。
- **本进程不执行工作流。** `inline_worker` 与 `interrupt_on_start` 被强制关掉，
  在 `.env` 里改不动。后者尤其要紧：它与运行台、worker 共用同一个 SQLite，若由它把
  `running` 标成 `interrupted`，会改坏**别的进程**正在跑的运行。
- **单进程串行执行。** 当前 worker 是「领取一个、跑完再领下一个」（`worker.run_once`）。
  一次画像约 21 分钟，因此任务会排队而非并行。要并行需另起 worker 进程或改这一层。

### 9.2 真回写验收（上线前跑单号）

回写缺省关闭（`WRITEBACK_ENABLED=false`，回写节点只产出「已跳过」而运行仍 `succeeded`）。
放行真实回写前**先跑单号**：

```
# 1. 用独立库，避免动到运行台/产线库
$env:DATABASE_URL="sqlite:///./data/verify_inbound.db"
$env:WRITEBACK_ENABLED="true"

# 2. 起入站接口与 worker（两个终端）
python -m customer_profile.inbound
python -m customer_profile.worker

# 3. 推一个号码
curl -X POST localhost:8099/api/v1/tasks -H 'content-type: application/json' \
  -H "X-API-Key: $env:INBOUND_API_KEY" \
  -d '{"phone_number":"<测试号码>","batch_id":"verify-single-1"}'
```

核对四件事：

1. `GET /api/v1/remote/data/history/{phone}` 在 `request_attempts` 里有记录（取数侧走真实接口）；
2. `POST /api/v1/remote/callback/update-profile` 在 `request_attempts` 里有记录且 `status_code=200`
   ——**这才是「真的写进去了」的证据**。只看运行状态会把「回写被跳过」误判成成功，因此
   `scripts/run_baseline.py` 也是查这张表而不是看状态；
3. 回传体顶层三键为 `phone` / `batch_id` / `analysis_result`，且 `batch_id` 等于推送时的值；
4. 库里的 `batch_id` 与推送值一致（前端据此判断任务来源）。

> **单号不过就停手。** 请求体形状是已知未澄清项（见 `../遗留问题清单.md` L-003：契约文档写
> 顶层三键，线上现役实现发的是 `data[]` 信封，两者只能有一种对）。单号验证就是它的兑现点，
> 不通过时不要继续推第二批。
