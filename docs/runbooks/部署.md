# 部署与运行

> 面向运维。记录操作方法、约束与坑；系统形态见 `../architecture.md`。

## 1. Docker Compose 部署

需要 Git、Docker Engine 与 Docker Compose。服务器首次获取本次部署分支：

```bash
git clone --branch codex/feature-docker-compose \
  https://github.com/Jerry-Kung/CustomerProfile.git
cd CustomerProfile
```

以下命令均在仓库根目录执行。

首次部署先复制配置模板；已有 `.env` 时直接编辑，不要覆盖：

```bash
cp .env.example .env
```

填写模型、画像数据服务、mhero 与语音识别服务的端点及凭据。生产运行使用
`REPLAY_MODE=off`；`WRITEBACK_ENABLED=false` 时只生成结果。若需要运行台，设置
`SERVE_UI=true`。镜像包含已入库的 `frontend/dist`，服务器无需安装 Node.js；修改前端后
先在开发环境重新构建并更新该目录。

构建并启动：

```bash
docker compose config --quiet
docker compose up --build -d --wait --wait-timeout 120
docker compose ps
curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/runtime
```

接口文档位于 `/docs`；启用运行台后访问 `/`。`/health` 只检查本服务初始化状态，
不验证外部模型、画像数据接口、语音识别或 worker 是否能完成真实任务。
`up --wait` 对 API 等待健康检查，对 worker 只等待容器运行；执行能力需通过任务与日志验证。

Compose 启动两个容器，共用一个 Python 3.12 镜像：

- `api`：提交与查询，关闭内置 worker，启动时不修改在跑任务的状态。
- `worker`：单个独立消费者，启动时把遗留的 `running` 标为 `interrupted`，等待人工处理；
  已入队的 `queued` 会继续执行。

两者共用本机 Docker named volume `profile-data`，数据库固定为
`/app/data/customer_profile.db`。Compose 覆盖 `.env` 中的 `DATABASE_URL`、`DATA_DIR`、
`INLINE_WORKER`、`WORKER_REPLICAS` 和各进程的 `INTERRUPT_ON_START`，确保这套部署保持
单机、单 worker。当前存储仅实现 SQLite，无需数据库、Redis 或 Dify 容器。
不要通过 `--scale worker` 扩容，也不要让另一套部署共用同一数据库。

默认主机端口为 8000，可在 `.env` 设置 `CP_API_PORT=18000`，或临时运行：

```bash
CP_API_PORT=18000 docker compose up -d --wait --wait-timeout 120
```

随后使用 `http://服务器地址:18000`。服务目前没有内置 API 鉴权，需要接入现有网关或
反向代理提供服务间认证。

### 1.1 配置与容器网络

`.env` 只在容器启动时注入环境变量，不进入镜像；构建上下文只允许运行代码、依赖文件和
前端产物。真实数据、录制 fixture、Git 历史、虚拟环境和缓存均不进入镜像。
不要把凭据作为构建参数传入。

可通过 `CP_ENV_FILE` 使用独立配置文件：

```bash
CP_ENV_FILE=/absolute/path/customer-profile.env docker compose up -d --wait --wait-timeout 120
```

后续管理命令也应保持相同 `CP_ENV_FILE`。该文件供 `env_file` 注入应用配置；
`CP_API_PORT` 这类 Compose 插值参数应放在仓库 `.env` 或通过命令环境传入。

容器内的 `localhost` 指向容器自身。外部服务在宿主机上运行时，基地址可使用
`http://host.docker.internal:端口`；Compose 为 Linux 配置了 `host-gateway` 映射，
Docker Desktop 也支持该地址。Linux 上宿主机服务必须监听容器可达的地址，
仅监听 `127.0.0.1` 无法通过宿主机网关访问。

`PROFILE_API_BASE_URL` 与 `MHERO_BASE_URL` 的 remote 路由均由相邻仓库
`customer-profile-api` 的 M2M 应用（`app.main_m2m:app`，`cdp-m2m:8084`）提供。
可以配置同一个服务根地址；两项调用凭据都应与下游的 `M2M_API_KEY` 匹配。
例如该服务在宿主机端口 8084 时：

```dotenv
PROFILE_API_BASE_URL=http://host.docker.internal:8084
MHERO_BASE_URL=http://host.docker.internal:8084
PROFILE_API_KEY=<下游 M2M_API_KEY>
PROFILE_MHERO_API_KEY=<下游 M2M_API_KEY>
WRITEBACK_ENABLED=false
```

`PROFILE_API_BASE_URL` 负责历史证据、Notes 模板与生成结果回写；
`MHERO_BASE_URL` 负责已有人设画像、人工确认的 Notes 和反馈。
`customer-profile-backend` 的任务接口并不提供这些 remote 路由。

外部服务在其他容器中时，将它们接入共同的 Docker 网络，再使用服务名及容器端口。
各仓库独立执行 Compose 默认网络互不相通，不能直接用 `cdp-m2m` 作域名。
在远端时填写容器可达的 DNS/IP、端口与既有网关路径。

主流程回写已适配 M2M 的原生 JSON 协议，直接发送顶层 `phone`、`batch_id`、
`analysis_result`，其中画像结果为解析后的 JSON 对象。对外查询的 `outputs.result1`
仍为 JSON 字符串，调用方继续按原方式解析。

默认保持 `WRITEBACK_ENABLED=false`。需要写入业务库时，在部署用 `.env` 中设置
`WRITEBACK_ENABLED=true`，然后重新创建容器，使 worker 加载新配置：

```bash
docker compose up -d --wait --wait-timeout 120
```

单独执行 `docker compose restart worker` 不会加载更新后的环境变量。
使用 `CP_ENV_FILE` 时修改对应文件，并在上述命令中保持相同的文件路径。

### 1.2 日志、升级与停机

API 与 worker 使用 Loguru 输出到标准错误，由 Docker 收集。`LOG_LEVEL` 统一控制
业务日志与 Uvicorn 日志；默认 `INFO` 展示入队、领取、工作流开始/结束及异常，
`DEBUG` 额外展示节点和请求尝试。关键业务提示使用中文，异常保留原文。
每条日志包含时间（带时区）、级别、进程组件、`run_id`、`node_id` 和代码位置；
不额外打印完整请求/响应、画像或客户输入，执行明细仍存于 SQLite。
修改 `LOG_LEVEL` 后需重新创建容器加载环境变量；日志保留与轮转取决于 Docker 日志驱动配置。

```bash
docker compose logs -f --tail=100 api worker

# 只重启 API；worker 正在执行的任务可以继续
docker compose restart api

# 修改 .env 后重新创建容器；restart 不会加载新的环境变量
docker compose up -d --force-recreate --wait --wait-timeout 120

# 升级代码并重新构建
docker compose up --build -d --wait --wait-timeout 120

# 停止服务，保留容器和数据卷
docker compose stop

# 删除容器与网络，保留数据卷
docker compose down
```

worker 收到 `SIGTERM` 后停止领取新任务，等待当前任务完成；Compose 给它 60 分钟的
停机宽限期，因此 `stop`、`down` 或更新 worker 可能等待较久。API 宽限期为 70 秒。
任务超过宽限期仍可能被强制停止，下次启动会标为 `interrupted`，不会自动重跑。
部署升级时先让 worker 收敛，再启动替代 worker；避免新旧版本同时消费同一数据库。

`docker compose down -v` 会删除数据卷，包括队列与执行记录。日常停机不要加 `-v`。
Compose 项目名决定数据卷归属；改变 `-p` 或项目名会得到另一套卷，不会自动迁移原数据。

### 1.3 数据备份

需要备份整个数据卷时，先停止 API 与 worker，让 SQLite 写入收敛，然后由临时容器读取卷：

```bash
docker compose stop
mkdir -p data/backups
docker compose run --rm -T --no-deps --entrypoint tar api \
  -czf - -C /app/data . > data/backups/customer-profile-data.tar.gz
docker compose up -d --wait --wait-timeout 120
```

该命令不启动临时 API，备份包含数据库及残留的 WAL/SHM 和其他数据目录产物。
每次备份应使用不同文件名，并将备份保存到部署机之外。
数据库只允许使用本机磁盘或本地 Docker 卷，不能放在 NFS、SMB、同步盘上；
SQLite WAL 依赖共享内存文件，网络挂载可能导致锁失效或损坏。

## 2. 本地 Python 部署

需要 Python 3.11+。首次配置同样从 `.env.example` 复制为 `.env`。

```bash
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

两个终端分别运行：

```bash
# API：只提交与查询
PYTHONPATH=src INLINE_WORKER=false WORKER_REPLICAS=1 \
  INTERRUPT_ON_START=false python -m customer_profile.main
```

```bash
# worker：执行；启动前确保旧 worker 已退出
PYTHONPATH=src INLINE_WORKER=false WORKER_REPLICAS=1 \
  INTERRUPT_ON_START=true python -m customer_profile.worker
```

两者需使用同一个本地 SQLite 文件。先启动 API 或 worker 均可，只有数据库层面的耦合。
开发或小规模使用可合为单进程：

```bash
PYTHONPATH=src INLINE_WORKER=true python -m customer_profile.main
```

保留 `SQLITE_BUSY_TIMEOUT_MS=5000` 或其他正值，让并发写入等待而不是立即报
`database is locked`。生产目前只支持本地 SQLite，配置 MySQL URL 不会创建 MySQL 存储。

## 3. 表结构变更

项目不使用迁移框架。新增列登记在 `persistence/store.py` 的 `_ADDED_COLUMNS`，启动时
按 `PRAGMA table_info` 判断后幂等补列。升级前备份，升级后重启进程即可完成补列，
无需手工 DDL。

## 4. 提交任务与回写

### 4.1 启动后的验收

先用 `docker compose ps` 确认 API 为 healthy、worker 为 running，查看控制台中
“执行进程已启动”。`/health` 只能证明应用已初始化；`/runtime` 应显示
`inline_worker=false`、`worker_replicas=1`、`replay_mode=off`。

然后通过 API 提交一次真实主流程，验证持久化队列、worker 与外部依赖。以下命令使用
API 容器自带的 Python，无需在服务器安装 `jq` 或 Python。管理命令须使用启动时的
同一 Compose 项目名；例如显式使用过 `-p customer-profile-runner`，这里也添加该参数。
输入 M2M 中已有证据资料的测试客户手机号；首次验收保持 `WRITEBACK_ENABLED=false`：

```bash
CP_BASE_URL=http://127.0.0.1:8000
# 若 CP_API_PORT=18000，则改为 http://127.0.0.1:18000
cp_python() { docker compose exec -T api python "$@"; }

curl -fsS "$CP_BASE_URL/health" | cp_python -m json.tool
curl -fsS "$CP_BASE_URL/runtime" | cp_python -m json.tool

read -r -p '输入已有资料的测试客户手机号：' CP_TEST_PHONE
CP_TEST_BATCH="deploy-check-$(date -u +%Y%m%dT%H%M%SZ)"
CP_RUN_ID=
if CP_REQUEST=$(cp_python -c '
import json, re, sys
phone, batch = sys.argv[1:]
if not re.fullmatch(r"1[3-9]\d{9}", phone):
    raise SystemExit("请输入有效的 11 位中国大陆手机号")
print(json.dumps({"workflow_id":"customer_profile_entry",
    "inputs":{"phone_number":phone,"batch_id":batch},"business_ref":phone}))
' "$CP_TEST_PHONE" "$CP_TEST_BATCH"); then
  if CP_RESPONSE=$(curl -fsS --max-time 30 -X POST "$CP_BASE_URL/runs" \
    -H 'Content-Type: application/json' -d "$CP_REQUEST"); then
    printf '%s\n' "$CP_RESPONSE" | cp_python -m json.tool
    CP_RUN_ID=$(printf '%s' "$CP_RESPONSE" | cp_python -c \
      'import json,sys; print(json.load(sys.stdin)["run_id"])')
  fi
fi
```

成功返回 HTTP 200 与 `run_id`，任务已经持久化为 `queued`。主入口手机号须为
11 位中国大陆手机号，省略 `batch_id` 时默认使用空字符串。其他工作流的入参契约不同。
若命令失败或 `CP_RUN_ID` 为空，先处理错误，不继续查询。缺少 `jq` 时旧命令无法生成
请求体，会导致 HTTP 422；管道后面的命令无法运行也会导致 curl 报错 23。
记录该 ID 并查询同一任务，不要通过反复 POST 检查是否完成；`business_ref` 和 `batch_id`
不是提交幂等键。提交超时不证明未入队，应先按业务标识查询已有运行。

以下按同一 ID 每 15 秒轮询，最多 240 轮；达到查询上限后任务仍会执行，可以继续按原 ID 查询。
一次录音识别可能需要 20–30 分钟：

```bash
if [ -n "$CP_RUN_ID" ]; then
  CP_STATUS=
  for CP_ATTEMPT in $(seq 1 240); do
    if ! CP_DETAIL=$(curl -fsS --max-time 30 "$CP_BASE_URL/runs/$CP_RUN_ID"); then
      CP_STATUS=
      break
    fi
    CP_STATUS=$(printf '%s' "$CP_DETAIL" | cp_python -c \
      'import json,sys; print(json.load(sys.stdin)["status"])') || break
    printf '%s: %s\n' "$CP_RUN_ID" "$CP_STATUS"
    case "$CP_STATUS" in
      succeeded|failed|cancelled|interrupted|skipped) break ;;
    esac
    sleep 15
  done

  if [ -n "$CP_STATUS" ]; then
    printf '%s' "$CP_DETAIL" | cp_python -c '
import json,sys
run = json.load(sys.stdin)
print(json.dumps({k:run.get(k) for k in ("run_id","status","error","is_replay")},
    ensure_ascii=False, indent=2))
if run["status"] == "succeeded":
    print(json.dumps(json.loads(run["outputs"]["result1"]), ensure_ascii=False, indent=2))
'
  fi
fi
```

验收通过须同时满足：状态 `succeeded`、`is_replay=false`，并且 `outputs.result1`
能解析为含 `phone`、`batch_id`、`analysis_result` 的 JSON 对象。若长期 queued，
查看 worker 是否领取；若 failed，查询详情与子运行的错误节点，结合
`docker compose logs -f --tail=100 api worker` 定位。

`GET /runtime` 报告回放模式、回写开关、模型、队列和配额，不返回凭据。
`writeback_enabled=false` 时回写节点不发请求，运行仍可能显示 `succeeded`；
成功表示流程完成，不代表已写入业务库。回写使用上述 M2M 原生 JSON 协议。

### 4.2 回写与上游接入

需要写入业务库时，使用有效的业务批次，开启 `WRITEBACK_ENABLED=true` 并重新创建容器。
除运行成功，还须确认画像生产子运行的回写请求返回 HTTP 2xx，并从 M2M 的画像查询
或业务后台核对测试客户的画像和快照已更新。

现有 `customer-profile-api` 提交的是 backend 的 Form 协议，画像、邀约与补偿任务共用
该入口，不能仅把 `REMOTE_API_URL` 改成本服务 `/runs`。推荐保留
`customer-profile-api → customer_profile_backend → CustomerProfile`；backend 需要增加
提交 JSON、持久化 `run_id`、轮询终态的适配器，并把 `outputs.result1` 解析后取
`analysis_result` 交给现有结果解析流程。邀约任务继续使用原有执行平台。

当前 backend 只更新自己的任务表，没有独立的 M2M 成功回写，因此这条推荐链路接入时
应由本服务开启回写负责成功更新；失败回调、用量上报和补偿查询应在适配器方案中明确落实。
如果以后改由 backend 统一回写，须先实现相应回调交付，再关闭本服务回写，避免两边都未写入
或重复写入。本文记录所需接入方式，两个上游仓库本次未改造。

## 5. 回放模式

`REPLAY_MODE=fixture` 时 LLM 与 HTTP 使用本地固定响应，不对外发出请求。
`REPLAY_STRICT=true` 时未命中 fixture 直接失败。

镜像不打包本机 fixture；容器回放需显式挂载经脱敏的 fixture 目录并配置 `FIXTURE_DIR`。
生产部署使用 `REPLAY_MODE=off`。
