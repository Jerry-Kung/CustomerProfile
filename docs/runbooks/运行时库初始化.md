# 运行时库初始化（UAT / 生产）

> 适用：把运行时库从本地 SQLite 切到内网 MySQL 的环境。设计与取舍见
> `../feature-db-mysql/01-方案.md`，系统形态见 `../architecture.md`。
>
> **本地与批次不受影响**：`experiments/**/trace.db`、快照产物、本地复现仍用 SQLite，
> 切换只改 `DATABASE_URL` 一项。

## 1. 为什么需要这一步

UAT 与生产的内网 MySQL **从本地不可达**，因此不能「在开发机建好库再搬过去」。
交付的是一件可在目标机器上重复执行的东西：建 schema、建表、登记迁移版本。

### 1.1 现在由部署自动完成

自 2026-11-12 起，**不需要任何手工初始化动作**。`docker compose up` 会先启动
`runtime-migrate` 容器，它做三件事：

1. 库不存在就建库（库已存在则跳过，不要求账号有 `CREATE DATABASE` 权限）；
2. 把 `information_schema` 里的**实际结构**与代码里的 DDL 逐表逐列比对；
3. **只补缺失项**——缺表建表、缺列加列，已存在的一律不动。

四个运行服务（`runtime-profile-api/-worker`、`runtime-invitation-api/-worker`）通过
`depends_on: service_completed_successfully` 等它成功退出才启动。初始化失败时它们
根本不会起来，故障在部署阶段暴露，而不是变成「服务 Up、任务全失败」。

因此下列情形都不需要人工判断：

| 情形 | 自动行为 |
|---|---|
| 全新空库 | 建库、建 6 张表、登记版本 |
| 已初始化过的库 | 什么都不改，打印「结构完整」 |
| 升级带来新列 | 只 `ADD COLUMN` 缺的列，已有数据不动 |
| 某张表被误删 | 只重建缺的那张 |
| 版本号与代码不一致 | 登记当前版本；列/表不齐则补 |

自检与修复共用**同一份** `MYSQL_DDL`（解析出来比对），不存在「期望结构写了两遍、
抄错一个列名」的漏洞。

> **并发安全**：多进程同时初始化时靠 `GET_LOCK` 串行化。已实测 6 个进程同时建一个
> 空库：全部成功、只有一个真正建表、最终 6 张表齐全。

### 1.2 什么时候仍要手工跑

| 场景 | 命令 |
|---|---|
| 只想知道库满不满足，不想改 | `docker compose run --rm runtime-migrate --check`（不满足时退出码 3） |
| 无 DDL 权限，SQL 交给 DBA | `python scripts/init_runtime_db.py --emit-sql db/init_runtime_db.sql` |
| 不走 compose | `python scripts/init_runtime_db.py` |

**建表能力只留在 `runtime-migrate` 这一个容器**，运行服务完全不带 DDL 权限——这不是
靠配置开关实现的，而是按后端类型写死在代码里：SQLite 由服务进程自建（本地产物，
给个路径就能跑），MySQL 服务进程一律不建表。SQLite 后端也由这个容器先建一遍，
因此在同一套 compose 下本地与 UAT 的部署动作完全一样。

## 2. 前置：建库与账号

DBA 执行一次（或由有权限的账号执行）：

```sql
-- 库：与业务库分开
CREATE DATABASE IF NOT EXISTS customer_profile_runtime
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_0900_as_cs;

-- 运行账号：只给 DML，不给 DDL
CREATE USER 'cp_runtime'@'%' IDENTIFIED BY '<rotate-me>';
GRANT SELECT, INSERT, UPDATE, DELETE ON customer_profile_runtime.* TO 'cp_runtime'@'%';

-- 迁移账号：只在初始化/升级时用
CREATE USER 'cp_migrate'@'%' IDENTIFIED BY '<rotate-me>';
GRANT ALL PRIVILEGES ON customer_profile_runtime.* TO 'cp_migrate'@'%';
```

三条口径，都有理由：

| 决定 | 理由 |
|---|---|
| **独立 schema**，不复用业务库 | 同实例上的 `customer_profile` schema 有 40+ 张业务表；混住之后权限、备份、清理口径都无法分开 |
| 排序规则 `utf8mb4_0900_as_cs`（大小写**敏感**） | 实例缺省是 `ai_ci`（不敏感），会让 `'Running' = 'running'` 成立。SQLite 的 TEXT 是二进制比较，不改会引入静默的行为漂移 |
| 运行账号不给 DDL | 建表由迁移步骤做一次；服务进程不该能 `DROP TABLE` |

## 3. 手工执行（可选）

> 日常部署**不需要**这一节：`docker compose up` 已自动执行。这里保留的是
> 「不走 compose」或「想单独确认」时的入口。

### A. 容器

```bash
# 已经随 up 跑过；单独再跑一遍也安全（幂等）
docker compose run --rm runtime-migrate

# 只自检，不改库。结构不满足时退出码 3，适合巡检与发布前检查
docker compose run --rm runtime-migrate --check
```

它跑 `python -m customer_profile.persistence.init_db`，读 `.env` 的 `DATABASE_URL`，
输出目标实例、本次建的表、补的列与迁移版本。

### B. 目标机上的 Python

```bash
# 先看会执行什么，不连库
python scripts/init_runtime_db.py --dry-run

# 正式执行
python scripts/init_runtime_db.py
```

需要目标机有 python 与该驱动；镜像里已装。

### C. 纯 SQL 交给 DBA（无 python、无网络）

```bash
python scripts/init_runtime_db.py --emit-sql db/init_runtime_db.sql
```

把生成的 `db/init_runtime_db.sql` 交给 DBA。注意这份 SQL 按「库为空」编写：
`CREATE TABLE IF NOT EXISTS` 不会给**已存在**的表补列。如果库已初始化且只缺个别列，
仍要用 A/B（它们会真的去比对列）。

## 4. 预期结果

执行完应有 **6 张表**：

| 表 | 内容 |
|---|---|
| `workflow_runs` | 运行与队列（复用同表，见 ADR 0001） |
| `definition_versions` | 定义快照：历史运行展示当时的图与提示词 |
| `node_executions` | 节点执行明细，唯一键 `(run_id, node_id, call_path)` |
| `request_attempts` | 每次外部请求的请求体、响应原文、usage |
| `profile_baselines` | 增量画像基线，按手机号一行 |
| `schema_migrations` | 迁移版本记录 |

`schema_migrations` 里应有一条，版本号与
`src/customer_profile/persistence/mysql_schema.py` 的 `SCHEMA_VERSION` 一致。

## 5. 配置服务进程

```ini
DATABASE_URL=mysql://cp_runtime:<password>@<host>:3306/customer_profile_runtime?charset=utf8mb4
```

**就这一项。** 没有「要不要建表」「期望哪个版本」之类的开关：

- **建不建表按后端写死**。MySQL 服务进程不建表（表由 `runtime-migrate` 建），运行账号
  因此不需要 DDL 权限；SQLite 服务进程自建（本地与批次要「给个路径就能跑」）。
- **期望版本取代码里的 `SCHEMA_VERSION`**，不需要运维抄一遍。启动时逐表逐列核验实际
  结构，对不上就拒绝启动——它比的是 `information_schema`，不只是版本表里的那一行，
  所以「有人手工删过表、还没重新部署」这种窗口也能拦住。

**密码里有 `@ # / ?` 等字符时不需要手工编码**：DSN 解析按最后一个 `@` 切分凭据段，
未编码的密码能直接用。但写进 shell 命令时仍要加引号。

## 6. 验收

```bash
# 1. 服务起得来
docker compose up -d runtime-profile-api
curl -s localhost:18173/health

# 2. 接单与执行（接一单，看运行列表出现记录）
curl -s -X POST localhost:18173/runs -H 'Content-Type: application/json' \
  -d '{"workflow_id":"customer_profile_pipeline","inputs":{"phone_number":"13800000000"}}'
curl -s 'localhost:18173/runs?limit=5'
```

运行台能列出来、点开有节点明细，即说明读路径（含包回填）通。

## 7. 回退

改回 `DATABASE_URL=sqlite:///./data/customer_profile.db` 即可，**不需要回滚代码**。
这也是 SQLite 后端一直保留的原因之一。

## 8. 常见问题

| 现象 | 原因与处置 |
|---|---|
| 部署卡在 `runtime-migrate` | 看它的日志：`docker compose logs runtime-migrate`。常见是库不存在且账号无 `CREATE DATABASE` 权限、或实例不可达 |
| 启动报「运行时库与期望结构不符」 | 初始化没跑或没跑成功。执行 `docker compose up -d`（会自动补），再确认退出码 0 |
| 只想确认库满不满足 | `docker compose run --rm runtime-migrate --check`；不满足时它会列出具体缺哪些表、哪些列 |
| 启动报 `Access denied` | 账号没权限，或密码里有特殊字符没加引号 |
| 表建出来了但排序规则不对 | 用的是旧版脚本；确认表上是 `utf8mb4_0900_as_cs`，`SHOW TABLE STATUS` 可查 |
| 写入报 `Data too long` | 列宽不足。实例开了 `STRICT_TRANS_TABLES`，**会报错而不是截断**。联系开发调整列宽并升 `SCHEMA_VERSION` |
| 新增了 `NOT NULL` 且无默认值的列 | 初始化会自动补列，但对**已有数据**的表只能先建成可空，并打印「需回填后手工收紧」。要让老行立刻满足约束，须先在迁移里给默认值 |
| `UPDATE ... WHERE id IN (SELECT ... LIMIT n)` 报不支持 | MySQL 不支持这种写法；代码里已改为「先查后改」。若出现在自写脚本里，同样拆两步 |
| 任务堆积但容器 Up | 查 worker 健康检查：它读存活信号，包含数据库最近一次成功时间 |
| 报「等待建表锁超时」 | 另一个进程正在初始化（同一实例上同名锁）。稍后重试；锁在会话结束时自动释放 |
