# 故障定位

> 按**现象**组织，每条给出：先看什么、常见原因、怎么处置。
> 系统形态见 `../architecture.md`，部署见 `./部署.md`。

## 1. 任务一直停在 `queued`，不开始

**先确认有没有 worker 在消费。**

```
GET /runtime        # 看 inline_worker 与 queued_runs / running_runs
```

- `inline_worker=false` 且没有独立 worker 进程 → 这是配置问题，起一个
  `python -m customer_profile.worker`，或把 `INLINE_WORKER` 改回 true。
- worker 在跑但队列不动 → 看 worker 的 stdout。它每领一个任务会打一行
  `[worker] 领取 <run_id>`。
- **排除法**：直接查库确认状态确实是 `queued`、且 `parent_run_id IS NULL`（子运行不入队，
  它们只由父运行执行，永远不该出现在队列里）：

```
sqlite3 data/customer_profile.db \
  "SELECT run_id, status, queued_at_ms, claimed_by FROM workflow_runs WHERE status='queued';"
```

## 2. 任务卡在 `running`，worker 也不动了

**worker 崩了。** 租约（`WORKER_LEASE_MS`，缺省 60s）到期后该运行的租约失效，但
**代码不会自动重领**（差异 W28，刻意的：重领会把跑到一半的运行整条重跑，而幂等回写尚未
落地）。

处置：该运行会被下次 worker 启动时的恢复逻辑标成 `interrupted`（保留已完成结果），
然后人工判断。查它跑到哪一步：

```
GET /runs/<run_id>            # nodes 里看哪些 succeeded、哪些 running
GET /runs/<run_id>/graph      # 图上叠加状态更直观
```

若要重新跑：确认外部副作用（尤其回写）的状态后再决定。**不要直接改库里的 status 让它重跑**
——那样会绕过队列与留痕。

## 3. `interrupted` 越积越多

它们**不是错误**，是「进程中断且未完成、已完成结果已保留」的运行，等人工决定。

处置：确认不再需要之后调用人工出口终结：

```
POST /runs/<run_id>/abandon     # 只接受 interrupted，其它状态返回 409
```

终结后状态变 `cancelled`，`error` 里保留原中断原因并追加「人工确认后终结」。

**不要用 `/cancel` 代替它**：`/cancel` 是「停止一条正在跑的运行」，`/abandon` 是
「结掉一条已经停掉的运行」。用错的表现是「界面上已是终态，但进程里还在写外部接口」。

## 4. `database is locked`

**先查 `SQLITE_BUSY_TIMEOUT_MS`**（缺省 5000，不该是 0）。设了还报，按顺序排查：

1. **库是否放在网络挂载上**。这是最常见也最危险的原因：WAL 依赖 `-shm` 共享内存，
   网络文件系统上锁语义不可靠，**可能损坏数据库**。必须用本地卷。
2. **是否有进程持着长事务**。所有写都是「多条语句 + 一次 commit」的短事务，若出现长事务，
   说明有代码在事务里 `await`（应视为缺陷）。
3. **是否开了一大堆 worker**。SQLite 的写是串行的，写压力大到超时说明该换库了——本项目
   量级不该到这个程度。

## 5. 运行变慢，是被限流还是本来就慢

**看尝试记录的时间分布，不要凭感觉。**

```
GET /runs/<run_id>/nodes/<node_id>/attempts
```

- 若相邻尝试的间隔大约等于 `60 / LLM_RPM_LIMIT` 秒，且**单次尝试本身很快** → 排队等额度。
  这是配额正常工作，不是故障。要更快就提高限额。
- 若**单次尝试的 `duration_ms` 本身很大** → 模型侧慢或网络慢，与配额无关。
- 录音类节点（`auc`）单次可达 20–30 分钟，这是实测口径，不是卡住。

TPM 被限流的表现类似，但触发条件与 prompt 长度相关：长 prompt 的节点会先被限。

## 6. 回写「成功」但其实没写

**先看 `/runtime` 的 `writeback_enabled`。**

为 `false`（缺省、测试、冒烟、影子模式）时，回写节点只产出「已跳过」的可解释结果，
**而运行状态仍是 `succeeded`**。这不是 bug，是刻意的：测试与影子模式禁止生产回写。
界面上的「成功」指「工作流跑完了」，不指「已写进生产库」。

要确认某次回写到底发没发：

```
GET /runs/<run_id>/nodes/<回写节点 ID>/attempts
```

回写节点定义在 `workflows/customer_profile_production.py`，标记为 `@writeback`。
跳过时输出里的 `body` 含 `writeback_skipped: true`、`status` 为 0。

## 7. worker 启动时报 `duplicate column name`

**正常，可以忽略。** 两个进程（API 与 worker）同时启动时会并发执行补列，后来者拿到该错误
即说明另一进程已经补好了。补列逻辑本身是幂等的（先读 `PRAGMA table_info`），这个错误只是
并发窗口的产物，已被吞掉。

## 8. 启动时报 `LLM_RPM_LIMIT 不能被 WORKER_REPLICAS 整除`

**这是配置错误，不是 bug。** 限额按 worker 数等分（ADR 0002），不可整除时会静默超发
（RPM=60 配 4 个 worker 实际打到 240），所以宁可拒绝启动。

处置：改 `LLM_RPM_LIMIT` 为可整除的值，或把 `WORKER_REPLICAS` 改回与实际进程数一致。

## 9. 前端打开是空白 / `/` 返回 404

`SERVE_UI=false` 时后端不托管前端，`/` 本来就没有内容——这是合法状态（只跑 API）。
要运行台：`SERVE_UI=true` 且先跑过 `cd frontend && npm run build`。

若置了 `SERVE_UI=true` 仍是 404，看启动日志有没有
`[前端] SERVE_UI=true 但未找到构建产物`——它打印告警并跳过，不会让服务启动失败。
