# 统一镜像发布

任务后端通过 Git subtree 导入 `services/task-backend/`，保留原提交历史。
首次合仓基于 CustomerProfile `dev@7a77c5c55dcd44f38e92dc7d86ed7c831f4eb6d2`
与 backend `main@05ced2f32692e5628f20678d3ef8e09790291a9f`。

根 Dockerfile 构建一个镜像，执行器使用 `/opt/runtime-venv`，任务后端使用 `/opt/task-venv`。
镜像入口根据后端 console 命令选择对应 Python 环境和工作目录。
任务后端从 MySQL 派发，执行器接单、执行并保存 SQLite 与运行归档。模块间沿用 HTTP 契约。

## 配置与开发

在仓库根目录准备两份配置，分别填写模型、ASR、业务接口，以及 MySQL、执行目标和回调设置。

```bash
cp .env.example .env
cp services/task-backend/.env.example services/task-backend/.env
```

执行器容器只注入 `.env`，任务后端容器只注入 `services/task-backend/.env`。
`scripts/compose.sh` 同时选定 Compose 插值文件与容器配置文件，先读取后端、再读取执行器配置。
执行器 `API_PORT / CP_API_PORT / INBOUND_PORT` 沿用原设置。任务 API 可用
`TASK_API_PORT / TASK_HOST_API_PORT` 分别设置容器与宿主机端口，宿主机端口也兼容旧 `HOST_API_PORT`。
MySQL、模型凭据和业务回调密钥由各容器自己的配置文件提供。

新安装模板中的画像执行地址为 `http://api:18173`，邀约执行地址为 `http://inbound:8099`。
修改执行器内部端口时同步调整这些地址。已有任务的目标 ID、revision、URL 和凭据须沿用，
待原目标运行、重试和失败通知排空后再调整。原生邀约的执行标识、入站密钥与业务回写要求见
[原生邀约接入](../../services/task-backend/docs/native-invitation-runner.md)。

本地开发为两个模块分别创建环境。

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
python3 -m venv services/task-backend/.venv
services/task-backend/.venv/bin/pip install -e 'services/task-backend[dev]'
./scripts/test.sh
```

已有环境可以用 `RUNTIME_PYTHON` 和 `TASK_PYTHON` 指定解释器。测试入口依次检查执行器、
后端单元测试、静态契约，以及使用真实接单路由与 SQLite、模拟上游服务的邀约联合测试。

配置检查可以在构建前执行，输出镜像版本和目标服务。

```bash
./scripts/release.py --profile invitation-runner --check
```

配置文件放在仓库外时显式传入两个路径。

```bash
./scripts/release.py --env-file /etc/customer-profile/runtime.env \
  --task-env-file /etc/customer-profile/task.env \
  --profile invitation-runner --check
```

## 两仓部署首次切换

先记录旧后端 Compose 的项目名和当前镜像，备份运行数据卷。统一 Compose 沿用
`name: customer-profile` 和 `profile-data`，默认数据卷名为 `customer-profile_profile-data`。
原部署使用了自定义项目名或卷名时，应先对齐这些名称。SQLite 和运行归档共同位于 `/app/data` 本地卷。
统一项目中的旧擎天调度组命名为 `qingtian-worker`，对应原后端项目的 `worker`，其目标身份沿用原配置。

在旧后端目录，用原环境配置停止旧项目的消费者与 API。目标身份和远端运行 ID 保存在 MySQL 中。

```bash
scripts/compose.sh --profile invitation-runner stop \
  worker commercial-worker profile-runner-worker invitation-runner-worker api
```

执行器还使用单个共用 `worker` 的旧部署，应先用旧 Compose 停止、等待并移除该容器，再更新代码。
发布脚本会检查同项目中仍在运行的旧共用执行进程。

将原两份配置分别放到合仓后的 `.env` 与 `services/task-backend/.env`，随后从新仓库发布。
已有 001–008 后端库的部署使用以下命令。

```bash
./scripts/release.py --profile invitation-runner
```

新 MySQL 安装或计划执行迁移时显式添加 `--migrate`。迁移使用原后端的顺序与幂等 SQL。
运行台前端产物随 Git 保存，修改前端后应先执行 `cd frontend && npm ci && npm run build`，
将构建产物提交后再发布。运行数据卷的备份、归档留存与恢复沿用
[执行器部署说明](部署.md) 和 [留痕存储设计](../feature-storage-opt/README.md)。

## 日常发布与恢复

```bash
# 整套服务
./scripts/release.py --profile invitation-runner

# 单独更新画像或邀约
./scripts/release.py --group profile
./scripts/release.py --group invitation --profile invitation-runner

# 单独更新任务后端
./scripts/release.py --group backend --profile invitation-runner
```

脚本先检查 Compose，再为源码构建带上海时区完整时间戳与提交号的镜像。
源码发布要求已提交跟踪文件的改动。指定镜像标签时也须包含完整时间戳，已有本地标签会被拒绝。
构建后逐个用临时容器解析目标进程的配置，再进入更新阶段。
同一 Docker Engine 和 Compose 项目的发布由进程锁串行化，避免多个发布同时重建执行进程。

发布按业务组暂停后端派发，等待对应执行 Worker 完成，重建执行服务并通过健康检查，
然后更新任务 API 和恢复派发。执行 Worker 沿用 60 分钟停机宽限，`--wait-timeout` 仅控制启动健康等待。
已有后端的日常发布通过 `--no-deps` 跳过迁移服务。后端组与执行器组可以分别采用明确的镜像版本。

发布记录保存在 `.releases/`，包含 Docker 项目与 Engine、镜像、镜像源码提交、发布脚本提交、服务范围、原容器镜像 ID、
执行阶段与结果。中途失败会中止后续步骤并记录失败阶段，恢复前先核对执行结果和当前运行身份。
需要回退应用镜像时，先确认对应的数据格式兼容性，再用已保存的镜像版本按相同分组顺序更新。

```bash
./scripts/release.py --image customer-profile-unified:20261109-143000-abcdef123456 \
  --skip-build --profile invitation-runner
```

`--skip-build` 使用本机已有的统一镜像，也接受 `repository@sha256:...` 精确引用。
所有部署服务引用相同的目标镜像。镜像中的 `io.customer-profile.layout=v1` 标识会在更新前校验。
镜像推送与生产环境切换按部署环境的仓库、认证和变更流程执行。
