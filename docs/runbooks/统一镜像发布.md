# UAT 合仓部署：直接使用 Docker Compose

UAT 使用根目录 `compose.yaml` 和一份 `.env` 部署。默认镜像为
`customer-profile-unified:uat`；只有 `api` 声明构建，其余服务共用该镜像。
容器命令直接指定各模块的 Python 环境。MySQL 队列、SQLite 执行历史与原 HTTP 协议保持独立。

本次代码在 `codex/unified-image-release` 分支。原始合仓基线为 CustomerProfile
`dev@7a77c5c` 与 backend `main@05ced2f`。先推送该分支，或合入 `dev` 后再更新服务器。

## 1. 保存旧配置和部署信息

在服务器原 CustomerProfile 目录中，更新代码之前执行：

```bash
mkdir -p ../customer-profile-uat-backup
chmod 700 ../customer-profile-uat-backup
cp .env ../customer-profile-uat-backup/runtime.env
cp compose.yaml ../customer-profile-uat-backup/compose.yaml
chmod 600 ../customer-profile-uat-backup/runtime.env
git rev-parse HEAD > ../customer-profile-uat-backup/runtime-ref.txt
docker compose ps
docker compose images
```

第一次切换使用新的备份目录；已有同名备份时换目录名，避免覆盖原备份。
旧 backend 目录也保存一份原 `.env`、代码提交号与镜像信息，保留原 MySQL 的恢复点。
以下是用户提供配置表达的预期值，应与服务器实际容器核对：

| 项目 | 本次配置 |
|---|---|
| 执行器 Compose 项目 | customer-profile-runner |
| 执行器数据卷 | customer-profile-runner_profile-data，挂载 /app/data |
| 画像 API / 运行台 | 宿主机 18000，容器 18173 |
| 邀约 API | 8099 |
| 任务后端 API | 宿主机 18007，容器 18008 |

```bash
docker ps --format '{{.Names}}  {{.Label "com.docker.compose.project"}}  {{.Label "com.docker.compose.service"}}'
docker volume inspect customer-profile-runner_profile-data --format '{{.Name}}'
```

从 `docker inspect <原执行器容器ID>` 核对 `/app/data` 的实际挂载。项目名与数据卷必须沿用；
如果原部署另有 `-p` 或 bind mount，先对齐实际挂载。卷的完整备份在第 5 步停止写入后执行。

## 2. 更新代码并放置配置

开发机 CustomerProfile 仓库中，推送本次分支：

```bash
git push -u origin codex/unified-image-release
```

服务器进入原 CustomerProfile 目录，工作区未提交代码应先保存：

```bash
git fetch origin
git switch codex/unified-image-release
git pull --ff-only origin codex/unified-image-release
```

把合并好的文件上传到服务器，复制为根目录 `.env`：

```bash
cp /实际上传位置/merged.env .env
chmod 600 .env
docker compose --profile invitation-runner config -q
```

不需要 `services/task-backend/.env`。旧 backend 目录保留原来的 `.env`，停止旧服务时继续使用。
普通 `docker compose` 自动读取当前目录配置；不打印展开后的 `config`，以免输出凭据。

合并文件去重了两边相同的 LOG_LEVEL、PROFILE_API_BASE_URL 和 PROFILE_API_KEY。
后端原 HOST_API_PORT 改为 TASK_HOST_API_PORT=18007，并补充 TASK_API_PORT=18008。
所有原凭据、Runner URL、目标 ID/revision、消费环境、模式和每组并发均保留。
首次切换保留原外部执行地址，不同时更换目标身份或 URL，以接续已有运行。

留痕配置为：

```dotenv
TRACE_PERSIST_MODE=high
TRACE_ARCHIVE_DIR=/app/data/trace-archives
TRACE_RETENTION_DAYS=30
TRACE_ARCHIVE_COMPRESS_LEVEL=6
```

归档位于持久卷内。代码已修复空目录配置的处理，留空会回落到 `<DATA_DIR>/trace-archives`。
原配置的真实业务回写开关保留，测试使用独立配置与模拟上游。

## 3. 提前构建共用镜像

在新仓库根目录执行，旧服务此时仍可运行：

```bash
docker compose build api
```

只构建一次，9 个应用服务共用 `customer-profile-unified:uat`。
MySQL 使用原有部署。`task-migrate` 属于 maintenance profile，不会随普通启动自动执行。
本次已有 001–008 库不需要迁移；仅首次新建库时明确执行：

```bash
# 仅新建库时执行，不属于本次 UAT 切换步骤
docker compose run --rm --no-deps task-migrate
```

## 4. 暂停提交并停止旧 backend

暂停业务任务提交、定时触发及直接调用执行器的上游。进入旧 backend 目录，用其原配置执行：

```bash
docker compose --profile invitation-runner ps
docker compose --profile invitation-runner stop api
docker compose --profile invitation-runner stop -t 3600 \
  worker commercial-worker profile-runner-worker invitation-runner-worker
docker compose --profile invitation-runner ps -a
```

原 backend 若使用过 `-p 旧项目名`，这些命令也带相同 `-p`。确认看到的是旧 backend 容器后再停止。
等待四个派发组退出后再进行下一步。MySQL 里的排队任务与在途身份保留，不删除队列或重置状态。

## 5. 停止旧执行器并备份运行卷

回到更新后的 CustomerProfile 根目录，用第 1 步保存的旧 Compose 定义操作旧服务。
`--project-directory .` 保持相对路径指向原执行器目录；显式沿用项目名和保存的原配置。

```bash
docker compose --project-directory . -p customer-profile-runner \
  --env-file ../customer-profile-uat-backup/runtime.env \
  -f ../customer-profile-uat-backup/compose.yaml stop api inbound

docker compose --project-directory . -p customer-profile-runner \
  --env-file ../customer-profile-uat-backup/runtime.env \
  -f ../customer-profile-uat-backup/compose.yaml stop -t 3600

docker compose --project-directory . -p customer-profile-runner \
  --env-file ../customer-profile-uat-backup/runtime.env \
  -f ../customer-profile-uat-backup/compose.yaml ps -a
```

这同时兼容旧共用 worker 与已拆分的两个执行 Worker。确认全部已停止，并核对日志中的在途任务
已结束；若发生强制终止或回写状态不明，先核对远端运行，避免启动恢复时误判。

全部写入退出后备份整个卷，包含 SQLite、WAL/SHM 和归档文件：

```bash
umask 077
docker compose run --rm -T --no-deps --user 0:0 --entrypoint tar api \
  -czf - -C /app/data . > ../customer-profile-uat-backup/profile-data.tar.gz
```

再移除旧执行器已停止的容器，保留镜像和数据卷：

```bash
docker compose --project-directory . -p customer-profile-runner \
  --env-file ../customer-profile-uat-backup/runtime.env \
  -f ../customer-profile-uat-backup/compose.yaml rm -f
```

旧 backend 容器保持停止，保留其目录、配置和镜像用于必要时恢复。

## 6. 部署新服务

仍在新仓库根目录执行：

```bash
docker compose --profile invitation-runner up -d --no-build --wait
docker compose --profile invitation-runner ps
```

启动 9 个应用容器，复用第 3 步构建的同一镜像与原数据卷。任务 API 与执行 API 健康后，对应
派发组按 depends_on 启动。没有自动执行数据库迁移。

```bash
curl -fsS http://127.0.0.1:18000/health
curl -fsS http://127.0.0.1:8099/health
curl -fsS http://127.0.0.1:18007/ready
docker compose --profile invitation-runner logs --tail 100 \
  task-api profile-runner-worker invitation-runner-worker
```

核对原历史仍可查询、后端仍连接原 MySQL、两个目标身份与环境保持不变，旧 backend 消费者全部
停止后恢复业务入口。健康检查只验证启动状态；真实模型、语音识别和回写从正常业务流继续观察。

## 日常更新

更新前保留当前镜像，构建新镜像后按顺序暂停派发、等待执行、重建服务：

```bash
docker tag customer-profile-unified:uat "customer-profile-unified:uat-before-$(date +%Y%m%d-%H%M%S)"
git pull --ff-only
docker compose build api
docker compose --profile invitation-runner stop -t 3600 \
  qingtian-worker commercial-worker profile-runner-worker invitation-runner-worker
docker compose stop -t 3600 profile-worker invitation-worker
docker compose --profile invitation-runner up -d --no-build --force-recreate --wait
```

只有 `.env` 变化时省略构建，其余更新步骤相同。`restart` 不重新注入配置。
备份镜像带当前时间戳，回退时使用实际保存的标签。
按业务组更新也直接指定服务：先停止该组派发、等待对应执行 Worker 结束；用
`up -d --no-build --no-deps --force-recreate --wait` 先更新组内 API 和执行 Worker，
健康后再用相同选项更新派发 Worker。`--no-deps` 保持其他组和任务 API 继续运行。
画像组为 api/profile-worker/profile-runner-worker；邀约组为 inbound/invitation-worker/invitation-runner-worker。

确认持久化和归档格式兼容后，可选择保存的镜像回退应用：

```bash
CP_IMAGE=customer-profile-unified:uat-before-20261109-150000 \
  docker compose --profile invitation-runner up -d --no-build --force-recreate --wait
```

回退前同样先停派发、等待执行结束。首次切换要退回两仓时，恢复保存的旧代码、配置和镜像，先启动
旧执行器，再恢复旧 backend。合仓本身无新增 MySQL 迁移；有新业务写入后，不用切换前备份覆盖当前库。
不要使用 `down -v` 删除原运行卷。
