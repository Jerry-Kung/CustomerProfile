# 统一镜像发布

任务后端通过 Git subtree 导入 `services/task-backend/`，保留原提交历史。
首次合仓基于 CustomerProfile `dev@7a77c5c`（含 dev-rules-opt01）与 backend `main@05ced2f`。
根 Dockerfile 构建一个镜像，执行器使用 `/opt/runtime-venv`，任务后端使用 `/opt/task-venv`。
MySQL 任务队列、SQLite 执行留痕和模块之间的 HTTP 契约保持独立。

## 一份配置

两个模块默认共用仓库根目录 `.env`。新安装复制 `.env.example` 后填写真实值；已有环境使用
从原两份配置合并的文件，避免重新复制模板覆盖凭据。文件权限设置为 `600`。

```bash
chmod 600 .env
./scripts/release.py --profile invitation-runner --check
```

`--check` 只解析 Compose 和发布范围，不连接 MySQL 或业务服务，不验证真实工作流。
完整进程配置检查由下面的 `--prepare` 完成，同样不连接业务数据库或调用外部工作流。
共享文件中每个模块读取自己的字段；服务级 `environment` 仍优先于文件中的同名值。

| 配置 | 用途 |
|---|---|
| API_PORT / CP_API_PORT | 执行器容器 / 宿主机端口 |
| TASK_API_PORT / TASK_HOST_API_PORT | 任务 API 容器 / 宿主机端口 |
| LOG_LEVEL | 两个模块的共同日志级别 |
| PROFILE_API_BASE_URL / PROFILE_API_KEY | 执行器取数回写、后端失败通知和邀约回写确认 |
| PROFILE_RUNNER_* / INVITATION_RUNNER_* | 各目标 URL、凭据、身份、版本、环境和并发 |
| MYSQL_* | 后端原有业务队列数据库 |

如果两模块的业务 API 地址或凭据不同，可继续显式传入 `--task-env-file` 使用独立后端文件；
不要让两个不同值在共享文件里互相覆盖。`--env-file` 指定仓库外配置时，默认两个模块均使用
该文件。原双文件方式仍兼容：

```bash
./scripts/release.py --env-file /etc/customer-profile/runtime.env \
  --task-env-file /etc/customer-profile/task.env --profile invitation-runner --check
```

## 首次从两仓切换

以下在服务器使用 Bash 执行。先在开发机推送本次分支，服务器再更新代码。
当前实现分支为 `codex/unified-image-release`；未合入 `dev` 前，仅更新 `dev` 不包含合仓实现。
以下路径与旧后端项目名需要替换为服务器实际值。整个过程沿用原 MySQL 和运行数据卷。

### 1. 保存原部署信息

在更新旧 CustomerProfile 目录前设置路径，确认旧后端项目与执行器项目不同。

```bash
OLD_BACKEND=/实际路径/customer_profile_backend
APP_DIR=/实际路径/CustomerProfile
OLD_BACKEND_PROJECT=实际旧后端Compose项目名
RUNTIME_PROJECT=customer-profile-runner
RUNTIME_DATA_VOLUME=customer-profile-runner_profile-data
BACKUP_DIR="$HOME/customer-profile-backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$BACKUP_DIR"
chmod 700 "$BACKUP_DIR"

docker ps --format '{{.Names}}	{{.Label "com.docker.compose.project"}}	{{.Label "com.docker.compose.service"}}'
cd "$OLD_BACKEND"
./scripts/compose.sh -p "$OLD_BACKEND_PROJECT" --profile invitation-runner ps
cd "$APP_DIR"
git status --short
git rev-parse HEAD > "$BACKUP_DIR/runtime-ref"
git -C "$OLD_BACKEND" rev-parse HEAD > "$BACKUP_DIR/backend-ref"
cp .env "$BACKUP_DIR/runtime.env"
cp "$OLD_BACKEND/.env" "$BACKUP_DIR/backend.env"
chmod 600 "$BACKUP_DIR/runtime.env" "$BACKUP_DIR/backend.env"
```

记录旧容器不可变镜像 ID，输出不包含环境变量：

```bash
for project in "$OLD_BACKEND_PROJECT" "$RUNTIME_PROJECT"; do
  docker ps -aq --filter "label=com.docker.compose.project=$project" |
    while IFS= read -r id; do
      docker inspect --format '{{.Name}} {{.Id}} {{.Image}}' "$id"
    done
done > "$BACKUP_DIR/container-images.txt"

RUNTIME_API_ID="$(docker ps -q --filter "label=com.docker.compose.project=$RUNTIME_PROJECT" --filter label=com.docker.compose.service=api)"
test -n "$RUNTIME_API_ID"
docker inspect --format '{{range .Mounts}}{{if eq .Destination "/app/data"}}{{.Type}} {{.Name}} {{.Source}}{{end}}{{end}}' "$RUNTIME_API_ID"
docker volume inspect "$RUNTIME_DATA_VOLUME" --format '{{.Name}}'
```

将上面的实际 `/app/data` 挂载与预期卷名核对。若原部署使用其他项目名、卷名或 bind mount，先
对齐统一 Compose 的挂载再继续，避免启动到一个空卷。确认 MySQL 已有可恢复备份；本次合仓
不增加迁移，不修改任务表、目标归属或历史执行身份。

### 2. 更新代码并安装合并配置

开发机在 CustomerProfile 仓库执行：

```bash
git push -u origin codex/unified-image-release
```

服务器在原执行器目录执行。工作区已有未提交代码时先保留，不使用强制覆盖命令。

```bash
cd "$APP_DIR"
git fetch origin
git switch codex/unified-image-release
git pull --ff-only origin codex/unified-image-release
```

将本地生成的合并 `.env` 上传到服务器一个临时位置，再安装到根目录：

```bash
install -m 600 /实际上传位置/merged.env "$APP_DIR/.env"
cd "$APP_DIR"
./scripts/release.py --profile invitation-runner --check
```

无需再准备 `services/task-backend/.env`。旧后端目录保留其原 `.env`，用于停止旧服务与必要时恢复。
MySQL、Runner URL、入站密钥与目标身份沿用原值，首次切换不同时改成内部服务名。
原目标在途运行、重试与失败通知排空后，可另行计划调整目标地址和版本。

### 3. 先构建镜像并检查配置

在停止旧服务前完成依赖下载、镜像构建和全部 9 个进程的配置解析。

```bash
cd "$APP_DIR"
export CP_IMAGE="customer-profile-unified:$(TZ=Asia/Shanghai date +%Y%m%d-%H%M%S)-$(git rev-parse --short=12 HEAD)"
./scripts/release.py --profile invitation-runner --image "$CP_IMAGE" --prepare
printf '%s\n' "$CP_IMAGE" > "$BACKUP_DIR/new-image.txt"
```

`--prepare` 不停止或重建运行中的服务，不派发任务，不执行迁移。源码构建要求跟踪文件已提交；
`.env` 与 `.releases/` 已被 Git 和镜像构建上下文排除。保留当前终端的变量，后续复用同一镜像。

### 4. 暂停提交并停止旧后端

暂停业务入口的任务提交与定时触发；直接调用画像或邀约执行器的上游也在本次窗口暂停。
先停旧任务 API，再停止四个派发组，等待在途线程退出。给出 3600 秒宽限，不使用强制删除。

```bash
cd "$OLD_BACKEND"
./scripts/compose.sh -p "$OLD_BACKEND_PROJECT" --profile invitation-runner stop api
./scripts/compose.sh -p "$OLD_BACKEND_PROJECT" --profile invitation-runner stop -t 3600 \
  worker commercial-worker profile-runner-worker invitation-runner-worker
./scripts/compose.sh -p "$OLD_BACKEND_PROJECT" --profile invitation-runner ps --all
```

确认旧后端已停止后，再进入执行器切换。MySQL 中的排队任务保留，新后端按原目标和运行身份接续；
无需删除队列、清理 processing 状态或批量重置任务。

### 5. 等待旧执行器退出并备份数据卷

先停执行器的接单 API，再等待各旧 Worker 完成当前运行。兼容旧共用 `worker` 与已拆分的两个 Worker。

```bash
cd "$APP_DIR"
./scripts/compose.sh --profile invitation-runner stop api inbound
for service in worker profile-worker invitation-worker; do
  docker ps -q --filter "label=com.docker.compose.project=$RUNTIME_PROJECT" \
    --filter "label=com.docker.compose.service=$service" |
    while IFS= read -r id; do docker stop --time 3600 "$id"; done
done
```

确认执行器项目没有仍在运行的旧应用容器，且停机日志没有强制终止或未确认回写，再备份整个卷。
复制前所有写入该卷的进程都应已退出，使 SQLite、WAL 与归档文件处于同一恢复点。

```bash
docker ps --filter "label=com.docker.compose.project=$RUNTIME_PROJECT"
test -z "$(docker ps -q --filter "label=com.docker.compose.project=$RUNTIME_PROJECT")"
docker run --rm --user 0:0 --network none \
  --mount "type=volume,src=$RUNTIME_DATA_VOLUME,dst=/source,readonly" \
  --mount "type=bind,src=$BACKUP_DIR,dst=/backup" \
  --entrypoint python "$CP_IMAGE" -c \
  'import os,shutil; p=shutil.make_archive("/backup/profile-data", "gztar", "/source"); os.chmod(p, 0o600)'
```

仅移除已经停止的旧共用执行器容器，避免后续误启动；数据卷不移除。

```bash
docker ps -aq --filter "label=com.docker.compose.project=$RUNTIME_PROJECT" \
  --filter label=com.docker.compose.service=worker |
  while IFS= read -r id; do docker rm "$id"; done
```

### 6. 启动统一服务

```bash
cd "$APP_DIR"
./scripts/release.py --profile invitation-runner --image "$CP_IMAGE" --skip-build
```

已有 001–008 后端库的本次切换不添加 `--migrate`，服务更新使用 `--no-deps` 跳过迁移。
只有首次新建库或另行确认需要执行历史迁移时才显式使用 `--migrate`。
脚本先验证各进程配置，按暂停派发、等待执行、更新执行服务并健康检查、更新任务 API、恢复派发
的顺序运行。新应用为 9 个容器，全部引用前面准备的同一镜像，MySQL 沿用原外部部署。

### 7. 验收并恢复入口

```bash
cd "$APP_DIR"
./scripts/compose.sh --profile invitation-runner ps
curl -fsS http://127.0.0.1:18000/health
curl -fsS http://127.0.0.1:8099/health
curl -fsS http://127.0.0.1:18007/ready
./scripts/compose.sh --profile invitation-runner logs --tail 100 \
  task-api profile-runner-worker invitation-runner-worker
```

核对运行台原历史仍可查询、后端仍连原 MySQL、两个原生目标 ID/revision 与环境保持不变；确认
旧后端项目没有运行中的消费者，再恢复业务提交。健康接口不验证模型、语音服务和业务回写，
后续从正常业务流观察任务、日志与回写结果；不要为部署验收重复提交未知状态的旧任务。

发布记录位于 `.releases/`，含项目、Docker Engine、镜像及源码提交、旧容器镜像 ID、阶段和结果。
失败会停止后续步骤并记录阶段；先核对在途运行和实际回写，再决定恢复方式。

## 日常发布与恢复

首次切换完成后，日常整套发布只需要一个命令：

```bash
./scripts/release.py --profile invitation-runner

# 单独更新画像或邀约
./scripts/release.py --group profile
./scripts/release.py --group invitation --profile invitation-runner

# 单独更新任务后端
./scripts/release.py --group backend --profile invitation-runner
```

代码更新后重新执行发布；仅改 `.env` 也需要重建对应容器，`restart` 不重新注入配置。
镜像每次使用上海时区完整时间戳与提交号，已有本地标签会拒绝覆盖。同一 Docker Engine 和
Compose 项目的发布由进程锁串行化。执行 Worker 的停机宽限为 60 分钟，`--wait-timeout` 仅控制
启动健康等待。运行台前端修改后先在开发环境重建并提交 `frontend/dist`，服务器不需要 Node.js。

统一镜像之间的应用回退，先确认 SQLite 和归档格式兼容，再指定保存的旧版本：

```bash
./scripts/release.py --image customer-profile-unified:20261109-143000-abcdef123456 \
  --skip-build --profile invitation-runner
```

首次切换失败要回到两仓时，先停止新派发组、等待新执行 Worker 退出，再恢复保存的旧执行器代码、
配置与镜像，最后恢复原后端项目及提交入口。旧后端目录、原镜像与数据库均保留。
本次没有 MySQL 迁移，不需要数据库回滚；已有新业务写入时不要用切换前备份覆盖当前数据库。
归档格式兼容性和未知回写须先核对，不能仅凭容器退出就自动重跑任务。

## 本地开发

两模块分别安装依赖；业务 `.env` 不用于测试。

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
python3 -m venv services/task-backend/.venv
services/task-backend/.venv/bin/pip install -e 'services/task-backend[dev]'
./scripts/test.sh
```

已安装环境可用 `RUNTIME_PYTHON` 和 `TASK_PYTHON` 指定解释器。测试入口覆盖执行器、后端单元测试、
静态契约，以及真实接单路由与 SQLite、模拟上游的跨模块测试。执行器测试会读取根 `.env` 的部分
设置；运行前将业务配置安全暂存到仓库外，测试结束后放回，或使用不含业务配置的独立测试检出。
其他运行约束见[执行器部署说明](部署.md)、[留痕存储设计](../feature-storage-opt/README.md)和
[原生邀约接入](../../services/task-backend/docs/native-invitation-runner.md)。
