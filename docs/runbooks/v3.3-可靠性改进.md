# v3.3 跑批可靠性改进

> 针对 `docs/runbooks/跑批可靠性.md` 中分析的问题，v3.3 实施了4项高优先级工程改进。

## 改进清单

### A4 - anomaly落库 ✓

**问题**：`LlmAttempt.anomaly` 只在内存中使用，未写入 `request_attempts` 表。重试成功后前几次的异常原因永久丢失，无法事后诊断。

**改进**：
1. `request_attempts` 表新增 `anomaly`、`finish_reason` 两列（通过 migration 机制自动补列）
2. `store.insert_attempt()` 增加对应参数
3. `tracker.py` 在记录尝试时传递这两个字段
4. `LlmAttempt` 增加 `finish_reason` 字段并在响应解析时提取

**验证**：
- 编译通过
- 下次跑批后在 `trace.db` 的 `request_attempts` 表可查到这两列

---

### A3 - LLM输出量下限闸门 ✓

**问题**：`171****0673` 案输出从 12k 字符塌陷到 575 字符（22倍），`completion_tokens` 从 4500 降到 205，但因为 `finish_reason=stop`、无语法错误，被判为成功。静默降级，下游照常补空。

**改进**：
1. `detect_output_anomaly()` 增加两项新检测：
   - `suspicious_finish_reason`：`finish_reason` 不是 `stop`/`end_turn` 则判异常（length/content_filter等）
   - `output_too_short`：指定 `min_completion_tokens` 后，实际 `completion_tokens` 低于阈值判异常
2. 所有调用 `detect_output_anomaly()` 的地方传入 `finish_reason`

**使用方式**：
- 对「输入很大、输出不该很少」的节点，在调用 `llm_call()` 时可传入自定义参数（未来需在executor层暴露）
- 当前先靠 `finish_reason` 检测异常终止，输出量阈值作为备用机制

**局限**：
- 当前 `llm_call()` 签名未暴露 `min_completion_tokens`，需后续在 executor 层添加支持
- 文档建议对 L1 三层合并这类大输入节点设置阈值（如 prompt_tokens / 20）

---

### A2 - 失败案自动重跑 ✓

**问题**：v3.2 首跑 4/8 案因上游瞬断失败，人工执行 `--resume --only <4号码>` 后 4/4 全部成功。同一代码、同一输入，纯粹是瞬时故障，却需要人工补救。

**改进**：
1. `run_baseline.py` 增加 `--retry-failed N` 参数（默认 0）
2. 主循环跑完后，自动重排失败案最多 N 轮
3. 每轮退避 60 秒，记录日志，更新 summary
4. `manifest.json` 记录 `retry_rounds` 字段

**用法**：
```bash
python scripts/run_baseline.py --retry-failed 2
```

**效果**：
- 零代码风险（只在脚本层加重试逻辑）
- 直接消除 4/8 类损失，无需人工干预

---

### A5 - 参数错配防护 ✓

**问题**：两处实际浪费：
1. **臂选错**：`--workflow-id` 漏传，8 案全跑在旧 production 链路，62 MB 产物作废
2. **转写缓存落空**：`--out-dir` 改后，缓存目录推导为空，11 段录音重新识别

**改进**：
1. 批次 ID 以 `A-` 开头时，检查 `workflow_id` 是否为实验臂，不匹配打 WARNING
2. 跑批开始时打印 `workflow_id` 到日志
3. 转写缓存目录为空且有输入待跑时，打 INFO 提示可能配错路径

**效果**：
- 错配时在日志前几行即可看到提示
- 不阻断运行（可能是有意配置），但有明确警示
