# 内网取数与本地复现

> 用途：UAT 部署在内网，运行台出网不可达。用**留痕库快照**把运行数据搬出来，在本地
> 起一个只读运行台复现当时的过程。系统形态见 `../architecture.md`，部署见 `./部署.md`。
>
> 为什么是拷库而不是导 JSON：运行台的展示依赖四张表之间的定位键，定义快照也在库里。
> 只要这四张表一起搬，恢复侧**不需要任何代码**。
>
> **2026-11 起：库只是骨架，运行时数据在包里。** 存储瘦身之后，节点输入输出、请求体与
> 响应正文不再留在 SQLite，而是按主任务打成 `trace-archives/YYYY-MM-DD/<run_id>.json.gz`。
> 只拷 `.db` 会得到一份**处处空白的快照**——而且它看起来一切正常。所以快照 = 骨架库 +
> 包目录，两者必须一起走。
> 为什么不能直接拷 `.db`：库是 WAL 模式，最近写入还在 `-wal` 文件里，热拷会丢数据。

## 1. 在内网机器上生成快照

**镜像里没有 `scripts/`。** 镜像只带 `src/`、`frontend/dist/` 与一个 replay 夹具，
所以 `docker exec <容器> python scripts/export_snapshot.py` 必然报
`No such file or directory`。直接在宿主机上跑也不行：库和包在命名卷
`customer-profile_profile-data` 里，宿主机仓库目录下没有那个库。两种可行做法，任选其一：

```bash
# A. 拷进容器再跑（脚本零第三方依赖，只读文件，不需要装 requirements）
docker compose cp scripts/export_snapshot.py api:/app/scripts/
docker compose exec api python scripts/export_snapshot.py \
    --out-dir /app/data/export --since 2026-10-20

# B. 临时容器挂卷（不进入运行中的容器）
docker run --rm -v customer-profile_profile-data:/app/data \
    -v "$PWD/scripts:/scripts:ro" python:3.12-slim \
    python /scripts/export_snapshot.py \
    --db /app/data/customer_profile.db \
    --archive-dir /app/data/trace-archives \
    --out-dir /app/data/export --since 2026-10-20
```

两条路径都要**显式给 `--db` 与 `--archive-dir`**（路径 A 保持 `/app/scripts/` 这一层时
才可省）：脚本按 `__file__` 上两级推 `REPO_ROOT`，拷到别处后缺省路径会落空，而落空的
表现是「库里一条运行都没有」或「包全 missing」，不是明确的路径错误。

确实要在宿主机上跑（例如拿不到 docker 权限）时，先把卷取出来：

```bash
docker compose cp api:/app/data ./data-volume
python scripts/export_snapshot.py \
    --db ./data-volume/customer_profile.db \
    --archive-dir ./data-volume/trace-archives \
    --out-dir ./export --since 2026-10-20
```

`fetch_run_archive.py` 有同样的约束，修法相同。

常用参数：

| 参数 | 说明 |
|---|---|
| `--since` / `--until` | 时间窗，按**根运行**的创建时刻筛选。只写日期时 `--until` 含当天整天 |
| `--phone` | 业务标识清单，逗号分隔。不给表示不按号码筛选 |
| `--db` | 源库路径，缺省 `data/customer_profile.db` |
| `--name` | 快照名，缺省 `snapshot-<UTC 时刻>` |
| `--archive-dir` | 包目录，缺省取 `TRACE_ARCHIVE_DIR`，再缺省 `<仓库>/data/trace-archives` |
| `--dry-run` | 只报告会选中多少运行；同时报告其中多少需要带包、多少已清理（`purged`）、会带多少条基线 |

筛选粒度是根运行；它的整棵子运行树（子流程、迭代各轮）会连带导出，否则本地无法下钻。
先 `--dry-run` 确认条数，再正式导出。

产出一个库、一个包目录、一份清单：

```
export/<name>.db                    快照库（四张表 + 定义快照 + 增量基线 + 索引；载荷列多为空）
export/<name>.archives/YYYY-MM-DD/  运行时数据包，与库内运行一一对应
export/<name>.manifest.json         生成时刻、来源、筛选条件、各表行数、包的数量与体积
```

`manifest.json` 是 `format: 3`，`counts` 里除四张表外另有 `profile_baselines` 行数——它是
本地能否跑出增量的前提（见 §3.1）。`format: 2` 及更早的快照没有基线表，只能复现全量。

`archives.count / bytes / missing` 三项照旧。
**`missing` 非空时脚本以退出码 3 结束**，并逐条打印是哪次运行的包找不到——这些运行的
运行时数据已经取不出来了，不能当成「这次没有数据」继续。

脚本在一个读事务里完成全部读取，**不需要停服务**，期间新写入不会混进快照，也不会被阻塞。
目标文件已存在时脚本拒绝覆盖——换一个 `--name`。

导出完成后可做一次自检（应为 `ok`）：

```
sqlite3 export/<name>.db "PRAGMA integrity_check;"
```

## 2. 走堡垒机取出

`.db`、`.archives/`、`manifest.json` **三样一起**拷到外部。`.db` 是骨架，`.archives/`
是运行时数据（缺了它运行台里节点详情全空），`manifest.json` 记录来源，出问题时用来对齐
「这份快照是哪个提交、哪段时间的数据」。

`.archives/` 的目录层级必须原样保留：读包时按根运行创建日去找 `YYYY-MM-DD/<run_id>.json.gz`，
压平或改名都会导致「包存在但读不到」。

注意：`-wal` / `-shm` **不必也不应**带出，快照库是普通模式，没有这两个伴生文件。

## 3. 本地复现

把快照放到本地任意目录（例如 `D:/uat/snap-1.db`），用一个**独立的数据目录**起服务，
避免和本地开发库混用：

```
set DATABASE_URL=sqlite:///D:/uat/snap-1.db
set TRACE_ARCHIVE_DIR=D:/uat/snap-1.archives
set INLINE_WORKER=false
set INTERRUPT_ON_START=false
set SERVE_UI=true
python -m customer_profile.main
```

`TRACE_ARCHIVE_DIR` 指向随快照取回的包目录（**不是**里面的某个日期目录）。漏配或指错时
运行台仍能打开，但节点详情为空、响应里 `payload_missing` 为真——这是刻意的：
「证据缺失」必须和「没有产出」能分开。

三个开关的含义：

- `INLINE_WORKER=false`：本地副本不得去消费队列、不得发起任何出网请求。
- `INTERRUPT_ON_START=false`：启动时不得把状态为 `running` 的记录改写成 `interrupted`。
  UAT 上抓快照时正好有运行在跑是常态，改写会让「它当时确实卡住了」这类判断失去依据。
- `SERVE_UI=true`：运行台只在前端构建过之后可用。

打开运行台即可按 `run_id` 查看节点、每次请求的请求体与响应正文，以及当时的定义版本。
快照库是**证据**，只读使用；不要在本地往里面提交新任务。

### 3.1 本地要跑增量，快照必须带基线

增量入口（`customer_profile_incremental`）读 `profile_baselines` 才能判断「哪些记录是新的、
上一版结论是什么」。这张表**不挂在任何运行上**，导出时按号码整表连带（给了 `--phone` 就只带
这些号码），不受时间窗影响——它是「当前状态」，没有历史版本。

缺了它不会报错：每一轮都读不到基线，于是全部落 T3 全量重建，产物照样出得来，看起来像
**「增量没生效」**。所以：

```
sqlite3 export/<name>.db "SELECT COUNT(*) FROM profile_baselines;"
```

条数与 `manifest.json` 的 `counts.profile_baselines` 一致才继续。为 0 时要么源库这一批确实
没发生过增量（P1 之前的数据），要么导出条件不含这些号码。

本地验证一次 T0：

```
set DATABASE_URL=sqlite:///D:/uat/snap-1.db
set INCREMENTAL_ENABLED=true
set INCREMENTAL_TIERS=T0,T1,T2
python scripts/replay_incremental.py --sequence experiments/incremental/sequences/<尾号>
```

逐轮回放的完整口径见 `./基线实验.md` §11。

## 4. 常见问题

| 现象 | 原因与处置 |
|---|---|
| 快照里没有某次运行 | 号码筛选比对的是 `business_ref`；时间窗比对的是**根运行**的创建时刻。先用 `--dry-run` 复核条件 |
| 本地运行台打不开某次运行的图 | 该运行的 `definition_version_id` 为空（历史数据），图退化为空；节点与尝试仍可看 |
| `--dry-run` 报 0 条 | 时间窗与号码是「且」的关系；两者同时给会取交集 |
| 容器内报 `No such file or directory: scripts/export_snapshot.py` | 镜像里不带 `scripts/`，这是预期。按 §1 的两条路径之一做 |
| 容器内提示找不到库 | `--db` 显式指到 `/app/data/customer_profile.db`；容器工作目录不一定在仓库根 |
| 导出体积过大 | 加时间窗缩小范围。单个画像运行约 18 个子运行、250 条节点执行，体积主要在请求体 |
| 本地怎么跑都是 T3 | 快照没带 `profile_baselines`（旧格式或号码筛选为空），见 §3.1；也可能是 `INCREMENTAL_TIERS` 被置成了 `T0` 以外的单档 |
| `counts.profile_baselines` 为 0 | 源库早于 P1（那时没有这张表），或 `--phone` 的号码在基线表里不存在。前者只能复现全量 |

## 5. 全量任务导出与本地入库

快照（§1）适合**复现运行台**；若要把 UAT 数据当作**功能验证与问题回归**的输入，
用运行台的**任务导出**更合适：它按时间窗导出全部根任务的完整过程，含节点输入输出、
请求响应、失败重试与当时的定义。

> **这条链不带 `profile_baselines`，因此复现不了增量。** `/traces/export` 逐棵导出运行树，
> 而基线表不挂在任何运行上，导出里没有它。拿这批数据在本地跑增量入口，每一轮都读不到
> 基线 → 全部落 T3，看起来就是「增量没生效」。**要复现增量只能走快照（§1）**；这条链
> 适合的是不需要增量的功能验证与回归。批次 `manifest.json` 的
> `baseline_readiness.usable_for` 也列了它适用什么。

导出响应头 `X-Trace-Payload` 说明这批数据的载荷完整度（运行台运行详情页顶部也会提示
载荷档位与被裁节点数，节点「原始数据」页标出裁剪前的键数——**看不到字段先看那里**，
再判断是「被裁」还是「没产出」）：

| 取值 | 含义 | 能不能当对比输入 |
|---|---|---|
| `full` | `high` 档，与改造前等价 | 能 |
| `sliced` | `low` 档：只有响应原文、根输出与诊断切片（含增量档位、基线写入、补缺统计等判定字段） | **不能**做逐节点新旧对比 |
| `skeleton` | 只有骨架（存量已清理或包丢失） | 不能，只能看状态与错误 |

入库后同样口径记在批次 `manifest.json` 的 `payload_kinds` 与 `payload_complete`，
并在批次 `README.md` 顶部写明少了什么。

现行格式是 `GET /traces/export` 导出的 zip，内含一行一棵根运行树的 JSONL：

```
python scripts/ingest_trace_export.py \
  --zip <导出包>.zip \
  --out-dir experiments/uat_data/<batch-id>
```

旧格式是 `all-tasks-complete.json`（单文件、根任务数组），历史批次仍可用
`scripts/ingest_uat_export.py` 入库。两者产出同构：

`runs/<号码>/{result,nodes,tree,attempts}.json` + `manifest.json` + `phones.txt` +
`summary.{json,md}` + 批次 `trace.db`，另把原始导出放进 `source/`。

同号码在一个窗口内可能运行多次（2026-11-02 那批最多 9 次）。第一次落 `runs/<号码>/`，
之后依次 `__run2`、`__run3`；`compare_batches` 与 `replay_from_archive` 都只取第一份。

回放是**可复现性**的要求，不是网络限制的要求：模型侧每次都真实调用，输入侧必须固定，
否则「新代码 vs 旧代码」比出来的差异里混着数据变化。回放工具
`scripts/replay_from_archive.py` 默认从 `experiments/uat_data/` 取源批次，也可以传
`experiments/batches/<batch-id>` 的目录路径。

> 2026-11-02 更正：此前这里写「本地访问不到 UAT 的取数接口」。现在 `mhero.dfmc.com.cn`
> 的临时对接接口从本地可达（`scripts/run_baseline.py` 实测 200），可直接取数跑批。
> **仍要注意**：`118.145.238.50:8084` 那套旧地址已随接口改版弃用，访问它返回
> `200 []`——空数组看着像「这个客户没资料」，实际是打到了废弃端点。

## 6. 客户资料清单接口与原始响应

取数层唯一的入口是 `GET /api/v1/remote/data/history/{phone}`，全部渠道的原始资料都从
这一份响应里来。接口契约原文见 `../reference/M2M历史资料接口规范-20261031.md`，这里只写
**出问题时要看哪里**。

### 6.1 怎么取

```bash
# 密钥取 .env 里的 PROFILE_MHERO_API_KEY（= 下游的 M2M_API_KEY）
curl -sS -H "X-API-Key: $PROFILE_MHERO_API_KEY" \
  'https://mhero.dfmc.com.cn/customer_profile/m2m_api/api/v1/remote/data/history/<phone>'
```

地址与密钥都以 `.env` 为准：`PROFILE_API_BASE_URL`（`base_url_for('profile')`）拼上
`/api/v1/remote/data/history/<phone>`。代码里 `Settings.profile_api_base_url` 的缺省值
只是兜底，未配 `.env` 时会指向已弃用的旧地址。

未知号码或无有效资料时返回 `200` 与空数组 `[]`——**空数组是正常结果，不是接口故障**；
但**三个号码同时返回 `[]` 时先怀疑端点**，而不是数据。2026-11-02 就出现过一次：
旧地址对三个有数据的号码全回 `[]`，换到 mhero 后同一个号码返回 19 条记录。

> **本地出网若走代理，httpx 会读 `HTTP_PROXY`/`HTTPS_PROXY` 并可能连不上。**
> 实测同一台机器上 `curl` 通、`httpx` 超时。排查取数失败时先排除这一层，
> 用 `trust_env=False` 复验一次再动代码。

### 6.2 原始响应落在哪

不需要额外抓取：每一次出网尝试都由运行台留痕，`runs/<号码>/attempts.json` 的
`response_text` 就是这份响应的原文，`request_json` 里有实际请求路径。查「接口给了什么」
先看它，再谈代码。

跑一次新批次后，取数层的判定结果在 `nodes.json` 的 `pipeline_l0_records` 节点里：
`records_json` 是记录层逐渠道的结论（`status` / `content` / `fetched_at`），
`pipeline_l4_triage` 的 `tier_reason` 说明这案为什么被判成 `sufficient` / `thin` / `empty`。

### 6.3 三个最常见的误判

| 现象 | 先看什么 |
|---|---|
| 某渠道恒为空 | 该渠道在响应里到底有没有出现。清单里没有的渠道记 `exception` 是**正确行为**，不是取数失败 |
| 正文是英文键名 | 该渠道是不是本体渠道但没被渲染（`ontology_payload.FIELD_LABELS` 缺标签时原样输出键名，属保底而非故障） |
| 录音位为空 | 先看 `media_urls`，再看 `raw_payload.recording_url`；两者都没有才是真没有录音 |

`fetched_at` 只有基础渠道与外部补充渠道才有，过程资料与录音没有——那是接口事实，
不是解析遗漏；记录层对它回落 `created_at`，因此记录上该字段恒有值。
