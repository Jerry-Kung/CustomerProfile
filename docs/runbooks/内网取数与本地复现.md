# 内网取数与本地复现

> 用途：UAT 部署在内网，运行台出网不可达。用**留痕库快照**把运行数据搬出来，在本地
> 起一个只读运行台复现当时的过程。系统形态见 `../architecture.md`，部署见 `./部署.md`。
>
> 为什么是拷库而不是导 JSON：运行台的展示依赖四张表之间的定位键，定义快照也在库里。
> 只要这四张表一起搬，恢复侧**不需要任何代码**。
> 为什么不能直接拷 `.db`：库是 WAL 模式，最近写入还在 `-wal` 文件里，热拷会丢数据。

## 1. 在内网机器上生成快照

在能访问 UAT 数据卷的主机上执行（容器部署时用 `docker exec` 进任一应用容器，或直接在
宿主机上跑，两者等价——脚本只读文件）：

```
python scripts/export_snapshot.py --out-dir /app/data/export --since 2026-10-20
```

常用参数：

| 参数 | 说明 |
|---|---|
| `--since` / `--until` | 时间窗，按**根运行**的创建时刻筛选。只写日期时 `--until` 含当天整天 |
| `--phone` | 业务标识清单，逗号分隔。不给表示不按号码筛选 |
| `--db` | 源库路径，缺省 `data/customer_profile.db` |
| `--name` | 快照名，缺省 `snapshot-<UTC 时刻>` |
| `--dry-run` | 只报告会选中多少运行，不落盘 |

筛选粒度是根运行；它的整棵子运行树（子流程、迭代各轮）会连带导出，否则本地无法下钻。
先 `--dry-run` 确认条数，再正式导出。

产出两个文件：

```
export/<name>.db             快照库（四张表 + 定义快照 + 索引）
export/<name>.manifest.json  生成时刻、源库路径与提交号、筛选条件、各表行数、体积
```

脚本在一个读事务里完成全部读取，**不需要停服务**，期间新写入不会混进快照，也不会被阻塞。
目标文件已存在时脚本拒绝覆盖——换一个 `--name`。

导出完成后可做一次自检（应为 `ok`）：

```
sqlite3 export/<name>.db "PRAGMA integrity_check;"
```

## 2. 走堡垒机取出

两个文件一起拷到外部即可。`.db` 是主体，`manifest.json` 记录来源，出问题时用来对齐
「这份快照是哪个提交、哪段时间的数据」。

注意：`-wal` / `-shm` **不必也不应**带出，快照库是普通模式，没有这两个伴生文件。

## 3. 本地复现

把快照放到本地任意目录（例如 `D:/uat/snap-1.db`），用一个**独立的数据目录**起服务，
避免和本地开发库混用：

```
set DATABASE_URL=sqlite:///D:/uat/snap-1.db
set INLINE_WORKER=false
set INTERRUPT_ON_START=false
set SERVE_UI=true
python -m customer_profile.main
```

三个开关的含义：

- `INLINE_WORKER=false`：本地副本不得去消费队列、不得发起任何出网请求。
- `INTERRUPT_ON_START=false`：启动时不得把状态为 `running` 的记录改写成 `interrupted`。
  UAT 上抓快照时正好有运行在跑是常态，改写会让「它当时确实卡住了」这类判断失去依据。
- `SERVE_UI=true`：运行台只在前端构建过之后可用。

打开运行台即可按 `run_id` 查看节点、每次请求的请求体与响应正文，以及当时的定义版本。
快照库是**证据**，只读使用；不要在本地往里面提交新任务。

## 4. 常见问题

| 现象 | 原因与处置 |
|---|---|
| 快照里没有某次运行 | 号码筛选比对的是 `business_ref`；时间窗比对的是**根运行**的创建时刻。先用 `--dry-run` 复核条件 |
| 本地运行台打不开某次运行的图 | 该运行的 `definition_version_id` 为空（历史数据），图退化为空；节点与尝试仍可看 |
| `--dry-run` 报 0 条 | 时间窗与号码是「且」的关系；两者同时给会取交集 |
| 容器内提示找不到库 | `--db` 显式指到 `/app/data/customer_profile.db`；容器工作目录不一定在仓库根 |
| 导出体积过大 | 加时间窗缩小范围。单个画像运行约 18 个子运行、250 条节点执行，体积主要在请求体 |

## 5. 全量任务导出与本地入库

快照（§1）适合**复现运行台**；若要把 UAT 数据当作**功能验证与问题回归**的输入，
用运行台的**全量任务导出**更合适：它按时间窗导出全部根任务的完整过程 JSON
（`all-tasks-complete.json`），含节点输入输出、请求响应、失败重试与当时的定义。

本地入库：

```
python scripts/ingest_uat_export.py \
  --export <解包目录>/all-tasks-complete.json \
  --out-dir experiments/uat_data/<batch-id> \
  --archive <导出包>.zip
```

产出与跑批批次同构（`runs/<号码>/{result,nodes,tree,attempts}.json` + `manifest.json` +
`phones.txt` + `summary.{json,md}` + 批次 `trace.db`），另把原始导出放进 `source/`。

回放是**可复现性**的要求，不是网络限制的要求：模型侧每次都真实调用，输入侧必须固定，
否则「新代码 vs 旧代码」比出来的差异里混着数据变化。回放工具
`scripts/replay_from_archive.py` 默认从 `experiments/uat_data/` 取源批次，也可以传
`experiments/batches/<batch-id>` 的目录路径。

> 的临时对接接口从本地可达（`scripts/run_baseline.py` 实测 200），可直接取数跑批。
> **仍要注意**：`118.145.238.50:8084` 那套旧地址已随接口改版弃用，访问它返回
> `200 []`——空数组看着像「这个客户没资料」，实际是打到了废弃端点。

## 6. 客户资料清单接口与原始响应

取数层唯一的入口是 `GET /api/v1/remote/data/history/{phone}`，全部渠道的原始资料都从
这一份响应里来。接口契约原文见 `../reference/M2M历史资料接口规范-20261031.md`，这里只写
**出问题时要看哪里**。

### 6.1 怎么取

```bash
# 密钥取 .env 里的 PROFILE_MHERO_API_KEY（= 下游的 M2M_API_KEY）
curl -sS -H "X-API-Key: $PROFILE_MHERO_API_KEY" \
  'https://mhero.dfmc.com.cn/customer_profile/m2m_api/api/v1/remote/data/history/<phone>'
```

地址与密钥都以 `.env` 为准：`PROFILE_API_BASE_URL`（`base_url_for('profile')`）拼上
`/api/v1/remote/data/history/<phone>`。代码里 `Settings.profile_api_base_url` 的缺省值
只是兜底，未配 `.env` 时会指向已弃用的旧地址。

未知号码或无有效资料时返回 `200` 与空数组 `[]`——**空数组是正常结果，不是接口故障**；
但**三个号码同时返回 `[]` 时先怀疑端点**，而不是数据。2026-11-02 就出现过一次：
旧地址对三个有数据的号码全回 `[]`，换到 mhero 后同一个号码返回 19 条记录。

> **本地出网若走代理，httpx 会读 `HTTP_PROXY`/`HTTPS_PROXY` 并可能连不上。**
> 实测同一台机器上 `curl` 通、`httpx` 超时。排查取数失败时先排除这一层，
> 用 `trust_env=False` 复验一次再动代码。

### 6.2 原始响应落在哪

不需要额外抓取：每一次出网尝试都由运行台留痕，`runs/<号码>/attempts.json` 的
`response_text` 就是这份响应的原文，`request_json` 里有实际请求路径。查「接口给了什么」
先看它，再谈代码。

跑一次新批次后，取数层的判定结果在 `nodes.json` 的 `pipeline_l0_records` 节点里：
`records_json` 是记录层逐渠道的结论（`status` / `content` / `fetched_at`），
`pipeline_l4_triage` 的 `tier_reason` 说明这案为什么被判成 `sufficient` / `thin` / `empty`。

### 6.3 三个最常见的误判

| 现象 | 先看什么 |
|---|---|
| 某渠道恒为空 | 该渠道在响应里到底有没有出现。清单里没有的渠道记 `exception` 是**正确行为**，不是取数失败 |
| 正文是英文键名 | 该渠道是不是本体渠道但没被渲染（`ontology_payload.FIELD_LABELS` 缺标签时原样输出键名，属保底而非故障） |
| 录音位为空 | 先看 `media_urls`，再看 `raw_payload.recording_url`；两者都没有才是真没有录音 |

`fetched_at` 只有基础渠道与外部补充渠道才有，过程资料与录音没有——那是接口事实，
不是解析遗漏；记录层对它回落 `created_at`，因此记录上该字段恒有值。
