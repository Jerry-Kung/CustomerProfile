# 基线实验

> 用途：拿一批固定手机号跑真实工作流，把**最终结果与全部中间节点输出**归档成可长期比对
> 的数据基线，供日后改动工作流时验证输出质量没有劣化。
> 系统形态见 `../architecture.md`，部署与配置见 `./部署.md`。

## 1. 它解决什么问题

工作流改了一处提示词或一个节点之后，「输出质量有没有崩」此前**无法回答**：没有任何历史
结果可对照，只能靠人读一两份新结果拍脑袋。基线就是那个对照物。

数据基线不是 Dify DSL 迁移台账（`docs/specs/ledger/` 里的「基线」是另一回事）。本目录讲
的是**运行结果**的基线。

## 2. 三件套与它们的边界

| 文件 | 职责 |
|---|---|
| `test_phone_numbers.txt` | 测试手机号清单（39 个虚拟号），入库。基线的**输入锚点** |
| `scripts/collect_test_phones.py` | 从 `json_by_phone/` 提取号码，`--check` 校验漂移 |
| `scripts/run_baseline.py` | 跑批次并归档。这是唯一需要手工执行的命令 |

`json_by_phone/` 已 gitignore：它文件名是虚拟号，但**正文含真实客户标签与手机号**，
属「真实客户数据」，禁止入库。

## 3. 操作流程

### 3.1 跑前自检

```
python scripts/collect_test_phones.py --check
```

期望输出 39、退出码 0。不一致说明交付目录变了或清单被改过——**先搞清楚为什么**，
再决定是刷新清单还是停下。盲目刷新会让「上次基线用的是哪批号」说不清。

### 3.2 跑批次

```
python scripts/run_baseline.py                          # 全量 39 个，4 并发
python scripts/run_baseline.py --limit 4                # 先跑前 4 个试水
python scripts/run_baseline.py --batch-id smoke-1 --only 13415100087
```

- **单号码耗时因分支而异**，实测：不走录音取证分支的号码约 26–29 分钟；走该分支的号码会额外
  跑 iteration 循环体，仅循环体两个 tool 就是 298 s + 1388 s（约 28 分钟），因此明显更长。
  `--per-phone-timeout` 默认 5400 s（90 分钟），给最慢路径留约 1.5 倍余量。
- **超时不是质量判定**，只是「别无限等」的保险：设小了会把本来能成功的号码误判成失败
  （实测有号码恰好在 45 分钟被取消，当时仍在跑后续节点）。汇总表里状态为 `timeout` 的号码
  应当补跑，而不是当成「这个号码有问题」。
- 全量 39 个号码按上面的耗时量级估算，4 并发下约 4–5 小时。**建议后台跑并盯日志**。
- `--concurrency` 上限是 4，脚本不给更高档位。
- 断点续跑**默认开启**：已有成功产物的号码会被跳过。中断后直接重跑同一条命令即可。

### 3.3 看结果

```
experiments/batches/<batch_id>/summary.md      # 一号码一行的汇总表
experiments/batches/<batch_id>/logs/run.log    # 逐号码进度
```

汇总表里状态不是 `succeeded` 的号码单列在「待补跑」，并给出可直接复制的补跑命令。

### 3.4 补跑失败的号码

```
python scripts/run_baseline.py --batch-id <同批次> --only <号码1,号码2>
```

**用同一个 batch_id**，这样产物并进同一批次，汇总也覆盖全部号码。批次目录会被更新
（`summary.json` / `summary.md` / `manifest.json`），但**已完成的号码产物不会被改**。

汇总始终是**整个批次**的视图：它从磁盘上的产物重建，而不是只反映本次调用。所以补跑 2 个
号码时，先前跑完的 37 个仍在表里。批次的**开批时刻**与**历次入队记录**（`runs_this_invocation`）
也会保留，补跑不会把它们改成补跑时的情况。

**重跑已经完成的号码是安全的**（例如手滑对同一个批次再跑一次 `--only`）：此时没有任何号码
待跑，脚本立刻退出，**批次文件一个字节都不会变**，只在 `logs/run.log` 追加两行说明。

## 4. 产物与目录结构

```
experiments/batches/<batch_id>/
├─ manifest.json      批次元信息：提交号、清单哈希、配置白名单快照、体积
├─ phones.txt         本批次号码清单快照
├─ trace.db           本批次全量留痕 SQLite（+ -wal / -shm）
├─ summary.json       机读索引
├─ summary.md         人读汇总表
├─ logs/run.log       进度日志（ASCII）
└─ runs/<手机号>/
   ├─ result.json     最终结果（result1 原文）与定义快照
   ├─ nodes.json      全部节点执行，含 call_path 与输入输出
   ├─ tree.json       子运行索引
   └─ attempts.json   出网尝试（含请求体与响应正文全文）
```

**一批次约 600 MB**（请求体全文是大头），三批约 1.8 GB。`manifest.json` 里记了
`bytes_written`。

单条节点输出超过 512 KB 会被替换为摘要（类型、字节数、sha256、前 200 字符）。要读原文
就按 `run_id` + `node_id` + `call_path` 回 `trace.db` 查，那几个定位键在 `tree.json` 与
`nodes.json` 里都有。

### 四条不许破的规矩

1. **批次目录一经写入即冻结。** 补跑写进同批次是允许的（只增不改），但**不要手工编辑**
   已有的产物或 `manifest.json`。基线是证据，证据不能事后编辑。脚本自己也守这条：没有任何
   号码待跑时它**零写入**，不会因为一次空转就改动批次文件（开批时刻与历次入队记录都会保留）。
2. **不往 `experiments/` 放代码或文档。** 该目录被 gitignore，放进去等于不存在。
3. **不要把批次库改成 `data/customer_profile.db`。** 见 §6。
4. **不要在长跑途中改工作流定义或代码。** 见 §5。

## 5. 基线自洽：长跑途中不要改工作流

批次可能连续跑 4–5 小时，而开发期改代码是常态。前半批用旧图、后半批用新图，整批数据
就**不可比**，且症状隐蔽（每份产物看起来都正常）。

三层防御：

- 每个号码的产物里都记了 `definition_hash`、`code_commit`、`definition_version_id`。
  **跑完先查这些值是否一致**：
  ```
  Get-ChildItem experiments\batches\<batch_id>\runs\*\result.json |
    ForEach-Object { (Get-Content $_ -Raw | ConvertFrom-Json).definition.definition_hash } |
    Sort-Object -Unique
  ```
  多于一个值就说明中途换过定义，批次只能当作两段用。
- 建议在固定 commit 的 `git worktree` 里跑（需把 `.env` 拷进去），主检出随便改都影响不到它。
- `manifest.json` 里记了开工时的 `code_commit`。

## 6. 为什么批次用自己的 `trace.db`

- `data/` 在 `./部署.md` 与 `.gitignore` 里被定义为**可随时重建**，与「基线须长期留存」
  语义冲突。
- `data/customer_profile.db` 是 API/worker 共用的生产留痕库。基线长时间大量写入会与
  worker 抢单写者锁，而留痕层是 `fail_soft`——超时不会让运行失败，但会**静默丢留痕**，
  比报错更糟。
- 独立库让归档变成一条复制命令，批次目录自包含。

代价：`definition_versions` 的 version_id 从 1 重排，与生产库不连续。跨库比对要用
`definition_hash` 与 `code_commit`，**不要**拿 version_id 对号。

## 7. 持久化：`experiments/` 在仓库工作树内

它被 gitignore，所以：

- `git clean -xdf` 或 `-X` 会**一并删除**整个目录。**禁用这两条命令**。
- 重新 clone 也带不走它。

满足「持久化存储」需要额外一步：批次跑完后把 `experiments/` 复制到仓库外一处（例如 D 盘
备份目录）。至少复制体积小的关键子集——`manifest.json` + `summary.json` +
`runs/*/result.json`，39 个号码约 1.3 MB。

## 8. 常见问题

**「回写明明被跳过了，为什么运行还是 succeeded？」**
这是刻意的：回写节点带 `@writeback` 标记，`WRITEBACK_ENABLED=false` 时它只产出
`{"writeback_skipped": true}`，不算失败。**只看运行状态会误判「真的写过了」**。要确认没写
就查库：

```
sqlite3 experiments/batches/<batch_id>/trace.db \
  "SELECT COUNT(*) FROM request_attempts WHERE target LIKE '%update-profile%';"
```

必须为 0。基线的验收就是这么做的，不是靠看状态。

**跑得比预期慢？**
4 路并发共享同一进程的出网闸门（脚本里提到 16 个位）。耗时只适合**同批次内**横向参考，
不要拿它跨批次比对——并发度与外部服务都在变。

**产出中文乱码？**
所有写入都是显式 UTF-8，stdout 只打 ASCII。若产物里出现乱码，说明踩到了已知的编码问题，
先核对文件字节而不是只看终端显示（Windows 控制台的代码页不是 UTF-8，终端乱码很常见，
文件本身可能是好的）。

**想验证「改了一处提示词之后质量没崩」？**
基线跑完后，用改动后的代码起一个新批次，挑 2-3 个相同号码，对比新旧两批的 `result.json`
与 `nodes.json`。自动对比工具尚未落地（见 `changelog.md` 的 V0.6 条目），当前是人工比对
两边的 `result1` 与节点状态。

## 9. 一个「成功」的基线可能没覆盖到某条路径

**这是本实验最容易误判的地方。** 节点的 `skipped` 状态意味着**它根本没执行**，而运行整体
仍可能是 `succeeded`。因此「批次全绿」不等于「所有分支都被走过」。

V0.6 的 `smoke-1` 就是实例：那次 `succeeded`，但 `test_drive_audio` 的 iteration 节点
**全部 `skipped`**（上游 if-else 分支未走），循环体一次都没执行——而循环体里恰好藏着一个
会让整条失败的缺陷（见下）。第二号码走到了该分支，立刻失败。

因此**看汇总表时不能只看运行状态**。要确认「某条路径真的跑过」，得查节点状态：

```
sqlite3 experiments/batches/<batch_id>/trace.db \
  "SELECT workflow_id, node_id, node_type, status FROM node_executions
   WHERE node_type IN ('iteration','tool') ORDER BY workflow_id;"
```

`skipped` 的节点没有执行过它下面的东西。

### 已修复：iteration 节点在「同图 tool 先执行」时失败

- **症状**：`RuntimeError: run_iteration_body_node 必须在一次运行内调用`，出现在
  `test_drive_audio` / `outbound_call_audio` 的 iteration 节点上，并向上冒泡使
  `evidence_subagent` 与主入口整条失败。
- **触发条件**：**运行期间又构造了一个 `Scheduler`**。子流程运行器每开一次子运行就新建
  一个调度器，每个构造都会覆盖共享的循环体入口槽位。因此两种形状都会命中：
  - `tool` 节点与 `iteration` 节点同图、且 `tool` 先执行（合成用例的确定性复现）；
  - **并发争抢**（真实链路的主因）：`evidence_subagent` 的 13 个 `tool` 节点共享同一前置
    节点、并发 fan-out，互相覆盖槽位。

  失败可能是**间歇性**的——同一个号码重跑未必复现，且症状可能先是「结果记到别的运行上」
  （不报错）再变成报错。看到这个报错不要归因于「偶发抖动」。
- **已修复**（`src/customer_profile/execution/scheduler.py`，V0.6）：循环体入口不再依赖
  共享槽位，而是按 `run_id` 路由到该运行的属主调度器。回归用例见
  `tests/test_iteration_nesting.py`。
- **若你在旧批次里看到这个报错**：该批次的产物是有效的证据（留痕完整、能看出卡在哪），
  但对应号码的结果不可用，补跑即可。

### 并发下的耗时不可比

`--concurrency` 会让单号码耗时被同进程内的其它运行拉长。因此耗时只适合同批次内横向参考
（哪个号码慢），**不要跨批次比对**。自动判定该用出网次数、token 用量、节点状态这类不受
并发影响的指标。

### 已知的既有故障：模型侧「空响应」会让整个号码失败

**这不是本文档前面那两个已修缺陷，是模型侧的既有病理**，V0.6 之前就存在（`smoke-1`、
`fix-verify` 的留痕里都有）。之所以在 `fix-verify-2` 才被完整观察到，是因为此前那次运行在
**更早的一步**就崩了——迭代循环体一次都没跑到，问题被挡在后面。修好调度器之后，循环体第一次
真正执行，才把它带到台面上。**不要把它的暴露当成调度器修复引入的回归。**

- **症状**：某个 LLM 节点在 3 次尝试后失败，错误串形如
  `LLM 调用在 3 次尝试后仍失败（empty_text; empty_text; empty_text）`，并向上冒泡使整条
  号码失败。`empty_text` 是 `detect_output_anomaly()` 的异常码（`execution/llm.py`）：
  响应正文去掉空白后为空。
- **`empty_text` 属于「可重试的异常输出」**，所以「3 次尝试」是**设计行为**不是缺陷：
  每次空响应记一次 anomaly 并重试，三次耗尽才抛 `LlmCallError`。
- **判据——看耗时是否卡在 ~590 s**：实测六个空响应全部停在 **590.3–592.1 s**，而提示词长度
  从 266 token 到 32408 token 差了两个数量级，耗时只差 1.8 s。模型不会在提示词翻百倍时还准确
  停在同一个秒数上，这是**时间闸门截断**而非生成本身结束。同时 `prompt_tokens` 正常、
  `completion_tokens` 高达 40–60k、`response_text` 为空。
- **不是我们的超时**：批量脚本的 `http_read_timeout` 是 1800 s，远大于 590 s；且响应为
  HTTP 200 并带完整 `usage`。
- **未证实的一环**：`request_attempts` 表**不存** `reasoning_content`，因此「模型把输出
  都花在思维链上、最终 `content` 为空」只是**合理推测**，本批次无法直接验证。请求体只有
  `model` / `messages` / `temperature`，**没有 `max_tokens`**。
- **对基线的实际影响**：这会**偶发**让某些号码失败（`smoke-2` 全绿，说明并非必然）。这类失败
  **不是该号码的数据问题**，也**不是工作流质量问题**。补跑同一个号码可能仍失败（同输入已连空
  3 次），因此**不要**把它当成「工作流改坏了」的信号，也不要据此判定优化任务未通过。
- **要区分开的另一种错误**：同一批里还有 `ReadError`（约 23 s 就返回）的尝试，那是**传输层**
  错误，与 `empty_text` 机制不同。

## 10. 录音转写的归档与复用

录音识别是整条链路里最慢的一段（单条可达 20–30 分钟），而它又**与被优化的工作流逻辑无关**：
同一段录音、同一组识别参数，结果必然相同。因此基线把识别结果归档下来，后续重跑工作流时直接
复用，不再重新识别。**这一节讲的是「转写」这一层的缓存，与 §4 的批次产物是两样东西。**

### 10.1 归档放在哪、长什么样

```
experiments/transcript_cache/<key前2位>/<key>.json
```

**与批次同级、跨批次共用**——同一段录音（键含 URL）不在每个批次里重录一份。放在
`experiments/` 下是有意为之：§7 要求批次跑完后整目录复制到仓库外备份，缓存因此在**同一次
复制**里被带走，不会因为「另行备份」而被遗漏。

条目里存的是**云服务响应体原文**（完整 utterances），不是下游用的六字段数组。这样复用路径与
真实路径**走同一个解析函数**（`execution.auc.parse_auc_result`），解析规则日后变化时复用路径
自动跟随；存裁剪结果会把某一时刻的解析规则冻进归档。原文本身也是语音识别的**原始**结论。

**键** = `sha256(录音URL + 识别参数)`。识别参数取 `build_submit_body(...)["request"]`。

### 10.2 怎么用

```
python scripts/run_baseline.py                              # 默认复用已归档的转写
python scripts/run_baseline.py --no-transcript-cache         # 本次不复用（仍会归档新的识别结果）
python scripts/run_baseline.py --no-cache-write              # 不写入归档
python scripts/run_baseline.py --transcript-cache-dir <目录>  # 换一个归档目录
```

- **读与写是两个独立开关**，因为它们是两件事：`--no-transcript-cache` 要的是「这次不复用」，
  而**仍然归档**才让后续运行有可复用的数据。两个都不想要就同时给。
- 复用时 LLM 节点（校对、有效性判断、录音文件分析）**照常真实调用**。这是刻意的：优化工作流
  时改的通常正是这些节点，把它们也缓存会让对比失去意义。
- 归档目录由 `--out-dir` 推导，默认 `<out-dir>/transcript_cache`。

### 10.3 命中在留痕里怎么认

命中时该次尝试的 `replayed` 为 `True`（`request_attempts.replayed`，`attempts.json` 里同名
字段）。同时它的 `duration_ms` 会显著小——没有出网。两者互为佐证：

```
sqlite3 experiments/batches/<id>/trace.db \
  "SELECT node_id, call_path, replayed, duration_ms FROM request_attempts
   WHERE target LIKE '%query_analyze%';"
```

### 10.4 两个必须知道的判据

**「命中数持续为 0」= 缓存已静默失效。** 判据在 `manifest.json` 的 `transcript_cache.stats`
与逐号码的 `logs/run.log`（`transcript cache (cumulative): hit=N miss=M`）。最可能的原因是
**录音 URL 形态变了**（例如日后带上了过期签名）：URL 一变键就变，全部未命中，而表面上一切正常，
只是慢回原样。注意日志里的是**累计值**——4 路并发共享一份缓存，本号码的增量没有意义。

**改了识别参数，旧条目自动不再命中。** 参数进键，所以改 `model_name` / `model_version` /
`enable_ddc` 之后会走真实识别并存成新条目，旧条目保留。这是刻意的：拿旧参数的转写冒充新配置
的结果会是一次无从察觉的质量污染。

### 10.5 归档坏掉时怎么办

一条坏条目（半截 JSON、放错位置、格式版本不符）**只当作未命中**，退回真实识别，不让整批号码
失败。写入失败同样只打 stderr 并计数（`stats.write_errors`），不影响该号码的结果——缓存是省
时间的加速器，它坏掉不该让一次已经成功的识别判定为失败。
