## 1. 问题

L1 在枚举字段上稳定地给出**契约之外的中文自由文本**，管线当前的处理是「降级保留 → 出口修不回来 → 整条剔除」，结果是对客 Notes 静默缺字段。

2026-10-28 小范围重跑验证（6 案，归档输入回放、模型真实调用）的实测数据：

| 号码 | 旧批丢弃 | 新批丢弃 | 对照组丢弃 |
|---|---|---|---|
| 13782985566 | 1 | 9 | 7 |
| 19247201510 | 1 | 7 | 6 |
| 15527381216 | 0 | 5 | 7 |
| 15334131738 | 15 | 5 | 21 |
| 17771471913 | 0 | 22 | 0 |
| 17897110986 | 16 | 0 | 1 |
| **合计** | **33** | **48** | **42** |

对照组与新批同一份代码、同一份输入，只差三条「小订/大定」规则是否启用，仍然丢弃 42 条。**结论：丢弃与近期的规则改动无关，是枚举归一能力的固有缺口。**

被丢弃时的实际取值（原文照录）：

| 字段 | 取值 | 契约要的键 |
|---|---|---|
| `family_structure` | 已婚有子女 / 已婚有小孩 | `has_children` |

| `purchase_type` | 贷款 / 首购 / 增购 | `personal` / `company` |
| `payment_method` | 分期 | `loan` |
| `viewing_progress` | 初步了解 | `first_time` |
| `license_plate_status` | 无车无牌 / 需上河南信阳牌照 / 已有车牌 | `needs_license` / `has_license` |
| `trade_in_requirement` | 有置换意向 / 有换购需求 | `yes` |
| `driver_license_status` | `{"key": "yes", "input_value": ""}` | `yes` |

## 2. 现有链路的两个断点

1. **归一表只认「展示名精确相等」**。`internal_fields.display_to_key` 拿取值与
   `display_map()` 里的展示名做**字符串相等**比对，`已婚有子女` 与展示名 `有孩子`
   不等，于是返回 `None`。`LEGACY_ENUM_ALIASES` 只收旧版键（`married` → `married_no_child`），
   不收中文口语表达。
2. **出口的修复是第二道精确匹配**。`callback_build._repair_enum_value` 依次尝试旧键别名与
   中文展示名反查，两者都不中即**整条剔除**，且不写 `to_confirm`。

## 3. 影响

- **静默丢失**：48 条被删的 Notes 中 47 条没有进 `to_confirm`；六案的 `callback.to_confirm`
  全为空。销售既看不到该字段，也收不到「这格原本有内容」的提示。
- **丢失的不都是垃圾**：`19247201510` 的驾照情况是 `basis=fact`、置信 1.0，因取值被写成
  结构化对象的非法形态而整条消失。
- **字段级缺口放大到区块级**：`viewing_progress` 缺失会影响画像卡进度判断，
  `trade_in_requirement` 缺失会让销售错过置换线索。

客观地说，门禁也**拦掉了真正该拦的东西**：旧批把「暂无明确家庭结构信息」「暂无明确置换需求」
这类占位句当正常值回传，新批不再回传，这部分是改善，不应回退。

## 4. 建议方案（用户 2026-10-28 拍板方向）

**门禁不做硬丢弃；对非法枚举值引入一次 LLM 统一映射转换。**

### 4.1 为什么倾向 LLM 而不是继续扩别名表

- **遵从性问题不是缺陷而是常态**：模型在长链条复杂任务里不严格按枚举清单填，是概率较高的
  行为，靠人工补别名表只能追着它的说法跑，永远滞后。
- **判断所需的知识是封闭的**：一个字段的合法键集合是几十个键的小集合，判断题只需「这个
  自由文本最贴近哪个键（或都不贴近）」，不需要任何客户上下文。
- **成本极低**：一次调用只带 `{字段名, 合法键及展示名, 一批待映射取值}`，输出
  `{原文 → 键}`；无客户信息、无长上下文。一个批次的多案可以合并成一次调用。

### 4.2 形态建议

- 位置：投影层枚举归一之后、gate 之前，作为一个**批量映射步骤**；或复用现有
  `llm_checker` 通道的骨架（`rules/checker.py`：code 节点落地、异常全部吞掉、关闭即零 token），
  但**不能沿用其动作白名单**——checker 只允许降级与转确认、明确不产生取值，本需求恰好要
  产生取值，两者是不同职责，应另立通道而不是改 checker 的边界。
- 输入：本批次全部「归不到合法键」的枚举取值，按字段分组去重。同一批次内相同的非法值
  （如 `已婚有子女` 反复出现）只问一次，结果可回填到全部出现处。
- 输出约束：只允许返回合法键，或显式返回「无法映射」。模型给出的键必须再过一次代码校验
  （`键 ∈ legal_keys(字段)`），不合法即视为未映射——**代码守住最后一道，不把模型输出当真值**。
- 失败处置：映射失败或整步异常时，退回今天的「降级保留」而不是直接剔除；同时写一条
  `to_confirm`（见 4.4）。
- 灰度：一条独立开关（如 `ENUM_MAPPING_ENABLED`），缺省关闭；关闭时行为与今天完全一致。

### 4.3 为什么不建议只加别名表

别名表可以作为**第一道确定性通路保留**（零成本、零延迟），但不应作为唯一手段：
本批实测的非法值里有 `需上河南信阳牌照`、`有换购需求` 这类带上下文的长短语，穷举不现实。
两层配合才合理——**先查表，查不到的再交给一次批量映射**。

### 4.4 配套：丢弃必须留痕

无论映射成功与否，「原本有值但没进 Notes」这件事应当对销售可见。建议对未映射且最终剔除
的条目补一条 `to_confirm`（原因写「该字段取值无法归入可选范围，请确认后补填」，**不得**
出现规则编号或内部键名，遵守 `docs/README.md` 的可读性约束）。

## 5. 验收口径

1. 用本次的 6 案（`experiments/uat_data/deposit-rerun-20261028-6` 与
   `deposit-control-20261028-6`）重跑，非法枚举导致的对客丢弃条数应显著下降；
   `已婚有子女` / `分期` / `初步了解` / `有置换意向` 这类值应落到正确键。
2. 占位串（`未知` / `暂无` / `未提供`）**仍应照旧丢弃**——本方案只处理「有信息但格式不对」，
   不处理「本来就没信息」。
3. 每个被映射的字段要在留痕里能查到「原值 → 键」，供核读。
4. 无法映射的条目必须出现在 `to_confirm` 中。
5. 关闭开关时，产物与今天逐案一致。

## 7. 待定项

- **`frequent_social_media` 的「微信」**：契约合法集只有微博/抖音/头条/小红书，`微信` 是
  真实出现的高频取值却无对应键。这是**契约缺口**而非映射问题，需业务方确认是否加键；
  在确认前，该值应视为无法映射而不是硬塞进某个键。
- **是否合并到一次调用**：单批次非法值数量通常几十条，合并成 1 次调用的收益明确；但若
  单案运行（如实时接口）无法等待批内合并，需按案单独调用，成本仍可接受。
