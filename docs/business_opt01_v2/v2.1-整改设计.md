## 0 结论先行

v2 首轮 8 案暴露三个问题，按严重度：

| # | 问题 | 定级 | 一句话根因 |
|---|---|---|---|
| 1 | 推理步骤/证据锚点不可读 | **致命** | 投影层把**内部审计文案**直接写进了销售可见的 `reasoning_detail` |
| 2 | 画像卡大量缺内容 | 严重 | L1 吐回空值占位、全链路没有一层负责字段级补全，L3 只做「没有就不写」 |
| 3 | Notes 购车行为类字段丢失 | 一般 | `localize_claims` 把「渠道为空」误判为「渠道对不上」，整条降级 |

三个问题**同源**：代码把**中间产物**当成了**对客产物**。v2 的架构（事实定稿 → 表达）
是对的，缺的是「定稿」这一步的人话输出与召回兜底。

## 1 新增硬约束（项目级，防遗忘）

**面向销售的产出一律真人可读。** `reasoning_detail.steps` 与 `evidence` 必须是
「结论怎么推出来的」与「依据在哪」，不得出现内部审计字段名、规则名、来源档代号、
中间变量名。

- **禁止出现**：`归属过滤` / `来源分级` / `枚举归一` / `单多值约束` / `契约校验` /
  `未知渠道`，也不得把来源档代号（`社交自呈现` / `一手交互` / `第三方预测` /
  `公开登记查询` / `人工/系统登记`）当作唯一证据内容；不得出现 `basis_of_inference`、
  `record_channel` 等内部字段名。
- **`evidence` 必须指向客户原始数据的一段内容**：录音里的某段话、三方数据里的某个
  标签、登记系统的某一项。推断类写清「从哪几条推出来的」，且必须是**人话**。
- **`steps` 是推导链**：1–3 条中文短句，说明由原始依据推出结论的逻辑。

本约束写进：`CLAUDE.md`、`docs/README.md`、`docs/business_opt01_v2/端到端方案设计.md`、
本文、`src/customer_profile/templates/README.md`，并由 `tests/test_projection.py` 的
「审计词黑名单」用例与 `scripts/probe_v21_audit.py` 的读数共同守住。

## 2 问题与根因（实测）

### 2.1 问题 1 · 推理步骤/证据锚点不可读

**根因（代码级）**：`src/customer_profile/projection.py::_to_notes_updates()`
（783–828 行）为每条 Notes 写死了三条**审计话术**：

```
"summary": f"由 {len(sources)} 条断言按来源分级投影得到"
"steps": [   "归属过滤：剔除主体非客户本人的断言（保留 N 条）",
             "来源分级：取最高档 社交自呈现",
             "枚举归一 / 单多值约束：按 note-attributes 契约校验" ]
"evidence": [ f"{TIER_LABEL[tier]}（{channel or '未知渠道'}）" ]
```

这三条是**投影规则的执行记录**，不是「为什么这个字段是这个结论」；任何字段都长一样。
`evidence` 只写「来源档（渠道名）」，指向的是**哪一路数据**，不是**哪一段内容**。

**实测（`scripts/probe_v21_audit.py`，8 案）**：

| 读数 | 值 |
|---|---|
| 审计词命中 | **190 / 190 条 Notes 全部命中**（`归属过滤`/`来源分级`/`枚举归一`/`单多值约束`/`契约校验` 各 190） |
| 来源档代号出现 | `社交自呈现` 143 条、`一手交互` 46 条 |
| 证据串总数 | 189 |
| 其中含「未知渠道」 | **128** |
| 形如「渠道：原文」的证据 | **0** |

**关键观察：上游已经切好了可读材料，只是没被用上。**
`localize_claims()` 已把 `fact` 的 `anchor` 回定位到原文、切出 `quote`（原文连续切片）
与 `span`；L1 模板要求 `inferred_*` 必填的 `basis_of_inference`（「职业为互联网中层」
「关注 30 万以上车型」这类人话）也在 claims 里。`_to_notes_updates` 两个都没读。

### 2.2 问题 2 · 画像卡大量缺内容

**实测**：

| 维度 | v2（8 案） | 基线（同 8 案） |
|---|---|---|
| `usage_scenarios` | 8 | 24 |
| `product_preferences` | 13 | 32 |
| `resistances` | 7 | 32 |
| `communication_strategies` | 13 | 32 |
| `purchase_motivations` | 15 | 21 |
| `inferred_tags` | 30 | 40 |
| Notes 合计 | 190 | 226 |

逐案 `usage_scenarios`：v2 为 `[1,0,0,0,2,1,2,2]`，基线恒为 3。**4 案直接为 0。**

**两层成因**：

1. **L1 吐回空值占位。** 8 案 L1 断言 271 条，其中 **81 条（30%）`value` 为空**。
   空值集中在 `hobbies`、`douyin_id`/`xiaohongshu_id`、`owned_brand_model`/`owned_car_age`/
   `old_car_model`、`seating_requirement`、`core_concerns`、`usage_frequency`、
   `driving_preference`、`special_requirements`、`budget_range`、`payment_method`、
   `license_plate_status`、`planned_purchase_time`。提示词要求「默认覆盖全部字段」，
   模型于是为每个字段输出一条、没依据的就给空 `value`；这些占位断言在投影层被当作
   「缺失」丢弃（规则 g）——**看起来像「模型没提取到」，实际是「模型占了个位」**。
2. **全链路没有任何一层负责字段级补全。** L2 兜底只裁决**已有冲突**的字段，不补
   「L1 压根没给结论」的字段；L3 表达提示词明写「事实表里没有的，就是不知道」
   「空白就让它空着，不得靠常识编」。于是 `facts` 缺什么，卡片的 `usage_scenarios` /
   `product_preferences` / `resistances` 就空什么——这正是设计稿 §2.1 自己诊断过的
   「没有任何一层负责给字段」，v2 只在 L2 改了「丢弃→降级」，**补全没落地**。

基线有、v2 缺的字段键（前 10）：`hobbies` 5、`follow_up_frequency` 5、`core_concerns` 4、
`usage_frequency` 4、`budget_range` 4、`driving_preference` 4、`planned_purchase_time` 3、
`seating_requirement` 3、`annual_income` 3、`purchase_purpose` 3。

### 2.3 问题 3 · Notes 购车行为类字段丢失

**实测**：`localize_claims` 降级 **228 条**，其中 **`unknown_channel` 209 条（占 92%）**；
`anchor_not_found` 15、`anchor_too_short` 2、`inferred_without_basis` 2。
L2 侧 `a_attribution` 拒 17。

**根因**：L1 模板明确「`inferred_*` 类结论 `record_channel` **可留空**」；而
`localize_claims` 把「渠道为空」当成「渠道对不上」→ `_downgrade("unknown_channel",
clear_channel=True)`，把 `inferred_high` 一并压成 `inferred_low`。购车行为类字段
（`purchase_purpose`、`primary_driver`、`follow_up_frequency`、`communication_rhythm`、
`budget_range`、`planned_purchase_time`）恰恰绝大多数是推断，`record_channel` 为空，
于是被这条**误伤**。

这条同时是 `findings.json` 里 `basis_collapse`（7/8 案「`fact` 与中间档在字段级全塌成
`inferred_low`」）的成因——所以它不是「Notes 略少」，而是**三分类在字段级别名存实亡**。

## 3 整改设计

### R1 · 可读性（对应问题 1）

1. `Claim` 增加 `quote`（原文切片）字段；`project_claims` 把 claims 里的
   `quote` / `anchor` 透传进 `Claim`（目前 `Claim` 明确丢弃了它们）。
2. `_to_notes_updates` 重写 `reasoning_detail`：
   - `evidence` = 该字段的**原文切片**（`quote`）优先；无 quote 的用 `basis_of_inference`
     的推断依据；两者都无才退回「渠道名 + 来源说明」；**渠道名取不到时不留「未知渠道」
     占位**（该条 evidence 直接不写）。
   - `steps` = **推导链**，1–3 条中文短句，由原文切片与推断依据写成；不得再出现规则名
     与来源档代号。
   - `summary` = 一句话说清结论怎么来的。
3. 新增「审计词黑名单」用例（机器判据）。

### R2 · 覆盖（对应问题 2）

1. **L1 模板收紧**：`value` 不得为空——**要么给出取值（可为 `inferred_low`），要么整条
   不输出**；删除「空值占位」这一形态。
2. **空值断言可观测**：`project_claims` 入口对空值断言**拒收并计数**（输出
   `empty_claims` 计数与字段名），把「L1 漏字段」变成 KPI，而不是静默丢。
3. **字段级补全**：42 字段里「L1 未给结论」的字段纳入 L2 兜底输入（新增一类
   `missing_fields` 候选），产出 `inferred_low`。**受约束**：只能基于已有 `facts` 与
   业务资产归纳，不得编造候选集外的取值（沿用「兜底是裁决者不是作者」的边界）。
4. **多值不再压缩**：多选枚举与聚合语义字段保留多个合法值。
5. **叙事型 section 放宽**：`usage_scenarios` / `product_preferences` /
   `purchase_motivations` / `resistances` / `emotion_state` 允许 L3 基于 `facts` +
   业务资产做**归纳**，措辞限于 `inferred_*` 口吻，不产生新的**确定**取值。

### R3 · Notes 保真（对应问题 3）

1. `localize_claims` 渠道处理**分层**：
   - `fact`：无渠道且无 quote → 降级（保持 v2 行为）；
   - `inferred_*`：无渠道**不降级**（本就允许），仅清空渠道字段。
2. 渠道名可从 `record_id` / 依据反查则**补全**，不轻易清空。
3. 回放验证 `unknown_channel` 降级趋近 0、`inferred_high` 字段数回升、`basis_collapse` 归零。

## 4 验收判据（零 token 回放）

语料：L8 8 案（带全量节点产出）+ 基线 39 案同号对照。
工具：`python -I scripts/probe_v21_audit.py` + `pytest tests/`。

| 维度 | 判据 | 口径 |
|---|---|---|
| 可读性 | `reasoning_detail` 审计词命中 = 0 | 黑名单 13 词 |
| 可读性 | 证据串含原文切片或推断依据的比例 ≥ 90% | 逐条扫 8 案全部 Notes |
| 可读性 | 「未知渠道」占位 = 0 | 全案 |
| 覆盖 | Notes 字段数逐案 ≥ 基线 | 同号对照 |
| 覆盖 | `usage_scenarios` 逐案 ≥ 基线 | 同号对照 |
| 覆盖 | 多值字段取值数 ≥ 基线（不压缩） | 多选与聚合字段 |
| 保真 | `unknown_channel` 降级 = 0 | L1 降级明细 |
| 保真 | `inferred_high` 字段数 > 0（三分类不再全塌） | 字段级 basis 统计 |
| 回归 | 全量 `pytest` 绿 | 干净检出 |

## 6 与 v2 的关系

v2.1 **不推翻** v2 的四层架构（L0 记录 → L1 取证 → L2 投影 → L3 校验与表达）与已定稿的
P1–P5，只修三处「中间产物当对客产物」的实现缺陷。AB 可比性四条判据不变；R2 全量 39 案
仍是对外验收的终点，本次整改的验收停在**离线回放**这一层。
