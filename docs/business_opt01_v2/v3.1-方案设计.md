## 0. 结论先行

v3 立住的三条接口（事实带坐标、身份字段来源白名单、长 JSON 可靠性）**本身没坏**，
但它们**只约束了「来源」与「格式」，没有约束「内容」**：锚点存在即可用，不管它跟取值
有没有关系；来源档在白名单里即可用，不管说话人是谁；`steps` 与 `evidence` 从**同一份
原料**渲染，自然长得一样。

v3.1 治的就是这三处「只判形式、不判内容」的漏洞，外加一条把确定性字段交还给代码：

1. **推导链与依据分离**（问题 1）：`evidence` 落**原材料**、`steps` 落**真思维路径**，
   由 L1 各层显式产出 `reasoning_chain`，不再由投影层从同一串依据里分流渲染。
2. **说话人归属硬约束**（问题 2）：销售顾问的自述/自我介绍不得进任何客户字段，
   代码侧按「值形态 + 锚点位置」双判，不再只信模型自报的 `subject`。
3. **锚点相关性门**（问题 3）：锚点不仅要能定位，还要**承载取值信号**；问候语、
   JSON 残片一类「能定位但零信息」的锚点不得当证据。
4. **确定性字段代码注入**（问题 4）：`phone_number` 由入参直给、`driver_license_status`
   由「有无试驾/旧车」规则判定，不再交给 LLM 猜。

v3.1 不做：不推翻 v3 的三分层与三接口，不重开 L0、不改对外契约、不动 L3。

## 2. 根因诊断（带实测证据）

语料：v3-fix 批 7 案（`A-pipeline-L8-v3-20261014-fix`），基线同号对照。

### 2.1 问题 1 · 推导链与依据内容雷同

**实测**：全 7 案共有 `steps` / `evidence` 的字段 **234** 个，其中两者**完全同集**的
**122 个（52.1%）**。逐案：17119850673 为 18/30、13527911093 为 26/31、13435844484 为 21/37。

**根因在投影层，不在提示词**。`_readable_evidence` 与 `_readable_steps` 从**同一组来源**
按**同一优先级**取料：

| 分支 | `evidence` 渲染 | `steps` 渲染 |
|---|---|---|
| 有 `quote` | `渠道：quote` | `原始依据：quote` + `来自渠道` |
| 有 `source_quote` | `原文「…」（经纠错归一）` | `原始依据：…（已按语义纠错归一）` |
| 只有 `basis_of_inference` | 逐条 `hint` | `推断依据：` + 同批 `hint` 拼接 |

只有 `quote` 一列还勉强有点差异（一个带渠道前缀、一个拆两行）；推断类两栏**字面相同**。
所谓「一个是论据、一个是论证过程」在设计上就没落地——`steps` 从来没有承载「从依据
到结论的推演」，只是把依据换了层包装。

### 2.2 问题 2 · 销售顾问信息混入客户字段

**实测两条**：

- `13435844484`：`customer_name = "郑小姐（顾问自称，非客户姓名）"`。**模型自己都写明了
  这是顾问自称**，却仍然落进了客户姓名位（`subject=customer`、渠道 `外呼录音信息`）。
- `17119850673`：v3-fix 已被规则 a 拦下（`facts.occupation` 为空，1a 里该条
  `subject=salesperson`）；但用户所列 v3 版中该条进了最终结果。

**根因有三层，缺一不可**：

1. **白名单只判渠道、不判说话人**。`NAME_SOURCE_WHITELIST` 收 `registry` / `firsthand`，
   而外呼录音（`firsthand`）里**同时有销售与客户**。顾问自报家门落在一条 `firsthand`
   记录里，渠道档合格，于是被放行。
2. **`subject` 是模型自报的，且默认「customer」**。规则 a 的归属过滤只在
   `subject != customer` 时生效；1c 分析投影层给每条结论默认写 `subject=customer`
   （13435844484 的 `occupation`、`customer_name` 皆如此），归属过滤因此形同虚设。
3. **没有任何一层做「值形态」检查**。「自称」「顾问」这类词明晃晃写在取值里，
   却没有一处代码或提示词据此拒收。

### 2.3 问题 3 · 锚点可定位但零信息

**实测**：

- `13530559591` 的 `title=Mr`，证据是 `外呼录音信息：喂，你好`——问候语；
- `13435844484` 的 `title=Mr`，证据是 `微信手机号搜索界面信息：gender": "男性`——OCR 的
  JSON 残片。

**根因有两处**：

1. **`_locate` 只判「在不在原文里」，不判「跟取值相不相关」**。`喂，你好` 确实在转写里
   逐字存在、且唯一，于是被判为合格锚点。接口一只要求「能定位」，没要求「有信息」。
2. **`_readable_steps` 的分支优先级反了**。一条断言**同时**有 `quote` 和
   `basis_of_inference` 时，`steps` 走 `quote` 分支、直接吐 `原始依据：<锚点>`，
   把 L1 已经写好的推断链**整条丢弃**——这正是「L1 推理里明明给了性别判断与根据，
   最终推理链却写成一团」的直接机制（见 `_readable_steps` 的 `quoted` 分支先于
   `hints` 分支）。

### 2.4 问题 4 · 确定性字段未走规则

**实测**：

- `driver_license_status`：7 案中 5 案为 `yes`，**全部由 LLM 依据归纳得到**，无一条走规则；
  2 案（`13415100087` / `13530559591`）为空。而「到店试驾」「有旧车置换」本身即驾照的
  充分证据——试驾者不可能没有驾照。
- `phone_number`：当前靠模型从截图（`wechat_id` / 微信号）里**反捞**，取值还被降为
  `inferred_low`；而本字段的真值**就是本案入参手机号**，根本不必推断。

## 3. v3.1 四项改造

### 改造一 · 推导链与依据分离（对应问题 1、3 的渲染侧）

**契约变更**：L1 各层的产出条目新增字段 **`reasoning_chain`**（数组，1–4 条短句），
语义是「**从依据推到取值**的思维路径」——写「因为 A，所以 B」的 B 在哪、怎么落的，
而不是复述 A。

- **1a 事实层**：`basis=fact` 的条目**不需要** `reasoning_chain`（有原文锚点，路径即锚点）；
  `basis=inferred_high` 的条目须给。
- **1c 分析投影层**：**每条**结论都须给 `reasoning_chain`。
- **1b 人设层**：沿用 v3 的 `provenance`，不进证据位（v3 §5.1 不变）。

**投影层渲染口径**（改 `_readable_steps` 与 `_readable_evidence` 的取料）：

- `evidence` 一律落**原材料**：`quote` > `source_quote` > 带 `value_signal` 的锚点，
  不再把 `basis_of_inference` 当 `evidence` 兜底（那正是两者雷同的来源）；
- `steps` 一律落 `reasoning_chain`；**缺 `reasoning_chain` 时**，才回退到现有推断依据拼接，
  且回退时**不再复用 `quote` 那一条**（避免退化回「原始依据：锚点」）。
- 分支优先级**倒置**：`reasoning_chain` 优先，`quote` 只进 `evidence`。

### 改造二 · 说话人归属硬约束（对应问题 2）

**三层同时收紧**：

1. **1a 提示词**：明确「**我方销售顾问的自述同样是事实，但其 `subject` 必须是
   `salesperson`，且不得写入任何客户字段**」。给出正反例（「我姓郑，是这边的销售顾问」
   → `subject=salesperson`；「我姓陈」→ `subject=customer`）。
2. **1c 提示词 + 代码**：1c **不得自行声明 `subject`**。合并层（`merge_l1_layers`）
   对 1c 产出的每条结论，`subject` **一律覆盖为**「该字段在 1a 中的 `subject`」；
   1a 没有该字段时按 `unknown` 处理，交归属过滤降级——不再默认 `customer`。
3. **代码侧值形态门（新增判据）**：新增 `SALESPERSON_MARKERS` 词表
   （「顾问」「销售顾问」「销售」「我是这边的」「自称」「我方人员」）。任何客户字段的
   候选，只要**取值本身**或**锚点切片**命中该词表 → 整条拒收（不是降级，与 v3 姓名
   白名单同口径：错的名字比没有更糟）。此门同时覆盖 `customer_name` / `occupation` /
   `title` / `company`。

> 与 v3 接口二的关系：v3 接口二管「**哪个渠道**能提供这个字段」，v3.1 的值形态门管
> 「**这条取值说的是不是客户**」。两道门是**与**关系，缺一不可。

### 改造三 · 锚点相关性门（对应问题 3）

**接口一扩展为「相关性」而非仅「可定位」**：

1. **新增 `value_signal`**：L1 对 `title` / `driver_license_status` 等**信号型字段**
   给出「锚点中**支撑该取值的那个最小片段**」。例：`title=Mr` → `value_signal="男性"`；
   `driver_license_status=yes` → `value_signal="试驾"`。代码侧校验
   `value_signal` 必须**是锚点切片的子串**，否则整条降级为 `inferred_low` 并记入审查。
2. **噪音锚点黑名单**：`_locate` 命中后，再判一次锚点内容——问候语（`喂` / `你好` /
   `您好`）、纯 JSON 残片（含 `": "` 或 `":"` 的片段）、长度不足且无实义的一律不作证据，
   该条**不进证据位**（字段可保留，但证据位留白，不硬凑）。
3. **修正 `_readable_steps` 优先级**（见改造一），保证 L1 已给出的推断链不被锚点覆盖。

**范围**：`value_signal` 先在**身份/信号型字段**上强制（`title` / `customer_name` /
`driver_license_status` / `phone_number`），其余字段先记录不强拦，观察后再收。

### 改造四 · 确定性字段代码注入（对应问题 4）

新增纯代码节点（0 token），在 L2 投影**之前**把确定值注入断言账本：

| 字段 | 注入规则 | 依据写法 |
|---|---|---|
| `phone_number` | **直取本案入参手机号**（START 节点） | 证据写「客户留资手机号」，`basis=fact` |
| `driver_license_status` | 命中任一即 `yes`：① 存在**试驾录音**记录且非空；② `old_car_model` 有值；③ `trade_in_requirement=yes` | 证据写「到店试驾记录」或「有旧车可置换」，`basis=fact` |

- 注入值是**确定事实**，`basis=fact`，不受 LLM 抖动影响；
- 若 LLM 也给了同字段结论，按 `basis` 取更硬的一条（沿用合并层口径，同档**以注入为准**）；
- **不做**「有驾照就一定爱开车」这类二级推断——只做**定义级**蕴含（试驾 ⇒ 有驾照）。

## 6. 施工回填（与本文设计的偏差）

施工中发现并偏离设计的三处，记此以免日后对不上：

1. **确定性注入的落点改在定位层之后**（原 §5 写「接在 `L1_MERGE` 与 `L1_LOCALIZE`
   之间」）。原因：注入的来源名（`客户留资手机号` / `试驾与置换记录`）在记录层没有对应
   记录，若接在 `localize_claims` **之前**，定位层会按「给了渠道却找不到记录」把注入值
   降为 `inferred_low` 并清空渠道，正好废掉它刻意标注的登记档。实际链路为
   `L1_LOCALIZE → L1_INJECT → L2_PROJECT`。

2. **改造一不动 `_readable_evidence`**（原 §3 改造一写「`evidence` … 不再把
   `basis_of_inference` 当兜底」）。原因：v3 的验收判据本身是「证据串含原文切片**或推断
   依据** ≥ 90%」（本文 §4），且 `tests/test_projection.py` 明确要求无锚点时证据位保留
   推断依据里的事实部分。去掉兜底会让那批字段**丧失唯一凭据**，是回归而非修复。
   雷同的真正根源只在 `_readable_steps` 镜像了证据——故只改 `_readable_steps`：优先取
   `reasoning_chain`，缺它时给一句**不复述材料**的说明，同集关系自然断开。

3. **改造二不把 1c 的 `subject` 一律置 `unknown`**（原 §3 改造二写「1a 没有该字段时按
   `unknown` 处理」）。原因：实测 `IDENTITY_KEYS` 16 个字段里，1c 单独检出、1a 没有的
   共 **38 个已进 Notes 的字段（占 16.2%）**，一律置 `unknown` 会被归属过滤整批拦下，
   把 v3 修好的覆盖打回去。实际口径：**1a 有同字段时以其 `subject` 为准**（堵住「1c 默认
   写 customer」这个洞），1a 没有时保留 1c 的判断，由值形态门精准兜底。

## 7. 风险与回退

| 风险 | 处置 |
|---|---|
| `reasoning_chain` 由模型写，可能又写成依据复述 | 验收判据 1 用**同集率**机器判定，不靠人看 |
| 值形态词表过宽，误伤客户自述（如客户自称「我是做销售的」） | 词表只收**顾问/我方**指向词，不含泛职业词；命中仅拒收，字段可经人工确认补 |
| `value_signal` 强制度拖累召回 | 先在 4 个信号型字段强制，其余记录不强拦（同 v3 接口二「先宽后可收」） |
| 1c 的 `subject` 一律覆盖，可能盖掉合理的 `spouse` 结论 | 覆盖只在 1a 有该字段时取其 `subject`；1a 无该字段时保留 1c 的判断，由值形态门兜底（见 §6-3） |
| 回退 | S1–S4 各自单独提交，便于二分 |

## 8. 与 v3 / v2.1 的关系

v3.1 **不推翻** v3 的三层分层与三条硬接口，是它们的**补丁**：v3 立住了「来源可信、
格式可靠」，v3.1 补上「**内容相关、说话人对**」。v2.1 的可读性三项与 v3 的可靠性两项
为不回退基线。
