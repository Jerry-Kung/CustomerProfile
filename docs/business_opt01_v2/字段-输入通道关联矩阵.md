## 1. 设计原则（用户给定）

1. **主观/特质类字段**（年龄、收入、兴趣爱好等）——**可用所有渠道**，
   包括第三方预测；因为这类字段本来就是「推断」，渠道越多越准。
2. **客观/行为类字段**（如「对我方销售人员的意见」）——**必须依赖相应的客观数据**
   （沟通记录、试驾录音等），不得用无关渠道硬猜。
   > 例：`planned_purchase_time`（多久后到店）可以从沟通记录推断，
   > 但用「手机号归属地」「社媒截图」去猜它，就是无理由的硬猜。

由这两条推出本矩阵的三档：

| 档 | 含义 | 允许的来源 |
|---|---|---|
| **A · 身份标识** | 客观标识，不得由推断生成 | 需 登记 / 一手 / 公开登记 之一；社交自呈现需背书；**预测一律不可单独支撑** |
| **B · 车辆与交易事实** | 涉及钱与车的硬事实 | 需 登记 / 一手 / 公开登记 之一；**预测不可单独支撑**；社交仅辅助 |
| **C · 主观特质与推断** | 本就是推断类 | **全渠道可用**；预测单独支撑时降为 `inferred_low` |

## 4. 三条硬规则（代码侧强制）

1. **预测不得单独支撑 A / B 档字段。**
   G5 只有与 G1–G4 中任一条同时出现时才计入；单独出现 → 该字段转 `inferred_low`
   或 `to_confirm`，不得写成确定值。（这是现行 opt01 `b_prediction_only` 规则，
   在 v2 里保留，但由「丢弃」改为「降级保留」。）

2. **态度/行为类字段（`C-态度`：`emotion` / `knowledge_of_mengshi` / `pain_points`）
   必须至少有一条 G1 或 G2 依据。**
   这三项是对「我方/品牌/用车」的态度，只有对话与登记里才有；
   社媒截图与第三方预测最多作辅助，不得单独成立。
   同理 `driving_preference`、`usage_frequency` 不得仅由 G4/G5 支撑。

3. **社交自呈现（G4）不得单独支撑 A 档的身份类字段**
   （`customer_name` / `title` / 三个账号 ID）。
   账号装饰不是客户事实——昵称、头像画面、性别标签、地区都属「账号的呈现」。
   G4 单独命中时降为 `observation`（`confidence ≤ 0.6`），且 `title` 需 G1/G2 背书。

## 5. 落地形态与后续完善

**落地形态**：本表应落成一份代码常量（形如
`{attribute_key: {"tier": "A|B|C|C-attitude", "allowed": {"G1": "●", ...}}}`），
由 L1 装配（裁剪输入）与 L2/L3 校验（判越界）共用，**测试钉住它与 L1 提示词里的
字段清单同集合**（防止日后单边漂移）。

**与现行 opt01 的接口**：现行 `projection.py` 的 `CHANNEL_TIER`（渠道→来源档）
可以直接复用为 G1–G5；本表在其上加一层「字段 → 允许哪些档」。

**后续完善的建议路径**：

1. **先按本表跑一轮**，统计两类越界：① 被矩阵挡住但实际有强证据的字段（**过严**）；
   ② 通过了矩阵但人读为硬猜的字段（**过松**）。
2. **过严的按业务反馈放宽**——初版按「宁严勿宽」起步，放宽有据可依；
   反之若初版就宽，事后收紧会引发字段量骤降的观感问题。
3. **`C 档` 的 `○/●` 区分是本次最不确定的部分**（哪些主观字段该允许预测单独成立）。
   建议第一轮把 G5 全部按 `○` 处理（即预测永远不单独成立），
   观察字段缺口后再逐字段决定是否放宽为 `●`。

**已知的待定项**：
- `occupation`：现列 C 档但 G5 为 `○`——因为它既是推断类，又是「妻子在电力局」那类
  归属错误的温床，暂按半严格处理；
- `intended_brand` / `intended_model` 的 G4 列为 `●`（社媒晒车可作为考虑车型的证据），
  但需排除「晒别人的车」，第一轮需重点观察；
- `phone_number` 实为留资输入本身，列在此表仅为完整性。
