# business_opt01_v2 · 方案分析与调整建议（v2 定稿）

> 定位：对「当前优化方案（opt01 四段式）」实测结果的复盘，以及对 v2 方案的定稿设计意见。
> **本文只做方案层面的分析与讨论，不含代码改动，不是施工设计文档。**
>
> 数据口径：R1b 批次 `experiments/abexperiments/batches/A-pipeline-R1b-20261010`
> （13 案探针集，提交 `b6a7023`，可比性四条判据全通过）；基线
> `experiments/batches/baseline-39-dsv41-noThink`（同 13 案）。所有数字均为本次重新实测。
>
> 本版已并入用户 2026-10-12 的六条决策（见 §5）。

## 0. 结论先行

1. **Notes 字段是「结构性被砍」。** 13 案探针集：基线 360 → R1b 192，降 46.7%。
   丢得最狠的字段恰好是「需要合理推测」那一类：`age` 13/13 全丢、`annual_income` 12/13、
   `follow_up_frequency` 11/13、`communication_rhythm` 与 `personality_and_preferences` 各 9/13。
2. **成本是「涨了」。** 单案 token 437,809 → 720,273，+64.5%。而且**其中 41.1% 是付费后弃用**
   （详见 §1.3）——这是本次新查出的、比原先判断更严重的一条。
3. **病根是「没有任何一层负责给字段」。** L1 抽了 391 条可用断言（高于基线的字段总量 360），
   最后只落成 192 个字段；中间丢掉的 86 条全是 L2 的主动拒绝。
   现行 opt01 是「减法架构」，从架构上禁止了推断，而 Notes 的 42 个字段里
   **大量字段在原文里本就不会被显式提及**。

**v2 的方向（字段级直出 + 三分类置信度 + 推倒 production 重写）正对症**，
但必须同时解决「成本」与「推断纪律」两件事，否则会走回基线或原地打转。

## 1. 实测数据

### 1.1 漏斗：字段死在哪一步

| 环节 | 13 案合计 | 单案均值 |
|---|---|---|
| L1 原始断言 | 421 | 32.4 |
| 定位后保留 | 391 | 30.1 |
| **经 L2 投影后 Notes** | **192** | **14.8** |
| 基线（同 13 案） | 360 | 27.7 |

**L2 拒绝明细（86 条）**：

| 规则 | 条数 | 性质 |
|---|---|---|
| `b_prediction_only`（身份字段仅由第三方预测支撑） | 38 | 主动放弃 |
| `d_enum`（取值无法归一到契约枚举键） | 30 | 转换失败 |
| `c_conflict`（同来源档多值冲突） | 9 | 主动放弃 |
| `a_attribution`（事实主体非客户本人） | 9 | 正确拦截 |

两个反直觉的发现：

- **`a_attribution` 只拒了 9 条**——opt01 最引以为傲的「妻子不能写成客户」并不构成召回瓶颈，
  低产不是它造成的。
- **`d_enum` 拒了 30 条，是第二大杀手**——L1 提示词让模型「对不上枚举就照实写原始表述」，
  模型照做了，随后被 L2 的精确匹配全数拒绝。**这是提示词承诺与实现能力的错配**，
  v2 必须把「转换不到就丢弃」改成「降级保留」。

### 1.3 成本：41% 花在「白跑」上

R1b 单案 720,273 token，按「谁在用这些 token」分成四桶：

| 桶 | 13 案合计 | 占比 | 单案 | 说明 |
|---|---|---|---|---|
| A · production 生成层（后文推倒重写） | 3,014,637 | 32.2% | 231,895 | 12 个 LLM 节点 |
| **B · 取数侧的 LLM 压缩（付费后弃用）** | **3,847,196** | **41.1%** | **295,938** | 见下 |
| C · 新链路（L1 取证 + 旧证据整理） | 2,087,345 | 22.3% | 160,573 | 其中 L1 自身 73,001/案 |
| D · 其他 | 414,377 | 4.4% | 31,875 | |

**B 桶是本次最关键的发现。** 明细：

| token | 工作流 / 节点 | 新链路是否需要 |
|---|---|---|
| 2,559,841 | `audio_content_extract` / LLM 识别结果校对 | **不需要** |
| 856,156 | `audio_content_extract` / LLM 内容有效性判断 | **不需要** |
| 421,030 | `moments_info` / 多图片内容总结 | **不需要** |
| 10,169 | `moments_info` / 内容解析 | 不需要 |

**核实结论**：v2 的录音链路直接调 `audio_content_extract` 子流程，但只消费它的
`auc_result`（纯 ASR 逐字数组，由「识别结果提取」节点产出）；**上面这两个 LLM 节点照跑不误**，
产物一个字节都不被使用。它们做的正是「把逐字原文压成摘要」——
而这恰恰是 v2 明令禁止的一步（原文必须逐字进入 L1）。
**每案约 29.6 万 token、全批 41.1% 的成本，是在为一份被丢弃的摘要付钱。**

> **一句话**：现行 opt01 最大的浪费不是新增了 L1，而是**既付了旧压缩链的钱，又付了 L1 通读原文的钱**。
> 收敛这一桶是 v2 成本下降的最大单项，且**零质量风险**（不改变任何产出，只关掉不用的节点）。

### 1.4 非契约 key

基线 13 案里有 40 条、20 个非契约 key（`comparison_brand(s)`、`competitor_price`、
`test_driven_models`、`car_paint`、`interior` …）。L2 只输出契约 42 键，这 40 条被静默丢弃。
其中有对应契约键的应**改判**，没有对应位的应**丢弃但留痕**（不留痕就无法审计「漏了什么」）。

## 2. 根因

```
L1（LLM，只抽取）：「把原文摘成断言」——不产出字段
L2（代码，只筛选）：「有据则留，无据则空」——没有任何一步负责「补全」
L3（LLM，尚未落地）：表达层
```

「有据则留、无据则空」这条单一取向，把「字段数量」压到与「原文显式提及」等同的水平。
而 42 个字段里，`age`、`annual_income` 客户从不会直说；`communication_rhythm`、
`personality_and_preferences` 是归纳结论，原文里永远找不到对应句子；
`follow_up_frequency`、`primary_driver` 是策略判断，本就是从事实推出来的。

**基线为什么能填？** 因为它允许模型「合理的联想发挥」。基线的问题是**发挥得没有纪律**
（编造、把第三方预测当事实、把妻子写成客户）；但「发挥」本身是 Notes 业务必需的。
**opt01 的错误是一刀切地把「发挥」也禁掉了。**

## 3. 对 v2 方案的逐条分析（已并入用户答复）

### 3.1 【对】字段级直出 + 三分类置信度

它把「产出职责」重新装回链路，从架构上恢复召回。三分类同时满足「业务要多」与「诊断要准」，
把「来源可信度」从**提示词里的祈祷**变成**结构化字段**——这正是基线缺失的一条
（基线把所有东西混在同一个证据数组、同一种自然语言格式里，
于是「妻子在电力局」和「客户在电力局」长得一模一样）。

**四条纪律**（缺一条就会走回基线）：

1. **三类落成结构化字段**，不能只在提示词里说。
   每个值带 `basis: fact | inferred_high | inferred_low` + `evidence[]`；
   `fact` 必须能指回原文锚点，`inferred_*` 允许无锚点但必须带 `basis_of_inference`。
2. **区分「有据推断」与「无据推断」**：找不到任何原始数据关联的字段，
   只能给 `inferred_low` 或留空，**不得**给 `fact` 或 `inferred_high`。
3. **回写带置信度标记**：`inferred_low` 的值必须以可识别方式标注，
   否则销售分不清「客户说的」和「模型猜的」。
4. **保持「无关字段不硬猜」的纪律**（下条）：该原则仍有效，但不通过硬绑定矩阵实现。

### 3.2 【暂缓，降为研究稿】字段 × 输入通道的关联矩阵

用户对「无关联字段可不输出」的解释是：**支持合理推测，但对完全无关的目标字段不要硬猜**。
例：`planned_purchase_time`（多久后到店）可以从沟通记录推断，
但用「手机号归属地」「社媒截图」去猜它，就是无理由的硬猜。

我据此起草了一张 `42 字段 × M 路输入` 的关联矩阵（见同目录
`字段-输入通道关联矩阵.md`）。**但用户 2026-10-12 决定：暂不做「输入通道—输出字段」的强绑定关联**，
理由是当前实施起来有风险。该文档**保留作研究用途，不作为落地件**。

**因此 v2 落地时的口径改为**：

- **不做**硬绑定：L1 不用矩阵裁剪输入，输出也不按矩阵逐格校验越界；
- **保留原则**：「无关的字段不硬猜」这条**仍然有效**，只是实现方式从「配置一张硬矩阵」
  改为**在提示词与字段描述层面表达**——即把「该字段通常能从哪类信息推断」写进 L1 提示词的
  字段说明里，作为**引导**而非**闸门**；
- **风险由三分类置信度承接**：即便模型读了无关输入产生推断，
  它也只会落在 `inferred_low`，不会冒充事实。这是比硬矩阵更轻的兜底。

**矩阵的定位**：研究稿。后续若要收紧，可先按矩阵**离线统计**历史产出的越界情况，
用数据说话，再决定是否升级为硬约束。矩阵中三条硬规则（预测不得单独支撑身份类、
态度类须有一手依据、社交自呈现不得单独支撑身份证）**仍建议保留为 L2 的校验规则**——
它们针对的是明确的错误类型，不涉及通道与字段的全面绑定。

### 3.3 【已定】M×N 分批：默认 M=1、N=1，超限才拆

用户答复：**实践中若发现上下文溢出或严重遗忘，及时考虑分拆输入输出。**

实测支持这个保守起点：L1 单次调用**单案 prompt 中位仅 6.5k token**，
只有含超长转写的案子会顶到上限（最大一案 30 万 token，含一段 74 万字符的试驾转写）。

- **默认**：一次调用读全部输入，输出按 N 类**在同一个 JSON 里分组**（不是 N 次调用）。
- **触发拆分**：输入超阈值（建议 8 万字符）或实测遗忘率上升时，
  **按输入类型拆**——把「登记/一手」与「社交/预测」等来源分开成两批，
  而不是机械地 M 路 × N 类。（原先设想的「按字段组拆」依赖 §3.2 的关联矩阵，
  该矩阵已降为研究稿，故此处改为按来源类型拆。）
- **禁忌**：不要「按输出类型 × N」重复读同一份输入，那是纯浪费（当前 L1 已占 10.1%，
  再乘 N 会迅速失控）。

### 3.4 【已定，修正我原先的过度保守】L2 汇聚层：代码规则为主 + LLM 兜底

我原先建议「L2 纯代码」，用户指出纯代码不够。**这个反驳是对的**，接受。
代码规则能解决确定性问题（事实优先于判断、高置信优先于低置信），
但解决不了**多条弱证据的同向汇聚**：

> 例：某字段有 3 条**低置信推断**，来源不同（一手交互 / 社交自呈现 / 第三方预测），
> 结论大体相似——代码规则会判定「同档多值冲突 → 留白转确认」，
> 而实际正确的处理是**合并升格为一条高置信推断**（三条独立来源同向，本身就是增强证据）。

**v2 的 L2 应是三层**：

1. **代码规则层（必须先跑）**：归属过滤、来源分级、冲突消解、枚举归一、
   单多值约束、跨字段规则、三条来源硬规则（预测不得单独支撑身份类 / 态度类须有一手依据 /
   社交自呈现不得单独支撑身份证类）。**凡是能写成规则的，不交给 LLM。**
2. **LLM 兜底层（只处理规则判不了的部分）**：输入是**已被代码整理过的候选集**
   （每条带来源与置信度），任务只有三件——
   ① 弱证据同向汇聚（如上例）；② 语义冲突判断（两条值是否真的矛盾）；
   ③ 给出终判与理由。**不得新增候选集之外的字段值。**
3. **回写层（纯代码）**：把终判序列化成契约形态。

**为什么这样能避免重蹈覆辙**：现行 opt01 的病根是「11 个 LLM 节点各自通读原始材料、互相不知道对方在写什么」。
v2 的 L2 兜底**只有一个节点**，且它的输入是代码整理过的结构化候选集、
输出有明确边界（只能裁决、不能新增）。**一个受约束的裁决者 ≠ 11 个自由生成的作者。**

### 3.5 【对】L3 最终校验层：查漏补缺 + 内容润色

用户明确：**这里不是「自己审自己」，主要功能是查漏补缺 + 内容润色**——
LLM 原始输出常有遵从性/语言表达问题，复审时找出来修掉。

**v2 的 L3 应是两段**：

1. **代码校验**（确定性，复用现行 opt01 已有的规则表）：
   枚举合法、单多值约束、跨字段规则（旧车⇒换购、等级唯一）、卡片-Notes 一致、
   `basis=fact` 必有锚点、**无依据确定值率为 0**。
2. **LLM 复审**（查漏补缺 + 润色）：对未通过代码校验的项、以及语言表达问题做修复；
   **不得新增事实**（修改后的值必须仍能在候选集里找到出处）。

### 3.6 【已定】production 整体推倒重写

用户决策：**production 的 11 路完全扔掉，是历史遗留包袱；原流程内容用新方案重写。
旧的 `pipeline_evidence_llm` 一并删除。**

这一条与 §1.3 的 B 桶合并，构成 v2 的成本主体：

| 动作 | 省下 | 风险 |
|---|---|---|
| 删 production 12 个 LLM 节点，改为「事实定稿 → 一次表达 + 一次复审」 | 32.2% | 重写；需保证 9 个 section 与 Notes 同源 |
| 关掉取数侧不用的 LLM 压缩（§1.3 B 桶） | 41.1% | 零（不改变产出） |
| 删 `pipeline_evidence_llm`（与 L1 职责重叠） | 12.2% | 零 |
| 新增 L1（1 次全量取证） | −10.1% | — |
| **净效应** | **约 −75%** | |

**但必须保住 production 里的业务资产**（重写时原样搬迁，不要连积累一起扔）：

| 模板 | 规模 | 内容 |
|---|---|---|
| 标签库 | 26.6 KB | 标签分类 / 内容 / 等级 / 描述 |
| 产品信息（长） | 2.0 KB | 车型价格区间与卖点 |
| 产品信息（短） | 5.0 KB | 销售速查手册 |
| 邀约策略库 | 4.8 KB | 策略 ID / 目标画像 / 钩子 / 动作 / 话术示例 |
| 证据线索格式 | 1.2 KB | 输出格式契约 |
| 画像格式 | 0.8 KB | 输出格式契约 |

## 4. v2 目标形态（定稿）

```
L0 预处理层（代码 + 取数，0 token）
  取数 + 多模态→纯文本 + 渠道分级 + 校验核对 + 保守模板路由
  【关键改动：录音只走纯识别子流程的 auc_result，
   关掉「LLM 识别结果校对」「内容有效性判断」「多图片内容总结」——
   这三项每案 29.6 万 token，纯浪费】

L1 投影层（1 次 LLM，仅在超限时按来源类型拆批）
  输入按渠道分节组装（不做字段级通道绑定），直出字段级结论：
    { attribute, value, basis: fact|inferred_high|inferred_low,
      anchor?(fact 必填), basis_of_inference[](推断类必填), confidence }
  默认覆盖全部 42 字段；无关联的字段不硬猜（由字段说明引导 + 置信度兜底，不靠硬矩阵）
  【核心改动：把「只抽取」改成「直出字段 + 三分类」】

L2 汇聚层（代码规则 + 1 次 LLM 兜底）
  ① 代码：归属过滤 / 来源分级 / 冲突消解 / 枚举归一 / 单多值 / 跨字段规则 / 三条来源硬规则
  ② LLM 兜底：只裁决规则判不了的（弱证据同向汇聚、语义冲突），不得新增候选集外的值
  ③ 代码：序列化为契约形态
  【注意：不是「纯代码」，但兜底只有一个受约束的节点，不是 11 个自由生成者】

L3 校验与表达层（代码校验 + LLM 复审）
  ① 代码：确定性校验（含「无依据确定值率 = 0」）
  ② LLM：查漏补缺 + 内容润色，不得新增事实
  【同时承担原 production 的「把事实写成话」，复用那 6 个预置模板资产】
```

**与现行 opt01 的差别**：

| 改动 | 现行 opt01 | v2 |
|---|---|---|
| **L1 职责** | 只抽断言 | 直出字段 + 三分类 |
| **L2 对枚举/冲突** | 拒绝并丢字段 | 降级保留 + LLM 兜底裁决 |
| **production** | 12 节点照旧跑 | 推倒重写，预置资产保留 |
| **取数侧 LLM 压缩** | 照跑（41% 白费） | 关闭 |
| **旧证据整理节点** | 保留 | 删除 |

| 7 | 字段×输入通道强绑定矩阵 | **暂不实施**（2026-10-12 追加）；文档保留为研究稿，不做输入通道与输出字段的强绑定 |
| 2 | M×N 划分 | 支持当前设想；**实践中若上下文溢出或严重遗忘，及时拆**（→ §3.3） |
| 3 | L2 汇聚层 | 代码规则为主，**引入 LLM 兜底**（弱证据同向汇聚等）（→ §3.4） |
| 4 | L3 最终校验层 | 不是自己审自己；主业是**查漏补缺 + 内容润色**；代码 + LLM 并用（→ §3.5） |
| 5 | production 11 路 | **完全扔掉**，用新方案重写；`pipeline_evidence_llm` 一并删（→ §3.6） |
| 6 | 其他待决项 | 以本文建议为准 |

**由第 6 条按建议定案的事项**：

| 事项 | 定案 |
|---|---|
| 三分类的一、三类边界 | 有锚点或 ≥2 条**独立**来源一致 = 高置信；仅 1 条弱事实或纯常识 = 低置信 |
| `inferred_low` 是否回写 | 回写，但**必须带可见标记** |
| 非契约 key（20 个） | 有对应契约键的改判，没有对应位的丢弃但**留痕** |
| 旧的「兼容覆写」节点（阶段二的临时手段） | 随 production 重写一并删除 |

## 6. 一句话总结

**现行 opt01 用「一刀切禁掉推断」换准确性，所以拿字段数换了正确率，还因为「旧压缩链 + 新取证」
双付而涨了成本。v2 的正确方向是：把推断装回来（三分类管住纪律）、
以「无关字段不硬猜」引导推断纪律、L2 用「代码为主 + 单一受约束 LLM 兜底」做汇聚、
推倒 production 重写成「事实定稿 → 一次表达 → 一次复审」，
并把取数侧那 41% 的无效压缩关掉。**
