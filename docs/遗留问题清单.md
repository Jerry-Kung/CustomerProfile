## L-008 · 商机等级回传契约只认 A/B/C/D，缺 H 与「待识别」

**状态**：已解决待验证（2026-10-20） · **归属**：本项目

**背景**：业务专家《客户商机等级定级规范》要求 AI 输出 `H` / `A` / `B` / `C` / 待识别
五档，而回传接口文档 `ai_insight.purchase_intent_level.value` 明文只认 `A` / `B` / `C` / `D`，
后台再派生同步到 `customer_profile_main.deal_level`。

**结论**：前端答复 `deal_level` 是**文本字段，并非 ABCD 纯枚举**，可直接承接
`H` / `A` / `B` / `C` / 待识别。因此过渡映射（`H`→`A`、「待识别」不回传、旧 `D`→`C`）
**已撤除**，`callback_build.build_ai_insight` 按定级结果原样回传；配置项
`PURCHASE_INTENT_LEVEL_PASSTHROUGH` 一并删除。

**待验证**：真实批次回传后确认三点——
1. 前端列表能显示并筛选 `H` 与「待识别」；
2. 后台 `deal_level` 列实际落库的是 `H` / `待识别` 原文，未被截断或改写；
3. 旧批次里的 `D` 值仍能正常展示（历史数据不回洗）。

**风险**：若后端派生同步逻辑仍按 ABCD 校验，`H` / `待识别` 可能被丢弃或落库失败——
需在首个真实回传批次上确认落库值。验证通过后删除本条。

## L-001 · `customer_segment` 缺人群标签字典

**状态**：待外部输入 · **归属**：业务方（前端侧）

**背景**：v2 回传契约要求 `ai_insight.customer_segment.value` 是**人群名称**
（示例值「高效务实中产」），但没给可选清单。当前管线产出的两个相近字段都不是这个形态：

- `overall_tag`（后端 `customer_profile_main` 的口径，取值来源不明确）
- Notes 的 `customer_type`（价格价值型 / 科技尝鲜型 / 潮流跟随型 / 个性体验型）

两者都不等于「高效务实中产」这类复合人群名。

**本轮处置（用户 2026-10-15 决定）**：**先让模型自由发挥**，不约束取值。
因契约规定「区块缺失或为 null 时保留原值」，故该字段可独立演进，
后续换用正式字典不会影响其它区块。

**风险**：自由发挥的人群名在不同批次间会漂移（同一类客户可能被叫成
「高效务实中产」「务实中产人群」「理性务实派」等），画像列表按该值筛选会失效。

**解除条件**：业务方给出人群标签清单后，
1. 按 `notes_contract` 的做法固化为离线快照；
2. 在 L2 投影层做枚举归一（复用现有 `normalize_enum` 机制）；
3. 回放历史批次，统计自由发挥的取值分布，评估与正式字典的映射代价。

**建议推动时间**：本轮功能上线前拿到清单，可省掉一次历史回洗。

## L-002 · `purchase_decisions` 6 个分类的归类归属未定

**状态**：已定（2026-10-16） · **归属**：本项目

**结论**：**由代码从 facts 投影，不交给表达层 LLM 归类。** 落在
`src/customer_profile/callback_build.py`，作为业务测试臂 L3 之后的回传旁支
（`pipeline_callback_build` → `pipeline_callback_writeback`）。

理由：
1. **唯一 id 必须由代码生成。** 契约要求 `(phone, item_id)` 全局唯一，且回写是**先删后建**，
   撞号会让整次回传失败——把「回传能否成功」交给模型抖动是不可接受的。
2. **归类可判定。** 六个分类与 facts 有明确对应（到店动因 ~ `purchase_purpose` +
   `core_concerns`；对比车型 ~ `competing_*` + `test_driven_models`；决策阻力 ~
   `brand_concerns` + 抗性，等），按「能写成代码的约束不交给模型」应落代码。
3. **与 Notes 同源。** 每条的 `reasoning_detail` 直接复用 Notes 那一条的措辞，
   同一事实在两处长得一样，而不是靠事后核对。
4. **表达层职责边界不变。** 结构由代码定、措辞由模型给；让表达层直接产出分类结构，
   等于让它同时决定结构与措辞，正是 production 图 12 节点各自为政的老路。

**残余不确定**：分类之间的边界（如「核心关注」与「到店动因」重叠）需实测调优，
属**规则参数**问题而非架构问题，改规则远比改架构便宜。

## L-004 · 编外字段的正式归属未决

**状态**：观察中 · **归属**：本项目 / 业务方

**背景**：17 个下线字段中有相当一批对销售策略有直接作用（详见核查清单 §5）。
本轮按「内部保留、回传前裁剪」处置。

**风险**：编外字段只在本项目内部有意义，业务系统看不到。
若业务方后续仍需要这些维度，需重新协商契约，届时这轮保留的值可直接复用。

**解除条件**：与业务方确认长期是否需要这些字段；
若长期不需要，可在后续版本精简内部保留范围。

## L-006 · 画像卡原有五节在新契约里没有落点

**状态**：待外部输入 · **归属**：业务架构师（前端侧）

**背景**：`result1` 里的画像卡原有 9 个板块。新契约的六键结构里，
`resistances` 与 `emotion_state` 有明确落点（分别进 `deal_battle.loss_conditions` 与
`decision_psychology`），但下面五节**没有位置**：

`inferred_tags` / `usage_scenarios` / `communication_strategies` /
`purchase_motivations` / `product_preferences`

本轮**刻意不动** `l3.SECTION_KEYS`：它是对外产物契约，一动 `result1` 形状即变，
既有批次的可比性与 `tests/test_l3.py` 的装配断言会一并失效。因此这五节仍在产出，
只是没有对应的回传位。

**待确认的三种处置**：停写（表达层提示词随之瘦身，属业务优化改动，须单独确认）、
保留但只作中间产物不再外传、或另有去向。

**风险**：不确认而长期保留，会维持一份「产出了却没人用」的 LLM 成本；
过早停写则可能删掉业务方确实在看的维度。

**解除条件**：业务方确认这五节的去留后，据此调整 `SECTION_KEYS`、`LIST_SECTIONS`
与 `templates/customer_profile_l3__l3_express.txt`。
