## L-008 · 商机等级回传契约只认 A/B/C/D，缺 H 与「待识别」

**状态**：已解决待验证（2026-10-20） · **归属**：本项目

**背景**：业务专家《客户商机等级定级规范》要求 AI 输出 `H` / `A` / `B` / `C` / 待识别
五档，而回传接口文档 `ai_insight.purchase_intent_level.value` 明文只认 `A` / `B` / `C` / `D`，
后台再派生同步到 `customer_profile_main.deal_level`。

**结论**：前端答复 `deal_level` 是**文本字段，并非 ABCD 纯枚举**，可直接承接
`H` / `A` / `B` / `C` / 待识别。因此过渡映射（`H`→`A`、「待识别」不回传、旧 `D`→`C`）
**已撤除**，`callback_build.build_ai_insight` 按定级结果原样回传；配置项
`PURCHASE_INTENT_LEVEL_PASSTHROUGH` 一并删除。

**待验证**：真实批次回传后确认三点——
1. 前端列表能显示并筛选 `H` 与「待识别」；
2. 后台 `deal_level` 列实际落库的是 `H` / `待识别` 原文，未被截断或改写；
3. 旧批次里的 `D` 值仍能正常展示（历史数据不回洗）。

**风险**：若后端派生同步逻辑仍按 ABCD 校验，`H` / `待识别` 可能被丢弃或落库失败——
需在首个真实回传批次上确认落库值。验证通过后删除本条。

## L-001 · `customer_segment` 缺人群标签字典

**状态**：待外部输入 · **归属**：业务方（前端侧）

**背景**：v2 回传契约要求 `ai_insight.customer_segment.value` 是**人群名称**
（示例值「高效务实中产」），但没给可选清单。当前管线产出的两个相近字段都不是这个形态：

- `overall_tag`（后端 `customer_profile_main` 的口径，取值来源不明确）
- Notes 的 `customer_type`（价格价值型 / 科技尝鲜型 / 潮流跟随型 / 个性体验型）

两者都不等于「高效务实中产」这类复合人群名。

**本轮处置（用户 2026-10-15 决定）**：**先让模型自由发挥**，不约束取值。
因契约规定「区块缺失或为 null 时保留原值」，故该字段可独立演进，
后续换用正式字典不会影响其它区块。

**风险**：自由发挥的人群名在不同批次间会漂移（同一类客户可能被叫成
「高效务实中产」「务实中产人群」「理性务实派」等），画像列表按该值筛选会失效。

**解除条件**：业务方给出人群标签清单后，
1. 按 `notes_contract` 的做法固化为离线快照；
2. 在 L2 投影层做枚举归一（复用现有 `normalize_enum` 机制）；
3. 回放历史批次，统计自由发挥的取值分布，评估与正式字典的映射代价。

**建议推动时间**：本轮功能上线前拿到清单，可省掉一次历史回洗。

## L-002 · `purchase_decisions` 6 个分类的归类归属未定

**状态**：已定（2026-10-16） · **归属**：本项目

**结论**：**由代码从 facts 投影，不交给表达层 LLM 归类。** 落在
`src/customer_profile/callback_build.py`，作为业务测试臂 L3 之后的回传旁支
（`pipeline_callback_build` → `pipeline_callback_writeback`）。

理由：
1. **唯一 id 必须由代码生成。** 契约要求 `(phone, item_id)` 全局唯一，且回写是**先删后建**，
   撞号会让整次回传失败——把「回传能否成功」交给模型抖动是不可接受的。
2. **归类可判定。** 六个分类与 facts 有明确对应（到店动因 ~ `purchase_purpose` +
   `core_concerns`；对比车型 ~ `competing_*` + `test_driven_models`；决策阻力 ~
   `brand_concerns` + 抗性，等），按「能写成代码的约束不交给模型」应落代码。
3. **与 Notes 同源。** 每条的 `reasoning_detail` 直接复用 Notes 那一条的措辞，
   同一事实在两处长得一样，而不是靠事后核对。
4. **表达层职责边界不变。** 结构由代码定、措辞由模型给；让表达层直接产出分类结构，
   等于让它同时决定结构与措辞，正是 production 图 12 节点各自为政的老路。

**残余不确定**：分类之间的边界（如「核心关注」与「到店动因」重叠）需实测调优，
属**规则参数**问题而非架构问题，改规则远比改架构便宜。

## L-009 · 规则层尚未在真实新批次上验证过命中

**状态**：待实现（仅剩「真实取数」这一半） · **归属**：本项目

**背景**：规则层（M0–M6）的全部验证都是**测试与离线对账**：单测 + 守卫 + 对归档批次的
离线重跑投影。归档的四个批次全部早于规则层，产物里没有 `rule_trace`，因此
`scripts/rules_report.py` 在本机跑出来是「每条规则 0 命中」——这不是规则没生效，
而是**还没有一个跑过规则层的批次**。

**风险**：离线对账只证明「同一份断言账本 → 同样的 facts」，证明不了端到端：新增的
`RULE_CHECK` / `RULE_APPLY` 两个节点、`RULE_APPLY` 之后的 Notes 与 basis 接线、
checker 的提示词渲染，都只在单测里走过。真实批次上第一次跑通之前，不能认为已落地。

**2026-10-26 进展**：用归档原始响应回放取数层、模型真实调用，跑完了 uat-18 全 16 案
（`experiments/batches/uat-18-20261026-replay`），并以 `2f5eab8` 的未改代码臂做对照
（`head-ctrl-replay`）。三条解除条件的前两条已满足，第三条对照未改代码的同一输入也满足：
流水 16/16 跑通、两个规则节点都有产物、`checker_status` 16/16 为 `disabled`（开关缺省关闭）、
`rules_report.py` 报出 141 次命中且与 `rule_trace` 逐条对得上、Notes 总量 327 vs 对照 328、
等级 14/16 一致而两处差异均归因于 L1 采样。详见
`docs/history/rules-opt01/离线重跑验证报告.md`。

**剩余部分**：上述批次**输入侧是回放的**（数据接口与录音识别取自归档），因此它证明的是
「同一份输入下规则层不劣化结果」，不证明「今天的数据接口仍能取到同样的输入」。
后者要等下一次真实取数跑批，届时本条可删除。

**解除条件**：跑一个**取数与模型都真实**的新批次（8 案起），确认流水跑通、非零命中、
逐案 Notes 条数与商机等级不低于对照基线。

## L-014 · prompt 通道规则的命中无法统计

**状态**：观察中 · **归属**：本项目

**背景**：SPEC 簇那 14 条是 prompt 通道——它们没有判据，只有正文，模型看了之后的行为
变化不会留下任何「这条规则命中了」的记录。`rules_report.py` 因此对它们恒报 0 命中，
并在输出里单独标注「prompt 通道无判据，不算零命中」。

**风险**：prompt 类规则一旦失效（正文被删、渲染没接上、字段改名）不会有命中数下降这种
信号，只能靠落点守卫（编号存在性）与 `l1_guide()` 的逐字比对兜住。这两者都只能证明
「正文在提示词里」，证明不了「模型照做了」。

**解除条件**：若日后需要评估 prompt 通道的实际效果，只能靠批次间对照（同一批输入在
正文有无两种情况下的字段覆盖差异），成本较高。在那之前，接受「只能靠守卫 + 核读」。

## L-015 · 前端是否把枚举键映射成展示名未确认

**状态**：待外部输入 · **归属**：前端 / 需求方

**背景**：2026-10-27 的英文残留治理（`EXPR-01` / `EXPR-03`）已确定**只治理正文**，
`basic_notes_updates[].attribute_value` 继续按契约返回英文枚举键（`unmarried_no_child`、
`Mr`、`master`）。理由：契约 `field_type=enum` 的设计就是「键供回写、`display_name`
供展示」，接口里每个枚举项都带中文展示名。改成中文会破坏回写与既有前端逻辑。

**风险**：如果前端页面对 `attribute_value` 直接原样显示，「婚姻状态」一栏就会显示
`unmarried_no_child`——这正是需求方最初反馈的现象。那属于**前端未做映射**，不是画像
产出侧的缺陷；在产出侧改键只会把问题从显示层挪到回写层。

**处置**：产出侧不改。治理范围限定为 `summary` / `steps` / `evidence` / `label` 与
四个区块的正文。

**2026-10-27 补充（旧键整改后）**：需求方报的 `replacement` / `commute` 一类**不是**本条
描述的形态，而是**已废弃的枚举键**——它们在现行契约里根本没有对应项，前端即便做了
`display_name` 映射也查不到中文。产出侧已修（`ENUM-01` + 回写投影取值校验 +
`LEGACY_ENUM_ALIASES`），见 `docs/history/旧版枚举键与production臂整改方案.md`。
本条**剩余范围收窄为**：现行契约的合法键（`unmarried_no_child` 等）前端是否已按
`display_name` 渲染。

**解除条件**：前端确认已按 `enum_options.items[*].display_name` 渲染枚举取值；
或需求方明确要求产出侧回传中文键——那需要同步改回写逻辑与 `notes_contract` 的枚举契约，
属于契约变更，得单独立项。

## L-016 · `EXPR-01` 对不含下划线的合法枚举键存在判据盲区

**状态**：观察中 · **归属**：工程

**现象**：uat-18 旧键整改重放（2026-10-27）中，`13100792128` 的 Notes 正文出现
`符合 basic`。`basic` 是 `knowledge_of_*` 三个字段的**合法键**（展示名「初步了解」），
理应被 `EXPR-01` 改成中文，但实际漏过了。

**原因**：`_replace_enum_keys` 的边界判据里，token 若被 **ASCII 空格**包围，只有
「含下划线」或「是英文占位串」才认定成键（`_is_internal_key_shaped`）。`basic` /
`deep` / `none` / `loan` / `smart` 这类单词键因此不被改写。这条约束是**刻意**的：
`smart 精灵` 里的 `smart` 既是品牌名又是 `core_concerns` 的合法键，去掉空格保护就会把
品牌名改成「智能精灵」。

**影响面**：仅剩下「英文单词型枚举键 + 前面是英文空格」这一种形态。旧版**废弃键**不受影响
——`commute` / `unmarried` / `replacement` 已由 `ENUM-01` 与回写投影按形态拦截，
不再进入对客产出。

**为什么不本轮修**：任何放宽都会重新引入品牌名误伤，而品牌名误伤改的是对客文案。
正确解法是按字段上下文判断（正文提到的是「本文档对应字段」的键），需要把字段信息传进
`check_prose_keys`，属独立改动。

**解除条件**：实现字段上下文感知的正文改写；或业务确认接受「单词型键在正文里保留英文」。
