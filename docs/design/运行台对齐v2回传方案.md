# 运行台对齐 v2 回传设计（方案）

> 目标：让「客户画像运行台」（`frontend/`）的**输出结果**与**中间链路**与当前工作流设计
> （业务测试臂 `customer_profile_pipeline` 的 v2 回传改造）保持一致。
> 面向 Claude Code：本文给出已实测的现状核对、差距清单、阶段划分与验收标准。
>
> 立项：2026-10-16。前置：`docs/design/AI画像v2回传改造方案.md`（P0–P5 已落地）、
> `docs/design/客户人设画像管线设计.md`（§2 分段、§5 输出契约）。
> 上游设计依据：`docs/design/Workflow_UI_Implementation_Guide.md`、`docs/history/V0.4只读运行台.md`。

## 1. 一句话

回传旁支落地后，运行台的**展示口径**没跟上：它只认 `result1` 一个产物、只按 `node_type`
给节点分类、把「回写已跳过」渲染成一段生英文 JSON。本轮把这三处对齐到设计稿的分段与双产物口径，
**只改前端**，不动执行逻辑、提示词、存储与接口。

## 2. 现状核对（2026-10-16 实测，非推断）

| 事实 | 实测结果 | 来源 |

## 3. 差距清单

### D1 · 回传体（六键）没有落点 —— 输出结果与设计不一致

设计稿 §5 明确「本轮对外产物**有两份**」：`result1`（九板块 + `basic_notes_updates`）与
回传体（`profile_summary` / `basic_notes_updates` / `ai_insight` / `purchase_decisions` /
`deal_battle` / `decision_psychology`）。

现状：顶部「查看聚合结果」只读**运行级** `outputs`，而它只有 `result1`。要看回传体，得在
节点列表里逐个找到 `回传体构造` 再点开——而它在 40+ 节点里没有任何视觉标识。

**影响**：运行台看不到本轮改造的核心产物，与「业务测试臂的产物是双份」这一设计事实不符。

### D2 · 中间链路的层级与成本语义丢失 —— 中间链路与设计不一致

设计稿 §2/§3 的核心是**分层**（L0 记录 / L4 分诊 / L1 取证 / L2 投影 / L3 表达）与
**成本分布**（L0/L4/L2 投影/L2 应用/审查/L3 校验装配全为纯代码、0 token）。

现状：类别芯片只按 `node_type`，`pipeline_l0_records`（L0 记录层，纯代码）与
`pipeline_l1_facts`（L1-1a 事实层，LLM）同样标成「数据处理」「模型分析」——**看不出是第几层，
也看不出哪些白跑 token**。

### D3 · 「回写已跳过」渲染成生英文 JSON —— 输出结果不可读

现状（按现行摘要逻辑模拟真实产出）：`writeback skipped：True · url：/api/v1/remote/callback/update-profile · reason：WRITEBACK_ENA…`

三层问题：键名是英文下划线、`True` 未中文化、`reason` 被 40 字截断到半句话。而这件事在设计上
是一个**有明确业务含义的正常态**（调测期不回传），却被渲染成一段要解读的机器文本。

## 4. 阶段划分

### P0 · 回传体落点（对应 D1）

**改什么**：`RunDetail.tsx` 的聚合结果浮层。

- 现有 `payload.outputs` 仍照旧渲染 `result1`；
- **新增**：从 `graph.nodes` 里找**回写节点**（判据：该节点 `node_id` 在 `graph.definition.nodes`
  中的 `config['@writeback'] === true`），沿其 `direct_predecessors` 取其上游构造节点的产出
  （`callback_json`），解析后作为第二段「回传体」渲染。
- 判据全部来自**定义快照**，不写死工作流名或节点 ID——换一条臂、或回写节点改名，仍然成立。

**为什么从节点产出取而不是给运行级 outputs 加键**：运行级 `outputs` 是 `END` 节点的
`result1` 一个入口，是**对外契约**（`docs/design/执行语义口径.md`：`result1` 为字符串是现有
对外契约，改动须走 API 版本变更）。给 outputs 加键等于改对外契约；从节点产出取是纯展示层。

**验收**：业务测试臂的一次运行里，聚合结果能同时看到 `result1` 与六键回传体；
两者的顶层键集合分别等于「`phone`/`batch_id`/`analysis_result`」与设计稿 §5 的六键。

### P1 · 中间链路分层（对应 D2）

**待拍板（见 §6 决策 1）**：分层的呈现方式。

**推荐做法**：给节点行增加一个**阶段芯片**，取值来源为「节点标题以 `L<数字>` 开头」，
如 `L1-1a 事实提取层 → L1`、`L2 投影层 → L2`。同时把 `node_type` 为 `code/start/end`
的一律标注「纯代码」，`llm` 标注「LLM」——这两类不依赖标题，**完全通用**。

**为什么要一起给「纯代码 / LLM」**：设计稿的成本结论（哪几层 0 token）是这一轮的第一等结论，
界面上不体现它，就等于运行台与设计稿的核心论点脱节。而该判据只看 `node_type`，不依赖命名，
对全部 17 个工作流都成立。

**已知不完美（须在文档与验收里写明，不掩盖）**：标题前缀法覆盖不全——
`确定性字段注入`（属 L1）标题无 `L1` 前缀、取数层各节点属 L0 之前。这些节点将**不显示阶段芯片**，
只显示类型类别。宁可缺，不用节点 ID 硬编码去补——硬编码会把展示层绑死在某一条臂上。

**验收**：业务测试臂一次运行里，`L0/L1/L2/L3` 各层节点显示正确阶段芯片；
`L1-1a/1b/1c` 显示为 `L1`；纯代码节点与 LLM 节点可一眼区分；
无阶段芯片的节点（如 `确定性字段注入`）如实显示其类型类别，不猜。

### P2 · 回写状态可读化（对应 D3）

**改什么**：`nodeSummary.ts` 的结果摘要 + `ResultView.tsx` 的结果渲染。

- **判据通用**：产出里存在 `writeback_skipped` 键即命中，不绑定工作流；
- 摘要一行：`回写已跳过（WRITEBACK_ENABLED=false）`，不发散它的英文键；
- 详情「业务结果」：渲染成一条中性说明（「本轮未开启回写，节点只产出「已跳过」结果；
  运行显示成功不等于画像已写进生产库」），并把原始 JSON 留给「原始数据」标签；
- **不改写语义**：`status: 0` 与「已跳过」照实呈现，不美化成「成功写入」。

**验收**：调测期运行里，回写节点的摘要与详情均为中文可读说明，不出现英文字段名堆叠；
开关打开后（P6 联调）该节点的摘要改走通用分支，不再误套「已跳过」。

### P3 · 构建与入库

**改什么**：无代码改动，是流程约束。

- `cd frontend && npm run build`（`tsc -b && vite build`，本机 node 24.15 / npm 11.12 可用）；
- `git add frontend/dist` —— 产物入库是本项目的既有决策（未装 node 的机器要能直接起）；
- 判断产物是否同步：`git status` 里 `frontend/dist` 无改动即已同步。

**验收**：`npm run build` 通过（无 TS 报错）、`npm run lint` 通过、dist 与 src 同批提交。

## 5. 验收标准（四条，逐条可证）

| # | 标准 | 怎么证 |
|---|---|---|
| A1 | 聚合结果同时呈现 `result1` 与六键回传体 | 取一次真实管线运行，两段都在，键集合符合设计稿 §5 |
| A2 | 节点行能看出层级与「纯代码 / LLM」 | 该运行里 L0/L1/L2/L3 芯片正确；纯代码与 LLM 可区分 |
| A3 | 回写节点在调测期呈中文可读的「已跳过」 | 该运行回写节点摘要与详情无英文键堆叠 |
| A4 | 后端零改动，且 dist 与 src 同批入库 | `git diff --stat` 不含 `src/`；`git status frontend/dist` 无残留 |

**验证手段**：前端无测试框架，故以「`npm run build` + `npm run lint` 通过」为静态门，
以「起本地服务（`python -m customer_profile.main` + `SERVE_UI=true`）打开上述真实运行」为动态门。
不新增前端测试框架——那超出本轮范围。

## 6. 已定口径（2026-10-16 用户拍板）

**决策 1 · 分层如何呈现**：**标题前缀派生层级芯片 + 成本标签**。
阶段芯片来自节点标题前缀（`L0`/`L1`/`L2`/`L3`，`L1-1a` 归 `L1`）；成本标签看 `node_type`
（`code`/`start`/`end` → 「纯代码」，`llm` → 「LLM」，其余不标）。无前缀的节点如实不显示
阶段芯片，**不用节点 ID 硬编码去补**——那会把展示层绑死在业务测试臂上。

**决策 2 · 「聚合结果」里回传体的位置**：**与 `result1` 并列，分两个可折叠段落**。
两段各自独立折叠，默认都展开首屏可见；`result1` 在前（对外契约产物），回传体在后。

**决策 3 · 「提交任务」是否开放到业务测试臂**：**不动**。
`SubmitRun.tsx` 继续只服务主入口 `customer_profile_entry`。放开提交面会改变运行台的写操作
边界，且与「输出/链路一致」是两件事，若确需另行立项。

## 7. 不做什么

- **不动执行逻辑、提示词、存储模型、通信协议**（沿用 `Workflow_UI_Implementation_Guide.md` §8 的边界）；
- **不动 `result1` 的对外契约**（加键须走 API 版本变更，不在本轮）；
- **不新增前端依赖**（不引路由库、UI 库、Markdown 解析库，沿用自建 `Markdown.tsx`）；
- **不改后端**（后端接口已足够，见 §2 关键推论）；
- **不新增前端测试框架**；
- **不做灰度**：三处差距一次改完。
