# 用户画像工作流运行页：前端优化实施说明

> 面向 Claude Code。本文提供已确认的设计方向、交互建议与实施边界，供结合项目代码落地；不是对现有架构、字段或组件的预设。

## 1. 任务背景与目标

本项目已从 Dify 工作流迁移为纯 Python 项目，并开发了用于展示工作流节点及运行过程的前端页面。当前页面主要采用纵向节点列表，展开后显示运行信息、输入和输出。

用户希望将该页面优化为简约、美观、专业的商务风格，并更直观地呈现业务产出。用户已认可“顶部运行概览 + 左侧节点及结果摘要 + 右侧节点详情”的视觉方向，准备在现有项目中试用。

本轮的核心体验目标：

1. 打开页面后，能快速理解本次运行的状态和主要产出。
2. 浏览列表时，能看出各节点做了什么，以及是否产出了有效信息。
3. 查看节点时，先读到易懂的业务内容，同时保留完整原始数据和排查入口。
4. 运行更新、切换节点、进入子流程时，保持阅读位置和上下文稳定。

本说明基于两张现有页面截图及一张已获认可的设计效果图，未经过完整代码走读。截图中的工作流名称、节点数量、字段和耗时只是一个运行样例，不代表所有工作流。

如同时提供了设计效果图，可用它把握风格、布局和信息层级；图中的业务结论、统计、按钮、筛选项均包含演示内容，不作为实际数据或新增功能清单。未提供效果图时，以下文字也可独立指导实施。

## 2. 开始实施前，建议先了解的项目情况

可以先阅读与本页直接相关的页面组件、样式、接口和运行记录，形成简短判断后直接推进实现。普通组件选型、间距、断点等细节，可依据现有项目自行决定，无需逐项等待确认。

建议重点确认：

| 需要了解的内容 | 对本次实现的影响 |
| --- | --- |
| 前端框架、已有 UI 组件库和设计规范 | 尽量复用已有能力，保持与应用其他页面协调 |
| 任务详情、节点详情、子运行的页面和路由关系 | 决定右侧面板、详情跳转及返回定位的接入方式 |
| 节点 ID、运行实例、执行状态和时间字段 | 决定选中项标识、排序、耗时和进度展示 |
| 输入、输出的实际数据类型及典型样本 | 决定业务结果渲染和摘要提取方式 |
| 页面采用轮询、SSE 或其他更新方式 | 复用现有更新链路，避免刷新导致状态丢失 |
| 当前已有的复制、导出、重试、筛选等操作 | 重设计后保留必要操作，避免功能回退 |

如果项目现状与本文示例不一致，可以调整具体实现并简要说明原因。只有遇到会显著扩大范围、改变核心业务语义或需要新增重要依赖的选择时，再与用户讨论。

## 3. 页面布局与信息层级

### 3.1 全局导航与顶部运行概览

建议沿用当前应用导航，不必为本次改版新增侧边栏或重做整个站点。

运行概览可采用以下顺序：

- 面包屑或返回入口：任务列表 / 运行详情。
- 主标题：当前工作流的业务名称，旁边展示整体执行状态。
- 次要信息行：业务标识、总耗时、节点执行情况、本次运行使用的定义版本等已有信息。
- 主要操作：按现有能力提供聚合结果、复制或导出等入口，突出最重要的一项即可。

业务名称与技术名称可以分开显示。例如，若 `evidence_subagent` 的实际职责确为证据汇集，可将业务展示名设置为“客户证据汇集”，技术名称放在辅助信息或详情中。具体命名以代码中的真实职责为准，不改变工作流标识。

如果已有可直接读取的最终产出，可在概览下设置紧凑的结果摘要区域；如果本次工作流没有独立最终产出，用简洁的运行概况即可，不必新增一套聚合逻辑来填满设计图。

“证据汇集完成”和“完整客户画像生成完成”应根据工作流边界分别表述。运行版本宜显示本次实际使用的版本，而非直接取当前最新版本。

### 3.2 主工作区：节点列表与详情面板

推荐桌面端采用两栏布局：左侧浏览节点，右侧查看当前选中节点。详情可以关闭；关闭后列表可扩展，但长文本阅读宽度仍宜受到合理限制。

尺寸可从以下范围开始调试：

- 主区域左右留白约 24～40px，两栏间距约 20～24px。
- 打开详情时，列表约占 55%～60%，详情约占 40%～45%。
- 若屏幕宽度不足以同时清楚展示两栏，可改为抽屉或全宽详情页，返回后恢复原位置。
- 详情较长时，可采用适度吸顶、分栏滚动或现有容器滚动方案，以避免遮挡及多层滚动冲突为准。

这些是布局起点，不是固定像素验收值。建议在项目常用的桌面分辨率下调整，尤其检查 1366 和 1920 像素宽度附近的实际阅读效果。无需为复刻效果图而锁定整页宽高。

节点列表负责保持流程全貌，右侧面板负责阅读详细内容。建议避免点击节点后在列表内展开一块占满屏幕的原始输出。

## 4. 节点列表的设计

### 4.1 默认可见内容

每个节点建议使用紧凑的两到三行结构：

| 位置 | 建议内容 |
| --- | --- |
| 第一行 | 简短业务名称、执行状态、耗时；序号作为弱化辅助信息 |
| 第二行 | 1～2 行结果摘要；需要时显示完整内容入口 |
| 第三行，可选 | 结果状态、节点类别或子流程入口，仅保留有用信息 |

节点名称中重复出现的“（新）”“SubAgent”等开发前缀可在展示层弱化。业务含义不明的名称，宜保留原名或结合现有配置提供别名，避免用通用字符串替换误删有效信息。

技术类型、节点 ID、调用路径、前置依赖等可移入详情。重要的已有能力仍保留可访问入口。

选中节点可使用浅蓝底、细蓝边框或左侧强调线。普通节点保持白底细边框，成功状态使用一个紧凑图标加文字即可，减少重复的绿色圆点和大胶囊。

### 4.2 结果摘要的来源与降级

摘要的优先顺序可以是：

1. 已有且适合直接展示的业务摘要或结构化结果字段。
2. 结合当前常见节点类型，从既有结果中提取简短预览。
3. 无法可靠提取时，显示安全的文本预览，或“已生成输出，查看详情”等中性描述。

例如，录音提取节点若已返回通话总结，可展示总结；若只返回原始长文本，则先提供文本预览。数据获取节点若有明确记录数，可展示数量；未提供数量时不推测。

摘要机制宜保持轻量，适配主要节点即可，其他节点采用通用降级。首轮通常不需要额外调用 LLM，也不需要为全部节点建设独立的模板系统。展示用摘要不改写或覆盖原始结果。

### 4.3 区分执行成功和结果有效

执行状态与结果状态表达不同含义，建议分别处理：

| 已有事实支持的情况 | 可采用的展示 |
| --- | --- |
| 调用成功且明确返回有效内容 | 执行成功 · 已获取信息 |
| 调用成功但明确没有可用记录 | 执行成功 · 暂无数据 |
| 返回部分内容且明确存在缺项 | 执行成功 · 部分信息缺失 |
| 因输入缺失而按逻辑跳过 | 已跳过 · 未提供录音等实际原因 |
| 调用失败 | 执行失败 · 简短失败原因 |

具体状态名称和映射可沿用项目枚举。若缺少判断结果有效性的可靠依据，保留执行状态并提供结果入口即可；不能只凭耗时很短、空对象或空字符串就认定“无有效信息”。

缺少数据一般使用中性灰色；错误和需要处理的异常才使用更醒目的颜色。颜色同时配合文字或图标。

## 5. 节点详情的设计

右侧标题区建议包含节点业务名称、执行状态、耗时、关闭按钮，以及存在时的子流程入口。

内容推荐按“业务结果 / 原始数据 / 执行信息”组织。若当前项目已有适合的分类，可调整名称和归属，重点是让可读结果默认可见，并使技术信息容易找到。

### 5.1 业务结果

按实际数据类型选择展示：

- 普通文本：清楚的段落和换行。
- Markdown 文本：渲染标题、列表、表格等，沿用项目已有的安全渲染方式。
- 结构化业务字段：简洁的标签和值，必要时使用小表格。
- 多条记录：紧凑列表或表格。
- 未识别的数据结构：提供通用格式化视图，仍可查看完整数据。

当前截图中的输出存在 JSON 包裹 Markdown 字符串的情况，可在识别到真实字段类型后读取并渲染对应内容。建议避免对全部字符串进行粗暴的转义字符替换、反复解析，防止破坏代码、路径或合法原文；识别失败时回退到原始文本。

效果图中的“核心结果”“分析说明”“结论边界”“数据来源”体现的是阅读层级，不代表每个节点都必须有这些模块。实际输出没有的栏目可以省略。只有记录中确有来源定位能力时，才提供“查看来源”入口。

输出原有的不确定性、来源限制和证据边界应保留。前端整理不能把模型推测改成确定事实，也不需要增加新的画像结论。

### 5.2 原始数据

建议保留完整输入和输出，并复用或补齐必要的格式化、展开折叠、复制能力。长数据的列表预览可截断，详情和复制仍应支持完整内容。

对“字段未记录”“加载中”“读取失败”“空值”“空对象”等情况，按照实际接口含义呈现，不宜合并成一个“暂无数据”。例如 `{}` 可显示为“记录的输入为空对象”，不能因此断言节点没有通过共享上下文获取输入。

### 5.3 执行信息与子流程

根据已有记录展示节点标识、技术名称、类型、时间、依赖、调用路径和错误详情。队列等待时间、模型用量、重试记录等仅在现有数据支持时显示，不属于首轮必增能力。

子流程入口可放在标题附近或节点辅助操作区。跳转时尽量保留父运行上下文，返回时恢复选中节点、滚动位置及必要的筛选状态。若已有独立路由方案，可继续复用。

## 6. 运行过程与交互稳定性

### 6.1 排序与并行

用户描述的目标是已完成节点按完成时间从上到下排列；原截图文案则写了按开始时间排列。建议检查当前排序和时间字段，优先对齐用户期望，并在界面上明确排序口径。

如果后端缺少可靠完成时间，或现有顺序包含重要的业务语义，可以先保留现有排序并准确标注，再说明差异；不宜伪造完成时间。时间相同时可使用已有稳定序号作为辅助排序依据。

如果实际业务允许并行，可将运行中节点放在紧凑的独立区域，结束后加入完成列表；也可沿用项目已有的合理方式。纵向位置不等于依赖关系，不建议用方向箭头把所有节点串成一条依赖链。

节点更新和选中状态宜绑定实际运行实例标识，避免并行、重复执行或已有重试记录让选中对象错位。具体标识使用项目已有机制即可。

### 6.2 增量更新与阅读位置

建议复用当前数据更新机制，并注意以下体验：

- 新结果到达时，已选节点及详情标签保持稳定。
- 用户正在阅读历史节点时，不强制滚动到最新位置。
- 如需自动跟随，可只在用户位于底部或明确开启跟随时生效。
- 新结果提醒、回到最新位置等可按实现成本决定是否加入。
- 运行中的节点显示明确状态，完成后正常更新结果。

若支持流式内容，完整结果与生成中状态可沿用现有机制；若目前只返回完成后的输出，不需要为本次视觉改版新增流式协议。

### 6.3 搜索、筛选与操作

节点较多时，名称搜索和异常筛选有助于定位，可根据现有能力和首轮成本取舍。“有结果”筛选需要可靠结果状态；暂时无法判断时可以不提供。

最终结果、导出、复制和重试等操作以实际能力为准。参考图里出现但当前没有的能力，可以暂时省略；避免可点击却无实际行为的占位按钮。

如果保留重试入口，按钮文案宜明确作用范围，并复用现有授权和执行规则。

## 7. 视觉规范与响应式建议

整体方向为浅灰背景、白色内容区、深蓝灰文字、少量蓝色交互强调。页面重点通过排版、间距、字重和选中态建立。

| 项目 | 建议起点 |
| --- | --- |
| 页面背景 | `#F5F7FA` |
| 内容背景 | `#FFFFFF` |
| 主要文字 | `#172B46` |
| 次要文字 | `#617187`，保持清晰可读 |
| 交互蓝 | `#265ECA` |
| 分隔与边框 | `#E5EAF1` |
| 圆角 | 6～8px，统一风格 |
| 页面标题 | 22～24px |
| 节点标题 | 14～16px，中等字重 |
| 正文 | 14px 左右，行高约 1.5～1.7 |
| 辅助信息 | 12px 左右，避免过小过浅 |
| 节点间距 | 8～12px |
| 节点内部留白 | 12～16px |

以上值可融入现有主题变量，而非额外建立一套冲突的设计系统。建议使用项目已有字体和图标，避免为视觉改版引入重量级新依赖。

普通卡片使用细边框和轻微圆角，阴影主要用于必要的浮层。无需渐变、玻璃效果、大面积彩色卡片或装饰性图表。

耗时、日期格式保持一致；ID 和原始代码可使用等宽字体。长名称和中文段落应自然换行或提供可访问的完整内容。业务标识的脱敏和复制方式以现有产品规范为准。

按钮和节点选择可通过键盘操作，选中及执行状态有可读文字。窄屏优先切换布局，避免把整个桌面界面等比缩小或产生页面级横向溢出。

## 8. 建议实施顺序与范围控制

### 第一轮：形成可实际试用的完整页面

建议在理解现有实现后，优先完成：

1. 顶部概览、两栏布局和统一视觉样式。
2. 节点业务名称、轻量结果摘要及可靠的状态展示。
3. 右侧详情、可读结果渲染和完整原始数据入口。
4. 现有运行更新、子流程跳转及主要操作的兼容。
5. 常用桌面尺寸下的布局调整与核心流程验证。

如果首轮已能低成本实现搜索、筛选或返回定位，可以一起完成。阶段分组、复杂依赖图、耗时分析看板、摘要生成服务等可留待明确需要时再评估。

本轮以展示与交互改进为主，通常无需修改工作流执行逻辑、LLM 提示词、存储模型或通信协议。确实缺少必要展示数据时，可评估最小范围的接口补充，并说明原因和影响。

实现方式可由 Claude Code 结合代码选择：页面内局部调整、复用已有组件，或适度抽取节点卡片和结果渲染组件均可。无需为了这次改版重构整个前端，或搭建通用工作流可视化平台。

### 验证与交付

建议以现有构建检查和真实样例验证为主，围绕本轮改动做必要检查：

| 场景 | 观察重点 |
| --- | --- |
| 已完成运行 | 首屏信息明确，主要节点摘要可读，完整结果可访问 |
| 运行中更新 | 状态正常刷新，选中项和阅读位置不意外丢失 |
| 数据缺失或失败 | 根据真实语义呈现，不把缺失一律显示为失败或成功有效 |
| 长文本、Markdown、JSON | 内容易读，渲染降级正常，原始数据保持完整 |
| 存在子流程的运行 | 入口有效，父子上下文及返回行为合理 |
| 常用窗口宽度 | 文字、按钮和详情无明显拥挤、遮挡或页面级溢出 |

验证范围以现有功能和本轮改动相关场景为准；必要的代表性样例可以使用开发测试数据，但不写入生产展示逻辑。无须为截图中未出现、项目中也不存在的功能构造复杂测试体系。核心体验和现有检查通过后即可交付试用，不需要反复增加假设性边界场景延长任务。

交付说明宜简短覆盖：完成了哪些页面改动；哪些建议因代码现状做了调整；执行了哪些验证；是否存在后续需补充的数据或能力。若开发环境支持，可以附上实际页面截图，便于用户对照确认视觉效果。

最终衡量标准是：运行状态一眼可见，节点产出容易理解，详细内容方便阅读，技术信息和原有能力仍然可达。
