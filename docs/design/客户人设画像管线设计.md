# 客户人设画像管线设计（v3.3）

> **这份文档是给人看的**：讲清这套管线**为什么这么分层、每层各干什么、结论被什么约束住**。
> 不重复代码细节——实现见 `src/customer_profile/workflows/customer_profile_pipeline.py`，
> 字段契约见 `src/customer_profile/notes_contract.py`。
> 配套材料：本批次的两份检核报告在 `docs/history/`（业务视角 / 销售视角），
> 已知薄弱环节与证据在文末 §7 指向它们。

---

## 1. 一句话概括

**输入一个手机号，输出一份销售能直接用的客户画像。**

产出分两块：

| 产出 | 内容 |
|---|---|
| **画像卡**（9 个板块） | 画像摘要、推断标签、用车场景、沟通策略、客户概览、购车动机、产品偏好、抗性/顾虑、情绪状态 |
| **Notes 补充字段**（47 个） | 写回业务系统的结构化字段，分 6 类：基础身份 16 / 购车需求 11 / 预算与金融 4 / 决策与节奏 4 / 个人偏好与备注 8 / 竞品对比 4 |

每条结论都带三样东西：**取值**、**置信档**、**依据锚点**（能回到客户原始数据里的一段内容）。

设计目标只有三条，全部围绕「销售照着说会不会出错」：

1. **不许编。** 结论必须能回指到客户原始数据里的一段话。
2. **宁可留白。** 拿不准就空着或降级，交人工/销售补充——**空着比填错强**。
3. **成本让位于准确性。** 能写成代码的约束不交给模型；确需模型判断的地方才调模型。

## 2. 整体流程

```
              手机号
                │
   ┌────────────┴─────────────┐
   │  取数层（14 路 tool）      │  朋友圈/微信/支付宝/抖音/小红书截图、
   │  + 录音转写链路            │  试驾/外呼录音、企业查询、极光、梦世、聊天记录、反馈
   └────────────┬─────────────┘
                ↓
        L0 记录层（纯代码 · 0 token）
          把各渠道产物统一成 records[]，逐字保留原文与时间戳
                ↓
        L4 分诊层（纯代码 · 0 token）
          判定 sufficient / thin / empty，只把「有内容」的渠道喂下去
                ↓
        L1 取证层（3 次 LLM，三层各司其职）
          1a 事实层  →  1b 人设层（不进证据位）  →  1c 分析投影层
                ↓
        L1 合并（纯代码）  并集：1a 的硬事实 + 1c 的推断，互补不重叠
                ↓
        L1 定位（纯代码）  逐条回原文找锚点；找不到就**降级保留**，不丢
                ↓
        确定性注入（纯代码）  手机号直取；驾照按试驾/旧车规则定
                ↓
        L2 投影层（纯代码 · 0 token · 全案枢纽）
          归属过滤 → 来源分级 → 冲突消解 → 枚举归一 → 单/多值约束 → 跨字段规则 → 缺失留白
                ↓
        L2 兜底（受约束的 LLM 裁决者）→ L2 应用（纯代码）→ L2 审查（代码能判的先判）
                ↓
        商机定级（v3.6：代码判定阶段 → 1 次独立 LLM 定级 → 代码收口）
          阶段由「有无试驾录音」决定；H/A/B/C/待识别；R04 阶段上限、R05 多维证据在代码层强制
                ↓
        L3 校验（纯代码）  →  L3 表达（1 次 LLM：把同一份事实写成 9 个板块）
                            →  L3 装配（纯代码：与 Notes 同源一致性检查 + 拼装）
                ↓
             result1
```

**成本分布**：全案 LLM 调用集中在 L1（3 次）、L2 兜底（按需）、商机定级（1 次）、
L3 表达（1 次）。L0、L4、L2 投影、L2 应用/审查、定级装配/收口、L3 校验/装配**全部是代码，0 token**。

## 3. 逐层说明

### 3.1 取数层（14 路 tool）

按渠道并行取数：社交平台截图（朋友圈、微信主页、微信手机号搜索、支付宝、小红书、抖音）、
录音（试驾、外呼）、企业信息、极光数据、梦世 IT、聊天记录、用户反馈、手机号归属地。

录音链路**刻意绕开**「录音信息提取」子流程，指向**角色标注变体**（`audio_content_extract_roled`）：
本管线只消费 ASR 数组（`auc_result`），原件里那两个 LLM 节点（识别校对、内容有效性判断）
产物一个字节不用，实测白烧全批 41.1% 成本的一大块。

变体在原纯识别链路（零 LLM）之上**多一次语义角色判定**：LLM 把转写切成连续的角色分段
（`销售方` / `客户方` / `未知来源`），由代码展开成逐句角色，交出的产物是
`transcript_bundle`（正文、六字段原文、句级角色与字符区间、勘误明细）。

> **为什么必须重判说话方。** 本批录音里 AUC 的 `speaker` 编号与逐句 `gender`
> 实测不可用：55 条有效录音中 41 条存在同一编号下性别稳定矛盾，说话人编号的连续段
> 有 78% 长度为 1。一旦把销售自述（「我们是4S店的」）归到客户方，整条画像的职业判断
> 都会跟着错。因此角色**只由语义判定**，编号与性别只作低置信参考。

> 为什么不就地删节点：原件被**基线臂**复用，就地删除会改变基线臂图结构、
> 让 `definition_hash` 漂移，AB 可比性判据失效。因此用变体，不动原件。
> 角色标注若要回退，只改 `AUDIO_EXTRACT_WORKFLOW` 一个常量即可指向纯识别变体。

### 3.2 L0 记录层（纯代码，0 token）

把清单与各渠道产物统一成一份 `records[]`，**逐字保留**原文、说话人标记、逐句性别、时间戳。

录音记录额外带三项：`content_raw`（勘误前原文）、`role_lines`（句级角色与正文字符区间）、
`corrections`（勘误明细）。正文用勘误后的写法，原文单列，二者不互相覆盖。

四条口径：
- **渠道有无由清单定，不由模型猜。** 清单里没有该 channel 就是结构性空，记 `exception`，
  不进取证输入包——这同时治好了「输入有录音、输出却说无录音」，因为「有没有」由记录层
  说了算，不由模型回忆。
- **录音转写逐字留存**，中间不插任何 LLM 摘要。勘误只改正文，原文始终可回溯。
- **`speaker` 与逐句 `gender` 只作原文属性附着，不作归属依据**——原因见 §3.1。
- **角色不回退到客户方。** 分段有缺口、角色非法、输出解析失败时，一律记 `未知来源`；
  判成客户方却命中销售自述句式的句子，由代码单向改判 `未知来源`。
  三种角色都进分析层，但 `未知来源` 的内容不作强证据。

### 3.3 L4 分诊层（纯代码，0 token）

按「有没有可用渠道、渠道里有没有内容」判 `sufficient` / `thin` / `empty`，
决定取证输入包的大小。信息稀薄的案子（只有姓名+电话）合该少写——这一点在实测中被验证：
同一批里信息最少的那个案子，V3.3 只输出 4 个板块、其余留空，是正确处置。

**thin 档的保留口径**（2026-10-28 起）：按来源档位与字段置信档判，保留三类字段——有登记档
渠道支撑（不论置信档）、第三方画像数据的高/事实档、无渠道但非低置信。仅社交自呈现、仅公开
登记查询、低置信推断一律不留。**不得**用证据文本反推档位：证据位只写「渠道：原文」，不含
档位标签，按标签匹配会得到空集（旧实现的缺陷，曾使 thin 案只剩姓名）。

### 3.4 L1 取证层（三分层）

拆成三层，各出各的，互不重叠：

| 层 | 职责 | 关键约束 |
|---|---|---|
| **1a 事实层** | 只抽「全 / 准 / 事实（含高置信推断）」，输出 JSONL | 硬事实优先 |
| **1b 人设层** | 半结构化画像 + 一段整体描述 | **不进证据位**：只作后续推理的一致性参考，其结论不得写进任何 `evidence` |
| **1c 分析投影层** | 基于事实 + 人设参考，补齐字段级结论 | 证据只能顺到带坐标的事实，不得停在人设层 |

> **为什么必须有「合并」这一层**：1c 的提示词明说「事实清单已给的字段不用重复」，
> 所以两层是**互补**而非重叠。若少了合并层，1a 检出的硬事实（如 `intended_brand=埃安`）
> 根本不进账本，在 Notes 里直接变空值。实测 8 案：1a=90 字段、1c=156 字段，
> 两层重叠仅 6，仅 1a 有 84。

**定位层（纯代码）**：逐条拿结论回原文找锚点。**找不到不丢，只降级**——值留在账本里，
置信档降为 `inferred_low`，转交人工确认。这是「宁降勿丢」口径的第一次落地。
降级原因分类：锚点未找到 / 无据推断 / 锚点过短 / 锚点嘈杂 / 信号不匹配 / 未知渠道。

**确定性注入（纯代码）**：手机号直取入参；驾照按「有试驾记录 / 有旧车」规则定。
接在定位层**之后**，否则定位层会按「给了渠道却找不到记录」把注入值降级，
正好废掉它刻意标注的登记档。

### 3.5 L2 投影层（纯代码，0 token）—— 全案枢纽

这是**唯一同时看得见所有字段、所有断言、所有来源**的地方，因此「字段间矛盾」在这里被消解，
而不是靠提示词祈祷模型不写矛盾。输入断言账本 `claims[]`，输出：

```
claims[]（L1 产出）
   ↓ a 归属过滤 → b 来源分级 → c 冲突消解 → d 枚举归一
   ↓ e 单/多值约束 → f 跨字段规则 → g 缺失即留白
facts          规范事实：一个字段一个值（或一组多值），有据可查
notes_updates  Notes 投影结果（契约全部字段）
to_confirm[]   无法坐实的字段：留白，交销售补充
```

随后：**L2 兜底**（一个受约束的 LLM 裁决者，为「规则判不了但值得补」的字段出判断）、
**L2 应用**（纯代码落值）、**L2 审查**（合规性复核：枚举合法、无效占位清除、
Notes 与 facts 同源、fact 必有锚点——**能代码判定的先由代码修**）。

**置信度口径（v3.5，用户口径）**：出口 `reasoning_detail.confidence` 以 L1 自报分为基准
按档校准，不再按档位给固定值。铁的事实（手机号直取、截图中可读的微信号、登记档来源）
给 1.0；事实与高可信结论给 0.7–0.9，多条高可信证据同向给 0.95；低置信推断给 0.4–0.6，
纯猜测给 0.2–0.3；L2 软补全给 0.25。

**姓名口径（v3.5）**：`customer_name` 只认一手自述与登记姓名；查不到时用「客户」+手机号后
四位兜底（如「客户0087」，无手机号则写「未知」），并在 Notes 说明「客户信息中未查找到
真实姓名」，置信度 1.0（查无此名本身是确定事实）。称呼（先生/女士/大哥等）、昵称、企业名
一律不得当姓名，L2 兜底也不得补姓名。

### 3.6 商机等级定级（v3.6，独立 1 次 LLM）

**业务口径**见专家规范 `docs/reference/客户商机等级定级规范.md`：等级衡量「截至当前时点，在标准跟进
条件下客户可实现的购车或成交潜力」，输出 `H` / `A` / `B` / `C` / 待识别。

**为什么单列一条链路**：这条字段对销售的重要程度断档领先其它字段（业务方 2026-10-19 要求）。
若随 L1 的字段清单顺带产出一行，它拿不到全量原始数据，也拿不到足量输出篇幅。因此：

```
商机定级输入装配（代码）
  - 阶段判定：有实质内容的试驾录音 → 转商机阶段；否则线索邀约阶段（与驾照注入同口径）
  - 输入：全部客户原始记录 + 已定稿事实 + 阶段（不渲染 L1 的字段清单）
        ↓
商机等级评定（1 次 LLM）
  - 按规范的六步流程推理；H/A 必须同时具备需求、时间、行动证据
  - 输出 5–8 条推理链（只讲等级怎么定出来的）
  - 证据写成可读化陈述：原始记录讲「谁说了什么、说明了什么」，
    L1 推断标注「经分析该客户大概率/有可能…」，画像卡与 Notes 结论写明出处
        ↓
商机定级收口（代码）
  - 枚举归一；线索阶段最高 A（R04）
  - H/A 缺任一维度证据 → 降 B（R05）
  - 证据剔除半句对白式碎片（不足 12 字）并留痕；推理链截断到 8 条
  - 解析失败时保留 L1 的兜底等级，不伪装成「待识别」
```

**同源**：定级写入 `facts.deal_level` 与 `facts.deal_level_detail`；回传体的
`ai_insight.purchase_intent_level` 与 L3 的 `customer_overview.business_opp_level`
都读这一份结论，表达层不得自行再推等级。

**回传口径**：定级规范产出的 `H` / `A` / `B` / `C` / 待识别**原样回传**
`ai_insight.purchase_intent_level.value`。前端确认该字段为文本字段而非 ABCD 纯枚举
（2026-10-20），因此无须过渡映射；L-008 随之关闭。

### 3.7 L3 校验与表达层

**它替代的是老的 `customer_profile_production` 图。** 那张图 12 个 LLM 节点各写各的，
9 个板块与 Notes 两处各自生成、无人对齐——基线「卡片说 A、Notes 说 B」正是这么来的。

L3 的口径只有一条：**先定稿事实，再把事实写成话。**

```
L2 facts（代码投影，已定稿）
  ↓ l3_validate  代码校验：无依据确定值率 = 0、枚举合法、单多值、跨字段
  ↓ l3_express   1 次 LLM：把同一份 facts 写成 9 个板块
  ↓ l3_assemble  代码装配：与 Notes 同源一致性检查 + 拼成 result1 形状
```

与 production 的三处根本差别：

1. **同源**。Notes 与 9 个板块读**同一份** `facts`，不可能互相打架。
2. **表达不新增事实**。LLM 只做组织与措辞；装配层逐条核对它引用的取值能否在 `facts`
   里找到出处，找不到即剔除并留痕。
3. **复用预置资产，不复制**。6 个业务资产（标签库、证据格式、画像格式、产品信息、
   产品速查、邀约策略）按**原名**引用公共资产模板（前缀 `customer_profile_shared__`），
   仓库里只有一份正文。**2026-10-27** 这 6 份随生产臂退役改名，正文逐字未动。

### 3.8 规则层（登记表 · 三通道 · 留痕）

原先「规则」散在三处：提示词正文里的取证书面要求、代码里的 if 判断、审查层的事后检查。
同一句话写在两处就必然漂移——`HARD-03` 的无锚点判据此前在 `review_notes` 与 `validate_l3`
各有一份，改一处漏一处。规则层把这三处收成一处：**一个编号、一处正文、可单独关闭**。

```
Rule（编号 / 内容类 / 通道 / 作用域 / 阶段 / 严重度 / 默认动作）
   ↓ 按通道执行
code        → 簇函数产出 Action[]，统一执行器排序后落地
prompt      → rules/texts/*.txt 的成对标记段，渲染进提示词
llm_checker → 模型判「有没有违反」，代码复核它答得能不能用
   ↓
RuleTrace（规则 / 阶段 / 字段 / 动作 / 前值 / 后值 / 版本）→ 批次产物
```

四条口径：

1. **规则自己不改状态**，只输出动作（`reject` / `downgrade` / `rewrite` / `require_confirm` /
   `annotate`）。执行器按「硬约束 > 一致性 > 合理性，字段级 > 簇级 > 全局，再按编号」
   排序，最多 3 轮收敛。投影层各段只应用一轮——它是有序流水线，段内收敛会打乱顺序。
2. **默认动作是降级或转人工，不是删除**。与 §4.2「降级仍写入」同一取向。
3. **checker 不产生取值**。动作白名单只有降级与转确认，任何带新值的裁决丢弃；送检清单
   只给中文字段名，模型看不到内部字段键。它失败**不阻断管线**——规则层不能成为新单点。
4. **对客产出不得出现规则编号与内部解释**。trace 里的 `reason` 是给工程与核读的。

两个开关：`RULES_DISABLED`（逗号分隔编号，单条灰度/回滚，投影段与 gate 段共用同一份读取）、
`RULE_CHECKER_ENABLED`（checker 总开关，缺省关闭，省下的就是 token）。

**`scope` 可挂多字段，且只渲染一次**（2026-10-28）：同一口径要同时约束几个字段时登记为
一条规则、`scope` 列出全部字段，不逐字段抄正文。《目标字段清单》只在**第一个字段**下
渲染正文，其余字段以「本条口径同样适用于：…」一行带出——逐字段各渲一遍会让同一段文字
在提示词里重复（`SPEC-17` 曾因此多出 920 字）。同一字段被两条 active 提示词规则占用时，
启动期自检直接报错（`render.field_notes` 有先到先得语义，不拦就会静默丢正文）。
先例是 `SPEC-17`（小订/大定不是拥车，挂拥车/置换/现车信息五个字段）与 `SPEC-18`。

两道检索守卫进测试集：**孤儿标记**（代码/提示词里出现的编号必须已登记且 active）与
**未落地规则**（active 规则至少要有一处落点）。守卫只做编号存在性检查，语义仍靠测试与核读。

**表达簇的三条规则（2026-10-27）**：`EXPR-01` 正文里的枚举键按契约展示名改写、
`EXPR-02` 证据位不得出现结论型措辞、`EXPR-03` 英文占位串整条去除。前者只动
`reasoning_detail.summary` / `steps`，**不动 `attribute_value` 与 `evidence`**——取值是
契约键（前端按 `display_name` 映射），证据要能指回原文。判据是「是不是某字段的合法
枚举键」而非「含不含英文字母」，品牌名与车型名因此天然不误伤；设计与实测见
`docs/history/对客产出英文残留治理方案.md`。

**形态簇的第四条规则：`ENUM-01`（2026-10-27）**。`HARD-01` 管占位串、`HARD-02` 管「非法枚举
且未降级」，这条管**降级后仍是内部枚举键**的取值：整条剔除，不把 `replacement` / `commute`
这类废弃键回传给前端。与 `HARD-02` 的分工是「降级可见」与「取值该删」两件事，判据靠
`internal_fields.looks_like_enum_key` 把「键形态」与「客户原话」（`说不清`）分开——
只按「不在合法键集合」判会误删客户表述。旧版键到现行键的映射在
`internal_fields.LEGACY_ENUM_ALIASES` 里一次声明，归一层与回写投影共用。
设计与实测见 `docs/history/旧版枚举键与production臂整改方案.md`。

**`SPEC-16`：消费等级的档位方向（2026-10-27）**。契约里「消费等级」是 1–6 档枚举
（`level_1`…`level_6`），但档位方向从未在任何输入里写明，模型偶发把方向读反（误以为
1 档最高）。同一条规则挂两个通道：prompt 通道的正文经 `rules.render.field_notes` 渲染到
《目标字段清单》`consumption_level` 行下（取数时可见）；code 通道在
`callback_build.build_basic_notes_updates` 里把说明拼到该字段 `reasoning_detail.summary`
末尾（销售点开可见）。**档位数从契约推导**（`notes_contract.legal_keys`），不写死——
契约增删档位时注释随之变化。拼接位置选在回写出口而不是投影层：它是回传体的唯一
出口，重复回写由「已拼过则原样返回」兜住，不会叠加。

## 4. 证据分级：结论被什么撑住

### 4.1 证据档（结论自身）

| 档 | 含义 |
|---|---|
| `fact` | 客户原话或截图里直接可读 |
| `inferred_high` | 多处事实交叉可推 |
| `inferred_low` | 单点弱信号，**须转人工确认** |

### 4.2 来源分级（谁说的）

**硬顺序**：人工/系统登记 > 一手交互 > 公开登记查询 > 社交自呈现 > 第三方预测。

三条**强制**规则：

1. 第三方预测**不得单独支撑**基础身份类字段（16 个）的确定性 → 降 `inferred_low`，仍写入；
2. 态度/行为类字段（`emotion` / `pain_points` 等）须有一手依据，社媒与预测最多作辅助；
3. 社交自呈现不得单独支撑基础身份类字段 → 同 1。

> 「降级仍写入」而不是「丢弃」，是 v2 起的方向：v1 的「拒绝即丢弃」实测是掉字段的主因。
> 唯一仍留白的是**同档单值语义多值冲突**——两个互斥的值都写出去，正是
> 「Notes 里旧车车型有值、购买类型却仍是首购」的成因。

### 4.3 枚举归一

合法键、单/多选、结构化枚举要填的 `input_value` 契约字段名，**全部从
`notes_contract.py` 读**，不在规则表里手抄，避免与线上接口漂移。归不到合法键的取值
**保留原值并降级**，不丢弃。

## 5. 输出契约

本轮的对外产物有**两份**，形状不同，不要混读：

| 产物 | 出处 | 形状 |
|---|---|---|
| `result1` | 业务测试臂工作流出口 | 9 个画像板块 + `basic_notes_updates` |
| 回传体 | `callback_build` 产出，由带 `@writeback` 的节点发出 | 顶层三键 `phone` / `batch_id` / `analysis_result` |

`result.json` → `result1`（JSON **字符串**）→ `analysis_result`。Notes 契约 **45 字段 / 7 分类**，
固化自线上 payload 快照（来源 `docs/reference/Notes_new.txt`，内容签名 `b36e78edf9a2`），
运行期不再取接口。签名与来源由 `scripts/snapshot_note_contract.py --check` 校验。

**回传体是六键结构**（接口文档 §2 的「四区块 + 两基础键」）：

```
profile_summary        { name, gender }
basic_notes_updates    [ 45 字段更新项 ]
ai_insight             { purchase_intent_level, customer_segment }
purchase_decisions     [ 6 类 × items[] ]
```

四个区块由 `callback_build.py` **从 facts 纯代码投影**（0 token，理由见 §6）。
`basic_notes_updates` 与自用图谱一样走回传白名单：`facts` 里保留的编外字段
（`old_car_model` / `company` / `purchase_nature` 等）不得出现在回传项里。

> **一处未决（待业务方与项目侧确认）**：`result1` 里的画像卡本节仍写 9 个板块。
> 新契约六键里**没有** `inferred_tags` / `usage_scenarios` / `communication_strategies` /
> `purchase_motivations` / `product_preferences` 的位置；`resistances` 与 `emotion_state`
> 有落点（分别进 `deal_battle.loss_conditions` 与 `decision_psychology`）。
> 那五节是停写、只作中间产物、还是另有去向，确认前不动 `l3.SECTION_KEYS`——
> 一动，`result1` 形状即变，既有批次的可比性与 `tests/test_l3.py` 的装配断言一并失效。

> 读结果时注意两层字符串：`result1` 是字符串，需二次 `json.loads`；
> 回传体的 `callback_json` 同样是字符串，由 `@body_ref` 解析成对象后再发出。

## 6. 关键设计决策一览

| 决策 | 理由 |
|---|---|
| 能写成代码的约束不交给模型 | 0 token 且可验证：L0/L4/L2 投影/L2 应用/L2 审查/L3 校验/装配都是纯代码 |
| 录音只取逐字 ASR，不取下游 LLM 压缩报告 | 压缩报告有信息损失且白花钱（实测 41.1% 成本里的一大块） |
| 改录音链路用「纯变体」而非就地删节点 | 就地删会让基线臂 `definition_hash` 漂移，AB 失去可比性 |
| 定位失败降级而非丢弃 | 丢弃是掉字段主因；降级保留 + 标低置信，交人工 |
| 冲突在投影层用代码消解 | 唯一能同时看见全部字段与来源的层，比提示词可靠 |
| L3 用 1 次 LLM 写全部 9 板块 | 同源保证卡片与 Notes 一致；production 的 12 节点各自为政是冲突根源 |
| **四区块由代码投影，不交给 LLM 归类** | 唯一 id 必须由代码生成——`(phone, item_id)` 唯一且回写是**先删后建**，撞号即整次回传失败；六个分类与 facts 有明确对应，按「能写成代码的约束不交给模型」应落代码 |
| **回传体走 `@body_ref`，不用 `@body_template`** | 文本模板恒把引用渲染成字符串，产不出契约要求的 `analysis_result` **对象**；`@body_ref` 整段取自绑定值并解析成对象 |
| 6 个业务资产按原名引用 | 一份正文、一处维护，「一字不改」才可验证 |
| **商机等级单开一次 LLM，不随 L1 顺带产出** | 销售按它排序跟进，重要程度断档领先；单开才能拿全量原始数据与足量推理链，规则收口（阶段上限 / 多维证据 / 原文定位）再在代码层强制 |
| **商机等级按 H/A/B/C/待识别 原样回传，不做映射** | 前端确认该字段是文本字段而非 ABCD 纯枚举；过渡映射会让 H 级在列表里降档显示，反而误导排序 |
| **规则升为一等公民，三通道按「判据形态」分配** | 能写成表格判据的走 code（0 token、可验证）；只影响「往哪找」的走 prompt；需要读懂意思的才走 checker。默认不建开放知识表（职业收入这类） |
| **规则只出动作，不改状态** | 动作可排序、可留痕、可回放；往旧分支里顺手改状态，规则马上退回「散落各处的 if」 |
| **checker 用 code 节点承载，不用 llm 节点** | 调度器对失败节点会阻塞整棵下游子树；做成 llm 节点则一次调用失败就挡掉定级与回传，与「checker 失败不阻断」冲突 |

## 7. 已知薄弱环节（下一轮优化的输入）

本批次（v3.3，全量 39 案）做过一次第三方审核，两份报告在 `docs/history/`。
按优先级：

1. ~~**审查层能判但不拦。**~~ **已处置（2026-10-26）**：四条 gate 判据（占位串、非法枚举、
   无锚点 fact、证据位自指）改为产出动作并由统一执行器落地——占位串整条删除、非法取值
   降置信到 0.5、证据位只摘那一条。原先判出违规只记一条 issue，违规值照样进最终 Notes。
   同轮合并了 `review_notes` 与 `validate_l3` 两份重复的无锚点判据。
2. ~~**归属（谁说的）判断不可靠。**~~ **已处置（2026-10-20）**：录音侧改由语义角色标注
   重判说话方（§3.1），代码侧单向兜底把销售自述句从客户方摘出，证据位标注「销售原话 /
   客户原话 / 说话者身份存疑」。剩余风险在非录音渠道（截图、聊天记录）——那里没有
   说话方信息，「这是谁发的」仍由 L1 自行判断。
3. **沟通策略是同模板复读**，且与个案事实相反（同一句政策话术在 20/39 案逐字复用）。
4. **客户明说的地域/距离/语言被丢弃**（异地购车、门店太远、「我听不懂粤语」），
   而它们恰是决定「这条线索能不能做」的第一顺位信息。
5. **产品参数会由模型内部知识补全**（两案写入逐字相同的「增程续航 1700+km」，
   而输入包里根本没有产品资料）。
6. **L3 同源守卫不可用**：12 字取窗口导致 114/115 报错是误报，真问题被淹。
