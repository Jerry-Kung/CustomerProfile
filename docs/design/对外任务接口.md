# 对外任务接口（V0.5.5）

> 本文记录**对外契约**：前端任务队列如何推送任务、接口如何响应、以及两边各自依赖什么。
> 运维操作（起进程、真回写验收步骤）见 `../runbooks/部署.md` §9。
> **给前端的联调说明**见 `../对外任务接口对接文档.md`——那份讲怎么调、拿到各响应码该怎么做、
> 结果从哪读；本文讲**为什么这样设计**，两份不重复。
>
> 立项：2026-10-16。承接臂：`customer_profile_pipeline`（业务测试臂）。

## 1. 这个接口解决什么

运行台（`API_PORT`，缺省 18173）是**内部只读面**：无鉴权，提交任务只是它顺带提供的一个入口。上线业务
测试后，任务由前端任务队列批量推送，需要一个**有鉴权、只做接单**的对外面。本接口就是
那个面，独立进程监听 8099。

三件事它**不做**：不执行工作流（由 worker 做）、不提供查询（由运行台做）、不轮询。
任务执行完成后由**回写接口**把结果送到业务系统，前端从那边得知结果。

## 2. 请求

```
POST /api/v1/tasks
X-API-Key: <INBOUND_API_KEY>
Content-Type: application/json

{ "phone_number": "13415100087", "batch_id": "batch-20261016-01" }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `phone_number` | string | 是 | 11 位中国大陆手机号（`^1[3-9]\d{9}$`，与运行台提交页、`collect_test_phones.py` 同形） |
| `batch_id` | string | 是 | 批次号，非空白 |

**`batch_id` 在本接口是必填，尽管工作流定义里它是可选的。** 它会被原样填进回写体的
`batch_id`（契约顶层三键之一），前端据此判断任务来源；空值会让那一键为空，来源就丢了。
工作流定义保持可选是有理由的——跑批脚本刻意传空串（它会被透传进 `result1`，填批次号会
污染与基线的可比性），那条路径不经本接口。

## 3. 响应

| 状态 | 场景 | 响应体 |
|---|---|---|
| `200` | 接单成功 | `{"status":"accepted","run_id":"…","workflow_id":"…","phone_number":"…","batch_id":"…"}` |
| `401` | 未带 `X-API-Key` | `{"detail":"缺少 X-API-Key 请求头"}` |
| `403` | 密钥不符 | `{"detail":"X-API-Key 无效"}` |
| `422` | 手机号形态非法 / `batch_id` 空白或缺失 | `{"detail":"…"}` |
| `429` | 待跑队列已满（`MAX_QUEUED_RUNS`）| `{"detail":"…"}`，带 `Retry-After: 30` |
| `503` | 未配置 `INBOUND_API_KEY`，接口整体关闭 | `{"detail":"对外任务接口未启用：未配置 INBOUND_API_KEY"}` |

**拿到 200 即表示任务已持久化入队**（`status=queued`），进程此刻崩溃任务也不会丢。
后续执行状态在运行台查看，业务结果在回写接口侧。

**`run_id` 只用于排查**，前端不必保存它——它不是业务主键，`batch_id` + 手机号才是。

### 3.1 401 与 403 分开、503 不是「不校验」

- **401 / 403 分开**：没提供凭据与提供错了是两件事，分开才让调用方知道该补什么。
- **未配置密钥 → 503（接口关闭），而不是放行。** 对外写面的空密钥若被当作「不校验」，
  这个端口就是任何人可写的入口：一条外部请求会变成一次真实算力消耗与一次生产回写。
- 密钥比较走常量时间比较（`secrets.compare_digest`），避免逐字节耗时差被用于爆破。

## 4. 接口侧的两条硬约束

### 4.1 入参在接单层校验，不靠执行期

少传或传错若只在 `start` 节点报错，调用方拿到的是一条「已接收」的 200，而它对应的是一次
失败的运行——错误与结果对不上。手机号还会进 `/data/history/{phone}` 与
`/data/profile/{phone}` 两条外部路径，非法值在那里表现为难以归因的 404。

### 4.2 接单进程不执行工作流，也不碰别人的运行状态

`inline_worker` 与 `interrupt_on_start` 在本进程被**强制关掉**，且不通过 `.env` 配置：

- 前者：一个接收进程同时跑 21 分钟的工作流会把接单能力拖住；
- 后者：本进程与运行台、worker **共用同一个 SQLite**。`interrupt_on_start` 的语义是
  「把上次进程遗留的 `running` 标为 `interrupted`」，在这里执行会把**别的进程正在跑的**
  运行标成中断。`scripts/run_baseline.py` 为同样的理由显式关掉它。

## 5. 与既有接口的分工

| 接口 | 端口 | 面向 | 写/读 | 鉴权 |
|---|---|---|---|---|
| 运行台 `customer_profile.main` | `API_PORT`（缺省 18173）| 内部（本项目/运维）| 提交 + 查询 + 人工终结 | 无 |
| **对外任务接口 `customer_profile.inbound`** | **8099** | **前端任务队列** | **只提交** | **`X-API-Key`** |
| worker `customer_profile.worker` | 无 | — | 消费队列、执行 | — |

本接口**不新增**执行路径：它调用的是运行台提交页同一个 `Service.submit`（同一个入队
语句），因此「先落库再返回」这条既有契约自动成立。
