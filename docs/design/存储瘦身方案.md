# 留痕存储瘦身方案（V0.6 定稿）

> 2026-11-05。测量样本：本地 UAT 归档 `experiments/uat_data/uat-traces-20261102-20261103/trace.db`
> ——18 小时全量，792 个主任务、12,582 条运行、169,866 条节点记录、11,192 次请求尝试，文件 1.66 GB。
> 量级与线上「几千次任务、几个 GB」一致，可直接类推。

## 1. 体积现状

| 列 | 占用 | 占比 |
|---|---|---|
| `node_executions.outputs_json` | 932 MB | 59.8% |
| `request_attempts.request_json` | 274 MB | 17.6% |
| `workflow_runs.inputs_json` | 156 MB | 10.0% |
| `workflow_runs.outputs_json` | 103 MB | 6.6% |
| `request_attempts.response_text` | 93 MB | 6.0% |
| 行骨架（状态、耗时、错误、时间、编号、索引） | 25 MB | 1.5% |

**体积问题完全是载荷问题**：骨架只占 1.5%，其余全是 JSON 文本列。

## 2. 四处可量化的浪费

1. **子运行重复输入**：一次主任务平均拉起 10.4 个子运行，每个都把全量 `customer_data`
   （约 11.8 KB）塞进 `inputs_json`。样本 9,504 行、121 MB，而这份数据随时可由
   `GET /api/v1/remote/data/history/{phone}` 重取。
2. **节点整包转发**：code / template-transform / 聚合三类节点输出合计 308 MB，多为同一份
   JSON 往下传；子运行镜像节点（`sub_run_id` 非空）又复制子运行输出 64 MB。
   但**单次运行内部**去重只省 2.8%，重复在运行之间与父子之间。
3. **`end` 节点与运行输出完全重复**：抽样 60 个主运行，`end` 节点输出与
   `workflow_runs.outputs_json` 逐字节相同，60/60。
4. **内联二进制**：图片被包成 `data:image/...;base64,...` 存了两处（节点输出 6.3 MB +
   请求尝试 3.1 MB / 18 小时），而原图 URL 本就在 `media_urls` 里。

运维侧：本地库 63.5 MB 中 53.7 MB 是 freelist（84.6%），删过的行从未 `VACUUM`；
代码里没有任何保留期逻辑。

## 3. 目标形态

**SQLite 只留运行骨架；运行时数据按主任务树打成压缩包；多模态只存 URL。**
按 `TRACE_PERSIST_MODE` 三档取舍。

### 3.1 骨架（永久保留）

`workflow_runs` 全列、`node_executions` 与 `request_attempts` 的非载荷列、`definition_versions`。
实测 25.4 MB / 792 主任务，折合**每主任务 33 KB**。

时间字段现状（实测填充率）：

| 字段 | 位置 | 填充率 | 说明 |
|---|---|---|---|
| `created_at_ms` | 运行 | 100% | **入队**时刻，与「实际开跑」不同，两者都要留 |
| `queued_at_ms` | 运行 | 6.3% | 仅根任务有值，子运行不入队 |
| `started_at_ms` | 运行 / 节点 | 100% / 99.99% | 实际开始执行 |
| `finished_at_ms` | 运行 | 99.9% | 未终结的 `running` 为空是正常 |
| `duration_ms` | 运行 / 节点 / 尝试 | 99.9% | — |
| `created_at_ms` | 请求尝试 | 100% | 每次外部调用的发生时刻 |

结论：**运行层四个时间戳本就齐全，不需要加列**——此前文档把它概括成「状态、耗时、错误」
没点名，才显得缺。真正缺的只有节点层的**绝对结束时刻**，它可由
`started_at_ms + duration_ms` 派生，不另存列。

归档包里额外写一份人能直接读的 ISO8601 时间（带 `+08:00`），免去拿到包的人手算毫秒。

### 3.2 运行时数据包

一个主任务一整棵树（实测平均 10.4 个子运行）打成一个包。按方案口径实测——子运行不重复存输入、
`end` 节点不存输出、媒体只存 URL——zlib-6 后：**平均 477 KB、中位 302 KB、最大 1.99 MB**
（40 个 pipeline 主任务，完整运行树）。相对现状每主任务 2.1 MB 的载荷约 **4.4 倍**（计入骨架后整档约 4.3 倍）；压缩主要来自
LLM prompt 与同一份渠道数据在树内的大量重复。

包内自包含：`runs / nodes / attempts / definition`，外加 `manifest.json`（时间戳、包版本、
内容模式、媒体 URL 是否可能过期）。

> 测量口径提醒：三档的体积都按「完整运行树」算。只统计根运行自己的节点行会显著偏低
> ——子树里的节点与尝试占了绝大部分。

### 3.3 多模态只存 URL

`data:` URI 一律替换成引用：
`{"_media": "image/png", "url": "...", "bytes": 233791, "sha256": "..."}`。
原图/录音在 `media_urls`（`https://online-business-cos.m-hero.com/...`）里，实测**无签名参数、
不设过期**，30 天内可直接重下。

护栏两条：写包时若发现 URL 带签名类参数（`Signature` / `Expires` / `X-Amz-*` / `token`），
记一条 WARN 并在 manifest 标 `url_may_expire`；`sha256` 用于下载后校验，取不到时明确报
「媒体已不可达」，不静默当成空数据。

## 4. `TRACE_PERSIST_MODE` 三档

| | `high`（缺省） | `low` | `none` |
|---|---|---|---|
| 骨架（SQLite） | 全留 | 全留 | 全留 |
| 包内节点输入输出 | 留 | 不留 | **不写包** |
| 包内 LLM/HTTP 请求体（prompt） | 留 | 不留 | **不写包** |
| 包内 `response_text` | 留 | **留** | **不写包** |
| 包内错误、`usage_json`、`provider_request_id` | 留 | 留 | 错误在骨架列；usage 不留 |
| 根任务 `outputs_json`（最终画像） | 包内 | 包内 | **直存骨架列**（唯一例外） |
| 多模态原始字节 | 只存 URL | 只存 URL | — |
| 每主任务增量（骨架 + 包） | 约 509 KB | 约 84 KB | 约 38 KB |
| 30 天总量（1,056 主任务/日） | 约 15.4 GB | 约 2.55 GB | 约 1.15 GB |

取值校验：启动时不允许未知值，非法值直接拒绝启动（不要静默回落到缺省，否则「以为开了
`none` 其实还在存包」是最难查的一类问题）。旧布尔变量若已存在，`true` → `high`、`false` → `low`。

### 4.1 `low` 的四项保留

`low` 不是「`high` 砍掉节点输出」，而是**按能不能重建来选**。保留四样：

1. **外部响应原文 `response_text`**（全树，39.2 KB/主任务压缩后）——排障主证据，
   也是回放 fixture 的来源。
2. **最终画像输出**（根运行 `outputs_json`，5.7 KB）——回答「当时我们写回了什么」，
   mhero 的 profile 接口给不了，它返回的是被人工确认覆盖后的当前值。
3. **原样数据输入**（`pipeline_l0_records` 的输出，15.4 KB）——注意它**不在**
   `workflow_runs.inputs_json` 里，那个字段平均只有 0.08 KB（手机号 + 批次号）。
   虽然 history 接口能重取，但取到的是**当前**值，不是当时喂进去的那份。
4. **诊断字段切片**（10 个字段，6.2 KB）——见下。

`low` 仍不记 prompt 与完整节点输出，所以**无法逐字重放当时的模型输入**。
但故障定位的「为什么」这一层保住了。

### 4.1.1 诊断字段切片

只从节点输出里按字段名切出判定痕迹，其余中间数据一律不留。字段清单与各自体积
（40 个主任务、完整运行树、zlib 后）：

| 字段 | 每主任务 | 回答什么问题 |
|---|---|---|
| `notes_updates_json` | 2.70 KB | 每条 Notes 在这一层长什么样，与最终落地差在哪 |
| `facts_json` | 1.09 KB | 事实层抽出了什么、商机等级依据 |
| `candidates_json` | 0.07 KB | 哪些值被列为候选但未采纳 |
| `to_confirm_json` | 0.06 KB | 哪些转成了待人工确认 |
| `rule_trace_json` | 0.06 KB | 哪些规则命中、触发什么动作 |
| `rejected_json` | 0.01 KB | 哪些被规则拒绝 |
| `checker_status` / `enum_illegal` / `unbacked_fact` / `placeholder_removed` | <0.01 KB | 审查结论与计数 |

合计 **6.2 KB/主任务**（原始 10.5 KB 中的一部分，见下方排除项）。

**明确排除 `callback_json`**：实测 40/40 与根输出 `result1` 逐字节相同，留它是纯冗余，
占 4.36 KB。

**保留 `notes_updates_json` 而非只看根输出**：实测 40 个样本里 36 个与根输出的
`basic_notes_updates` 不同——字段集合都不一样（根输出有 `brand_concerns`、`intended_model`
而中间层没有；中间层有 `payment_method`、`industry`、`hobbies` 而根输出没有）。
「某个字段为什么没进最终 Notes」只能在这一层回答。

### 4.1.2 `low` 的体积与代价

| 组成 | 每主任务 |
|---|---|
| 骨架 | 32.8 KB |
| 根输出 | 5.7 KB |
| 原样输入 | 15.4 KB |
| `response_text` | 39.2 KB |
| 诊断切片 | 6.2 KB |
| **合计（压缩后）** | **约 84 KB** |

30 天约 2.55 GB，比加入切片前的 2.36 GB 只多 14%。加这 6.2 KB 换来的是
「为什么这个字段没写进去」「为什么这条被拒了」这类问题的可回答性——这类问题
在只留根输出时完全无解。

### 4.2 `none`：骨架 + 最终画像，排障靠现场重建

不写包，SQLite 里只有骨架：运行身份、状态、四类时间戳、耗时、错误文本、业务标识、
节点状态与 `attempt_count`、每次外部调用的目标 URL/状态码/耗时、定义快照。
18 小时 25 MB（骨架）+ 4 MB（最终画像），30 天约 1.15 GB。

排障时能重建到什么程度：

| 事物 | 能否重建 | 依据 |
|---|---|---|
| 客户全部输入资料 | 能 | `GET /api/v1/remote/data/history/{phone}`，取的是**当前**值 |
| 当时的图结构与提示词模板 | 能 | `definition_versions` 在骨架里，且按哈希去重、体积可忽略 |
| 失败发生在哪个节点、哪次调用、什么错误码 | 能 | 骨架里的节点状态与尝试目标列 |
| 当时我们写回的画像内容 | **不能** | profile 接口返回的是被人工确认覆盖后的当前值 |
| 当时的 LLM 请求体与响应原文 | **不能** | 未记录，只能重新推理一次 |

因此 `none` 下的「重建」是**用当前输入重跑一次**，不是复现历史。这会真实消耗 LLM token，
而且结果必然与当时不同（模型版本、上游数据都变了）。定位口径要随之改变：从「比对当时
输入输出」变成「确认哪一步失败、用当前数据重跑是否复现」。**建议 `none` 只用于存储极紧的
生产环境，且保留随时切回 `low` 的能力**——切回后新运行即恢复留包，历史包不补。

`none` 下唯一的载荷例外是**根任务最终画像输出**（`workflow_runs.outputs_json`，仅根运行）。
实测 zlib 后每主任务 5.07 KB，30 天 157 MB，占本档的 15%，换来「当时我们写回了什么」这一条
profile 接口永远给不了的证据。子运行的 `outputs_json` 仍不保留——它们只是中间结果。

这样 `none` 的定位就统一了：**能重建的都不留，重建不出来的留最小的一份**。
客户输入可从 history 接口取，图与 prompt 从定义快照重建，失败位置在骨架里；
只有「当时的回写内容」和「当时的模型输入输出」无法重建，前者代价低所以留，
后者代价高所以不留。

### 4.3 `none` 下节点骨架也 30 天清理

`none` 里节点骨架占 21.5 / 25.4 MB（85%）。若节点骨架也随包 30 天清理，骨架从年增
约 12 GB 降到约 1.9 GB 且不再加速；代价是 30 天后只能看到「哪次运行失败、错误是什么」，
看不到失败在哪个节点。**已定：`none` 开、`high`/`low` 不开**。理由是没有包可对照时，
节点行的独立价值最低；`high`/`low` 有包，节点骨架是包的索引，删掉反而让包难定位。

## 5. 实施顺序

### L0 立即（零代码）

- 存量库 `VACUUM`；新库 `auto_vacuum=INCREMENTAL`。
- 确认 WAL 自动 checkpoint，避免 `-wal` 常驻。

### L1 写包 + 瘦身写入（不动表结构）

1. `RunTracker.run_finished` 之后由 worker 收尾时写包，落在
   `DATA_DIR/trace-archives/YYYY-MM-DD/<run_id>.json.gz`。走线程池，不阻塞事件循环；
   失败按既有 fail-soft 口径记 ERROR，不影响业务运行。`TRACE_PERSIST_MODE=none` 时跳过写包，
   但根任务的 `outputs_json` 仍写入骨架列（见 §4.2）。
2. 写入路径不再内联二进制（见 §3.3）。
3. **原样输入只留一份**：真正的客户数据快照在 `pipeline_l0_records` 节点的输出里
   （15.4 KB），`workflow_runs.inputs_json` 只有手机号 + 批次号（0.08 KB），不要误以为
   它承载了输入。子运行不再重复携带 `customer_data`；`low` / `none` 下该节点输出按
   §4.1 的口径单独保留。
4. `end` 节点不存输出，读路径回落到 `run.outputs_json`。
5. `list_runs` / `list_node_executions` 目前 `SELECT *`，把 400 KB 的节点输出拖进列表页，
   改成显式列清单。`none` 下没有载荷可拖，但同一套列清单对三档都省内存。
6. 载荷不落库后，这些列在 SQLite 里恒为空：保留列定义不删（迁移期混存要能读旧行），
   写入端按模式跳过。
7. **诊断字段切片**（`low` 及以上）：写包时按 §4.1.1 的字段清单从各节点输出里抠出这
   10 个通用键，其余丢弃。这一段是 `low` 能不能回答「为什么」的关键，实现时字段清单要
   集中在常量里，不要散落在写包逻辑中。

   实现期补了**按节点的清单**（`archive.NODE_DIAGNOSTIC_FIELDS`）：增量入口的档位判定、
   基线写入、跳过判定等字段只有特定节点才有，且与其它节点的同名键语义不同，不能混进
   通用清单。口径与准入标准见 `../feature-storage-opt/01-设计稿.md` §8.1。

### L2 存量迁移 + 读路径改造

1. 一次性迁移脚本：扫历史行 → 写包 → 清空四个表的载荷列 → `VACUUM`。
2. `/traces/export` 目前从 SQLite 流式导出；迁移后改为「骨架 + 从包回填」，否则导出会缺数据。
   `none` 下导出只剩骨架，端点要如实标注「本次导出不含运行时数据」。
3. 新增取包脚本 `scripts/fetch_run_archive.py`：按 run_id 或手机号 + 时间范围取回本地解包。

### L3 保留期（worker 定时任务）

- 包文件 30 天后删除；骨架永久（`none` 下节点骨架同 30 天，见 §4.3）。
- 挂在 worker 主循环里（已有秒级轮询），按天节流一次，不引入外部 cron。

## 6. 30 天稳态与增长

| 模式 | 每主任务 | 日增 | 30 天 | 年增（不清理骨架） |
|---|---|---|---|---|
| 现状 | 约 2.1 MB | 2.2 GB | 66 GB | — |
| `high` | 约 509 KB | 约 537 MB | 约 15.4 GB | 骨架部分约 12 GB |
| `low` | 约 84 KB | 约 88 MB | 约 2.55 GB | 同上 |
| `none` | 约 38 KB | 约 39 MB | 约 1.15 GB | 约 12 GB；开 §4.3 后约 1.9 GB |

相对现状的压缩：`high` 约 4.3 倍，`low` 约 25 倍，`none` 约 57 倍。

### 6.1 `high` 档里四项删减各占多少

同一批 40 个主任务、完整运行树，逐项叠加测量：

| 步骤 | 每主任务 | 相对上一步 | 30 天 |
|---|---|---|---|
| A 现状（全留） | 561 KB | — | 16.9 GB |
| B 子运行不重复存输入 | 537 KB | −4.3% | 16.2 GB |
| C `end` 节点不存输出 | 503 KB | −6.3% | 15.2 GB |
| D 媒体只存 URL（= `high`） | 477 KB | −5.1% | 14.4 GB |
| E 镜像节点只存引用（候选，未采纳） | 445 KB | −6.9% | 13.4 GB |

四项合计 **−14.8%**。所以 `high` 的收益是「压缩 4.4 倍 × 删减 15%」两部分，
不是只靠压缩。

删减只省 15% 的原因：zlib 在**同一棵树内**已经把重复串（同一份 `customer_data`、
同一段 prompt）压得很小，删减省下的是压缩之后仍然残留的那部分。这也解释了为什么
「去重」在这里不如「压缩」——重复内容的重复**距离很近**（同一棵树内、相邻行），
通用压缩算法本来就能吃掉它。

**E 项（镜像节点）是 `high` 还能再砍 6.9% 的唯一大块**：`sub_run_id` 非空的 tool 节点，
其输出与子运行自身输出重复。本轮没采纳，因为要先确认前端详情页不依赖它。
若确认不依赖，`high` 可降到约 445 KB / 30 天 13.4 GB。

## 7. 不砍的东西

- `definition_versions.definition_json`：0.1 MB / 18 小时，决定历史运行能否显示当时的图与
  提示词，也是**三档共同**的重建依据。全留。
- 错误文本、耗时、尝试目标 URL/状态码：体积可忽略，**三档全留**。
- `usage_json`、`provider_request_id`：`high`/`low` 留；`none` 不留（这档连包都不写）。
- `response_text`：`high` / `low` 必留，理由见 §4.1。
- **`low` 的四项**（§4.1）：`response_text`、根输出、`pipeline_l0_records` 的原样输入、
  诊断字段切片。这四项是「问题定位」的最低可回答集；再往下删就会丢掉「为什么」。
- 三档共有的最小证据集：根任务最终画像输出。`none` 也留，理由见 §4.2。
- `callback_json` 不留：与根输出 `result1` 逐字节相同（实测 40/40）。
