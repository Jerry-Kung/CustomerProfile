# business_opt01_v2 · 端到端方案设计

> 定位：v2 优化的**落地设计**（施工级）。上游依据是同目录 `方案分析与调整建议.md`
> （对 opt01 四段式的复盘与定稿意见）——那一份讲「为什么」，本文讲「怎么做成什么样」。
>
> 分支：`dev-business-opt01-v2`。旧目录 `docs/business_opt01/端到端方案.md` 是 opt01
> 第一版的设计，v2 在其上重写，**两版不混用、不互相引用**。
>
> 本文写**设计与契约**，不贴代码实现——节点 ID、函数名、绑定一律以代码为准，此处不复述。
> 凡属推算的成本数字标「预估」，实测数字注明来源批次。

## 0. 结论先行

**v2 把 opt01 的「减法架构」改回「产出架构」：不再是「有据则留、无据则空」，而是
「每一层都为每个字段给出结论，并标明这个结论有多硬」。**

四层一句话：

| 层 | 形态 | 职责 | 与 opt01 的差别 |
|---|---|---|---|
| **L0 预处理** | 代码 + 取数，0 token | 取数、多模态→文本、渠道分级、校验核对、分诊路由 | **关掉取数侧白跑的 3 个 LLM 节点** |
| **L1 投影** | 1 次 LLM（超限才按来源拆批） | 读全部原始记录，**直出 42 字段级结论 + 三分类置信度** | 从「只抽断言」改为「直出字段」 |
| **L2 汇聚** | 代码规则 + 1 次受约束 LLM 兜底 | 归属/分级/冲突/枚举/跨字段，代码判不了的交给兜底 | 从「拒绝并丢弃」改为「降级保留 + 裁决」 |
| **L3 校验与表达** | 代码校验 + 1 次 LLM 复审（表达复用预置资产） | 查漏补缺 + 润色 + 把事实写成话 | 替代 production 的 12 个自由生成节点 |

**净成本效应预估约 −75%**，且其中 **41.1% 是「零质量风险」**——关掉取数侧
一份「付费后弃用」的 LLM 压缩链（见 §2.3）。

**一句话**：opt01 用「一刀切禁掉推断」换准确性，因此拿字段数换了正确率、还因
「旧压缩链 + 新取证」双付而涨了成本。v2 要的是——**把推断装回来，用三分类管住纪律；
把取数侧的无效压缩关掉；把 production 的自由生成换成「事实定稿 → 一次表达 → 一次复审」。**

## 1. 边界与对外契约（v2 不改的部分）

改的是**内部链路**，对外的输入输出契约一字不动。

**输入**：接口「获取全量用户数据」（`GET .../data/history/{phone}`）返回的全量客户数据。
15 个渠道，各渠道的完整程度与可靠程度不等。

**输出**（对外形状不变）：

- **Notes 更新项**：42 字段，形状
  `basic_notes_updates: [{attribute_key, attribute_value, reasoning_detail{summary,steps,confidence,evidence}}]`，
  回写企业级 IT 系统的客户信息表；
- **客户画像卡**：9 个 section，形状固定——`profile_summary` / `inferred_tags` /
  `usage_scenarios` / `communication_strategies` / `customer_overview` /
  `purchase_motivations` / `product_preferences` / `resistances` / `emotion_state`。

**优先级**：准确性、自洽性、可读性优先，推理成本次之。两条硬要求不变——
「数据过少时输出至少与常理一致」「推理链逻辑清晰、引用原始数据准确翔实」。

> **可读性是硬约束，不是形容词**（v2.1 补，见 `v2.1-整改设计.md` §1）：对客产出
> （Notes 的 `reasoning_detail.steps` / `evidence`、画像卡 section）**不得**出现内部
> 审计与规则用语、来源档代号、内部字段名或 `未知渠道` 之类的占位串；证据锚点须精确到
> 客户原始数据中的一段内容。

**回写开关不变**：`POST .../callback/update-profile` 仍以 `WRITEBACK_ENABLED` 控制，
缺省关闭；测试与影子模式禁止生产回写。

## 2. 设计依据（实测，非估算）

数据口径：13 案探针集。实验臂 `A-pipeline-R1b-20261010`（提交 `b6a7023`，可比性四条全通过）；
基线 `baseline-39-dsv41-noThink`（同 13 案）。全部数字为实测。

### 2.1 字段为什么掉

| 环节 | 13 案合计 | 单案均值 |
|---|---|---|
| L1 原始断言 | 421 | 32.4 |
| 定位后保留 | 391 | 30.1 |
| **经 L2 投影后 Notes** | **192** | **14.8** |
| 基线（同 13 案） | 360 | 27.7 |

**L2 拒绝 86 条**：`b_prediction_only` 38、`d_enum` 30、`c_conflict` 9、`a_attribution` 9。
丢掉的最集中在推断类字段：`age` 13/13 全丢、`annual_income` 12/13、
`follow_up_frequency` 11/13、`communication_rhythm` 与 `personality_and_preferences` 各 9/13。

**根因是「没有任何一层负责给字段」**：L1 只抽断言（421 条，高于基线的 360 个字段总量），
L2 只筛选（「有据则留，无据则空」），没有任何一层长出结论。而 `age`、`annual_income`
客户从不会直说，`communication_rhythm`、`personality_and_preferences` 是归纳结论，
原文里永远找不到对应句子。**基线能填，正是因为它允许模型合理推论；opt01 的错误是把
「推论」也一刀切禁掉了。**

### 2.2 两个工程缺陷（v2 必须避开）

- **`d_enum` 拒了 30 条，是第二大杀手**。L1 提示词让模型「对不上枚举就照实写原始表述」，
  模型照做了，随后被 L2 的精确匹配全数拒绝。**提示词承诺与实现能力错配**——
  v2 把「转换不到就丢弃」改成「降级保留」。
- **`a_attribution` 只拒了 9 条**——opt01 最引以为傲的「妻子不能写成客户」并非召回瓶颈，
  低产不是它造成的，v2 保留该规则但不再指望它提产。

### 2.3 成本的 41% 是「付费后弃用」

R1b 单案 720,273 token，按「谁在用这些 token」分四桶：

| 桶 | 占比 | 单案 | 说明 |
|---|---|---|---|
| A · production 生成层 | 32.2% | 231,895 | 12 个 LLM 节点，后文推倒重写 |
| **B · 取数侧 LLM 压缩（付费后弃用）** | **41.1%** | **295,938** | 见下 |
| C · 新链路（L1 取证 + 旧证据整理） | 22.3% | 160,573 | 其中 L1 自身 10.1% |
| D · 其他 | 4.4% | 31,875 | |

**B 桶明细**：`audio_content_extract` 的「LLM 识别结果校对」（2,559,841）与
「LLM 内容有效性判断」（856,156）、`moments_info` 的「多图片内容总结」（421,030）——
**这三项照跑不误，但 v2 只消费 `auc_result`（纯 ASR 逐字原文），产物一个字节不用**。
它们做的恰是「把逐字原文压成摘要」，而 v2 明令禁止这一步（原文必须逐字进入 L1）。
**每案约 29.6 万 token、全批 41.1% 的成本，是在为一份被丢弃的摘要付钱。**

> **收敛 B 桶是 v2 成本下降的最大单项，且零质量风险**——不改变任何产出，只关掉不用的节点。

## 3. 端到端架构总览

```
L0 预处理层（代码 + 取数，0 token）
  取数 → 多模态→纯文本 → 渠道分级 → 校验核对 → 分诊路由
  【关闭：录音子流程的「识别结果校对」「内容有效性判断」、朋友圈的「多图片内容总结」】

L1 投影层（1 次 LLM，仅超限时按来源类型拆批）
  输入按渠道分节组装（不做字段级通道硬绑定）
  直出 42 字段级结论：{attribute, value, basis, subject, record_channel,
                      anchor?, basis_of_inference?, confidence}
  【核心：把「只抽取」改成「直出字段 + 三分类」】

L2 汇聚层（代码规则 + 1 次受约束 LLM 兜底）
  ① 代码：归属过滤 / 来源分级 / 冲突消解 / 枚举归一 / 单多值 / 跨字段 / 三条来源硬规则
  ② LLM 兜底：只裁决规则判不了的（弱证据同向汇聚、语义冲突），不得新增候选集外的值
  ③ 代码：序列化为契约形态

L3 校验与表达层（代码校验 + 1 次 LLM 复审；表达复用预置资产）
  ① 代码：确定性校验（含「无依据确定值率 = 0」）
  ② LLM 复审：查漏补缺 + 内容润色，不得新增事实
  ③ 表达：由定稿事实写出 9 个 section；Notes 与卡片同源
```

**与 opt01 的差别**：

| 改动 | opt01 | v2 |
|---|---|---|
| L1 职责 | 只抽断言 | 直出字段 + 三分类 |
| L2 对枚举/冲突 | 拒绝并丢字段 | 降级保留 + LLM 兜底裁决 |
| production | 12 节点照旧跑 | 推倒重写，预置资产保留 |
| 取数侧 LLM 压缩 | 照跑（41% 白费） | 关闭 |
| 旧证据整理节点 | 保留 | 删除 |

## 4. L0 预处理层（代码 + 取数）

### 4.1 职责

把散落的 15 路输入收成一份**逐字、带来源分级、带坐标**的记录集，交给 L1。
**本层不产生任何字段结论，也不做任何有损压缩**——压缩是有损的，原文才是取证的地基。

### 4.2 取数

沿用现有「获取全量用户数据」HTTP 节点。返回的是**清单**（记录元信息 + 内容），
空渠道在记录层留痕、不进 L1 上下文（opt01 阶段一已实现的收益：不再被 9 个结构性空渠道污染）。

### 4.3 多模态 → 纯文本

| 输入形态 | 取数路径 | 关键口径 |
|---|---|---|
| 试驾 / 外呼录音 | **纯识别子流程**，逐文件取 `auc_result`（逐字转写） | 走迭代，实测试驾有 19/39 案带 2 个录音文件 |
| 聊天记录 / 截图文案 | 现有截图与聊天子流程的文本产物 | — |
| 朋友圈图片 | 图片内容文本 | **不再做多图片 LLM 总结** |

### 4.4 【关键改动】关闭取数侧白跑的 3 个 LLM 节点

这是 v2 成本下降的最大单项（−41.1%），改动方式有两种，择一：

1. **在 `audio_content_extract` 子流程内加「纯识别」出口**：把两个 LLM 节点挂在一条
   不参与结果的支路上并标 `skipped`，只保留「识别结果提取」节点产出 `auc_result`；
   或直接删除该子流程内的这两个 LLM 节点与其提示词资产。
2. **在父链路侧不复用该子流程**，改为直接调用底层 ASR（若底层接口可直取）。

**推荐方案 1**（改动面最小、可回退）。无论哪种，验收判据是：
**L0 产出的录音文本与关闭前逐字一致**（证明是「关掉不用的节点」而非「改了产出」）。
`moments_info` 的「多图片内容总结」同理关闭。

> **零质量风险的理由**：这三个节点的产物在 v2 链路里**没有任何消费方**
> （L1 只读 `auc_result` 与文本产物）。删的是「产生了但没人读」的输出。

### 4.5 渠道分级

来源分级由**代码按渠道定**，不由模型猜。五档，可信度从高到低：

```
人工/系统登记 > 一手交互 > 公开登记查询 > 社交自呈现 > 第三方预测
```

分级表（渠道 → 档）与 opt01 一致，可直接复用。

### 4.6 校验核对

对每条记录做确定性核对，产出「本次实际有内容的渠道清单」：
`status=ok` 且有实质内容才算可用；识别「无数据」的固定提示语（sentinel）不算内容。
这是分诊与 L1 输入装配的共同输入。

### 4.7 分诊路由（保守模板）

纯代码，按「有哪些渠道、各有多长」判三档：

| 档 | 判据 | 处置 |
|---|---|---|
| `sufficient` | 有一手交互（录音/聊天）且有实质内容 | 走完整事实流程 |
| `thin` | 只有声明/社交/弱登记/预测 | 只输出**登记档**能坐实的字段，其余留白转确认 |
| `empty` | 几乎无数据 | 输出「待补充」骨架，不产生任何具体断言 |

判据是结构事实，交模型既多一次成本又引入抖动——**能写成代码的不交给提示词**。

## 5. L1 投影层（1 次 LLM）

### 5.1 职责变化

opt01 的 L1 是「证据线索汇总整理专家」，输出**断言账本**，明说「你的输出不是画像，
也不是结论」。v2 的 L1 是**投影者**：读全部原始记录，**直接给出 42 个字段各自的结论**，
并给每个结论标一个置信度档位。

**这是全案最重要的改动**——它把「为每个字段给结论」的职责重新装回链路。

### 5.2 输入装配

沿用现有 L1 输入装配的三要素，**不改**：

1. **按渠道分节**，节首标「来源分级」与「记录编号」；
2. **来源档从高到低排序**（登记事实与录音原文前置，长上下文里靠后内容召回更低）；
3. **枚举键清单置于开头**——R1 实测把它放末尾时，尾部那串短 token 会诱导模型把锚点
   也写成短裸串，导致大量正确断言被长度门丢弃。置开头后记录原文成为模型**最后读到的内容**。

**关键改动：不做字段级通道硬绑定。** 不按一张「字段 × 允许通道」的矩阵裁剪输入——
该矩阵已降为研究稿（见 `方案分析与调整建议.md` §3.2 与 `字段-输入通道关联矩阵.md`）。
「无关字段不硬猜」的原则改由**字段说明层面的引导**实现（见 §5.6）。

### 5.3 输出契约（JSON）

```json
{
  "fields": [
    {
      "attribute": "old_car_model",
      "value": "2019款别克君威",
      "basis": "fact",
      "subject": "customer",
      "record_channel": "外呼录音信息",
      "anchor": "我现在开的是一九年的君威",
      "confidence": 0.9
    },
    {
      "attribute": "annual_income",
      "value": "30-50万",
      "basis": "inferred_high",
      "subject": "customer",
      "record_channel": "",
      "basis_of_inference": ["职业为互联网中层", "关注 30 万以上车型"],
      "confidence": 0.7
    }
  ]
}
```

字段语义：

- `attribute`：42 个契约键之一（含 `deal_level` 这类跨产物字段）；
- `value`：结论值。枚举字段优先输出**合法枚举键**（对照节首清单）；
- `basis`：`fact` / `inferred_high` / `inferred_low`（判据见 §5.4）；
- `subject`：事实主体（`customer` / `spouse` / `family` / `colleague` / `salesperson` /
  `other` / `unknown`）。**这一项不可省**——L2 的归属过滤靠它；
- `record_channel`：来源渠道名（L2 据此判来源档）。推断类可留空；
- `anchor`：**逐字复制**原文短句——`basis=fact` **必填**，是「可回溯」的凭据；
- `basis_of_inference`：推断依据列表——`basis=inferred_*` **必填**，写清「从哪几条推出」；
- `confidence`：0–1，供卡片叙述与人工复核排序用，**不参与字段取舍**（取舍看 `basis`）。

> **与 opt01 断言的迁移关系**：形状几乎同构，`attribute/value/subject/record_channel/anchor`
> 语义不变，只是把 `claim_type`（fact/observation/prediction）换成 `basis`
> （fact/inferred_high/inferred_low），并新增 `basis_of_inference`。L2 的 `Claim` 结构可平滑加一列。

### 5.4 三分类判据

| 档 | 判据 | 回写 |
|---|---|---|
| `fact` | 有锚点原文直接支撑，或登记系统直接给出 | 正常回写 |
| `inferred_high` | 无单句锚点，但有 ≥2 条**独立来源**同向支撑，或由已定稿事实合理推出 | 正常回写 |
| `inferred_low` | 仅 1 条弱事实，或纯常识/社交自呈现单独支撑 | 回写，**必须带可见标记** |

> **v3.2 口径变更**：`inferred_low` 的判据**不再包含「第三方预测单独支撑」**。第三方画像
> 标签（极光）单独支撑某字段时改记 `inferred_high`——这批标签是采购来的商用画像数据，
> 在客户无试驾、无沟通记录时是唯一可靠的画像信源（见 `v3.2-方案设计.md`）。

**区分「有据推断」与「无据推断」**：找不到任何原始数据关联的字段，只能给
`inferred_low` 或留空，**不得**给 `fact` 或 `inferred_high`。

### 5.5 锚点与定位

沿用现有定位层：`anchor` 回定位到原文、切出 `quote` 与 `span`；定位不到即丢弃
（**`fact` 无锚点即不成立**，这是「可回溯」的强制点）。

判断口径 **`fact` 从严、`inferred_*` 免锚**：

- `fact`：无 `anchor`、或锚点定位失败 → 降级为 `inferred_high`（若能为结论找到 ≥2 独立来源）
  或 `inferred_low`，**不直接丢弃**；
- `inferred_high` / `inferred_low`：不要求锚点，但 `basis_of_inference` 必须非空，
  否则降为 `inferred_low`。

> 与 opt01 的差别：opt01 定位失败即**整条丢弃**（R1 曾因长度门丢掉 226 条）；
> v2 定位失败只**降级**，不丢字段——这正是召回回升的关键。

### 5.6 提示词改动要点

以现有 L1 取证提示词为底本改写，改动集中在四处：

1. **任务口径**：从「整理成断言账本」改为「为每个字段给出结论并标置信度」；
2. **覆盖要求**：默认**覆盖全部 42 字段**——能坐实的给 `fact`/`inferred_high`，
   只能猜的给 `inferred_low`，**确实毫无关联的才留空**；
3. **「不硬猜」引导（替代硬绑定矩阵）**：在**字段说明**里逐字段写「该字段通常能从哪类
   信息推断」，作为**引导**而非闸门。例：`planned_purchase_time` 写「从沟通记录的时间表述
   推断；**不得**用手机号归属地、社媒截图等无关渠道硬猜」；
4. **保留原有三条禁令**：账号装饰不是客户事实；`customer_name` 只写能判为真实姓名的部分；
   企业信息注销如实写。

### 5.7 M×N 与拆批

- **默认 M=1、N=1**：一次调用读全部输入，输出在**同一个 JSON 里按字段组织**
  （不是按字段组重复调用）。
- **触发拆分**：输入超阈值（建议 **8 万字符**）或实测遗忘率上升时，**按输入来源类型拆批**
  （如「登记 + 一手」与「社交 + 预测」分开），而非机械地 M 路 × N 类。
  L1 单案 prompt 中位仅 6.5k token，只有含超长转写的案子会顶到上限
  （最大一案 30 万 token，含一段 74 万字符的试驾转写）。
- **禁忌**：不得「按输出类型 × N」重复读同一份输入——L1 已占约 10% 成本，再乘 N 会迅速失控。

## 6. L2 汇聚层（代码规则 + 1 次受约束 LLM 兜底）

### 6.1 三层结构

```
① 代码规则层（必须先跑）
     ↓ 产出「已整理候选集」（每条带来源档与 basis）
② LLM 兜底层（只处理规则判不了的部分）
     ↓ 产出「终判 + 理由」
③ 回写层（纯代码）
     ↓ 序列化为契约形态
```

**凡是能写成规则的，不交给 LLM。** LLM 兜底只有一个节点，输入是代码整理过的结构化候选集，
输出有明确边界（**只能裁决，不能新增**）。**一个受约束的裁决者 ≠ 11 个自由生成的作者。**

### 6.2 代码规则层（规则表）

在 opt01 投影规则表基础上，**把「拒绝丢弃」改为「降级保留」**：

| 规则 | opt01 行为 | **v2 行为** |
|---|---|---|
| a 归属过滤：非客户主体的断言不得写身份字段 | 丢弃 | **保留**（`family_structure` 豁免，同 opt01） |
| b 来源分级：身份字段仅由**社交自呈现**支撑 | 丢弃 + 转确认 | **降级 `inferred_low`**，仍写入（不丢字段） |
| b 来源分级：身份字段仅由**第三方预测**支撑 | 丢弃 + 转确认 | **记 `inferred_high`**（v3.2 变更：采购的商用画像数据在无一手记录时是唯一可靠信源） |
| c 冲突消解：同来源档多值（单值语义） | 留白转确认 | 保留（单值语义确应留白）；**聚合语义字段汇总** |
| **d 枚举归一：取值无法归一到契约键** | **丢弃** | **降级保留**：留原值 + 标 `inferred_low` + 转确认 |
| e 单/多值约束 | 强制 | 保留 |
| f 跨字段规则（旧车⇒换购、注销企业、等级唯一） | 强制 | 保留 |
| g 缺失即留白 | 留白 | 留白（但此时「缺失」已因 d 的降级大幅减少） |

**三条来源硬规则**（针对明确错误类型，保留为强制规则，不涉及通道与字段的全面绑定）：

1. **预测可以单独支撑身份类字段，但记 `inferred_high`、不得写成确定值**（v3.2 变更；
   此前为「单独出现即降 `inferred_low`」）。第三方画像标签是采购的商用画像数据，
   在无试驾/沟通记录时是唯一可靠信源；它仍**不等于** `fact`（不是客户原话）；
2. **态度/行为类字段**（`emotion` / `knowledge_of_mengshi` / `pain_points`）**须有一手依据**
   （登记或一手交互），社媒与预测最多作辅助；
3. **社交自呈现不得单独支撑身份证类字段**——账号装饰不是客户事实。

**冲突消解取「更强的一条」**：`fact` > `inferred_high` > `inferred_low`；
同档且同源多值（单值语义）→ 留白转确认。

### 6.3 LLM 兜底层（唯一受约束的裁决者）

- **输入**：代码整理后的候选集（每条带来源档、`basis`、值）；
- **只做三件事**：
  ① **弱证据同向汇聚**——多条不同来源的低置信推断结论相似时，合并升格为一条高置信；
  ② **语义冲突判断**——两条值是否真的矛盾（代码只会判「同档不同值」）；
  ③ **给出终判与理由**；
- **硬边界**：**不得新增候选集之外的字段值**。修改后的值必须仍能在候选集里找到出处。

> **典型场景**：某字段有 3 条低置信推断，来源不同（一手/社交/预测）但结论大体相似——
> 代码只会判「同档多值冲突 → 留白」，正确处置是**合并升格为一条 `inferred_high`**
> （三条独立来源同向本身就是增强证据）。这正是纯代码不够、必须引入 LLM 的地方。

### 6.4 回写层（纯代码）

把终判序列化成契约形态。**落库形态在 L2 出口统一收口**，不指望模型自觉：

- 结构化枚举项 → JSON 字符串，形如 `{"key":"yes","input_value":"5年"}`；
- 多选枚举 → `a||b`；
- 自由文本聚合 → 中文顿号连接。

`reasoning_detail.evidence` 写「来源档（渠道）」，**引文由代码从原文切片填入**，
不在此刻编造引文。

## 7. L3 校验与表达层（代码校验 + 1 次 LLM 复审）

### 7.1 定位

不是「自己审自己」。主业是**查漏补缺 + 内容润色**——LLM 原始输出常有遵从性与语言表达
问题，复审时找出来修掉。

### 7.2 代码校验（确定性）

复用 opt01 已有规则表，新增两条：

- 枚举合法（键在契约内）、单/多值约束、跨字段规则（旧车⇒换购、等级唯一）；
- 卡片与 Notes **同源一致**（同一事实在两处取值相同）；
- **`basis=fact` 必有锚点**；
- **无依据确定值率 = 0**（不得出现「标了 `fact` 却指不出原文」的值）。

### 7.3 LLM 复审（查漏补缺 + 润色）

对未通过代码校验的项、以及语言表达问题做修复；**不得新增事实**——
修改后的值必须仍能在候选集里找到出处。

### 7.4 表达层（替代 production 的 11 路）

**把已定稿的事实写成话**——这是原 production 的职责，v2 用**同一份事实**重写：

- **Notes 与卡片同源**：Notes 来自 L2 的 `facts`（代码投影），卡片的 9 个 section 由
  L3 表达读**同一份 `facts`** 写出。基线的问题正是「卡片与 Notes 各自生成、无人对齐」。
- **表达不得新增事实**：只做组织与措辞，不引入新结论。

### 7.5 必须原样保留的业务资产（重写时搬迁，不连积累一起扔）

6 个预置模板一字不改：

| 模板 | 规模 | 内容 |
|---|---|---|
| 标签库 | 26.6 KB | 标签分类 / 内容 / 等级 / 描述 |
| 产品信息（长） | 2.0 KB | 车型价格区间与卖点 |
| 产品信息（短） | 5.0 KB | 销售速查手册 |
| 邀约策略库 | 4.8 KB | 策略 ID / 目标画像 / 钩子 / 动作 / 话术示例 |
| 证据线索格式 | 1.2 KB | 输出格式契约 |
| 画像格式 | 0.8 KB | 输出格式契约 |
