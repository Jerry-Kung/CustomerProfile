## 0. 结论先行

v2.1 在它自己设定的三项整改（可读性 / 覆盖 / 保真）上**基本达标**，但把病灶推到了下一层：
**证据链质量**。v3 的目标是「让每一条结论的依据都能被验证」，而不是再加一层分析。

v3 做什么：

1. **L1 拆成三层**（沿用用户设计）：事实提取 → 人设画像 → 分析投影。
2. **两条钉死的边界**：人设层不进证据位；L1-1a 事实层与事实/推断分离保留。
3. **三条硬接口**（v3 的成败全在这里）：事实必须带来源坐标、身份字段来源白名单、
   长 JSON 输出的可靠性。
4. L2 由「汇聚」改为**审查核验层**；L3 保持现状不动。

v3 不做什么：

- 不建 ASR 词表，**信任 LLM 纠错能力**（用户决定，§5.3）；
- 不动 L3（§7）；
- 不改 L0 与对外契约（§1）。

**成本**：净增 2–3 次 LLM（L1 两次；L3 若后续调整再加不超过 1 次）。相对 v2.1 在可接受范围。

走查后均**余 2 个未闭合的 `{`**（最外层 `{"analysis_result":{`）。这是系统性缺陷，三试复现。

## 3. v3 分层（沿用户设计）

```
L0 预处理层（不动）

L1 投影层（拆为三层，2 次 LLM + 若干代码节点）
   L1-1a 事实提取层：从全量输入识别所有「事实」与「高置信推断」，投影到 Notes 字段并钉死
        —— 事实与推断**结构分离**，只聚焦「全 / 准 / 事实」，不做联想
   L1-1b 人设画像层：基于 L1-1a 事实 + 原始数据，输出一份客户「人设画像」
        —— 只作一致性参考，**不进证据位**（§5.1）
   L1-1c 分析投影层：基于「事实」+「人设参考」+ 原始信息，补齐 Notes 与画像卡剩余字段
        —— 兼顾原 L1 投影 + L2 汇聚的产出职责

L2 审查核验层（由汇聚层改）
   合规性审查：枚举合法、无效占位清除、Notes 与 facts 同源、fact 必有锚点
   可代码修补的代码修补；需语义判断的走一次局部 LLM 重写

L3 表达润色 + 复审层（**本稿不动**，见 §7）
```

### 3.1 三层职责与输入输出的契约

| 层 | 主要输入 | 主要输出 | 证据位 |
|---|---|---|---|
| L1-1a | 全部有内容的渠道原文 + 字段清单 | `facts[]`（`fact` / `high_confidence_inference` 两类），每条带来源坐标 | 是（唯一证据来源） |
| L1-1b | L1-1a 的 `facts` + 原始数据 | `persona{}`（半结构化画像 + 一段整体描述） | **否** |
| L1-1c | `facts` + `persona`（参考）+ 原始数据 | `fields[]`（补齐的字段级结论）+ 卡片 section 素材 | 是（须回溯到 `facts`） |

## 4. 三条硬接口（v3 的核心）

以下三条是本稿真正要立的东西，直接对应 §2.2 的问题 1–3 与 5。**它们是接口契约，不是提示词建议。**

### 接口一 · 事实与推断结构分离，事实必须带来源坐标

L1-1a 的输出按性质分块，不再混在同一个 `evidence` 数组：

- **锚定型事实**（`anchor_kind: verbatim`）：值可在原文中定位，代码切出原文切片作为 `quote`。
  性别、姓名、车型、电话号码一类归此。
- **当归型事实**（`anchor_kind: normalized`）：ASR 纠错、归一产生的值，原文中**无字面匹配**
  （安安 → 埃安）。必须**同时记录原文与理由**：

  ```json
  {"value": "埃安", "anchor_kind": "normalized",
   "source_quote": "安安I60", "rationale": "ASR 音近纠错"}
  ```

  `source_quote` 记原文、`rationale` 记为什么改，使对客产出可读、可审计——这正是问题 2
  「结论当证据用」的对症点：结论可以当**结论**，但不得冒充**原文**。

- **推断**（`inferred_high` / `inferred_low`）：`basis_of_inference` 必须能**追溯**到一条
  带坐标的 `fact` 或一个可指认的原始字段，**不得把结论本身写成依据**（问题 2）。

**约束**：进「钉死」集合的每条事实必须带来源坐标；无坐标者降回推断，不得当事实。

### 接口二 · 身份字段来源白名单

针对问题 3，对**身份类字段**（`customer_name`、`title`、`phone_number` 等）设来源白名单，
由代码强制（非提示词）：

- `customer_name`：只认一手自述（「我姓…」）、登记姓名、或明确叫法；
  **营业执照主体名、微信昵称、店铺名一律不进**，另置他处；
- `title`（性别）：按**优先级 + 降级**使用，而非单一来源定论——
  登记称呼 > 一手自述 > 头像性别标签（最多 `inferred_low`，`confidence ≤ 0.6`）>
  录音性别标签（仅弱辅助）。
  说明：头像性别标签同属「账号自呈现」，与 L1 既有禁令一致，**不得**作为最可靠源；
  录音性别标签天生不可靠，且说话人未必是客户。

### 接口三 · 长 JSON 输出的可靠性

针对问题 5，且 v3 在 L1 又新增两处长结构化输出，失败点由 1 增至多处。

1. **先上 JSONL**（每行一个字段/条目）：某行 JSON 坏只丢那一行，不丢整段。
   （用户指定先试此路径，拆组为后备，见 §7）
2. **解析抢救**：解析失败时截到最后一个完整对象，余下标 `to_confirm`，**整案不判失败**。
3. **节点级降级**：任一 LLM 节点失败降级为「该节点产物置空 + 审计留痕」，
   不得冒泡成整案 `failed`。

## 5. 两条钉死的边界

### 5.1 人设层不进证据位（用户已定）

L1-1b 的 `persona` 只作**一致性参考**：L1-1c 与 L3 可用它保持口吻与逻辑不自相矛盾，
但**任何写进 Notes 或卡片的取值，其证据仍须回到原始数据或带坐标的 `fact`，不得引用人设结论**。

实现上：`persona` 每个字段带 `provenance`（从哪几条 `facts` 推出）；下游引用顺
`provenance` 回到原始层，而非停在人设层。不设此约束，人设层即证据链的断点。

### 5.2 L1-1a 事实层保留（用户已定）

事实层单独占一次调用，收益是**上下文隔离**——事实提取时模型注意力只在「原文里有什么」，
不与「该推什么字段」的目标竞争。这正是 v2.1 中 `age` 证据被推断目标污染的机制。

### 5.3 ASR 勘误信任 LLM（用户已定）

不建品牌/车型别名词典，初始错误率交由 L1-1a 纠错。**代价需记入验收**：
当归型事实（接口一）必然增多，其 `source_quote` + `rationale` 的可审计性成为质量门。

### 5.4 L1-1c 引用口径（承接 5.1）

L1-1c 的 `evidence` **必须**能顺藤摸到一条带坐标的 `fact`，不得停在人设层。示例：

- ✅「客户从事水果零售」——来自 fact `occupation`，带执照/对话坐标；
- ❌「客户是务实型个体户」——人设结论，无坐标，不得作证据。

## 10 施工回填（与本文设计的偏差）

施工中发现并偏离设计的两处，记此以免日后对不上：

1. **L1 三层的输入装配不另设代码节点。** 设计稿 §3 与任务书 §2-P3 曾设想
   `build_persona_input` / `build_fields_input` 两个 `code` 节点来拼装下游输入。
   实施改为**直接用节点绑定**（LLM 执行器本就支持 `{{ arg1 }} {{ arg2 }} {{ arg3 }}`
   多入参模板渲染），少一层装配节点 = 少一处失败面。产物形状不变。
2. **P4 只落地代码审查**（见 §7-7）。
3. **节点重命名**：`pipeline_l1_llm` → `pipeline_l1_facts` + `pipeline_l1_persona` +
   `pipeline_l1_fields`。历史批次的离线回放不受影响（探针读的是批次产物里已固化的
   旧节点 ID），仅新批次产物用新 ID。

## 8. 风险与回退

| 风险 | 处置 |
|---|---|
| 人设层虽不入证据位，仍可能「诱导」L1-1c 写死人设结论 | 验收加「证据位自指」与「无坐标事实」两条机器判据 |
| 身份字段白名单过紧，把有效姓名拦掉 | 白名单按「一手自述 / 登记」给足形态，先宽后可收 |
| 长 JSON 改 JSONL 后，下游消费方需同步改造 | 逐节点评估消费方；改动面在装配层，不散落 |
| L1 加两层引入新的归零点 | 接口三的「节点级降级」为硬要求，先于 L1 拆分落地 |
| 回退 | 每项单独提交；L1 拆分与接口改造分开提交，便于二分 |

## 9. 与 v2 / v2.1 的关系

v3 **不推翻** v2 的四层架构与 v2.1 的三项整改（可读性 / 覆盖 / 保真），只在 L1 内部
**拆层**并**钉死证据链边界**。v2.1 已达标的三项是 v3 的**不回退基线**。

**施工顺序建议**（正式版动手时）：
接口三（可靠性）→ 接口一/二（证据链）→ L1 三分层 → L2 审查层 → （择机）L3。
理由：先修「整案归零」，否则其余改动的效果无法稳定观测。
